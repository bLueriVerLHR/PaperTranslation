编译优化的层次与约束

从程序表示到机器资源

编译优化将源程序转换为适合目标机器执行的代码。这个过程受两类约束：变换必须保持程序语义，生成的指令又必须适应有限的寄存器、访存带宽和执行资源。循环优化与寄存器分配分别作用于不同层次，却通过指令数量、依赖关系和活跃范围联系在一起。向量化或展开减少了某些开销，也可能增加寄存器压力；中端预计的收益，需要经过后端生成代码后才能评价。

全书先沿同一个例子分析从 C/C++ 到优化 LLVM IR的表示变化，再通过SSA 与基础优化说明局部变量、控制流与数据依赖如何显式化。随后讨论循环变换、向量化与并行生成，最后进入活跃范围、寄存器分配及实验分析。示例用于解释变换关系，实际生成结果取决于输入、目标平台和优化配置。

循环变换与并行层次

概念 改变什么 主要利用什么 会自动产生 CPU 线程吗
循环向量化 多次迭代打包成向量运算 数据级并行 SIMD 不会
SLP 向量化 多条同形标量指令组成向量 同一局部区域中的数据级并行 不会
循环展开 复制循环体，减少回边 控制开销降低、指令级并行 ILP 不会
循环结构变换 调整嵌套顺序、分裂或融合循环 局部性、依赖分离、优化机会 通常不会
线程级自动并行化 将独立迭代交给多个工作线程 多核吞吐 特定框架可以
OpenMP 显式表达并行、任务、SIMD 和 offload 语义 编译器与运行时合作 parallel 会，simd 不会

LLVM Greedy 与经典线性扫描采用不同的分配组织。传统 linear scan 按活跃区间起点前进；Greedy 使用优先队列、物理寄存器冲突查询、驱逐和区域切分。该提交的 Greedy 在一类局部区间上使用线性指令顺序，但这一局部策略并不决定全局算法。两者的关系将在寄存器分配基础与Greedy 寄存器分配中展开。

这张图划分各阶段的职责，不规定固定的 Pass 顺序。promotion 接收的是 Clang 前端已经生成的合法 IR；默认管线也可能在 SROA 内部完成提升，而没有独立的 mem2reg。OpenMP、Polly 与 MLIR 的线程并行入口位于不同表示层次，不能统一排列在 LV 之后。具体输入输出与前置条件见从 C/C++ 到优化 LLVM IR。

SSA（Static Single Assignment）要求每个 SSA 值只有一个定义。循环里的 i 并不是被反复赋值的同一个 IR 名字，而是入口值、更新值通过 header 的 phi 合流。phi 按控制流前驱选择值，它不是“同时计算两边”。这种表示让 def-use 关系清晰，但内存并不因为标量 SSA 就自动没有别名。

Pass 有三种职责：

  1. Analysis 生成可复用事实，例如循环树、支配关系、SCEV、别名、块频率。
  2. Transform 修改程序，例如展开或向量化。
  3. Target interface 提供目标特定成本与能力，例如 TTI 对向量操作的估价。

变换后必须维护或使分析失效。删改 CFG 却继续使用旧的 DominatorTree、LoopInfo 或 SCEV，会变成编译器正确性问题，而不是“性能差一点”。

Pass 管线与源码入口

llvm-project/llvm/lib/Passes/PassBuilderPipelines.cpp 组织中端管线，决定各类分析和变换何时运行。结合这一入口分析具体 Pass，可以区分算法自身的能力与默认管线提供的执行条件。该提交中的几项安排如下：

  • 前期循环管线包含 LICM、LoopRotate、SimpleLoopUnswitch 和完整展开等步骤；LICM 在 rotation 前后可用不同的推测策略。
  • PassBuilder::addVectorPasses 中先有 LoopVectorize，后续安排展开和清理，并在条件允许时加入 SLP。不同优化级别有不同分支，不是一份固定清单。
  • EnableLoopInterchange 的初始值为 true；EnableLoopFlatten 为 false；unroll-and-jam 有独立开关。源码有 Pass，不代表每个默认管线都启用它，更不代表每个循环都会被它改写。
  • 向量化后的清理有实际目的：展开可能使 alloca 的变量索引变成常量，从而再次暴露 SROA 机会。

后端管线入口位于 llvm-project/llvm/lib/CodeGen/TargetPassConfig.cpp。标准实现的 createTargetRegisterAllocator 在优化路径选 Greedy，在非优化路径选 Fast；目标可以覆盖，-regalloc=... 也可显式改变选择。这些选择描述标准实现的默认路径，不构成所有目标和配置的统一规则。

合法性、成本与实现预算

优化方案的选择包含不同层次的判断。合法性分析确定变换是否保持语言与 IR 语义；成本模型依据目标能力和输入特征估计收益；实现还要限制编译时间与代码体积，并考虑可用分析和机器资源。三者提供的约束不同，某一层的肯定结果不能代替其余判断。

合法性与收益需要分别判断。浮点归约的树形重排可能缩短依赖链，却改变舍入顺序，因而未必符合语言级语义；循环展开可能保持语义，却使同时活跃的值超出可用寄存器，增加溢出到栈的存取（spill）。

分析具体循环时，可以沿依赖关系、合法性证据、成本选择和后端资源消耗追踪变换结果。这样既能解释某个 Pass 为何接受或拒绝候选，也能定位预期收益在何处被额外指令、访存或寄存器压力抵消。

从 C/C++ 到优化 LLVM IR

本章沿一个小 C 函数分析编译各阶段的程序表示：带语义的 AST、含局部内存的 LLVM IR、提升后的 SSA，以及适合循环分析和向量化的控制流。阶段之间的输入输出关系说明了分析事实从何而来，也为SSA 与基础优化中的算法提供背景。

前端生成、中端优化与后端降低

Clang 前端完成预处理、语法与语义分析、类型及 ABI 处理，再生成 LLVM IR。LLVM 中端通常在 IR 上执行优化，后端才将其降低为目标指令并分配寄存器。

mem2reg 接收的已经是合法 LLVM IR，其作用是把符合条件的局部内存状态提升为 SSA 值。它不承担 C 源码解析或 AST 到 IR 的生成工作。

生产管线按优化级别、目标、LTO、profile、语言功能和插件配置组装。某些步骤会重复运行，某些管线不显式安排 mem2reg，部分循环也可能在向量化前已被完整展开或删除。因此，编译过程需要按实际输入和执行路径分析，而非理解为若干 Pass 各运行一次的固定序列。

Driver 的任务构建与 cc1 前端入口

运行 clang 或 clang++ 时，首先进入 driver。它根据 -E、-S、-c、-emit-llvm、目标、输入语言等决定建哪些任务，也选择 include 搜索、sysroot、运行库和链接器配置。

源码路径：

  • llvm-project/clang/lib/Driver/Driver.cpp：Driver::BuildCompilation、BuildActions、BuildJobs。
  • llvm-project/clang/lib/Driver/ToolChains/Clang.cpp：Clang::ConstructJob，为编译任务构造参数。
  • llvm-project/clang/lib/FrontendTool/ExecuteCompilerInvocation.cpp：CreateFrontendAction、ExecuteCompilerInvocation。
  • llvm-project/clang/lib/Frontend/CompilerInstance.cpp：承载 diagnostics、目标、预处理器、ASTContext、Sema，并执行 FrontendAction。

cc1 主要指 Clang 的内部前端入口或任务模式，是否作为独立进程执行受 driver 配置影响。Driver 同时配置工具链、系统头文件与 ABI 相关参数；直接调用 clang -cc1 时，这些设置需要单独处理，因此它与普通编译命令的条件并不相同。

同一个 C 文件针对 Windows x64 与 Linux x86-64，可能有不同 ABI、目标 triple、DataLayout 和属性，即使都叫 x86-64。LLVM IR 也不是完全与目标无关的通用源码。 目标无关优化很多，但前端已经选择了类型布局、参数传递和若干目标事实。

预处理与词法：此时尚未出现 LLVM 指令

#define STEP 1
#include "config.h"
#if ENABLE_KERNEL
void f(void) { /* ... */ }
#endif

预处理决定哪些 token 真正进入编译：展开宏、处理 include、选择条件分支，并保留源位置用于诊断。词法把字符变成标识符、数字、运算符等 tokens。

路径：llvm-project/clang/lib/Lex/Lexer.cpp、llvm-project/clang/lib/Lex/Preprocessor.cpp、llvm-project/clang/lib/Lex/PPMacroExpansion.cpp。

宏展开和 #if 条件选择发生在类型检查之前，分别不同于 LLVM 的函数内联和 SCCP。头文件在预处理及后续语义处理中提供声明或定义；包含头文件与链接阶段加载库是不同操作。

Parser 与 Sema：从语法树到具有 C/C++ 意义的程序

Parser 解析 for、函数声明、表达式与语句的语法结构；Sema 处理名字查找、类型检查、重载决议、隐式转换及模板相关语义。两者在解析过程中协作，语义处理并不是在整棵无类型语法树构造完毕后才统一开始。

路径：

  • llvm-project/clang/lib/Parse/ParseAST.cpp：ParseAST，循环调用 ParseTopLevelDecl，并通知 ASTConsumer。
  • llvm-project/clang/lib/Parse/ParseStmt.cpp：语句解析。
  • llvm-project/clang/lib/Sema/SemaExpr.cpp：表达式语义。
  • llvm-project/clang/lib/Sema/SemaStmt.cpp：语句语义。
  • llvm-project/clang/include/clang/AST/：AST 表示。

C++ 会带来额外语义：构造/析构、引用、虚调用、模板实例化、异常和清理等。有些语言要求的常量求值也在此阶段进行，例如 constexpr 场景；它不是之后把两个 LLVM 常量相加的同一种职责。

AST 里保留源码的结构

考虑下面贯穿本章的例子：

static float scale_one(float x, float a) {
    float t = a * x;
    return t + 1.0f;
}

void scale(float *restrict out, const float *restrict in,
           unsigned n, float a) {
    for (unsigned i = 0; i < n; ++i)
        out[i] = scale_one(in[i], a);
}

这是 C 示例；restrict 不应直接当作标准 C++ 关键字使用。数组有效范围与 restrict 契约仍由调用者满足。

AST 的简化示意：

FunctionDecl scale
└─ CompoundStmt
   └─ ForStmt
      ├─ DeclStmt：unsigned i = 0
      ├─ 条件：i < n
      ├─ 更新：++i
      └─ 赋值
         ├─ ArraySubscriptExpr：out[i]（写入位置）
         └─ CallExpr：scale_one
            ├─ in[i] 经读取转换得到 float 值
            └─ a 经读取转换得到 float 值

真实 AST 还会显示 DeclRefExpr、ImplicitCastExpr 等。它们很有意义：名字引用可指向一个变量位置，而计算 a * x 需要读取其值；Sema 用隐式转换节点记录这些语言语义。

此时依然有 ForStmt、源码变量和函数调用。LLVM IR 里则没有普通 C 的 ForStmt；循环会变成基本块与分支。

AST CodeGen：变量、表达式和语句各怎样降低

从 ASTConsumer 到一个 LLVM Function

沿这条源码路线阅读：

ParseAST 通知 ASTConsumer
  → BackendConsumer / CodeGenerator
  → CodeGenModule：顶层声明、全局对象、函数及 ABI
  → CodeGenFunction：某个函数的入口、body、结束处理
  → 具体语句/表达式 emitter

对应路径与符号：

  • llvm-project/clang/lib/CodeGen/CodeGenAction.cpp：BackendConsumer::HandleTopLevelDecl、HandleTranslationUnit。
  • llvm-project/clang/lib/CodeGen/ModuleBuilder.cpp：CreateLLVMCodeGen、HandleTopLevelDecl。
  • llvm-project/clang/lib/CodeGen/CodeGenModule.cpp：EmitTopLevelDecl、EmitGlobalDefinition、EmitGlobalFunctionDefinition。
  • llvm-project/clang/lib/CodeGen/CodeGenFunction.cpp：GenerateCode、StartFunction、EmitFunctionBody、FinishFunction。

ABI lowering 也发生在这里：一个 C++ 结构体参数可能拆成几个 IR 参数、经指针传递，或通过隐藏返回值指针返回。IR Function 的签名不总与源语言函数签名一一对应。相关入口在 llvm-project/clang/lib/CodeGen/CGCall.cpp，目标差异的实现集中于 llvm-project/clang/lib/CodeGen/Targets/。

声明：给可修改局部量一个位置

llvm-project/clang/lib/CodeGen/CGDecl.cpp 中，EmitAutoVarDecl 会调用 EmitAutoVarAlloca、EmitAutoVarInit 等处理局部对象的存储与初始化；还要考虑 alignment、debug info、lifetime 和语言清理。

对于容易理解的普通自动局部标量，前端可以先用 alloca 提供地址，以 load/store 实现每次读写。这避免让 AST emitter 自己为每个源码变量运行完整 SSA 构建算法。

但“所有变量永远先产生一个 alloca”也不准确：常量、表达式临时值、不同 storage duration、参数、优化选项和特殊语言构造有不同路径。前端可以直接产生 SSA 临时值，或做局部简化。

表达式：先区分“地址”与“值”

对 out[i] = in[i] * a：

  1. 计算 in[i] 的位置：通常生成带元素类型的 GEP 地址运算。
  2. 从该位置 load，得到一个 float SSA 值。
  3. 与 a 的值计算 fmul，得到另一个 SSA 值。
  4. 计算 out[i] 的位置，再 store 结果。

路径：llvm-project/clang/lib/CodeGen/CGExpr.cpp 的 EmitLValue、数组下标与 load/store 发射；llvm-project/clang/lib/CodeGen/CGExprScalar.cpp 的标量表达式发射。

GEP 是地址计算，不是访问数组内容。 getelementptr float, ptr %in, i64 %index 按 float 元素步长计算地址；读取数据还需要 load。opaque pointer 的 ptr 不带 pointee type，并不意味着元素大小可以不知道，GEP 仍有显式源元素类型。

语句：for 变成 CFG

llvm-project/clang/lib/CodeGen/CGStmt.cpp 的 EmitStmt 分派到 EmitForStmt、EmitIfStmt、EmitReturnStmt 等。

教学上一个 for 被拆成：

entry：初始化 i
  ↓
cond：读 i，判断 i < n ── false ──→ exit：返回
  │ true
  ↓
body：读取 in[i]、调用 helper、写 out[i]
  ↓
inc：更新 i
  └──────────────────────────────→ cond

break、continue、return、异常与析构会增加或改变边。对于 C++，跳出某作用域前可能必须发射 cleanup；不是简单把每个 break 都替换成一条裸 branch。

快照：mem2reg 前的 IR 已经包含什么

下面是人为压缩的完整教学 IR，用 64 位指针目标常见的索引形式示意，并非该提交或本机工具的实际输出。为集中展示局部变量，直接使用参数 SSA 值，不展示 Clang 可能产生的参数栈槽、属性、metadata 与清理。

define internal float @scale_one(float %x, float %a) {
entry:
  %t.slot = alloca float, align 4
  %product = fmul float %a, %x
  store float %product, ptr %t.slot, align 4
  %t = load float, ptr %t.slot, align 4
  %result = fadd float %t, 1.000000e+00
  ret float %result
}

define void @scale(ptr noalias %out, ptr noalias %in, i32 %n, float %a) {
entry:
  %i.slot = alloca i32, align 4
  store i32 0, ptr %i.slot, align 4
  br label %cond
cond:
  %i.cond = load i32, ptr %i.slot, align 4
  %more = icmp ult i32 %i.cond, %n
  br i1 %more, label %body, label %exit
body:
  %i.body = load i32, ptr %i.slot, align 4
  %index = zext i32 %i.body to i64
  %src = getelementptr float, ptr %in, i64 %index
  %x = load float, ptr %src, align 4
  %y = call float @scale_one(float %x, float %a)
  %dst = getelementptr float, ptr %out, i64 %index
  store float %y, ptr %dst, align 4
  br label %inc
inc:
  %i.old = load i32, ptr %i.slot, align 4
  %i.next = add i32 %i.old, 1
  store i32 %i.next, ptr %i.slot, align 4
  br label %cond
exit:
  ret void
}

逐项看已有的信息：

  • 函数与类型已经确定： out/in 是指针，n 是 i32，计算是 float。
  • 控制流已经确定： entry/cond/body/inc/exit 和 branch 就是循环。
  • 每个临时值已经是 SSA： %product、%x、%i.next 都只有一个定义。
  • 源码变量 i 的“当前内容”还在内存中： 修改它使用 store，读取它使用 load。
  • 真正的数组访问仍在内存中： in/out 并不是局部 slot，不能期待 mem2reg 消灭数组读写。
  • 语言契约已开始进入 IR： 示意的 noalias 表达相关参数事实；实际属性和 metadata 的生成细节仍要看具体 CodeGen。

所以，“LLVM IR 已是 SSA，为什么还要 mem2reg”并不矛盾。原 IR 的指令结果符合 SSA；mem2reg 把符合条件的内存状态也重编码成 SSA 值。

mem2reg 输入的来源与已有处理

进入 mem2reg 之前，必然已经完成足以生成合法 IR 的语言处理：目标选择、预处理/词法、解析/Sema、AST CodeGen、ABI 与基本控制流/访存发射。

输入是否已经经过其他 LLVM Pass，取决于其生成方式：

输入来源 mem2reg 之前的处理
教学手写 .ll 只需先有合法 IR，不存在 Clang AST 步骤
Clang -O0 -S -emit-llvm 已有前端生成与必要整理；常带 optnone，普通优化 Pass 可能跳过
禁用 LLVM Pass 的前端输出 保留 AST CodeGen 与其局部工作，不代表完全没有折叠/简化
普通 clang -O2/-O3 的中间状态 管线可能已做模块处理、属性推导、内联、SROA/promotion 等
从另一前端导入的 .bc 初始 IR 风格与已有优化可能不同

最重要的是：“mem2reg 前”是一个观察切面，不是所有编译任务都有的唯一时间点。

默认优化经常由 SROA 内部调用 promotion，而不是显式安排名为 mem2reg 的独立 Pass。因而，debug-pass-manager 输出中没有 PromotePass，并不能说明未发生 SSA 提升；局部 load/store 的变化还需要与 SROA 等实际执行步骤对应。

快照：提升以后，i 的状态成为循环 PHI

对上面的教学 IR 运行 promotion 后，helper 的 %t.slot 可消失，scale 的 %i.slot 可变成：

entry:
  br label %cond
cond:
  %i = phi i32 [ 0, %entry ], [ %i.next, %inc ]
  %more = icmp ult i32 %i, %n
  br i1 %more, label %body, label %exit
body:
  %index = zext i32 %i to i64
  %src = getelementptr float, ptr %in, i64 %index
  %x = load float, ptr %src, align 4
  %y = call float @scale_one(float %x, float %a)
  %dst = getelementptr float, ptr %out, i64 %index
  store float %y, ptr %dst, align 4
  br label %inc
inc:
  %i.next = add i32 %i, 1
  br label %cond
exit:
  ret void

这是对应函数 body 的片段。初始边带来 0，回边带来 i.next；body、inc 使用同一个当前 %i。

提升后，循环状态每次经回边递增 1 的关系由 PHI 和更新指令显式表达。SCEV 可直接分析这种 recurrence，不必在 i.slot 的 load/store 链中反复寻找最后写入者。

但是 promotion 没有做三件事：没有自动删除 helper call、没有生成向量指令、没有给 i 分配硬件寄存器。

内联与清理：让循环体显露计算，而不是隐藏调用

内联 helper 并清理后，循环体可出现：

%x = load float, ptr %src, align 4
%product = fmul float %a, %x
%y = fadd float %product, 1.000000e+00
store float %y, ptr %dst, align 4

这一步为向量化提供一个很简单的逐元素模式。若 helper 没内联，LV 需要理解该调用是否安全、有无向量版本、是否支持相应处理，不能把任意 call 当成无副作用的乘加。

这里没有把浮点运算擅自变成实数代数或 FMA。是否 contract、是否允许 reassociation，都需要保留前端传来的浮点语义与目标约束。

内联也可能把 helper 的 alloca 带进 caller，因此 inline → SROA/promotion → InstCombine 之类的后续整理很自然。生产管线不是“一次提升后永不再提升”。

Pass Manager 的组织与分析维护

Clang 前端完成 Module 后，把它交给后端入口；中端优化与机器 codegen 是这里的不同子阶段。

llvm-project/clang/lib/CodeGen/BackendUtil.cpp 的 EmitAssemblyHelper::RunOptimizationPipeline：

  1. 根据目标/选项构造 PassBuilder。
  2. 注册 Module、CGSCC、Function、Loop analyses 及 manager proxies。
  3. 按优化级别、LTO 等选择管线；普通路径调用 buildPerModuleDefaultPipeline。
  4. 执行 ModulePassManager；选择输出 IR 时序列化结果，选择机器输出时继续 codegen。

对应管线定义在 llvm-project/llvm/lib/Passes/PassBuilderPipelines.cpp。四个层次不是四种 IR 语言，而是 Pass 处理对象的粒度：

层 处理范围 例子
Module 一个 IR 模块中的函数与全局对象 模块属性、全局清理
CGSCC 调用图的强连通分量 内联及调用图更新
Function 单函数 CFG 与指令 SROA、InstCombine、SCCP、LV
Loop 单个循环或相关 loop nest LICM、rotate、部分展开/循环变换

LV 虽然名字是 LoopVectorize，却以 Function Pass 驱动并自行处理循环；Pass 名字不能直接用来猜它的 manager 层次。

AnalysisManager 按请求计算并缓存事实。Transform 声称保留的分析可复用，否则失效/重算；“某个 analysis 在这里可用”并不意味着它一定在固定前一行运行。阅读管线时应分清安排了一个变换和按需取得一份分析结果。

进入循环优化之前：三个层面的准备

语义事实：知道什么不能动

目标循环需要带着正确事实进入中端：

  • 整数位宽、signedness 相关比较、溢出规则。
  • 浮点 flags/环境、是否允许 contraction/reassociation。
  • 调用副作用、异常、volatile/atomic/同步。
  • 指针别名、参数/对象信息、对齐、已知范围和 assumptions。

有些由前端直接产生，有些由跨函数属性推导、内联、AA 等后续推导。它们是证明基础，不只是优化速度开关。

表示形状：让循环成为可处理的对象

常见准备包括：

  • SROA/promotion 使可提升的局部状态变成 SSA。
  • InstCombine、EarlyCSE、SimplifyCFG 等去掉冗余和多余 CFG。
  • 内联暴露隐藏计算；TRE 可以把某些自递归变成循环。
  • LoopSimplify 整理 preheader、latch、dedicated exits 等可达规范形式。
  • LCSSA 把 loop 内定义、loop 外使用的值经退出 PHI 表达。

这些不是每种优化都必须逐项重新执行的全称清单。 输入可能早已满足形状；一些不可约 CFG 无法直接规范成所需自然循环；某 Pass 可自行处理特例。

分析事实：知道循环如何运行、机器支持什么

DominatorTree/LoopInfo、ScalarEvolution、AA、TTI/TLI 和按需要的 MemorySSA 等，回答：

哪里是循环，入口和回边在哪里？
谁支配谁，某条指令是不是必定执行？
诱导变量如何递推，trip count 有没有上界或倍数？
哪些访问可能重叠，哪些写会影响读取？
目标的向量、访存、指令成本如何？

这些分析结果共同约束展开因子、向量通道数量及运行时守卫的成本选择。

Loop adaptor 中的规范化准备

函数管线通过以下 adaptor 执行循环 Pass：

FPM.addPass(createFunctionToLoopPassAdaptor(std::move(LPM1),
                                            /*UseMemorySSA=*/true));

LoopSimplify 和 LCSSA 不必在调用处单独列出。该提交的 FunctionToLoopPassAdaptor 在构造时准备了一段 canonicalization pipeline。

位置：llvm-project/llvm/include/llvm/Transforms/Scalar/LoopPassManager.h：

LoopCanonicalizationFPM.addPass(LoopSimplifyPass());
LoopCanonicalizationFPM.addPass(LCSSAPass());

执行位置：llvm-project/llvm/lib/Transforms/Scalar/LoopPassManager.cpp 的 FunctionToLoopPassAdaptor::run。有循环时先运行 canonicalization，再取得新的 LoopInfo 和标准分析集合；若请求 UseMemorySSA，再取得并传递 MemorySSA。

它体现一种很重要的设计：变换所需的输入形式可由执行框架统一保证，而不必在每个 Pass 前手写一遍准备步骤。

同时这不是对所有带“loop”字样的 Pass 的普遍承诺；例如 Function 级 LV 自己获取/整理有关循环状态。应追当前实际使用的入口。

前期循环管线与多轮标量清理

看 PassBuilder::buildFunctionSimplificationPipeline，排除 O1 的专门分支、按固定提交中的普通相应路径：

SROA → EarlyCSE
  → 分支/相关值等简化（部分步骤受选项控制）
  → SimplifyCFG → InstCombine / AggressiveInstCombine 等
  → TailCallElim → SimplifyCFG → Reassociate
  → [Loop adaptor 的 LoopSimplify + LCSSA]
  → LPM1：LoopInstSimplify、LoopSimplifyCFG、LICM、Rotate、LICM、Unswitch 等
  → 函数级 SimplifyCFG、InstCombine
  → LPM2：Idiom、IndVarSimplify、LoopDeletion、FullUnroll 等
  → SROA 与后续标量清理，包括相应位置的 SCCP、DCE 家族等

图中仅列出主要步骤；PGO/LTO、选项、目标 callbacks 和优化级别会改变完整管线。该版本在前期 loop passes 后仍安排 SCCP 等标量清理，更早的折叠与简化也可由其他步骤完成。常量传播、死代码删除和循环变换由此交错运行，而非各自一次性完成。

为什么完整展开可能在这里很早？小常数循环完全展开后能暴露常量和数组固定索引，再由 SROA、InstCombine 等删除大量工作。等到向量化阶段，它可能已不再是循环。

为什么向量化常较晚？前期内联、别名/属性推导、结构整理能改善可分析性；向量化会生成主体、guard、fallback、尾部等更复杂结构，太早做可能妨碍其他标量变换。

快照：最终向量方案比“一条 SIMD 指令”复杂

假设一个候选使用 VF=4、IC=1，普通 fixed-width 主体可概念化为：

入口检查 n
  → 计算能处理多少完整 4 元素批次
  → 按需要执行 SCEV/alias/runtime 收益 guard
  → vector body：向量 load → splat(a)*X+1 → 向量 store，索引加 4
  → 剩余元素：标量或其他向量尾部
  → exit

对 noalias 足够的教学参数，不一定需要额外 alias guard。若失去相关事实，可加快路径/原标量 fallback；如果目标选择 tail folding，结构也会改变。

对照各阶段，可以区分五类表示变化：

  1. 前端的 ++i 最初是变量位置上的更新；后面成为 SSA recurrence，再成为向量索引步进。
  2. helper 最初是一个 call；适用内联后才显露 fmul/fadd。
  3. 本来每次读一个 float，向量主体可每次读多个；但最终还要经过后端目标合法化。
  4. i.slot 被提升并不意味着 out/in 的实际数据也从内存消失。
  5. 优化后的向量 IR 仍无最终物理寄存器；Greedy 在更后面的 Machine IR 上安排资源。

C++ 额外复杂性：不能把语言语义当作“优化噪声”

在简单 C 示例里看不到的内容，真实 C++ CodeGen 可能已放进 IR：

  • 引用绑定与对象生命周期。
  • 构造、析构与作用域 cleanup。
  • 虚调用、对象布局、this 与隐藏 ABI 参数。
  • 异常的 invoke、unwind 和异常处理块。
  • 模板实例化后实际可发射的函数体。

这些语言语义可能限制加载的推测执行、尾递归消除、内联或循环向量化。删除相关处理需要证明，例如调用不会抛出异常、对象状态不逃逸；仅凭它们不参与主要数值运算，不能判定其效果不可观察。

此外，Clang 的 C/C++ 前端通常直接走 AST→LLVM IR，不是默认先经过 MLIR。MLIR 很适合某些高层域和转换流程，但不能把它插进普通 Clang 默认编译路线当必经层。

链接与 LTO：为什么有时优化又跨过目标文件边界

普通分离编译中，某个 .c/.cpp 编译任务只能优化当前可用 Module 里的内容；外部函数若仅有声明，不能任意克隆它的 body。链接器合并普通机器目标文件，不会自动让已结束的中端重新看到所有函数源码。

LTO 使 bitcode/摘要等参与链接时的优化阶段：Full LTO 和 ThinLTO 用不同方式获得跨模块信息和进行后续优化，可能打开跨文件内联、属性推导等机会。所以有 pre-link/post-link 管线，而不是一个固定 -O3 清单。

普通 .ll/.bc 输出也不自动等于已配置 LTO 可执行链接。要区分“保存 IR”“以 IR 参与 LTO”与“链接机器目标文件”三件事。

SSA 与基础优化

前端生成合法 IR 后，中端通过 SSA 和基础优化显式化值的定义、使用及控制关系。本章承接编译流程，分析这些表示如何支持传播、删除和控制流变换，并为循环分析及后续寄存器分配提供基础。

这些优化与 SSA 的关系并不相同：mem2reg 构造标量 SSA，常量传播和死代码删除利用已有的 def-use 关系，内联与尾递归消除则改变函数或控制流并维护 SSA。区分这些职责，有助于追踪每个变换的输入和结果。

定义命名与控制流合并

int choose(bool cond, int x) {
    int y;
    if (cond) y = x + 1;
    else      y = x + 2;
    return y * 3;
}

SSA 的教学表示：

define i32 @choose(i1 %cond, i32 %x) {
entry:
  br i1 %cond, label %then, label %else
then:
  %y.then = add i32 %x, 1
  br label %join
else:
  %y.else = add i32 %x, 2
  br label %join
join:
  %y = phi i32 [ %y.then, %then ], [ %y.else, %else ]
  %result = mul i32 %y, 3
  ret i32 %result
}

%y.then、%y.else、%y 是三个不同定义。PHI 表示从哪个前驱进入 join，就取该边所携带的值，不是两条路径都执行，也不是先计算两边再挑一个。

普通指令的定义应支配使用；PHI 的 incoming use 则按对应前驱边处理，这让两个分支定义能在 join 合流。只有真的存在不同来源、且结果需要在汇合后使用，才需要保留非平凡 PHI。

SSA 的核心收益： 一个值的使用列表直接指向同一定义；替换这个定义的所有使用，就能沿 def-use 链传播结果。不必每次都问“同名变量在到达这里之前最后被谁赋值”。但内存仍可能被任意别名写入，普通 load 不能仅靠寄存器 SSA 获得相同保证。

mem2reg：消除不必要的内存身份

从 alloca/load/store 到值

前端为了表达可修改局部变量，尤其非优化生成阶段，常产生：

entry:
  %slot = alloca i32
  br i1 %cond, label %then, label %else
then:
  store i32 1, ptr %slot
  br label %join
else:
  store i32 2, ptr %slot
  br label %join
join:
  %v = load i32, ptr %slot
  ret i32 %v

若 %slot 的地址身份没有被程序观察，内存对象只承担“保存当前标量值”的职责，可以变为：

join:
  %v = phi i32 [ 1, %then ], [ 2, %else ]
  ret i32 %v

这里的 reg 是 SSA 虚拟值，不是分配 RAX 或某个硬件寄存器。最终它也可能在后端被 spill。mem2reg 与寄存器分配基础、Greedy 寄存器分配中的 register allocator 是完全不同阶段。

哪些对象允许提升

两个入口必须分开读：

  • llvm-project/llvm/lib/Transforms/Utils/Mem2Reg.cpp：Pass 包装，promoteMemoryToRegister 扫描函数 entry 的 allocas，反复收集可提升者并调用 PromoteMemToReg。
  • llvm-project/llvm/lib/Transforms/Utils/PromoteMemoryToRegister.cpp：isAllocaPromotable、SSA 构建、快路径和重命名的真正实现。

本提交的判断主要允许直接、非 volatile、类型一致的 load/store，以及规定范围内的 lifetime/droppable 等使用。特别注意：

  • store ptr %slot, ptr %somewhere 是存储地址本身，不是向 slot 存值；地址可能逃逸，不能这样提升。
  • 把地址交给普通未知调用，不能当作“私有标量”忽略调用读写。
  • 任意非零 GEP、聚合字段或数组索引，不属于 mem2reg 直接处理的一般模式。
  • volatile 访问的可观察语义不能因局部对象而删除。
  • 本提交并不一律拒绝 atomic load/store。 对满足这种封闭局部 alloca 使用模式的对象，源码注释解释其原子性没有跨观察者意义；不能把这个结论推广到共享内存。
  • alloca 声明的类型不必机械地等于实际访问类型；实现要求相关 load/store 访问类型一致，并按实际使用判断。

包装器在 entry 找候选，不意味着底层 API 的理论只适用于“第一块叫 entry”的形式。教学复现应以包装 Pass 的输入约束为准。

理论：支配边界与 pruned SSA

若 block X 定义了变量，在一些分叉、汇合之后，哪个位置需要 PHI？支配边界 DF(X) 可理解为“X 支配某个到达这里的前驱，但不能严格支配这里”的汇合边界。多个定义的边界可能产生 PHI，而 PHI 自身又是新定义，因此需要 iterated dominance frontier，IDF。

但并不是在所有 IDF 点都插 PHI。若一个汇合后的值从不被读取，插入它毫无意义。LLVM 先计算 LiveInBlocks，再用其限制 IDF；这就是 pruned SSA：只在需要活跃值的位置合流。

本提交真实片段，位于 PromoteMem2Reg::run，省略上下文：

ComputeLiveInBlocks(AI, Info, DefBlocks, LiveInBlocks);
IDF.setLiveInBlocks(LiveInBlocks);
IDF.setDefiningBlocks(DefBlocks);
SmallVector<BasicBlock *, 32> PHIBlocks;
IDF.calculate(PHIBlocks);

接着为相应块 QueuePhiNode，再由 RenamePass 遍历 CFG，维护当前 incoming value：遇到 store 更新当前值，遇到 load 以当前值替换，进入带 PHI 的块以 PHI 作为当前值，并填充 incoming edges。

理论教材常通过遍历支配树、为每个变量维护定义栈来解释重命名；本实现则使用工作列表、当前值与撤销状态维护遍历过程。二者表达同一类 SSA 构建问题，但数据结构与状态更新方式需要分别对照。

对于单次 store、同一 block 内所有使用等简单情形，rewriteSingleStoreAlloca、promoteSingleBlockAlloca 等快路径可以避免完整 SSA 构建。未初始化读取不能凭空变成 0：本实现以 UndefValue 等 IR 规则处理相关状态，源语言读取未初始化对象的规则还要另行遵守。

SROA 与 mem2reg 的关系

结构体、数组或按字段访问的对象，往往需要先把对象分割为更合适的小片段。llvm-project/llvm/lib/Transforms/Scalar/SROA.cpp 做 Scalar Replacement of Aggregates，处理切片并对合适部分进行 promotion；不是“直接对所有数组运行 mem2reg”。

默认优化管线常直接安排 SROA 及其提升能力，不一定显式列出一个独立 mem2reg。手工运行 opt -passes=mem2reg 可以隔离算法作用，但生产管线消除局部 load/store 的路径还包括 SROA 内部的提升。

常量折叠、简化与传播：三个相关但不同的问题

常量折叠：已知输入，直接求值

%a = add i32 2, 3
%b = mul i32 %a, 4

第一条可得到 5，替换其使用后第二条变成常量乘法，可得到 20。folding 是对已知 operands 的计算；“替换并继续传递”才是传播层面的动作。

主要路径：llvm-project/llvm/lib/Analysis/ConstantFolding.cpp 的 ConstantFoldInstruction 等入口，结合 llvm-project/llvm/lib/IR/ConstantFold.cpp 的常量层实现。

常量折叠必须遵守整数位宽、目标 DataLayout、浮点格式及具体 IR 语义。APInt/APFloat 等表示将这些条件与宿主机器的原生运算分开，避免把宿主环境的结果直接当成目标语义。

指令简化：输入未知，也能利用恒等关系

例如整数 %x + 0 可简化为 %x，不需要知道 x 的具体数值。llvm-project/llvm/lib/Analysis/InstructionSimplify.cpp 提供简化查询；llvm-project/llvm/lib/Transforms/InstCombine/InstructionCombining.cpp 中的 InstCombine 工作列表可做更广泛的局部等价变换、规范化和持续清理。

区分两者：InstructionSimplify 的接口通常返回可替代的现有值/常量，不负责任意新建复杂指令序列；InstCombine 作为变换会构造与改写指令，并驱动后续处理。ConstantFolding 则专注常量求值。它们相互调用或协作，不是三套互不接触的编译器。

折叠能力分布在 IR 构造、InstCombine、SCCP 和克隆剪枝等环节，并非由一个统一的 constprop Pass 承担。分析某次常量化时，需要追踪实际执行的位置。

SCCP：同时推导“什么值”与“哪些边能走”

Sparse Conditional Constant Propagation 使用两个相互影响的事实：

  1. 某个 SSA 值能否被确定为常量或限制在一个范围。
  2. 哪些 CFG blocks/edges 可能执行。

经典教学 lattice 可以写成：

尚无信息 → 常量 c → 不再能用单一常量表示

不同常量合流得到更不精确的状态。这不是硬件值从未知变成常量；它是分析信息从少到多、逐渐发现更多可能性。 LLVM 当前的 ValueLatticeElement 更丰富，包含 unknown、undef、constant、notconstant、整数范围以及 overdefined；不能把三点格当作精确完整实现。

路径：llvm-project/llvm/lib/Transforms/Scalar/SCCP.cpp，求解器在 llvm-project/llvm/lib/Transforms/Utils/SCCPSolver.cpp，抽象状态在 llvm-project/llvm/include/llvm/Analysis/ValueLattice.h。

entry:
  br i1 true, label %left, label %right
left:
  br label %join
right:
  br label %join
join:
  %v = phi i32 [ 7, %left ], [ 9, %right ]
  ret i32 %v

若简单地把 PHI 的所有 syntactic operands 合并，7 与 9 不同，会失去常量结论。SCCP 知道 right 边不可执行，只合并可执行 incoming edges，所以 %v 为 7。这正是 Conditional 的价值；Sparse 则意味着主要沿 SSA 使用链和可执行边传播，避免每轮反复扫描所有无关指令。

工作列表持续传播到固定点。相关事实变成常量后，可折叠条件、删除不可达结构；函数间版本 IPSCCP 进一步利用可追踪调用和返回，但受可见性与调用者信息限制，不能假定 externally callable 函数只收到当前分析位置出现的常量实参。

IR 语义的边界：数学相等未必足够

  • 固定位宽整数有 wrap、nsw / nuw 等不同约束；违背 no-wrap 条件可能产生 poison。
  • 浮点 x + 0 不应不加条件地等同于数学实数恒等式，NaN、符号零、异常环境与 flags 都影响判断。
  • undef、poison、freeze 是 IR 概念，不等价于“一颗可随便设成任意整数的变量”。
  • 未知且有副作用的普通函数调用不能仅凭结果似乎稳定而在编译时折叠。

本节是在解释证明边界，不是鼓励程序依赖未定义行为。精确语义应回到 llvm-project/llvm/docs/LangRef.md。

死代码删除：为什么“没人用结果”不是全部条件

DCE：从无用叶子反向剥离

%a = add i32 %x, 1
%b = mul i32 %a, 2
ret i32 0

b 无使用且可安全删除；删掉 b 后，a 也失去最后使用。这种链式过程适合工作列表，不用每删一条就重扫整个函数。

llvm-project/llvm/lib/Transforms/Scalar/DCE.cpp 的 DCEInstruction：

isInstructionTriviallyDead?
  → 保留可挽救的 debug info / knowledge
  → 解除 operands 的使用关系
  → 把因此变死的 operand instructions 加入 WorkList
  → 删除当前指令

死指令判定与相关公共实现可追 llvm-project/llvm/lib/Transforms/Utils/Local.cpp。

普通 store 没有 SSA 返回值，call 的返回值也可能没有使用者，但这些操作可能修改内存、执行 I/O、抛出异常或影响执行进展，不能仅凭 use_empty 删除。volatile/atomic 与同步语义也必须考虑。特定库调用或 intrinsic 在证明允许时有例外，判断应以精确语义为准。

ADCE：从有意义的根正向保留，而不是只等 use 归零

简单 DCE 容易漏掉内部互相使用、却整体没有可观察贡献的环。ADCE 乐观地把指令当 dead，从必须保留的效果、返回等根开始标 live，再沿数据依赖和控制依赖保留所需部分。

为什么控制依赖重要？若两个分支分别写入 1 和 2，决定走哪条的条件也是可观察效果所必需，不能删掉条件而随机选择其中一边。

路径：llvm-project/llvm/lib/Transforms/Scalar/ADCE.cpp，会使用 PostDominatorTree 和反向图上的依赖关系处理控制流。postdominate 可粗略理解为某块正常到达出口的路径都经过另一个块；具体算法还要正确处理无出口等情况。

“死循环里只有无用算术”并不自动等于可以让函数返回。终止性/进展语义也是可观察行为；本提交 ADCE 有默认关闭的 adce-remove-loops 选项处理 may-be-infinite 情况，其他 mustprogress 等事实和 Pass 也会影响能做的事。ADCE 的 optimistic dead 策略仍受终止性与进展语义约束，不允许任意改变无限循环。

DSE：内存写入的死活，另有一套证明

*p = 1;
*p = 2;

若访问不是 volatile/需保留的原子操作，中间没有读取、异常或其他障碍，且第二次覆盖必然在需要的路径发生，第一次写可能死。它不是普通 use-empty DCE 的问题。

llvm-project/llvm/lib/Transforms/Scalar/DeadStoreElimination.cpp 文件头给出 MemorySSA-backed 方法：从较后的 MemoryDef 往上找可能被杀死的定义，再检查期间没有读取、没有阻碍、覆盖范围充分和执行条件成立。

若中间插入 observe(p)，必须知道该调用是否读 p；如果只覆盖半个对象，不能宣称整个旧 store 都死。标量 SSA 解决的是值使用，MemorySSA＋别名分析帮助解决的是内存效果。

SimplifyCFG 与不可达代码

不可达块、无意义跳转、常量分支、可合并块等，主要由 CFG 清理和其他变换配合处理。路径：llvm-project/llvm/lib/Transforms/Scalar/SimplifyCFGPass.cpp、llvm-project/llvm/lib/Transforms/Utils/SimplifyCFG.cpp。

因此“死代码清除”是一个家族：DCE、ADCE、DSE、unreachable/CFG cleanup、GlobalDCE 各有对象和证明，不是一个 Pass 包办。

函数内联：消除边界，比消除 call 更重要

一个会暴露常量的调用点

static int scale(int x, int mode) {
    if (mode == 0) return x * 2;
    return x * 3;
}
int caller(int x) {
    return scale(x, 0) + 1;
}

内联把 callee 的逻辑带进 caller，并以实参替换形参。第二个实参为 0，所以 mode 分支可折叠，最终可能只剩 x*2+1 的计算。

节省 call/ret 是一部分；更重要的是暴露：常量实参、对象身份与访问、可删除路径、嵌套调用目标、归约或循环体中的可优化表达式。后续 InstCombine、SROA、SCCP、DCE、LV 才能利用它们。

内联不是文本粘贴：调用点被拆成前后块，callee 基本块和指令被克隆、重新命名；形参映射实参；多个 return 跳到 continuation，并可能经 PHI 合并返回值。还要处理 byval、alloca、lifetime、invoke/异常路径、调试位置与不同函数属性约束。

理论收益和代价

收益模型估计的是这个调用点特化后的结果，不是原函数源码行数。例如函数本体较大，但常量参数能剪掉绝大多数分支，仍可能值得；小函数位于大量冷调用点，也可能因为体积累计而不划算。

代价包含：I-cache、编译时间、caller 扩张、寄存器 live ranges、栈大小和递归展开风险。profile 可引导热调用更积极、冷调用更保守，但不是保证每个热 call 必内联。

SCC（strongly connected component）标识互相递归可达的调用组；无限把自己/互递归函数内联会指数或无限扩张。调用历史、预算、属性与策略限制必须阻止这种情况。函数声明的 C++ inline 也不是“一定消除所有调用”；它有语言层含义，编译器的推荐属性和 alwaysinline/noinline 又是另一层机制，仍受合法性规则约束。

间接调用需要先知道目标，或由去虚拟化/特化等形成可内联场景；只有外部声明而无可用 body，无法克隆不存在的实现。符号可替换性、链接语义、calling convention 等同样不能忽略。

与后文连接： 循环中的小辅助函数被内联后，LV 才看得到逐元素计算；但内联把更多值放到 caller，也可能让 Greedy 需要切分和 spill。不能仅凭 call 指令消失判断净收益。

尾递归换循环：把栈状态显式写成 PHI

最干净的尾递归例子

unsigned sum_down(unsigned n, unsigned acc) {
    if (n == 0) return acc;
    return sum_down(n - 1, acc + n);
}

这里自调用后只把结果返回，没有剩余的计算或析构。教学上的循环形式：

unsigned sum_down_loop(unsigned n, unsigned acc) {
    while (n != 0) {
        acc += n;
        --n;
    }
    return acc;
}

在 IR 层，参数的当前值由 loop header PHI 表示：初始边输入函数实参，递归边输入“下一轮实参”。原来的 self-call 和对应 return 换为回边；base case 的 return 保留。

define i32 @sum_down_loop(i32 %n0, i32 %acc0) {
entry:
  br label %loop
loop:
  %n = phi i32 [ %n0, %entry ], [ %n.next, %step ]
  %acc = phi i32 [ %acc0, %entry ], [ %acc.next, %step ]
  %done = icmp eq i32 %n, 0
  br i1 %done, label %exit, label %step
step:
  %acc.next = add i32 %acc, %n
  %n.next = sub i32 %n, 1
  br label %loop
exit:
  ret i32 %acc
}

这些是教学 IR，不宣称本机已经生成。前端还有 ABI、属性和局部对象信息；真实输出可能不同。

源码与合法性边界

路径：llvm-project/llvm/lib/Transforms/Scalar/TailRecursionElimination.cpp，重点读：

  • canTRE：本提交拒绝 dynamic allocas，因为迭代之间正确释放动态栈分配尚未在此实现。
  • AllocaDerivedValueTracker 与 tail-call 标记逻辑：追踪指针是否派生于/逃逸自 caller 栈对象，避免下一轮破坏仍需存在的内存。
  • TailRecursionEliminator::findTRECandidate：找当前函数的递归调用，并检查 tail-call 等条件。
  • TailRecursionEliminator::eliminateCall：生成/更新回边、参数 PHI 和相关返回值处理。

递归语义中的“新栈帧”可能提供独立局部对象；不能在它们的地址仍被下一层使用时无条件复用同一个位置。C++ 析构、EH 清理、call 后 store 或其他效果，也可能使看起来在 return 表达式里的调用并不是真正可消除的尾位置。

尾递归消除需要维护参数状态、返回路径和对象生命周期，不只是替换函数末尾的调用。对没有额外对象约束的简单例子，递归链的调用开销与栈深可以消除；包含 allocas 的其他递归仍需逐项检查，不能据此承诺零额外栈增长。

非尾递归的部分扩展：累加器

unsigned fact(unsigned n) {
    if (n == 0) return 1;
    return n * fact(n - 1);
}

乘法在递归返回后执行，原形不是直接尾调用。但若运算与使用形状符合规则，可引入初始为 1 的 accumulator，把每次 n 乘进去，再回边。unsigned 模乘具有适用的结合、交换性质；带不同 no-wrap 或浮点语义时必须另查。

本提交 canTransformAccumulatorRecursion 检查关联/交换性或支持的特定 unary recurrence、identity、调用结果在 operand 中的使用方式，以及结果仅被相应 return 使用；insertAccumulator 创建状态 PHI。

这不意味着 LLVM 会自动把任意 Fibonacci 的两分支递归变成线性时间循环。某个尾分支被消除，不等于所有递归结构都被消除，更不等于做了动态规划。

TRE 与后端尾调用不是一件事

概念 典型结果 关键条件
自递归消除 TRE 同一函数内的 loop/PHI 自调用、可改写参数与状态、栈对象等安全
sibling/tail call lowering 跳转到另一函数，复用当前调用框架 ABI、calling convention、参数传递、目标支持
musttail IR 强制尾调用契约 严格的 LangRef 约束，不是普通优化提示

TRE 属于中端结构变换，能让后续 LoopInfo、SCEV、LICM、展开等看到新循环；普通尾调用 lowering 则通常仍跨函数，不会因此在 caller 中形成一个可向量化 loop。

基础变换之间的因果关系

前端 alloca / load / store
  → SROA / promotion：移除不必要内存身份，建立清晰值流
  → 内联：把调用点实参与 callee 计算放进同一推理空间
  → InstCombine / SCCP：常量与简化传播，识别不能走的路径
  → DCE / ADCE / DSE / SimplifyCFG：清掉没有贡献的计算与结构
  → TRE：把适合的递归状态转成显式 loop / PHI
  → 后续循环分析、结构变换、LV / SLP / unroll
  → 后端有限寄存器上的资源安排

这是解释依赖关系的图，不是声称 LLVM 默认严格按这一次序各运行一次。llvm-project/llvm/lib/Passes/PassBuilderPipelines.cpp 可见 SROA、InstCombine、SCCP、ADCE、SimplifyCFG 在不同阶段出现；TailCallElim 也在相应函数优化阶段安排。内联作为跨函数管线的一部分，会让后续函数级优化重新获得机会。

为什么需要多轮？内联暴露常量，常量传播删分支，删分支使 PHI 简化，PHI 简化让某个对象可提升，提升后又暴露 DCE 或循环规律。生产管线通过阶段化和固定预算获得大部分收益，而不是对所有 Pass 无限制跑到全局固定点。

一个小实验，把 SSA、控制流和消除连起来

下面的完整示例 IR 可保存为系统 TEMP 实验目录中的 ssa-demo.ll。示例不包含目标特定运算，用于观察局部状态提升和控制流清理。

define i32 @ssa_demo() {
entry:
  %slot = alloca i32
  br i1 true, label %left, label %right
left:
  store i32 7, ptr %slot
  br label %join
right:
  store i32 9, ptr %slot
  br label %join
join:
  %v = load i32, ptr %slot
  %unused = mul i32 %v, 100
  %result = add i32 %v, 1
  ret i32 %result
}

沿用优化诊断与对照实验中的 $Opt、$Exp，可以用以下未实测的命令比较提升与清理结果：

& $Opt -S -passes='mem2reg' "$Exp\ssa-demo.ll" `
    -o "$Exp\ssa-promoted.ll"
& $Opt -S -passes='mem2reg,sccp,dce,simplifycfg' "$Exp\ssa-demo.ll" `
    -o "$Exp\ssa-clean.ll"

第一步预期关注 slot 是否被消除、join 是否经 PHI 表示两条输入；第二步关注恒 true 路径使 %v 为 7、result 为 8、无用链与 right 路径被清理。各工具版本的清理分工和中间形状可能不同，不应把某个精确块名当正确性要求。

循环优化的理论基础

循环首先是一种控制流结构

LLVM 的普通 LoopInfo 主要识别自然循环：header 支配循环内各块，回边回到 header。支配的意思是从函数入口到该块的所有路径都经过支配者。不是所有任意 CFG 环都能直接当作这种 Loop 处理。

为了让变换有统一入口，编译器常整理出：

  • preheader： 循环外唯一准备入口，适合放检查和外提代码。
  • header： PHI 与循环控制的汇合点。
  • latch： 回边所在块。
  • dedicated exits： 退出块不同时接受无关的循环外边。
  • LCSSA： 循环内定义、循环外使用的值经退出 PHI 输出，像给循环加上清晰的数据接口。

阅读路径：llvm-project/llvm/lib/Transforms/Utils/LoopSimplify.cpp、llvm-project/llvm/lib/Transforms/Utils/LCSSA.cpp、llvm-project/llvm/include/llvm/Analysis/LoopInfo.h。

规范化为各类优化提供相对统一的输入，降低处理 CFG 特例的复杂度。孤立运行某个 Pass 与默认管线可能得到不同结果，其中一个原因就是前置形式和分析条件不同。

ScalarEvolution 的递推抽象

考虑：

for (int i = 0; i < n; ++i)
    a[i] = b[i] + 1;

IR 用 PHI、add、icmp 与 GEP 分别表达状态合流、更新、比较和地址计算。SCEV（Scalar Evolution）尝试把 i 抽象为相对于某个 Loop 的递推 {0,+,1}，把地址抽象为基址、步长与迭代号的组合。SCEVAddRecExpr 是这种递推的核心表示之一。

这种抽象支持多类分析：

  • 回边执行次数，以及迭代次数的常量、上界与已知倍数。
  • 地址间距离、连续访问与等步长关系。
  • 表达式相对于循环的不变性。
  • 递推规律依赖的额外谓词及其成立条件。

回边次数与迭代次数采用不同的计数定义。对于至少执行一次的简单循环，迭代数通常是回边次数加一；零次迭代、多个退出和不同计数定义要额外处理。溢出同样重要：数学整数上的 i+1 与有限位宽、可能 wrap 的 IR 运算不是同一回事，nuw / nsw 等事实和证明条件会影响推导。

路径：llvm-project/llvm/lib/Analysis/ScalarEvolution.cpp，以及 llvm-project/llvm/include/llvm/Analysis/ScalarEvolutionExpressions.h。向量化入口使用 PredicatedScalarEvolution：某些结论依赖运行时可检查的谓词，不是凭空假定不溢出。

内存依赖与执行顺序

对相同内存位置，重要的三类关系是：

依赖 原执行顺序 重排风险
RAW / true dependence 写后读 读不到应读的新值
WAR / anti-dependence 读后写 写提前覆盖应读旧值
WAW / output dependence 写后写 最终留下错误的一次写

两个读之间通常没有这种内存顺序约束。依赖还分循环内与循环携带：后者跨不同迭代。

// 跨迭代 RAW，距离 1
for (int i = 1; i < n; ++i)
    a[i] = a[i - 1] + b[i];

// 若 a、b 不重叠，各迭代可独立
for (int i = 0; i < n; ++i)
    a[i] = b[i] + 1;

第一段要求迭代 i 在 i−1 更新以后读取，因此不能直接让两个线程无约束同时执行，也不能直接把相邻四次迭代当独立 lane。它可以保序展开；某些特殊递推可以用专门变换处理，但不是普通独立迭代打包。

再看距离 4：

for (int i = 4; i < n; ++i)
    a[i] = a[i - 4] + 1;

在满足其他条件时，以 4 为宽度分批、批之间保序，批内可能没有 RAW 链；更大宽度则可能把生产者和消费者放进同一批。这说明存在循环携带依赖不等于所有 SIMD 都不可能，还要看方向、距离、访问顺序和 VF。线程级任意调度的证明往往要求更强。

别名分析与依赖分析不是一回事

Alias Analysis 回答两次内存访问会不会碰到同一位置；Dependence / LoopAccessAnalysis 进一步问它们在不同迭代如何发生关系。

a 和 b 都是 float * 并不能证明它们不重叠。即使源码看起来写了两个变量，调用者仍可能传入 a=b+1。LLVM 会利用别名信息、SCEV 地址表达式、对象信息和访问关系综合分析。

路径：llvm-project/llvm/lib/Analysis/BasicAliasAnalysis.cpp、llvm-project/llvm/lib/Analysis/DependenceAnalysis.cpp、llvm-project/llvm/lib/Analysis/LoopAccessAnalysis.cpp。后者的 MemoryDepChecker 与 RuntimePointerChecking 直接连接到循环向量化。

restrict 是程序员的语义契约，不是免费性能按钮。若程序违反限制，不能指望编译器仍保持原本的偶然执行行为。错误的独立性声明是正确性 bug。

        /            \
  可证明安全       条件不成立
  快速向量循环      原标量循环
        \            /
            汇合

对于简化的连续访问模型，检查可以理解为判断两个半开地址区间是否重叠。实际实现还要处理访问分组、地址步长、溢出、检查数量及生成代码的成本，不能仅比较两个起始指针。

运行时检查不意味着每次迭代都检查；它通常是进入快路径前的开销。循环长时容易摊薄；短循环则可能不值得。路径：llvm-project/llvm/lib/Transforms/Utils/LoopVersioning.cpp、llvm-project/llvm/lib/Transforms/Utils/LoopUtils.cpp，以及前述 LoopAccessAnalysis。

这种设计组合静态证明、动态守卫与保守回退：静态信息不足时，编译器仍可在检查成立的输入上使用优化方案，在其他输入上保留原有执行路径。

归约：不是无依赖，而是可转换的依赖

float sum = 0;
for (int i = 0; i < n; ++i)
    sum += a[i];

这是 loop-carried recurrence，不是独立迭代。若运算允许结合重排，可维护多个局部累加器，最后归并。

  • 整数模加法有结合性，但带有特定溢出语义或标志的 IR 仍需按其语义判断。
  • 浮点加法通常不结合。(large + small) + (-large) 与 large + (small - large) 可能不同。
  • min/max、乘法等也必须检查类型、NaN、符号零和具体运算语义。
  • 某些目标和实现支持 ordered reduction，保持要求的顺序；不能说“没有 fast-math 就绝对不能向量化任何浮点归约”。

路径：llvm-project/llvm/lib/Analysis/IVDescriptors.cpp，其中 RecurrenceDescriptor、InductionDescriptor 识别这些模式；llvm-project/llvm/lib/Transforms/Vectorize/LoopVectorizationLegality.cpp 的 canVectorizeFPMath 检查相关合法性。

归约识别的本质： 找出一种可证明等价的状态重编码，而不是忽略依赖。

收益模型：理论上更并行，不保证机器上更快

简化成本模型可以把向量快路径分成启动检查、各向量批次和尾部处理，再考虑缓存、分支及资源竞争。LLVM 的 TTI 指令成本是目标相关估计，不是精确的实际耗时，也不能作为跨 CPU 通用的常数。

循环优化可能卡在三类瓶颈：

  1. 依赖延迟： 一个累加器的串行链限制吞吐，多累加器可帮助。
  2. 执行吞吐： 有足够独立指令，但执行端口饱和。
  3. 访存带宽： SIMD 和多线程都不能无限提高内存带宽；线程可能只增加争用。

分析时间同样受预算约束。内存访问的两两比较随访问数量增长，候选方案搜索也可能迅速扩大。保守上限限制整个程序的编译成本，同时可能使某些理论上可行的变换不进入实际搜索范围。

自动向量化

Loop Vectorizer 的迭代打包

void saxpy(float *restrict y, const float *restrict x,
           float a, int n) {
    for (int i = 0; i < n; ++i)
        y[i] = a * x[i] + y[i];
}

在 VF=4 的简化模型中，向量主体可表示为：

X = load <4 x float> x[i:i+4]
Y = load <4 x float> y[i:i+4]
Y = splat(a) * X + Y
store Y
 i += 4

这里 splat 是把一个标量广播到各 lane。不是启动四个线程，不是保证生成某条特定 SIMD 指令，也不意味着可擅自融合乘加。是否形成 FMA 另受浮点 contraction 语义和后端选择约束。

  • VF（vectorization factor）： 一次向量操作覆盖多少标量迭代；可为 fixed 或 scalable ElementCount。
  • IC（interleave count）： 一轮向量循环有多少组向量工作，粗略相当于向量主体再作一定展开。
  • 每轮覆盖量： 在普通模型下为 VF×IC 次标量迭代；可伸缩向量的实际 lane 数还与运行时 vscale 有关。

以 VF=4、IC=2 为例，一轮处理两组 4 个元素。它可能增加独立访存与计算，隐藏延迟，但也增加同时活跃的向量临时值。

控制流、指令与 PHI 的合法性

在 LoopVectorizationLegality::canVectorizeInstrs 中，header PHI 要能解释为诱导变量、归约或其他支持的递推模式。一个未知的跨迭代状态并不能自动扩成向量。

循环中的函数调用也要有安全和可向量化的解释：目标是否有向量版本、是否可展开或标量化、副作用和访问语义如何。不能把任意 foo(i) 同时执行四份。

条件分支可通过 if-conversion 转成掩码/选择：

if (a[i] > 0)
    b[i] = expensive(a[i]);

教学图是先生成 mask = A > 0，再对活跃 lane 执行。普通 select 并不能让前面的非法 load 或有副作用调用变得安全：如果两个候选值已经先执行，未选中的危险操作仍然发生。必须证明推测执行安全，或使用支持的 masked / predicated 运算，必要时标量化。

本提交还出现 uncountable early exit 的专门检查与开关，因此“所有提前退出循环均不支持”过于绝对。具体支持条件由退出形状、副作用和相应开关共同决定。

跨 lane 重排的内存条件

canVectorizeMemory 使用 LoopAccessAnalysis。关键不是“存在 store 吗”，而是所有可能冲突是否安全。

典型结果有四种：

  1. 静态证明访问独立，直接继续。
  2. 有距离约束，可以限制最大安全 VF。
  3. 存在可动态判定的别名，规划 runtime checks 与 scalar fallback。
  4. 无法证明、无法经济地检查或存在不支持的依赖，拒绝。

连续 load/store 通常具有较直接的目标实现；结构体交错访问可能组成 interleaved access，不规则访问可能需要 gather/scatter，部分指令则按 lane 标量化。不同方式的成本依赖目标能力；gather/scatter 和标量化可能增加开销，因此 IR 中出现向量类型并不直接证明端到端收益。

interleaved memory access 与 IC 描述不同对象：前者针对 RGBRGB... 等交错地址布局的访问分组，后者表示每轮执行多少组向量迭代。

第三关：怎样选 VF 和 IC

LoopVectorizationCostModel::computeMaxVF 给出候选边界；LoopVectorizationPlanner::plan 和相关候选成本逻辑在这个边界内选择计划。TTI 给出运算、内存、shuffle、掩码等估价。

教学上可比较“每批成本 / 本批标量迭代数”，但真实判断还需要：

  • 外围检查和最低可获益 trip count。
  • scalar remainder 或向量 epilogue。
  • scalarization、extract/insert、reduction 收尾成本。
  • 固定与 scalable VF 的目标支持。
  • profile、优化体积政策、用户 hints。
  • 寄存器使用估计。

本提交 selectInterleaveCount 使用 calculateRegisterUsageForPlan，不是完全忽略寄存器压力的“越宽越好”。但中端的估计仍不是最终分配：目标合法化、指令选择和调度还会改变临时值和生命周期。

扩大 VF/IC 既可能减少同形工作的执行与控制开销，也可能增加 shuffle 和资源需求。成本选择需要比较完整方案的净收益，而不只是选取硬件支持的最大宽度。

VPlan：先表示方案，再改写真实程序

在分析过程中直接改写真实 IR，会使候选比较与回退更复杂。VPlan 用专门的计划图表示控制结构和数据流，使变换与成本比较先在计划层完成，再执行选定方案。

  • VPValue / VPUser 表示计划的数据关系。
  • VP basic block / region 表示计划控制流。
  • recipe 描述如何生成 widened、replicated、reduction 或其他 IR。
  • 计划可以保留标量工作，不要求每个 recipe 都变成一条 SIMD 指令。

recipe 的实现位于 llvm-project/llvm/lib/Transforms/Vectorize/VPlanRecipes.cpp，计划级改写位于 llvm-project/llvm/lib/Transforms/Vectorize/VPlanTransforms.cpp。分析其生成结果时，需要先区分输入代表 VF 个 lane 的值，还是单一标量值，再对照实际生成的 IR。

本提交的普通入口断言说明：非 VPlan-native 外循环路径时主要处理最内层循环；外层向量化还有条件与限制。不能由“代码包含外循环逻辑”推论“任意嵌套自动一起向量化”。

尾部：n 不是 VF 的倍数怎么办

三类常见办法：

  1. 标量尾循环： 主体处理完整向量，剩余元素标量执行。
  2. 较小 VF 的向量尾部： 用另一个方案覆盖余量，再视需要处理最后几个元素。
  3. tail folding： 最后一批也进入向量循环，用 active-lane mask 只访问合法元素。

掩码运算不能越界产生未定义行为；目标的 masked load/store 支持与成本非常重要。tail folding 能减少额外尾循环，也可能增加每轮掩码和谓词成本。

向量类型只表明部分指令的表示。完整方案还包括 guard、runtime check、vector body、epilogue 和 scalar fallback；将这些部分放在同一 CFG 中，才能分析快路径的适用输入及额外成本。

SLP：不用循环，也能自动 SIMD

out[0] = a[0] + b[0];
out[1] = a[1] + b[1];
out[2] = a[2] + b[2];
out[3] = a[3] + b[3];

SLP（Superword Level Parallelism）从局部同形标量指令组寻找 SIMD。实现核心在 llvm-project/llvm/lib/Transforms/Vectorize/SLPVectorizer.cpp 的 BoUpSLP：

寻找 root / 相邻 stores / 可组合值
  → buildTree：从结果向上匹配同形 operand bundles
  → 检查依赖和调度可行性，选择 lane 顺序
  → getTreeCost：向量收益减去 pack / shuffle / extract 等成本
  → vectorizeTree：生成向量代码，修复外部标量使用

名字叫 tree，但共享值和外部使用让真实结构不必是纯树。不是遇到四个 add 就可以合并：若中间 store 与 load 可能别名、指令不能共同调度，或输出必须频繁提取回标量，可能不划算。

该提交的 SLP 源码包含 may-alias runtime-check 的规划接口。这表明实现具备相关规划能力，但候选能否成功 version 仍需结合具体路径和条件检查，不能从接口存在推断所有情况均受支持。

Loop Vectorizer 与 SLP 的协作： 循环展开把跨迭代同形指令显式摆出来，SLP 可能再组合；但 LV 通常直接以迭代为单位规划。两者存在相互作用，不能简单视为互斥开关。

未向量化与未加速的阶段诊断

SAXPY 未生成向量代码时，首先需要定位实际接受分析的函数和循环。内联可能使原函数消失，hints 或管线配置也可能使 Pass 不运行。确认执行入口后，合法性诊断可以进一步区分别名、递推、副作用和浮点语义等限制。

合法性通过仍可能因成本不足而保留标量方案。反过来，IR 中存在向量操作也不意味着机器码高效：目标降低可能引入标量化或大量 shuffle，寄存器分配可能产生 spill，运行时又可能受访存带宽限制。将诊断、IR、机器码和性能观测对应到各自阶段，才能确定问题发生在候选生成、方案选择还是最终执行。

自动循环展开

保序展开的基本结构

for (int i = 0; i < n; ++i)
    a[i] = a[i] * c + 1;

因子 U=4 的教学结构：

// 示意：实际编译器还必须正确处理边界运算和溢出
for (; remaining >= 4; i += 4, remaining -= 4) {
    a[i]     = a[i]     * c + 1;
    a[i + 1] = a[i + 1] * c + 1;
    a[i + 2] = a[i + 2] * c + 1;
    a[i + 3] = a[i + 3] * c + 1;
}
for (; remaining > 0; ++i, --remaining)
    a[i] = a[i] * c + 1;

展开本身仍可保持所有原迭代的顺序，所以有 loop-carried dependence 也不必禁止。例如 a[i]=a[i-1]+b[i] 可以复制四次并保留串行链。只有进一步调度、打包或重关联才需要对应的独立性证明。

展开不等于并行化，也不保证增加有效 ILP。若各份循环体仍沿同一递推状态串行连接，复制后的计算仍受这条依赖链限制。

控制开销、调度窗口与常量暴露

  1. 摊薄控制开销。 U 次工作只执行一次外层控制更新与跳转。
  2. 扩大调度窗口。 让多个独立 load 和运算同时可见，处理器与编译器能重叠延迟。
  3. 暴露常量。 完全展开小常数循环，使 i 每次变成常数，分支、地址和 lookup 可折叠。
  4. 促进其他优化。 SLP、CSE、SROA、死代码消除能利用重复体的显式关系。
  5. 在合法时增加累加器。 拆短归约依赖链，但这不只是复制；必须满足归约重排的语义。

代价包括代码体积增长、指令缓存与解码压力、活跃值增多、spill、余数处理及编译时间。因此，收益可能随展开因子先增加后下降，不能假定 U 越大越好。

三种展开和一次 peeling

策略 条件 / 行为 典型适用点
full unroll 将有限次迭代显式列出，消除循环 小常量 trip count，常量传播收益明显
partial unroll 每轮复制 U 份，仍有循环 控制成本、吞吐改善
runtime unroll trip count 运行时才知道，构造分组和余数路径 能摊薄 setup 的长循环
peeling 剥离前几次或特定迭代，剩下循环保留 第一轮特殊行为、稳定后简化

peeling 与 unroll 都涉及克隆，但目的不同。剥离一轮后可能证明剩余 PHI 固定或分支条件稳定；展开则让一个新主体覆盖多次原迭代。

策略选择与 CFG 重建

入口和策略在 llvm-project/llvm/lib/Transforms/Scalar/LoopUnrollPass.cpp：

  • gatherUnrollingPreferences：收集默认、优化级别、TTI、大小政策与用户覆盖。
  • tryToUnrollLoop：整理分析、trip count、上界、倍数和 metadata，判断可选动作。
  • computeUnrollCount：选择因子和 full / partial / runtime 的相关策略。
  • 最后调用 UnrollLoop 实施。

真正的 CFG/SSA 重建在：

  • llvm-project/llvm/lib/Transforms/Utils/LoopUnroll.cpp：UnrollLoop。
  • llvm-project/llvm/lib/Transforms/Utils/LoopUnrollRuntime.cpp：运行时展开和余数处理。
  • llvm-project/llvm/lib/Transforms/Utils/LoopPeel.cpp：peeling。

展开策略与 CFG/SSA 重建承担不同职责。前者通过启发式选择复制份数，后者必须使每个克隆的值、退出边和回边保持精确语义。

展开因子的成本估计

LLVM 使用 IR/目标成本估计，不是源码行数。常量迭代数、最大迭代数、已知倍数有不同用途：

  • 精确 TripCount 小，可能全展开。
  • 只知道上界，仍可能需要保留每轮退出条件，不能无条件执行到上界。
  • 只知道迭代数是 k 的倍数，可以减少某些余数处理。
  • 完全未知时，runtime unroll 需要额外计算和 CFG，成本更高。

LoopUnrollPass.cpp 中还有完整展开收益分析：估计复制后的常量化、可删除指令等，允许某些收益特别明显的情况提高可接受阈值。并非所有候选都做无限精细模拟；分析预算也是限制。

本提交可见默认阈值和 O3 aggressive 阈值等选项，但这些值不是“机器码最多多少字节”，也不是统一性能定律。TTI 和优化体积模式会调整。这些参数的层次和覆盖关系决定候选的实际阈值，分析时需要结合 TTI 与管线配置。

克隆后的值映射与控制流修复

以原 header PHI 为例：

s_phi = phi(initial_s, s_next)
s_next = f(s_phi, a[i])

展开 U=2 后，第二份的输入必须是第一份的结果，不是再从 original PHI 读一遍；回边要连到最后一份。类似地：

  • 每个克隆指令的 operand 要映射到正确的一份。
  • 第 k 份的 induction value 对应原第 k 次迭代。
  • 中途退出要保持原来该退出点可观察的状态。
  • 外部使用要通过正确退出 PHI/LCSSA 获得结果。
  • LoopInfo、支配关系和 SCEV 必须更新或失效。
  • metadata 要避免错误地对新循环重复施加原 transformation request。

UnrollLoop 不仅克隆基本块，还需要完成值映射、回边连接、退出状态传递及分析维护。CloneBasicBlock 提供复制操作，后续接线和修复才使新 CFG 保持原语义。

unroll-and-jam 的跨层重组

原来：

for (int i = 0; i < m; ++i)
    for (int j = 0; j < n; ++j)
        y[i][j] = x[j] * scale[i];

外循环按 2 展开，再把两份内循环 jam：

for (int i = 0; i + 1 < m; i += 2)
    for (int j = 0; j < n; ++j) {
        y[i][j]     = x[j] * scale[i];
        y[i + 1][j] = x[j] * scale[i + 1];
    }
// 外层余数另行处理

这里两个外迭代共享 x[j] 的读取，可能减少访存并制造 SLP 机会。但执行顺序从“整个第 i 行，再整个第 i+1 行”变成按列交错，故依赖证明比保序展开更强。数组间别名也会影响合法性。

路径：llvm-project/llvm/lib/Transforms/Scalar/LoopUnrollAndJamPass.cpp、llvm-project/llvm/lib/Transforms/Utils/LoopUnrollAndJam.cpp。本版本管线注释专门要求把 unroll-and-jam 放在普通 unroll 前，避免普通展开先破坏想处理的嵌套形状。

循环展开与寄存器分配的连接

假设未展开时只需维持一个地址、一个加载值和一个中间乘积；展开四份后，为了重叠 load，调度可能同时维持四组临时值。

更多 ILP
   ↘
    更多同时活跃值 → 超过可用寄存器 → store/reload → 收益可能反转
   ↗
更大 VF / IC

展开并不必然增加寄存器压力：常量折叠与死值消除也可能减少工作，实际压力取决于最终调度下的活跃峰值。LLVM 中端与后端不是一次联合的全局最优化求解，评价展开收益需要继续检查最终机器码，而不只统计减少了多少循环控制指令。

循环结构优化

LICM 的外提、下沉与访问条件

for (int i = 0; i < n; ++i)
    a[i] = b[i] * (p + q);

若 p+q 的 operands 在循环外定义、运算可安全执行，它可以进 preheader。路径：llvm-project/llvm/lib/Transforms/Scalar/LICM.cpp。

“地址不变”与“load 结果不变”不同：循环每轮从 *p 加载，若循环中任何 store 可能改 *p，就不能把 load 外提。MemorySSA、别名分析和副作用信息帮助回答这个问题；相关表示在 llvm-project/llvm/lib/Analysis/MemorySSA.cpp。

还要考虑零次迭代：原来不进入循环就不执行 load；外提之后若无条件访问坏指针，会改变语义。需要能安全推测执行，或原位置必定执行等充分条件。LICM 也可 sinking，或在证明允许时做内存 promotion，不能把它缩减成“把纯表达式搬出去”。

外提也会影响后端资源：结果需要贯穿更长路径时，live range 可能延长。减少重复计算与增加寄存器占用需要共同评价。

LoopRotate 的入口检查与循环形状

简单 while 形状可教学性地变成入口 guard 加 do-while：

if (n > 0) {
    do {
        body();
        ++i;
    } while (i < n);
}

入口 guard 保持零次执行语义，主体与 latch 更适合若干分析和优化。路径：llvm-project/llvm/lib/Transforms/Scalar/LoopRotation.cpp。它可能复制 header，所以不是免费的结构整理；-Oz 等体积政策会影响 header duplication。

Unswitch 的循环选择与代码体积

for (int i = 0; i < n; ++i) {
    if (mode) a[i] = b[i] + 1;
    else      a[i] = b[i] * 2;
}

若 mode 不变且语义允许，可以变成 if(mode) 选两个各自无该分支的循环。这样后续 LV 可能看到更简单的 body。路径：llvm-project/llvm/lib/Transforms/Scalar/SimpleLoopUnswitch.cpp。

代价是克隆循环。多个不变条件可能造成组合爆炸，因此 non-trivial unswitch 有收益、大小和预算限制。名称里的 Simple 不等于永远只做一个局部替换。

LoopInterchange：用依赖约束换局部性

C 的二维连续数组通常行优先。以下按列访问：

for (int j = 0; j < cols; ++j)
    for (int i = 0; i < rows; ++i)
        a[i][j] += 1;

在依赖与访问语义允许时，交换 i、j 可以使内层按行连续访问，改善缓存行利用并提供连续向量访存的机会。实际收益还取决于数组布局、工作集和目标实现。

理论上，对依赖从迭代点 x 指向 y，变换后的执行时间戳必须仍让 x 在 y 前。方向向量记录各维是 <、=、> 或不确定；交换维后，需要满足合法的字典序方向条件。距离向量 (1,-1) 原来第一维先正向，交换成 (-1,1) 就可能把消费者排在生产者前。

路径：llvm-project/llvm/lib/Transforms/Scalar/LoopInterchange.cpp。开头定义 CharMatrix 方向矩阵，并有 cache、指令顺序、向量化机会等收益规则；依赖来自 llvm-project/llvm/lib/Analysis/DependenceAnalysis.cpp，cache 估计来自 llvm-project/llvm/lib/Analysis/LoopCacheAnalysis.cpp。

循环交换需要分别检查 重排合法性、IR 形状可变换性与收益。PHI、归约或不规则 loop nest 可能超出当前实现支持的范围；即使能够构造等价源码，也不意味着该 Pass 能改写相应 IR。

LoopDistribute 的依赖分区

for (int i = 1; i < n; ++i) {
    a[i] = a[i - 1] + b[i];
    c[i] = d[i] * e[i];
}

若相关数组不冲突，两组工作之间也无其他依赖，可分成：

for (int i = 1; i < n; ++i)
    a[i] = a[i - 1] + b[i];
for (int i = 1; i < n; ++i)
    c[i] = d[i] * e[i];

第一组串行，第二组可 SIMD。这相当于通过依赖图分区，把有环/递推的部分与独立部分分开。并不是拆掉所有依赖；必须保留分区之间所要求的顺序。

路径：llvm-project/llvm/lib/Transforms/Scalar/LoopDistribute.cpp。文件开头明确说主要目标是隔离依赖循环，使用 LoopAccessAnalysis，并特别照顾内存操作的 lexical order；还支持 runtime versioning。

分裂会增加循环控制，可能减少 producer-consumer cache reuse，并重复某些标量计算。对于共享中间数据的循环，SIMD 机会与局部性损失需要共同评价。

Fusion、Flatten、Idiom 与强度削弱

Fusion 合并相邻循环，减少遍历或使生产结果更快被消费。若 b[i] 在第一个循环产生、第二个循环使用，融合可能改善局部性；若第二个循环需要尚未产生的 b[i+1]，直接交错执行就会破坏依赖顺序。路径：llvm-project/llvm/lib/Transforms/Scalar/LoopFuse.cpp。它不是“看到两个同上界循环就合并”。

Flatten 尝试把合适嵌套变成单个计数循环。理论上可令 t=i*n+j，但边界乘法溢出、索引恢复成本和循环间副作用都是限制。路径：llvm-project/llvm/lib/Transforms/Scalar/LoopFlatten.cpp；本版本有独立、默认关闭的管线开关。

Idiom recognition 识别 memset/memcpy 或其他特定计算模式，把细粒度循环改成目标可进一步优化的操作。路径：llvm-project/llvm/lib/Transforms/Scalar/LoopIdiomRecognize.cpp。库语义、重叠和访问条件仍必须满足，不能把任何字节拷贝循环都换成 memcpy。

LoopStrengthReduce 将部分反复乘法式地址计算重写成目标合适的递增地址/偏移表达。路径：llvm-project/llvm/lib/Transforms/Scalar/LoopStrengthReduce.cpp。它可能增加诱导变量数量，因此也与寄存器压力有关。

Tiling 的迭代域分块

矩阵计算同时涉及三类局部性：数据在 cache 中复用、结果在寄存器中累积、线程处理相对独立的数据块。分块把大迭代域切成小块，块大小与 cache 和寄存器资源匹配。

普通 C 优化管线并不保证为任意矩阵乘自动寻找最优 blocking。更显式的高层结构通常在 MLIR affine/linalg 或 Polly 中处理。MLIR 分块路径之一：llvm-project/mlir/lib/Dialect/Affine/Transforms/LoopTiling.cpp；多面体路线见自动并行化与 OpenMP。

结构变换改变后续 Pass 的输入和可用机会。完全展开可能消除可交换的 loop nest，分裂可能改善向量化条件却损失融合带来的局部性。因此，管线需要在相互影响的候选之间选择，并限制分析和代码体积预算；依次运行所有变换并不能保证最优结果。

自动并行化与 OpenMP

默认优化管线与线程化的职责边界

普通 LLVM 循环向量化、SLP、展开的职责不是通用线程级自动并行化。默认 C/C++ 优化管线不会仅因为看到独立循环，就普遍插入一组 OpenMP fork/join。

线程化还要考虑：运行时依赖、线程数、粒度、同步、嵌套并行、可观察副作用和内存模型。原先按确定顺序发生的调用、异常、I/O、volatile 或同步操作，不能在没有语义依据时重新分发给多个线程。

即使每个迭代独立，T 个线程的教学时间模型也有“启动＋调度＋串行部分＋并行部分/T＋同步＋内存争用”。当单次循环很短，启动和同步成本可能抵消并行执行的收益。

SIMD 的收益门槛通常低于线程启动门槛；SIMD 合法性也不总是等价于任意线程调度合法性。 有限距离依赖可能支持受限 VF，却不支持把所有迭代任意分发。

Polly：用多面体统一表示迭代域和调度

对于规则嵌套：

for (int i = 0; i < m; ++i)
    for (int j = 0; j < n; ++j)
        a[i][j] = b[i][j] + 1;

多面体模型把：

  • 迭代域 表示成整数点集合，例如 0 <= i < m, 0 <= j < n。
  • 访问关系 表示成迭代点到数组位置的映射。
  • 依赖关系 表示成必须保序的迭代点对。
  • schedule 表示成迭代点到执行时间戳的映射。

传统 loop interchange 是交换时间戳维度；tiling 引入块坐标和块内坐标；fusion/distribution 调整不同语句的调度关系。合法性核心是每条依赖边在新 schedule 下仍指向未来。若某个调度维度没有携带依赖，就有并行化机会。

它不是只能表示 a*i+b*j 这种单一表达：实践有整数集、参数、分段关系和部分非仿射处理；但规则、可分析区域仍是强项。一般指针链、未知副作用或复杂非仿射结构会限制 SCoP 检测与优化。

源码阅读链：

  1. llvm-project/polly/lib/Analysis/ScopDetection.cpp：哪些区域可建模。
  2. llvm-project/polly/lib/Analysis/ScopInfo.cpp：域、访问与语句模型。
  3. llvm-project/polly/lib/Analysis/DependenceInfo.cpp：构建依赖。
  4. llvm-project/polly/lib/Transform/ScheduleOptimizer.cpp：修改调度。
  5. llvm-project/polly/lib/CodeGen/IslAst.cpp：AST 与并行标记。
  6. llvm-project/polly/lib/CodeGen/IslNodeBuilder.cpp：生成 IR，遇到并行节点转入并行循环生成。
  7. llvm-project/polly/lib/CodeGen/LoopGenerators.cpp：标量/并行 loop 框架。

Polly 是独立可选组件，不等于普通 LLVM -O3 默认为任意程序开启的线程化功能。

Polly 的并行检测与执行策略

本提交 IslAstInfo::isParallel 与 isExecutedInParallel 是两件事。后者在 IslAst.cpp:626 附近先检查 PollyParallel；除非 force，否则不把最内层循环线程化，注释理由是内层迭代常较少、不划算；还要求适用的外层并行标记，并排除这里的 reduction-parallel 情形。

这说明：

依赖分析的“可并行”是事实；代码生成的“实际线程化”是策略。

LoopGenerators.cpp 中可以看到线程数、调度策略、chunk size 设置和 ParallelLoopGenerator::createParallelLoop。继续追具体运行时后端，应读 llvm-project/polly/lib/CodeGen/LoopGeneratorsKMP.cpp 与 llvm-project/polly/lib/CodeGen/LoopGeneratorsGOMP.cpp。

某处 force 选项也不应被理解为通用地“无视依赖强行线程化”；这里描述的是策略门槛，是否合法仍是前置事实。

MLIR AffineParallelize：在更高层 IR 保留结构

llvm-project/mlir/lib/Dialect/Affine/Transforms/AffineParallelize.cpp 将候选分析与并行 IR 改写分开组织：

按 pre-order 访问 affine.for（先外层）
  → isLoopParallel：判断独立性，按选项识别 reductions
  → 收集候选
  → 计算父级 affine.parallel 数量
  → 不超过 maxNested 时 affineParallelize
  → 得到 affine.parallel

分析入口位于 llvm-project/mlir/lib/Dialect/Affine/Analysis/LoopAnalysis.cpp。仿射循环与访存信息尚未被低层指令淹没，适合直接进行域和依赖推理。

得到 affine.parallel 不等于操作系统线程已经启动。 它表达并行语义；后续要选择 lowering 到 SCF/OpenMP/其他执行模型并链接适当运行时。OpenMP 转换的一条相关路径是 llvm-project/mlir/lib/Conversion/SCFToOpenMP/SCFToOpenMP.cpp，但具体 pipeline 还需要先把对应 affine 结构降低到合适形式。

这是高层 IR 的价值：先决定“哪些工作可并行”，后决定“在哪种硬件和运行时执行”。

OpenMP：程序员提供语义，编译器负责实现

#pragma omp parallel for schedule(static)
for (int i = 0; i < n; ++i)
    y[i] = f(x[i]);

这里程序员承担符合 OpenMP 规则、无非法数据竞争的责任；编译器不需要重新证明整段普通 C 循环在任意线程下无竞争，但仍需检查 directive、canonical loop、数据环境等语言要求，并按规范生成实现。

典型 CPU 路线：

#pragma omp parallel for
  ↓ Clang Sema：检查规范、循环和 shared/private/reduction
  ↓ CodeGen：outline 出 worker（microtask）
  ↓ 生成 runtime fork 调用，传捕获的参数
  ↓ worker 从运行时得到线程负责的迭代范围
  ↓ 执行本线程 loop；按构造语义同步和归约

关键源码：

  • llvm-project/clang/lib/Sema/SemaOpenMP.cpp：前端语义。
  • llvm-project/clang/lib/CodeGen/CGStmtOpenMP.cpp：EmitOMPParallelDirective、EmitOMPParallelForDirective、EmitOMPWorksharingLoop、EmitOMPSimdDirective。
  • llvm-project/clang/lib/CodeGen/CGOpenMPRuntime.cpp：emitParallelCall、emitForStaticInit、emitForDispatchInit、emitReduction。
  • llvm-project/llvm/lib/Frontend/OpenMP/OMPIRBuilder.cpp：构造 OpenMP IR 的共享基础设施；不同构造和配置使用的路径不完全相同。

emitParallelCall 构造 __kmpc_fork_call(loc, n, microtask, ...) 调用，把 outlined 函数与捕获参数交给运行时。捕获数组指针不意味着复制整个数组；传递与私有化方式取决于数据环境。

runtime 真正做了哪些事

主要 CPU 运行时在 llvm-project/openmp/runtime/src/：

文件 阅读焦点
llvm-project/openmp/runtime/src/kmp_csupport.cpp __kmpc_fork_call 等编译器 ABI 入口
llvm-project/openmp/runtime/src/kmp_runtime.cpp team、线程生命周期、fork/join 框架
llvm-project/openmp/runtime/src/kmp_sched.cpp static 循环范围计算
llvm-project/openmp/runtime/src/kmp_dispatch.cpp dynamic/guided 等 work dispatch
llvm-project/openmp/runtime/src/kmp_barrier.cpp barrier 与相关同步
llvm-project/openmp/runtime/src/kmp_tasking.cpp task 执行与调度

运行时会管理线程团队并复用资源，因此一个 parallel region 不必每次从零创建全部 OS 线程。不过，唤醒、调度和同步仍有成本。

  • static： 预先划分迭代，调度开销低；工作均匀时合适。
  • dynamic： 工作线程不断领取 chunk，应对负载不均，但有更多调度/同步。
  • guided： 常用递减 chunk 在前期低开销和后期平衡之间取折中。

chunk 过小会增加调度和可能的 false sharing。两个线程写不同元素也可能写同一 cache line，导致一致性流量；“没有数据竞争”不等于“没有共享代价”。

omp parallel 建立并行 team，多个线程执行区域
omp for 把迭代分配给既有 team，不单独等价于创建 team
omp simd SIMD 语义与相关承诺，不创建 CPU team
omp parallel for 创建 team 并分配循环
omp parallel for simd 线程间分工，每个线程内再 SIMD
omp task 建立任务，调度不等于固定迭代静态分片
omp target offload 执行模型，还涉及设备与映射

simd 也不保证最终一定是一条宽 SIMD 指令：目标支持、构造语义和实现限制仍影响 codegen。相反，明确的并行语义可能给优化提供原本难以从普通源码推导的事实。

归约例子：

float sum = 0;
#pragma omp parallel for reduction(+:sum)
for (int i = 0; i < n; ++i)
    sum += x[i];

线程持有私有部分结果，结束时组合。相比把共享 sum 每轮 atomic，通常减少同步。浮点最终结果可随组合顺序和线程数变化；应用是否接受，需要用户设计，而不是默认把串行 bitwise 一致性当作保证。

线程化的语义条件与资源约束

线程化首先需要明确 private/shared 数据环境及别名关系，分析跨迭代 RAW、WAR、WAW 和归约。副作用、异常、I/O、同步以及原执行顺序决定哪些调度保持语义；独立的变量名并不能替代独立的存储对象证明。

合法性成立后，还要评价粒度和资源。每个线程的工作量需要足以摊薄启动与同步，false sharing 可能增加缓存一致性开销，访存带宽也可能限制扩展。外部线程池、嵌套 parallel、亲和性和 NUMA 则影响实际调度与数据位置。这些条件共同决定线程化是否适用，而非仅由循环语法决定。

寄存器分配基础

虚拟值与有限物理资源

LLVM IR 值的命名数量不受目标寄存器数量直接限制，目标机器的物理寄存器却有限，且具有不同用途与约束。指令选择后的 Machine IR 用虚拟寄存器表示值，寄存器分配器决定各段值如何驻留。

虚拟值与机器指令
   → 每个值什么时候必须存活
   → 哪些值不能共用某个物理资源
   → 指派 / 切分 / spill / rematerialize
   → 物理寄存器与栈槽

它不是给源代码变量逐个选一个固定寄存器。一个源码变量可以有多个 SSA 值；一个 live range 被切开后，不同段可以用不同寄存器甚至栈。反过来，多个不同时活跃的值可以共用同一物理寄存器。

活跃性与反向数据流

基本块层的经典反向数据流方程：

LiveOut(B) = 并集 { LiveIn(S) | S 是 B 的后继 }
LiveIn(B)  = Use(B) ∪ (LiveOut(B) − Def(B))

Use(B) 指在本块对应定义之前读取的值。循环 CFG 上通常需要迭代到固定点。往指令内部细化，可以得到每个程序点的活跃集合。

interference（冲突） 表示两个值在需要保存不同内容的重叠时间不能占用同一资源。COPY 关系、子指令位置和机器约束使实际冲突分析比粗略区间重叠更精细。

一个简化单块例子：

0: a = ...
1: b = ...
2: use a
3: c = ...
4: use b
5: use c

忽略子指令 slot，a 约活到 2，b 活到 4，c 从 3 活到 5；a 与 b 冲突，b 与 c 冲突，a 与 c 可复用。分配的目标不是让名字不同，而是让同时所需的信息不被覆盖。

LiveInterval 并不一定是一个连续区间

核心路径：

  • llvm-project/llvm/include/llvm/CodeGen/LiveInterval.h：LiveRange、Segment、VNInfo、subrange。
  • llvm-project/llvm/lib/CodeGen/LiveIntervals.cpp：构建与维护区间。
  • llvm-project/llvm/lib/CodeGen/SlotIndexes.cpp：机器指令的位置编号。

LLVM 的 live range 可有多个半开 segment，存在空洞；VNInfo 区分值的不同定义来源。subranges / lane masks 又可表达部分子寄存器的活跃性。

SlotIndex 不只是源码行号：一条机器指令内部需要区分 block boundary、early-clobber、普通 register slot、dead definition 等位置。这帮助处理“输入读取与输出写入”是否可共享物理资源。

如果把所有段粗暴包成一个从 first def 到 last use 的大区间，就会把实际空洞当作活跃，产生虚假的冲突；这也是现代实现比最简线性扫描更精细的原因之一。

真实机器比 K 种颜色复杂

寄存器类。 整数、浮点、向量或特殊指令各有合法候选集合；不是任意值可进任意寄存器。

别名与 register units。 x86 的 RAX/EAX/AX/AL 存在重叠，向量宽度也涉及资源关系。LLVM 将物理寄存器映射为共享 units，避免把重叠名字误当独立资源。某些写还带有目标特定零扩展等语义。

固定占用。 某些指令必须使用特定寄存器，inline asm 有约束，部分寄存器保留给栈指针等用途。

call regmask。 调用按约定破坏一组 caller-saved 寄存器。跨 call 活跃值不能仅凭“别的虚拟值没占它”就留在会被 call clobber 的寄存器中。

callee-saved。 使用它可能需要函数序言/尾声保存恢复，有第一次启用成本；但对跨调用热值可能比反复 spill 更好。

two-address 和 tied operands。 输入输出可能要求同一寄存器；early-clobber 输出可能在其他输入读取前就被覆盖。

这些约束解释了为何峰值活跃值数≤寄存器数，并不必然可分配：某些值共同只能选择很小的子集合。

LiveRegMatrix：不必先建立一个巨大冲突图

路径：llvm-project/llvm/lib/CodeGen/LiveRegMatrix.cpp、llvm-project/llvm/lib/CodeGen/LiveIntervalUnion.cpp。

Greedy/Basic 通过 LiveRegMatrix 查询“当前 LI 放到物理寄存器 p 是否冲突”。每个 unit 可维护已经分配区间的 union，然后按所需时间段查询交集。

checkInterference 区分：

  • IK_Free：可用。
  • IK_VirtReg：其他已分配虚拟区间挡路，可能驱逐/切分。
  • IK_RegUnit：固定物理占用等障碍。
  • IK_RegMask：调用 clobber 等障碍。

驱逐其他虚拟值不能消除 fixed 或 regmask 冲突。 不分清这几类，就会误以为总能“把别人赶走腾位置”。

四种处理办法：assignment、splitting、spilling、rematerialization

  1. assignment： 一整段当前区间分给某个物理寄存器。
  2. splitting： 切开区间，在边界插 COPY 或必要的内存转换，让热区与冷区、不同压力区域独立分配。
  3. spilling： 部分值驻留栈槽，定义后 store、使用前 reload；reload 后仍然需要一个短生命周期寄存器。
  4. rematerialization： 对可廉价且语义安全地重算的值，在使用附近再算，如某些常量生成；不一定非得先存再读。

“spill 一个虚拟寄存器”不是把所有用途都变成直接内存操作。指令可能允许折叠内存 operand，也可能必须新建 reload vreg。spiller 因而会产生新的分配任务，这些短范围需要重新进入分配流程。

路径：llvm-project/llvm/lib/CodeGen/SplitKit.cpp、llvm-project/llvm/lib/CodeGen/LiveRangeEdit.cpp、llvm-project/llvm/lib/CodeGen/InlineSpiller.cpp、llvm-project/llvm/lib/CodeGen/VirtRegMap.cpp。

经典线性扫描的排序与 active 集合

Poletto–Sarkar 风格最简算法：

按 interval.start 排序
active = 按结束位置排序的已分配区间
for current:
    释放所有 end <= current.start 的 active
    有空闲寄存器 → 分配
    没有 → 从 current 与 active 选择牺牲者
           常见简单启发式：结束最晚者

线性扫描利用位置单调推进的性质：已经结束的区间不再影响后续位置，active 集合据此维护当前占用，而无需预先建立完整冲突图。排序和集合操作仍有成本，因此名称不保证整个实现严格 O(n)，加入机器约束后也未必只需一轮处理。

最简形式损失来源：CFG 被线性化、区间空洞、冷热差异、固定寄存器、复制偏好、跨调用选择。现代 linear scan 可以加入 inactive、拆分和位置约束，不能把整个算法家族都说成只能一次粗暴 spill。

图着色与 PBQP：两种更全局的理解

图着色把值作为节点、冲突作为边、物理寄存器作为颜色。经典 simplify/spill/select 方案在难处做启发式决定；真实分配还要处理预着色、不同候选集合与复制合并。一般寄存器分配的困难不能靠“LLVM IR 是 SSA”完全消除，因为实际机器约束和后端 PHI/两地址处理已经改变问题。

PBQP（Partitioned Boolean Quadratic Programming） 的教学模型：每个节点 i 从候选寄存器或 spill 选一个 one-hot 方案；单点成本向量给出选择费用，成对成本矩阵给出相互选择费用。

总成本 = 所有节点所选项成本 + 所有相关边所选组合成本
冲突值选重叠物理寄存器 → 无穷大 / 不允许
复制相关值选择相同资源 → 可降低复制成本
spill 项 → 估计的内存代价

RegAllocPBQP.cpp 文件头明确说明：建问题、求解、映射回分配；若选择 spill，插入 spill code 后重复。实际求解器采用寄存器分配特化启发式，不是证明所有函数都求到全局最优。

继续读 llvm-project/llvm/include/llvm/CodeGen/PBQP/。原理文献在实现文件头给出：Scholz 与 Eckstein（2002），Hames 与 Scholz（2006）。图着色、PBQP 是理解问题的模型；它们不意味着 LLVM Greedy 默认先构造并求解一张完整着色图。

工作队列与分配结果的返回协议

seedLiveRegs：把需要分配的区间入队

    取出一个 LI，确认它尚未分配
    若已无有效使用，清理
    使受变更影响的冲突查询缓存失效

全局范围与局部范围的排序

  • RAGreedy::enqueue（本提交 420 行附近）调用 PriorityAdvisor。

全局与拆分范围通常按 long→short 排序。 长区间跨越较多位置，需要在更多程序点保持可用资源，较早处理能提前暴露切分需求，减少后续对短区间安排的扰动。这里的 size 度量 live segments，而不是动态执行次数。

LLVM Greedy 中含有局部线性顺序策略；Greedy 整体不是传统 linear scan。

既不能说它完全不利用扫描观察，也不能把整个 allocator 称为“按起点一次扫描”。

队列优先级与 spill weight

队列优先级决定尝试分配的顺序，spill weight 估计将范围保留在寄存器中的价值。两者服务于不同决策，并非同一个度量。

llvm-project/llvm/lib/CodeGen/CalcSpillWeights.cpp 的 VirtRegAuxInfo::weightCalcHelper 汇总读写使用的频率相关权重，处理 COPY hints、可 rematerialize 的值、某些看起来像 induction update 的情形，并做归一化。

概念上它估计“因 spill 导致的动态工作 / 这段区间占用的空间”。实际公式有保护常数、目标因子和特殊情形，不应将教学比例当成精确源码公式。

归一化用于比较单位资源的收益：两个值同样使用十次，若一个贯穿很长区间，另一个集中在十条指令内，后者占用资源的时间较短。频率权重则区分动态执行成本，冷路径的一次 load 与热循环中的大量 load 不应按相同代价处理。

没有采样或插桩 profile 时，块频率也可能是静态估计；allocator 不是在编译时知道真实每次运行。能安全重算的常量通常比只能从内存恢复的值更便宜；induction 更新 spill 则可能每轮昂贵。

第一步：tryAssign 与寄存器偏好

RAGreedy::tryAssign（532 行附近）用 AllocationOrder 遍历合法候选，并问 Matrix->checkInterference。

AllocationOrder 不是简单从 R0 到 R31：它结合寄存器类、目标顺序、保留寄存器和 hints。COPY 的源/目的若用同一物理寄存器，复制可能在 rewrite 后消失。

已经发现一个空闲寄存器时，也可能继续改善：

  • 若 preferred register 被可低代价驱逐的范围占用，可以为 hint 腾位置。
  • 若 hint 在冷块遇到冲突，可以尝试 around-hint splitting。
  • 若可用寄存器有额外 cost，可尝试腾出更便宜替代。

因此 tryAssign 不总是纯粹只读查询；它可能引入驱逐或切分。理解总流程时必须检查 NewVRegs，而不只检查返回值。

callee-saved 的第一次使用为何单独考虑

selectOrSplitImpl 找到空闲 CSR 后，某些情况下还调用 tryAssignCSRFirstTime。原因：首次启用一个 callee-saved register 可能让函数产生额外保存恢复；对只在冷块使用的值，局部 spill 可能更便宜。

但不能反过来说 CSR 总是贵：一个热循环或跨大量 calls 的值，避免反复 reload 的收益可能远超一次保存恢复。这里比较的是增量成本，受块频率与后续 frame lowering 影响，并不是“一律先用 caller-saved”的充分策略。

第二步：eviction 不等于 spilling

当前区间 A 想用 p，但 B 已占有 p：

若 B 是可移动的虚拟区间且驱逐代价可接受:
    Matrix.unassign(B)
    将 B 放回待处理集合
    将 A 分给 p

B 后续可能换寄存器、切分或最终 spill。立即 spill 所有阻碍者的是更粗策略；Greedy 先保留修正机会。

RAGreedy::tryEvict 与 evictInterference 在 RegAllocGreedy.cpp；默认判断在 llvm-project/llvm/lib/CodeGen/RegAllocEvictionAdvisor.cpp 的 DefaultEvictionAdvisor::shouldEvict 和相关成本检查。

需要考虑的不是一个 B：p 的不同 units 和不同时间段可能被多个范围占据。成本会考察多个阻碍者、被破坏 hints、权重和 urgency。某些不可 spill 的短范围或严格受限类，需要更紧急地得到寄存器。

这里的 ML advisor 文件（llvm-project/llvm/lib/CodeGen/MLRegAllocEvictAdvisor.cpp、llvm-project/llvm/lib/CodeGen/MLRegAllocPriorityAdvisor.cpp）允许用训练策略替代部分启发式，受构建和配置控制。它们不是一套完全独立 RA，也不能据目录存在就说默认启用了机器学习。

驱逐链与分配阶段的进展约束

如果 A 驱逐 B，B 再驱逐 A，两者即可循环。Greedy 用两类结构限制这种行为：

  1. cascade 编号： 记录驱逐链，在策略判断中阻止形成无休止循环；urgent 等特殊情形有自己的规则。
  2. stage： 区间逐渐从原始分配阶段进入等待切分、切分与 spill 等阶段，不能无限重复同一探索。

状态定义可追 llvm-project/llvm/include/llvm/CodeGen/RegAllocEvictionAdvisor.h；附加信息维护在 llvm-project/llvm/lib/CodeGen/RegAllocGreedy.h 的 ExtraRegInfo。

不能把它夸大为“单个启发式函数保证最优”。它们保证算法在工程预算内取得进展，并避免策略反复制造同类工作；代码质量仍是启发式结果。

第三步：第一次放不下，为什么不马上切分

读 selectOrSplitImpl（本提交 2658 行起）：

tryAssign
  → 若适用，考虑首次 CSR 成本
  → tryEvict（stage 条件允许时）
  → 首轮仍放不下：标记 RS_Split，延后重新入队
  → 下一阶段 trySplit
  → 对已到末段/不可 spill 的困难范围尝试 last-chance recoloring
  → 正常可 spill 的范围，最后交 spiller

首轮延后为切分收集更完整的压力信息。长区间先处理时，较小区间可能尚未占用资源；立即切分只能依据当前部分安排。让其他区间先进入分配结果，再决定切分边界，可以利用更多实际冲突信息。

源码注释说明，第一轮延后 split/spill，使第二轮能够利用更完整的 interference 信息。局部策略、阶段和新范围的细节影响实际顺序，上图是主骨架而非逐分支替代源码。

last-chance recoloring 也不是每次普通失败都立刻执行的万能一步。 本版本在这里有 stage/unspillable 条件；它用于有限回溯式挪动一组颜色，仍有深度和搜索范围限制。

切分的热区驻留与边界转换

假设值 v 在入口定义，热循环多次读取，之后冷错误路径也读取：

entry → hot loop → exit
          |
       cold error

一个贯穿全图的 LI 若找不到始终空闲的寄存器，不应立即把热循环每次 use 都变成 reload。可形成：

入口 / 冷区：栈或其他片段
热循环区域：v_hot 长驻一个寄存器
区域边界：load / store / COPY

边界代价执行一次或很少次，换来热区避免大量访存。这是 Greedy 的核心观察：资源紧缺具有时间与路径局部性，整段 spill 过于粗糙。

trySplit 会按具体情形尝试 local splitting、region/global splitting、其他适用方案；相关函数如 tryLocalSplit、tryRegionSplit 可在 RegAllocGreedy.cpp 检索。具体编辑由 SplitKit 的 SplitAnalysis / SplitEditor 等完成。

  • 局部切分沿使用点和冲突空隙寻找适合的片段。
  • 区域切分尝试围绕特定物理寄存器保留一个可获益区域，其余部分成为别的范围。
  • 新范围重新计算权重、约束并进入工作队列。

切分会制造 COPY 与边界转换；若收益不能超过它们，切分并不划算。不能把“切得越碎越好”当成策略。

SpillPlacement 的驻留成本模型

llvm-project/llvm/lib/CodeGen/SpillPlacement.cpp 的文件头说明了基于 Hopfield 网络的组合优化模型：

  • CFG 的 edge bundle 对应一个节点。
  • 节点状态表示该边束上更偏向 register 还是 stack；实现还保留 undecided 状态。
  • 必须/偏好寄存器或栈的块给节点 bias，按块频率加权。
  • transparent blocks 对两端状态施加连接：两端驻留状态不同，可能需要转换。
  • 通过迭代更新，降低表示 spill 执行频率的能量函数。

这里的 Hopfield 网络是确定性组合优化模型，而非训练得到的预测器。其能量作为 Lyapunov 函数，在更新时不增加，并收敛到局部最小；文件标题虽然包含 Optimal，注释仍明确限制为可能的局部最小，不能据此宣称全局最优。

数学上可理解为两类代价的折中：某块不用寄存器会多执行多少 reload，邻接驻留状态改变会多执行多少转换。热边上频繁切换代价大，因而倾向在一整个热区域保持同一种状态。

llvm-project/llvm/lib/CodeGen/EdgeBundles.cpp 与 llvm-project/llvm/lib/CodeGen/SplitKit.cpp 说明了边界约束如何参与选择：bundle 将需要一致处理的边界组织成节点，因此不能对 CFG 每条边独立决定驻留状态。

Spill 与 rematerialization 的最终落地

InlineSpiller.cpp 不只负责插 store 和 load：它还可能折叠 memory operand、消除冗余、追踪可重算定义、合并某些片段，并维护 LiveIntervals 与调试位置。

一个常量 materialization 值若被 spill，某次 use 附近重新生成常量可能比 stack load 便宜。若它依赖其他已经不活跃的输入或不安全操作，则不能任意重算。

reload 形成的片段往往已经很短，无法通过反复 spill 无限制缩小；某些范围成为 unspillable，需要结合严格约束与有限 recoloring 处理。不相容的 inline asm 约束仍可能使分配无解，LLVM 会报告错误，Greedy 并不保证任意约束都可满足。

最终 VirtRegRewriter 根据映射改写 operand，后续栈帧/序言尾声处理把栈槽和保存恢复变成真实目标指令。分配器作出的栈槽选择，不等于那一刻已经确定了最终栈偏移。

驱逐与重新分配的简化示例

教学简化： 只有 R0/R1，无别名和固定限制。

L: 很长，全局值，只在入口、出口与冷块少量使用
H: 热循环里高频使用，中等长度
S: 某个局部短值

可能过程：

  1. 长范围 L 先被安排到 R0；别的范围占 R1。
  2. H 入队，空闲检查失败；H spill weight 高。
  3. 若符合驱逐策略，H 驱逐 L，得到 R0；L 重新入队。
  4. L 不一定马上 spill：可能 R1 某区域空闲，或被切成冷区/出口短片段。
  5. 热循环维持 H 在寄存器；只在冷区或边界为 L 做转换。

传统最简 linear scan 不采用同样的全局重新分配过程：它按 start 单调走、依据当前 active 集合处理。增强型 linear scan 也可以通过 splitting 改善，但 Greedy 的工作顺序和可修正分配从一开始就是主结构。

这不是声称 LLVM 对该抽象例子一定走这个路径；真实 cascade、hints、stage、成本和物理约束可改变决定。例子用来解释 “先分配≠永远保住寄存器”。

观察 实现对应 解决的问题

优化诊断与对照实验

三类循环的变换条件

以下三个函数分别包含独立元素计算、循环携带递推和浮点归约，可以用于比较不同依赖对优化的影响。实验需使用同一套构建或安装的 Clang、opt、llc 及相应 OpenMP runtime；复现固定提交的实现时，工具版本也应匹配。示例和命令是验证方案，并非本书已测得的编译结果。实验输出保存到独立的临时目录，与源码检出目录分开。

// demo.c
void axpy(float *restrict y, const float *restrict x,
          float a, int n) {
    for (int i = 0; i < n; ++i)
        y[i] = a * x[i] + y[i];
}

void recurrence(float *a, const float *b, int n) {
    for (int i = 1; i < n; ++i)
        a[i] = a[i - 1] + b[i];
}

float sum(const float *a, int n) {
    float s = 0;
    for (int i = 0; i < n; ++i)
        s += a[i];
    return s;
}

axpy 的元素计算彼此独立，recurrence 包含距离 1 的跨迭代递推，sum 则形成浮点归约。它们的优化条件不同：递推约束数据的执行顺序，浮点有序归约还受目标能力与变换策略影响，未生成向量代码并不对应同一种原因。

源码阅读中的表示与证据

沿编译流程追踪同一个函数，可以对照 AST、内存形式 IR、SSA 和循环 CFG 的变化。SSA 与基础优化中的 alloca 提升、PHI 插入、常量传播和死代码删除，解释了循环状态为何更适合后续分析；内联与尾递归消除则会进一步改变 CFG。

分析循环变换时，应先确定依赖和语言语义，再进入成本选择。保序展开可以保留跨迭代依赖，但这不等于同一循环能直接 SIMD 化或分配到多个线程。restrict 提供部分别名证据，递推、调用、浮点语义和循环形状仍可能限制向量化。沿 processLoop、legality、VPlan 到生成阶段追踪，能把这些条件对应到运行时检查、快路径、fallback 与尾部处理。

结构变换和并行生成涉及另一组证据：interchange 需要分析依赖方向；OpenMP pragma 经前端降级后具有运行时调用和并行语义；OpenMPOpt 主要优化这种已有语义。Polly 与 MLIR 的特定路线则在不同表示层次进行并行检测和生成，不能与普通循环管线混为一体。

寄存器分配需要继续追踪变换后的活跃范围。Greedy 的 enqueue/getPriority、selectOrSplitImpl、eviction advisor、SplitKit 和 SpillPlacement 分别参与排序、候选选择、驱逐和切分。队列优先级并不等同于 spill weight；stage、global/local 属性、size、hints 和寄存器类优先级共同影响顺序。其工作队列支持重新入队与区域切分，不按活跃区间起点单调推进；线性顺序策略只用于部分局部范围。

从生成结构解释实际性能

运行时 guard、尾部处理和线程启动具有固定成本，短循环可能难以摊薄，较长循环又可能改变工作集的缓存行为。比较输入规模时，需要同时观察路径选择和缓存条件，才能解释加速曲线的变化。

生成向量循环也不直接保证吞吐提升。目标降低后的指令、shuffle、mask、spill、访存带宽和输入规模都可能主导执行时间。类似地，SpillPlacement 的能量不增与收敛性质不意味着证明了全局最优；局部选择的效果仍需放回完整分配和生成代码中评价。

  → 决定真实吞吐、带宽、同步和延迟

这条链表明，中端证明、目标成本和后端资源分配共同约束优化结果。并行性只是可利用的机会之一；安排计算顺序、减少数据访问和控制活跃峰值同样影响最终执行成本。

关键实现的控制流分析

本章通过短实现片段分析合法性检查、并行候选收集和寄存器分配队列。摘录均来自固定提交，省略周边逻辑，不是可独立编译的完整函数；分析重点是输入事实、返回协议和状态更新如何连接后续执行。

向量化：hints 不能跳过合法性

位置：llvm-project/llvm/lib/Transforms/Vectorize/LoopVectorize.cpp，LoopVectorizePass::processLoop。

LoopVectorizationRequirements Requirements;
LoopVectorizationLegality LVL(L, PSE, DT, TTI, TLI, F, *LAIs, LI, ORE,
                              &Requirements, &Hints, DB, AC,
                              /*AllowRuntimeSCEVChecks=*/!OptForSize, AA);
if (!LVL.canVectorize(EnableVPlanNativePath)) {
  LLVM_DEBUG(dbgs() << "LV: Not vectorizing: Cannot prove legality.\n");
  Hints.emitRemarkWithHints();
  return false;
}

构造参数与检查结果的含义如下：

  • L 是当前循环；PSE 是带谓词的标量演化；DT/LI 给控制流结构；LAIs/AA 给内存访问与别名。
  • TTI/TLI 使合法性也能考虑目标和库调用支持，不是纯数学数组模型。
  • Requirements 记录所需语义条件；强制向量化提示不会自动满足这些条件。
  • size 模式影响是否允许 runtime SCEV checks，因为 guard/版本化有代码体积成本。
  • canVectorize 返回 false 后不进入后面的成本选择。收益高不能补救没有合法性证明。

这段控制流把合法性检查置于成本选择之前。pragma vectorize(enable) 影响策略，不能替代依赖证明或改变语言与 IR 语义；OpenMP simd 提供的语义承诺则属于另一层输入事实。

自动并行化：分析与降低是两步

位置：llvm-project/mlir/lib/Dialect/Affine/Transforms/AffineParallelize.cpp，AffineParallelize::runOnOperation。

std::vector<ParallelizationCandidate> parallelizableLoops;
f.walk<WalkOrder::PreOrder>([&](AffineForOp loop) {
  SmallVector<LoopReduction> reductions;
  if (isLoopParallel(loop, parallelReductions ? &reductions : nullptr))
    parallelizableLoops.emplace_back(loop, std::move(reductions));
});

PreOrder 先访问外层循环，后续处理据此控制已有父并行区域数量。parallelReductions 决定是否请求归约识别，并不把任意递推都视为 reduction。候选收集之后，仍需检查 maxNested，再调用 affineParallelize。

该步骤收集候选并生成 parallel IR，后续 lowering 再选择运行时或目标。检测、IR 变换和运行时执行是不同阶段；这里的分析调用本身并不创建线程。

Greedy 的局部顺序与全局优先级

位置：llvm-project/llvm/lib/CodeGen/RegAllocGreedy.cpp，DefaultPriorityAdvisor::getPriority。

if (Stage == RS_Assign && !ForceGlobal && !LI.empty() &&
    LIS->intervalIsInOneMBB(LI)) {
  // ...
  if (!ReverseLocalAssignment)
    Prio = LI.beginIndex().getApproxInstrDistance(Indexes->getLastIndex());
  else {
    // ...
    Prio = Indexes->getZeroIndex().getApproxInstrDistance(LI.endIndex());
  }
} else {
  // ...
  Prio = Size;
  GlobalBit = 1;
}

省略的注释在完整文件中解释：原始 local range 按线性指令顺序安排；global 和 split range 按长到短。

Greedy 按区间结构采用不同排序策略。优先队列先取高优先级，因此默认 local 路径通过起点到函数末端的距离，使较早起点先被处理；global 路径则使用 Size。stage、hint 和寄存器类等信息还会编码到更高位。

这一优先级策略受分支条件限制：只有部分局部区间进入线性顺序路径，全局区间及切分范围另行处理。队列优先级仍不同于 spill weight。

延后切分与第二轮分配

位置：同文件，RAGreedy::selectOrSplitImpl。

if (Stage < RS_Split) {
  ExtraInfo->setStage(VirtReg, RS_Split);
  LLVM_DEBUG(dbgs() << "wait for second round\n");
  NewVRegs.push_back(VirtReg.reg());
  return MCRegister();
}

把原来的 vreg 放进 NewVRegs 并不表示它已经被切成新值；在此处是告诉基类再安排一次。空 MCRegister 也不意味着立即报错。

进入此段之前已尝试 assign/evict，后续才进一步 split/spill。将原范围重新入队，使切分决策能利用其他范围占位后形成的压力信息。selectOrSplit 因此还具有延后处理的返回路径，函数名不能完整表达其状态协议。

新活跃范围的入队与后续处理

位置：llvm-project/llvm/lib/CodeGen/RegAllocBase.cpp，allocatePhysRegs。

VirtRegVec SplitVRegs;
MCRegister AvailablePhysReg = selectOrSplit(*VirtReg, SplitVRegs);

后续在处理特殊失败返回后，若有可用物理寄存器会 Matrix->assign；然后遍历 SplitVRegs，剔除不再使用者，并将有效区间入队：

LLVM_DEBUG(dbgs() << "queuing new interval: " << *SplitVirtReg << "\n");
assert(SplitVirtReg->reg().isVirtual() &&
       "expect split value in virtual register");
enqueue(SplitVirtReg);
++NumNewQueued;

切分、驱逐和溢出产生的有效范围由同一工作队列继续处理，因此分配过程并不在原始 N 个 vreg 处理完后结束。Stage、cascade 和预算约束后续尝试，限制反复驱逐、切分和重新入队的过程。
