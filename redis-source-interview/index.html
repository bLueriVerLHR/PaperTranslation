1. Redis 为什么快：从一条 GET 的路径讲起

面试先答：内存、结构、执行模型共同决定性能

Redis 通常避免每条读请求都访问磁盘；它按数据规模选编码，减少分配和指针追踪；网络使用事件循环与批处理，而普通核心命令对共享键空间的执行主要集中在主线程。“因为单线程所以快”不是完整解释：单线程减少协调成本，但大命令同样会占据这条串行执行通道。

从 socket 到 value

下面是对主要逻辑关系的概括，不是说每个配置下每次调用都严格经过同一条栈：

连接产生可读事件
  → networking.c: readQueryFromClient
  → 输入缓冲区、RESP 解析、待执行命令
  → processCommandAndResetClient
  → server.c: processCommand（命令/权限/状态等检查）
  → server.c: call（调用、计时、统计、传播等执行管理）
  → t_string.c: getCommand → getGenericCommand
  → db.c: lookupKeyReadOrReply → lookupKey
  → 键查找、过期判定、必要的访问统计
  → 类型检查、回复缓冲区 → socket 写出

GET 不只是哈希查找。它还可能检查过期、更新访问统计、构造回复；返回一个很大的字符串时，即使定位 value 的算法复杂度很低，传输和复制成本仍与返回字节数有关。应用端等待时间还包含网络、连接池排队、Redis 排队和客户端处理，不能全部归因于命令执行。

单线程到底指什么

事件驱动不是给每个连接创建一个执行线程。ae.c 调度文件事件与时间事件；Linux 后端在 ae_epoll.c 中使用 epoll 等待就绪事件。epoll 降低了大量连接的等待管理成本，并没有把一条复杂命令自动拆成并行计算。

当前 iothread.c 的 I/O 线程有自己的事件循环，并与主线程交换待处理客户端。源码明确说明：I/O 线程读取后排入的完整命令，由主线程执行。当前配置说明中，线程可以处理读、写和协议解析。因此更准确的回答是：

普通核心命令对键空间的执行主要串行化；网络处理、异步释放、部分后台 I/O 等可以并发。开启 I/O 线程不是让多个线程随意并发修改同一个字典。

模块及其线程安全 API 是另一套扩展边界，不能据普通命令模型推断所有模块都相同。

为什么 pipeline 有用，但不是事务

若逐条发送命令并等待，每条命令都支付一次往返等待。pipeline 将多条命令提前送出，摊薄 RTT、读写调用和协议处理的固定成本。收益随 RTT、并发与命令成本变化，不应承诺某个固定倍数。

但 pipeline 不保证一组操作不可被其他客户端穿插，也不提供回滚。它还会增加在途请求和输出缓冲占用。超大批次或慢消费者可能把吞吐优化变成内存与尾延迟问题，应按命令数、字节数和时限设置批次边界。

当前源码的进一步优化：预取不等于并行执行

memory_prefetch.c 使用状态机依次预取 bucket、entry、key payload、value payload；多个查找轮流前进，使一个查找等待内存时可以与另一个查找的工作重叠。networking.c 先解析一定数量的待执行命令，满足条件时在主线程做预取；memory_prefetch.h 还提供单命令内部的 dictPrefetchKeys。

它利用的是内存级并行，不是把命令提前提交或改变命令语义。预取是提示，不能代替正式查找；跨越可能修改数据的命令后，还必须按真实当前状态执行。批次太小、数据已在缓存或预取过多时，也可能没有收益。

追问：一个大命令会影响其他连接吗

会。大范围查询、大集合遍历、长脚本、编码转换和同步释放都可能占据主线程。I/O 线程能缓解网络侧瓶颈，却不能消除串行执行中的长工作。排查时应区别：CPU 热点、内存访问等待、网络吞吐、持久化 I/O 与队列等待。

2. 对象、SDS 与内存布局：为什么同一种类型有不同编码

类型是语义，编码是实现

String、List、Hash、Set、ZSet、Stream 是对用户暴露的逻辑类型；INT、RAW、EMBSTR、LISTPACK、HT、QUICKLIST、SKIPLIST 等是内部编码。相同命令语义可以由不同布局实现。TYPE 与 OBJECT ENCODING 回答的是两层不同问题。

redisObject 中的 type 与 encoding 都是位域，此外有引用计数、指针，以及对 kvobj 有意义的元数据位与 LRU/LFU 信息。不要把“对象头固定只有这几个字段”当跨版本事实：当前对象设计包含把键和值组织在同一对象附近的扩展。

SDS 为什么比 C 字符串更适合数据库

SDS 的外部指针指向数据，而长度、分配容量与类型标记保存在前面的头部。不同长度范围使用不同宽度的头部，较小字符串不必支付 64 位长度字段的全部开销。

设计 直接收益 不应忽略的边界
显式长度 sdslen 不需要扫描到 NUL；可容纳二进制数据 按 C 字符串处理二进制内容仍会截断，调用者必须传长度
alloc 与可用空间 append 可先判断是否需要扩容 分配器实际可用容量与请求容量不完全相同
尾部保留 NUL 兼容部分 C 字符串接口 NUL 不替代逻辑长度
多种头部宽度 小对象减少元数据字节 TYPE_5 特殊：长度嵌在 flags 中，没有一般形式的 spare capacity

_sdsMakeRoomFor 的 greedy 路径，在所需容量小于 SDS_MAX_PREALLOC 时按所需容量加倍，否则增加固定预留；non-greedy 路径不做这类主动预留。不能泛化成“任何 Redis 字符串增长都永远翻倍”。空闲空间减少频繁 realloc 的机会，但会增加保留内存；重分配后原指针可能失效。

INT、EMBSTR、RAW 的设计取舍

  • INT：可被严格解释为整数的字符串可避免保存独立字符缓冲区。不是见到数字字符就一定编码；范围、字符串格式、引用状态等都影响路径。"001" 与 "1" 的字节语义不能被随意合并。
  • EMBSTR：对象头与短 SDS 在一次分配中布局，减少分配次数、元数据开销和缓存缺失。当前 createStringObject 的界限是 44 字节，源码解释其与 jemalloc 64 字节分配级别的关系。它不是 Redis 协议规定，也不能套到所有新型键值对象布局。
  • RAW：对象与 SDS 分开，便于 value 缓冲区独立扩容；少了 EMBSTR 的合并布局收益。

“EMBSTR 不可修改”应解释为实现通常会先转换到可修改的 RAW 表示，而不是说这个 key 在命令语义上不可写。

当前 kvobj：把内存布局优化做到 key/value 层

object.h 描述 kvobj 的 iskvobj 标记：可以在对象附近嵌入 key，短 String value 也可内嵌；过期等元数据按 bitmap 对应的类别布局在对象前方。

可选元数据 | redisObject | kvbits | key 的 SDS | 可选短 value 的 SDS

这是减少散碎分配和指针间接访问的优化，不表示所有对象都内联、所有 value 都短，也不表示原始 robj 与 kvobj 可以在任何场景中不加区分地操作。布局变动还可能带来重分配，源码中的调用者必须处理返回的新地址。

向外拓展：小对象经常是元数据主导

数百万个很小的 key/value，内存可能主要花在对象头、索引桶、分配器级别、指针和 TTL 元数据上，而不是业务 payload。优化思路有两种：一是减少分配与冗余元数据，二是用紧凑结构把多个业务字段聚合。但聚合成一个巨大 Hash 会把读取、删除、迁移和热点集中到同一 key，不能只看节省的字节。

不要只用字符串长度估算内存，也不要把 used_memory、分配器占用与进程 RSS 当同一个数。实际布局、碎片、fork/COW、客户端缓冲和持久化缓冲都可能影响观测。

3. 哈希表、渐进式 rehash 与 SCAN

面试先答：平均 O(1) 不代表每次访问都有恒定延迟

dict 使用哈希定位 bucket，并处理冲突链。平均查找效率依赖哈希分布、负载和 key 比较成本；哈希本身要处理 key 的字节，长冲突链和长字符串比较也会增加成本。这里的 O(1) 通常针对集合元素数的平均情况，不是忽略一切字节成本的绝对承诺。

当前 dict 有两组 ht_table、ht_used、ht_size_exp，以及 rehashidx。容量是 2 的幂，定位使用 hash 与 mask 的按位与。rehashidx == -1 表示没有进行迁移。

为什么不能一次搬完整张表

若同步将上百万个元素一次迁完，主线程会出现长停顿。渐进式 rehash 保留旧、新两张表，将迁移拆到多个正常操作和周期性维护中，避免把全部工作压在一次扩容请求上。

迁移期间必须维持的关键不变量是：未搬的项仍在旧表，已搬的项在新表；查找和更新不能只假设单表；新增项按迁移状态使用新表。迁完后替换并释放旧表。源码中的查找还可以跳过已经迁移的旧 bucket。

“渐进式”并不等于“严格无停顿”

dictRehash(d, n) 限制迁移的 bucket 数，并对空 bucket 探测设置 n * 10 的访问上限，避免稀疏表无限扫描。一个非空 bucket 内的整条冲突链仍要处理，所以 bucket 预算不是严格的元素预算。新 bucket 数组的分配与初始化也有成本。

当前 _dictRehashStepIfNeeded 会优先迁移本次访问命中的旧 bucket，以利用缓存局部性；否则沿 rehashidx 继续。这说明优化不只有“大 O”，还有让已经载入 CPU cache 的数据发挥作用。

扩容条件也不是一句“负载因子大于 1”能涵盖：后台子进程存在时有避免 resize 的模式，但达到强制阈值仍可能调整。目的是平衡查找退化、内存占用与 COW。

kvstore 为什么包了一层 dict

当前 redisDb.keys 和 expires 为 kvstore。其头文件说明，这是按 index 组织的 dict 数组；Cluster 模式中，可将属于同一 slot 的 key 放在对应 dict，便于访问和维护槽内数据。

数据库外层索引与 Hash 类型 value 内部的哈希表不是一回事。一个 Redis Hash key 先在数据库索引中被找到，其字段再由 Hash 自己的编码处理。

SCAN 的游标为什么不是 offset

dictScan 使用位反转游标，使扫描可以应对 2 的幂表容量变化；rehash 时先扫描小表，再扫描大表中对应的扩展 bucket。它不保存全量扫描快照，也不把游标解释成第几个 key。

完整迭代的经典保证应附上条件：在整个迭代期间持续存在的元素会被返回；重复可能发生；迭代中新增、删除或短暂存在的元素没有快照式的确定结果。 COUNT 是工作量提示，不是每批精确结果数量，冲突链与编码等都可能影响结果规模。

与 KEYS 一次遍历相比，SCAN 能分批让出执行机会，但一次过大的 COUNT、很重的回调或紧接着对结果执行昂贵操作仍会带来延迟。不要把“使用 SCAN”当生产安全性的充分条件。

可用于面试的设计推导

如果为每个扫描维护强一致快照，需要额外内存或版本维护；如果扫描时冻结 rehash/写入，又会影响前台操作。Redis 选择轻量、无跨调用迭代状态的游标，并把去重和业务一致性要求交给调用者。需要精确盘点时，业务可能应使用专门索引、快照或离线统计，而不是要求在线 SCAN 自动提供事务快照。

4. listpack、quicklist、intset：为何线性扫描有时更划算

先理解“少量元素”的成本模型

小集合中，指针、独立分配和 cache miss 的成本，可能超过在一段连续内存里扫描几十个元素的成本。Redis 因此为小 Hash、Set、ZSet 和 List 提供紧凑表示，再在规模或元素长度超过限制时转换。

这不是 O(N) 击败 O(1) 的普遍定律，而是在受控的小 N下用更低常数和更小内存换取线性操作。阈值提升后，原本有界的小扫描与 memmove 可能变成延迟问题。

listpack 为什么不是“换名字的 ziplist”

listpack 将编码后的整数或字符串条目连续保存，并给条目附上表示自身编码长度的 backlen，以支持反向遍历。经典 ziplist 的前一条目长度字段存在级联更新问题；listpack 不靠记录前一条目的长度来反向定位，避免该类连锁长度修正。

但是 listpack 仍是连续内存。中间插入、删除、增长可能触发 realloc 与 memmove，已有元素指针可能失效。lpInsert 返回新的 listpack 地址；批量插入路径可以合并 realloc/memmove，而不是反复逐个搬移。

List：小 listpack 到分段 quicklist

当前 t_list.c 会在增长预计超过限制时，把 listpack 转成 quicklist。quicklist 是双向节点组织，每个 packed node 里放一个 listpack，另有适合大元素的节点表示。它在“一个巨大连续块”与“每个元素一个链表节点”之间折中。

  • 两端操作可利用两端节点，但节点内搬移、节点创建与压缩状态仍有成本。
  • 随机索引要定位节点并在节点内部定位元素；不是普通数组式的 O(1) 随机访问。
  • 节点填充更大，通常减少指针与分配开销，但节点内修改的最大搬移量可能更大。
  • 压缩中间节点可以节省内存，代价是压缩/解压 CPU；两端保留未压缩区域便于常用操作。

源码还支持 quicklist 缩回 listpack：要求只剩一个 packed node；因缩小触发时使用更严格、约半阈值的边界，防止反复插删导致编码来回抖动。滞回也是缓存淘汰、自动扩缩容和稀疏/稠密表示切换中常用的设计技巧。

Set：有序整数数组也不是哈希表

intset 在连续存储中保存有序、不重复的整数。查找可二分；插入通常需要移动后面的元素。因此查找的对数复杂度，不能直接当成插入的复杂度。

增加无法用当前宽度表示的整数时，需要将整组元素升级到更宽的整数编码。升级是 O(N) 工作，不能把 SADD 的所有 intset 路径视为平均常量操作。加入非整数时，当前 Set 路径可以按条件转为 listpack 或哈希表；不能背成“非整数必定立刻转 HT”。

Hash：字段和值的紧凑表示

普通小 Hash 可以用 listpack 保存字段和值；查找字段时扫描，而不是得到 Hash 这个名字就认定内部是哈希表。大 Hash 转 HT 后，仍有字段字符串、value、entry 等分配开销。字段级 TTL 还需要扩展元数据及过期索引，不等于只给外层 key 设置 EXPIRE。

5. ZSet 为什么同时需要 dict 和跳表

先从查询需求推导结构

排行榜至少有两种不同的访问：按 member 查它的 score，以及按 score/排名找一段有序 member。只用哈希表，第二类查询要额外排序；只用有序结构，按 member 定位通常没有哈希查找的平均效率。

大 ZSet 的 zset 同时持有 dict 与 zskiplist：两种索引服务两种查询，插入、更新和删除必须保持一致。小 ZSet 可能仍是 listpack，不能把所有 ZSet 都画成这张双索引图。

跳表的层与 span

跳表底层维护顺序，上层用稀疏的前向链接跳过一段元素。随机层高避免维护复杂平衡旋转，平均查找和插入为 O(log N)；最坏退化不能完全排除。排序依 score，score 相同还要按 member 字节比较决定顺序，重复分数合法，重复 member 不合法。

span 记录跨越元素数，支持边走边累加名次，因此排名查询不是先线性数一遍。当前 server.h 还有重要实现细节：普通节点的 level[0].span 被复用存放节点信息，不能照搬“每一层 span 都以完全相同方式解释”的旧结构说明。尾指针与 backward 指针方便反向访问。

操作需求 大集合中的主要机制 成本边界
按 member 查 score dict 定位相应节点 平均哈希成本，仍有哈希和字符串比较
按 score 定位范围起点 跳表导航 平均 O(log N)
返回范围内 M 个结果 定位后遍历/输出 通常 O(log N + M)，还要计返回字节数
查名次 上层导航并累加跨度 平均 O(log N)
更新 score 原位置更新或拆下重插 保持顺序和跨度不变量

这里的复杂度描述针对典型跳表路径，具体命令的额外选项与协议输出会增加工作；listpack 路径另算。

本提交不再适合画成“字典另存一份 score”

zslCreateNode 将节点、level 数组和成员 SDS 放在一次分配里。zsetAdd 的 dict 查找得到的是跳表节点，score 从节点读取；更新 score 时，zslUpdateScore 的源码说明保持节点地址不变，无需随 score 改变再更新 dict 中的节点引用。

这同时节省了重复元数据、分配和维护工作。它也提醒我们：双索引不等于双份完整 payload，可以共享同一实体的内存表示。

另一项小优化：复用已经完成的查找

新增成员时，dictFindLink 同时取得已有项或候选 bucket；后续通过 dictSetKeyAtLink 插入，避免调用另一条路径重新计算/寻找同一个位置。这个思想在数据库查找后更新、容器插入 API 中很常见：将“找到位置”与“在该位置操作”的结果复用。

为什么不是红黑树

可以用平衡树实现有序查询，Redis 选择跳表并不证明跳表在所有条件下优于树。比较点应包括：范围遍历、rank 支持、实现与维护复杂度、节点大小、随机层高、缓存局部性、更新 workload，以及是否还需要 member 的独立索引。两者都存在多次指针访问；紧凑数组在小 N 下可能更经济。

业务拓展：分页和热榜

高 offset 分页可能付出跳过前面大量结果的成本；score 游标更容易避免深分页，但要设计同 score 的 tie-break 与并发变化下的边界。单个超热排行榜仍属于一个 key，Cluster 不能把其内部 member 自动拆给多个节点。若应用分区排行榜后合并，排名与一致性语义也随之变化，不能只承诺“拆分以后一样准确且更快”。

6. 过期、淘汰与释放：三个时间点、三种机制

TTL 到点，为什么内存不一定立即下降

要区分：逻辑上已过期、从索引中删除、底层内存真正释放。过期 key 可能尚未被后台周期处理；读取路径会检查并按实例角色/标志处理过期；异步释放又可能把实际回收推迟。RSS 还受分配器影响，不能要求删除后立即按 payload 大小下降。

当前 lookupKey 在找到对象之后调用 expireIfNeeded，并有副本、读写和特殊访问标志等分支。因此“每次读都立刻把过期 key 物理删除”不精确；readonly replica 要避免自行强制删除造成与主库不一致。

被动检查与主动过期怎样配合

被动检查处理被访问的 key，但无人访问的过期对象不能永远占内存；主动周期有预算地扫描过期索引。activeExpireCycle 保存跨调用的进度，依据 active-expire-effort、hz、过期比例和时间限制调整工作，提供 fast/slow 周期。

它不是给每个 key 配置一个独立系统定时器。提高 effort 可更积极清理，但会与前台命令争用 CPU。大量 key 同时到期容易集中形成清理和缓存回源压力：应用 TTL 加抖动可以平滑业务负载，却不能代替容量与峰值规划。

淘汰与过期有什么不同

过期依据 TTL 判断数据是否继续有效；淘汰在内存压力下按策略选牺牲品，未到 TTL 的 key 也可能被淘汰。常见策略族包括 allkeys/volatile 下的 LRU、LFU、random，volatile-ttl，以及 noeviction。volatile 类只从有 TTL 的候选中选；候选不足时，配置了淘汰策略也可能无法腾出足够内存。noeviction 下，受限写入可能被拒绝，但不应解释为任何命令一律禁止。

这份 unstable 源码还包含额外策略及保护机制；本文讨论面试中常见的策略族，而不是宣称这是一张当前提交的穷尽清单。

为什么 Redis 不是严格 LRU 链表

evictionPoolPopulate 采样若干候选，并把较适合淘汰的项留在池中；LRU 通过对象访问时钟估计空闲时间。这样不必每次访问都维护全局精确 LRU 双向链表，减少指针写入和元数据成本，代价是选出的并非数学意义上全局最久未访问的 key。

LFU 也不是无界精确计数。源码将访问时间与频度复用在 LRU 位域中，频度为 8 位；LFULogIncr 随计数增加降低继续递增的概率，并在选候选时考虑时间衰减。历史热点如果不衰减，会长期挤占新热点；概率增量避免计数很快饱和。

为什么只读访问也可能触发 COW

lookupKey 命中后可能更新 LRU/LFU 元数据，读业务因此也可能写内存页。当前源码在有持久化子进程时避开这些访问元数据更新，注释明确针对 copy-on-write 成本。这里不是缓存正确性变化，而是对替换统计精度的暂时取舍。

DEL 和 UNLINK 的关键差别

删除必须先让 key 不再从数据库索引可见；释放一个带大量独立分配的 value 则可能耗时。UNLINK 让高释放成本对象的内存回收移到后台线程，减轻前台延迟。

但 UNLINK 不保证每个对象都由后台线程释放，也不代表立刻释放全部内存。freeObjAsync 先估算 effort，只有超过当前阈值 64 且引用计数满足条件时才安排后台任务，否则同步释放。这里的 64 是释放工作量判定，不是 value 大于 64 字节；一个大 RAW 字符串的分配数量与巨大 HT 的许多 entry 完全不同。

向外拓展：内存上限不等于进程 RSS 上限

淘汰内存统计不能简单纳入所有缓冲。evict.c 解释：删除传播本身会增加 AOF/复制缓冲，若全部计入需要淘汰的内存，可能形成“越删缓冲越大、越要继续删”的反馈循环。因此统计中的排除项是为了机制稳定，不代表这些内存从机器上消失了。

容量规划仍需为客户端输出、复制、AOF、分配器碎片和 fork/COW 留余量；maxmemory 应低于机器所有可用内存，而不是把剩余每个字节都分配给数据集。

7. RDB 与 AOF：写入成功到哪里才算持久

先把状态链讲清楚

命令完成、内存状态已修改
  → 日志进入 Redis 的 AOF 缓冲
  → write 把日志交给内核/文件系统
  → fsync 请求将数据持久化
  → 重启时根据持久化文件恢复

这些阶段不是同一个时刻。客户端收到成功、AOF 缓冲已有内容、系统调用 write 返回、持久化介质保证数据可恢复，都不是天然等价。真实保证还受配置、文件系统、硬件和失败类型影响。

RDB：快照及其非免费后台成本

rdbSaveBackground 通过 redisFork(CHILD_TYPE_RDB) 创建子进程，子进程序列化某一快照视图。fork 后父子共享页面，父进程继续修改时依靠 COW 保留子进程的视图。

收益是让大量序列化工作不全在主执行路径完成；代价有 fork 本身的停顿、页表复制、后台 CPU/I/O 与写入引发的页面复制。不是 fork 一开始立刻复制整份数据库，也不是后台执行就没有主线程影响。 大数据集配合高写入率，COW 可能显著增加内存；这是内存余量与 fork 延迟监控的重要理由。

只依靠周期快照时，最后一次有效快照之后的写入可能丢失。快照方便恢复/备份，不提供任意两次快照之间的零丢失保证。

AOF：不同 fsync 策略是不同的风险预算

策略 主要取舍 面试时必须加的边界
always 更紧密地同步日志与持久化确认 存储延迟进入关键路径；不承诺所有硬件故障下绝对无损
everysec 通常后台按秒级安排 fsync，平衡延迟和丢失窗口 “约一秒”是常见目标，不是绝对最大丢失时间
no 同步时机更多交给系统 性能与风险受系统刷写行为影响

当前 flushAppendOnlyFile 在 everysec 模式会检查后台 fsync 是否还在进行，某些情况下推迟 write；源码中有约两秒的推迟处理及 delayed fsync 统计。这直接说明慢存储能影响前台延迟，“AOF 全部后台所以前台无感”不成立。

空 AOF 缓冲也可能仍需 fsync：之前 write 的内容尚未持久化。不能仅依据缓冲为空判断“磁盘已同步”。

重写不等于压缩历史命令文本

AOF rewrite 从当前有效状态生成更紧凑的恢复基础，不必保留所有历史 SET/更新。当前源码明确区分 BASE、INCR、HISTORY 文件，manifest 描述其顺序与状态；新的写入可继续进入增量文件，成功后更新清单并回收历史文件。

因此当前实现不是只认一个永远追加的 appendonly.aof，也不应套用每个旧版“双写重写缓冲”的具体结构。理解目标比背旧字段更重要：重写期间不能漏掉父进程新增写入，切换必须保持可恢复的一组文件，而不是只换一个看起来最新的文件名。

AOF BASE 还可能采用 RDB 形式。排查恢复问题时，要看 manifest、文件内容类型和实际配置，而不是看后缀猜恢复顺序。备份同样应保留一组一致文件，不能随意独立复制其中一个分片。

性能与可靠性一起问

若启用 always 后 P99 上升，先验证 fsync/存储延迟，再讨论配置改变；改成 everysec 是改变数据风险，不只是性能参数调优。若 BGSAVE 期间内存猛涨，关注 COW、写入分布、分配器与数据规模；单纯多开 I/O 线程并不针对 fork 的核心问题。

源码证据： rdb.c:2226–2245、aof.c:52–65、aof.c:1234–1243、aof.c:1408–1498、aof.c:3219、server.c:2066–2069。

8. 复制、PSYNC 与 Cluster：内存中的成功不等于集群承诺

复制默认是异步的，故障转移可能丢写

主库执行写入，并把复制流传播给副本。客户端得到主库成功，不自动意味着某个副本已经处理、更不意味着其日志已经持久化。如果主库此时失效并提升尚未收到该写入的副本，可能丢失已确认的业务写入。

WAIT 等待指定数量副本对该连接之前写入的复制 offset 进行处理确认；WAITAOF 则涉及本地及副本的 AOF 同步确认。二者回答的不是同一个问题。等待命令超时不表示前面的写入被撤回；满足等待条件也不能直接把整个系统称为强一致共识系统，故障转移和恢复仍有各自边界。

PSYNC 为什么要同时检查 replid 和 offset

offset 代表复制历史中的位置，不是独立可解释的数据库版本。两个不同历史的主库即使 offset 相同，也不能凭它继续复制。

masterTryPartialResynchronization 检查当前/历史有效 replid 及其适用 offset，再检查 backlog 是否还保留请求位置。历史匹配且窗口覆盖，才能 CONTINUE；否则全量同步。若 backlog 太小，短暂断线后的写流也可能把所需数据挤出窗口，反复导致昂贵全量同步。

一个容量规划近似式是：

B≳R×T×F

其中 B 是计划的 backlog 字节，R 是复制流写入速率，T 是希望覆盖的断线/恢复时间，F 是峰值和估算余量。它是工程估算，不是实现保证；业务 payload 字节与实际复制流字节也不必相等。

本提交的 backlog 不应画成孤立的固定环形数组

当前 backlog 包含对复制 buffer block 的引用，并用 radix tree 索引部分 block offset；副本也引用共享复制 buffer 的起始位置。对旧版“一个固定环形字节数组”的背诵，要区别抽象历史窗口和当前物理布局。

共享 buffer 减少同一复制流对多个副本的重复保存，但慢副本可能让块较久不能释放。源码通过引用和分批 trim 处理回收，避免大量块一次释放冻结主线程。backlog 配置大小不应被简单理解成任何时刻所有复制相关实际分配的严格上限。

Cluster 的 slot 是路由单元，不是 key 内部分片

当前 cluster.h 定义 16384 个 slot。keyHashSlot 计算 CRC16 的低 14 位；符合规则的非空 {...} hash tag 可使多个 key 落到同一 slot，便于局部多 key 操作。

同 slot 是必要的路由条件，不代表迁移过程或所有命令都无需检查。一个超大 Hash、超热 String 或榜单仍是单个 key，不会自动按字段/member 拆到其他节点；客户端连接更多节点也不能拆掉它的热点。

MOVED 与 ASK 的语义为什么不同

  • MOVED：请求应按当前 slot 所有者去处理，客户端通常更新或刷新路由。
  • ASK：迁移中的临时重定向；向目标发送 ASKING 再执行本次请求，不把它当作永久所有权变更。

getNodeByQuery 还处理迁移/导入、多 key、缺失 key 等条件，某些组合可返回 TRYAGAIN。故障、迁移与路由都是状态机，不是单纯用一个 hash 函数定位机器。

Sentinel 与 Cluster 不要混为一谈

Sentinel 常用于监控非 Cluster 主从拓扑并协调故障转移，本身不按 slot 分片用户数据；Cluster 负责分片和相应集群机制。这是部署模式层面的区分，本文没有展开 Sentinel 全部选举路径，也不声称验证了脑裂与 failover 的所有场景。

源码证据： replication.c:264–280、315–410、replication.c:606–610、replication.c:1006–1084、replication.c:4892–4955、cluster.h:22–24、54–82、cluster.c:1230–1535。

9. 事务、Lua、锁与缓存一致性：由原子性向业务边界扩展

MULTI/EXEC 的原子性不等于数据库回滚

MULTI 收集命令，EXEC 检查是否应拒绝整批，并逐项执行。入队时的错误可以把事务标记为无效；WATCH 检测到改动会导致条件执行失败。执行过程中的某条命令出错，并不会把此前已执行的写入自动撤回，其他队列命令也有各自的结果。

execCommand 的核心是一段循环：逐个恢复命令参数，做权限检查，再 call。它不是带 undo log 的通用事务系统。不可穿插的执行组织与全体成功/失败回滚，是两个不同维度。

WATCH 是乐观条件检查，不是持有 key 锁

WATCH 注册观察关系，被观察 key 的相关变化会把客户端标记为 DIRTY_CAS；EXEC 检查标记，当前源码还显式检查被观察 key 已过期的情况。业务读、计算、等待期间没有获得 Redis 内部锁，必须处理失败并重试。

高争用下，重试可能放大负载。可以用更短的原子命令或脚本减少客户端读改写窗口，但脚本自身也有执行与数据规模成本。

Lua 能减少 RTT，也会占据执行通道

适合把检查与少量更新组成一次服务端操作，例如计数与条件扣减。原子执行指执行期间对相应普通命令的隔离，不代表脚本错误能回滚之前写入，也不代表脚本跨节点天然形成事务。

不要在脚本中扫描巨大数据集或进行无限循环。script.c 的 kill 路径检查是否已经发生写入：写过数据的脚本并不能总被安全中止，因为不能靠简单终止恢复之前状态。超时监控也不等于达到时限便自动安全回滚。

用 Redis 锁时，先明确三条不变量

获取：不存在时写入唯一 owner token，并同时设置租期
释放：仅当当前 owner token 等于自己的 token 时删除
使用：业务执行必须考虑租期到期、暂停、重试及主从切换

常见获取形式是 SET lock token NX PX ttl。NX 判断和租期要在一个操作中完成，避免 SETNX 后进程在设置过期前崩溃。释放必须“比较 owner 后删除”原子执行；直接 DEL 可能删掉新持有者的锁。

下面是思路示意，不是已经运行或证明完整可靠的锁库：

if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0

不过唯一 token 只保证不要误删别人的锁，不保证旧持有者在暂停、租期过后不会继续写外部资源。需要更强保护时可设计 fencing token：下游拒绝旧顺序号的写入，并且顺序号来源自身要满足所需的一致性与故障恢复条件。不能简单宣称在可能丢写的复制拓扑里加个 INCR 就获得可靠 fencing。

主库锁刚确认但尚未复制便故障转移，也是潜在双持有者来源。锁正确性必须纳入部署和失败模型，而不是仅证明一台 Redis 上的 SET 是原子的。

10. 向外拓展：Stream、基数估计及当前新增结构

Stream 为什么组合 radix tree 和 listpack

stream 持有 rax，迭代器同时维护 radix-tree 游标与当前 listpack。宏观索引按消息 ID 定位一段数据，块内紧凑保存多个 entry，比每条消息都独立建立完整索引更节省元数据；代价是块内解析与维护复杂度。

消息 ID 的时间部分不是业务执行成功时间，也不是跨系统事务序号。消费者组保存 last delivered ID、消费者与 PEL。PEL 追踪已交付但尚未确认的消息；消费后不 ACK，消息并不自动变成“永远完成”。失败恢复、claim、幂等处理与 ACK 的先后都应由业务设计。

当前 streamCG 的 PEL 除 radix tree 外，还维护按 delivery time 组织的双向链表，注释指出用于高效访问较旧 pending entry。同时维护多个索引不只用于 ZSet：同一消息要按 ID 查，又要按时间找待认领项，就可能需要不同索引视角。

不要把有 PEL 等同于业务 exactly-once。处理完业务后、ACK 前崩溃可能重投；先 ACK 后业务写入失败可能丢处理。下游事务和幂等键决定最终效果。当前 Stream 还出现生产者去重相关结构，但这同样不自动使外部副作用具备 exactly-once。

radix tree 的空间优化

rax.h 解释路径压缩：一串只有单个孩子的节点可以合并保存公共路径，减少分配与指针。当前还支持已知固定 key 长度的模式，直接在父节点槽保存值指针，省掉叶节点分配。

收益依赖 key 的前缀分布和固定长度条件，不能简单说“字典树永远更省内存”。插入分歧前缀要拆节点，删除后可能重压缩；结构节省也要支付维护复杂度。

Bitmap 与 HyperLogLog 分别解决什么

Bitmap 适合有界、较稠密 ID 的布尔状态。定位 bit 可直接利用 byte/bit offset，但整个 BITCOUNT 与大型位运算仍要扫描相应字节。超大离散 ID 可能为中间空洞分配大量空间；“一个状态只占一 bit”不能忽略 ID 空间跨度和扩容成本。Bitmap 是精确状态表示，不是概率去重器。

HyperLogLog 只估计基数，不保留所有成员，因而不能拿它查某个用户是否存在，也不能替代精确 Set 的删成员能力。本提交定义 P=14，即 16384 个 register，每个 6 bit；dense register payload 为：

16384×68=12288 字节

这只是 register payload，还要加头部、对象及分配器开销；小基数可以用稀疏表示。常见约 0.81% 的标准误差量级来自概率分析，不是“每一次估计最多误差 0.81%”的硬上界，更不是本文测量结果。

Hash 字段过期：两个层次的最早时间

当前 t_hash.c 的说明中，每个 Hash 维护字段 TTL 的私有 ebuckets；含字段过期的 Hash 又注册到数据库级索引中，时间代表该 Hash 的下一次最早过期。这样可以先定位该处理哪个 Hash，再处理其过期字段，不必每轮扫全部字段。

同一个 Hash 连续修改多个字段过期时间时，还会尽量合并对全局索引的更新。这是“批处理维护索引”而不是简单减少命令次数。新增字段 TTL 后，不同编码的兼容性与迁移成本也应纳入评估。

Hash Templates：共享字段名，代价是 schema 变化

当前源码描述不可变模板保存排序后的字段名，同 schema 的多个 Hash 共享它，各 Hash 只保存自己的 values。模板字段可二分定位；TMPL_LP 的 value 还需要 listpack 定位，TMPL_ARRAY 则有按 index 访问 values 数组的路径，不能把两种编码的查找成本合并为一个 O(log N)。

此设计适合大量稳定同构对象，减少重复字段名。频繁增加/删除字段意味着切换或创建模板，schema 不稳定会削弱收益；模板被少量 key 使用时还可能付出额外成本。

该提交配置中 hash-min-template-entries 0 表示关闭写路径的自动模板转换。这是版本明确的拓展知识，不应替换成所有线上 Redis 的默认 Hash 行为。

Array：稀疏与稠密表示的切换

当前 t_array.c 与 sparsearray.h 引入按非负 64 位 index 访问的 Array。它用 directory/slice，必要时加入 superdir；稀疏 slice 保存排序的 offset/value 对，稠密 slice 用直接数组和滑动窗口。Tagged word 内联部分整数、短字符串和浮点表示，减少小 value 分配。

配置中的默认 slice size 为 4096、稀疏转稠密阈值为 10、回退阈值为 5，且回退还受节省内存的条件约束：又一次用滞回来防止表示抖动。

分析复杂度时，不能机械照抄头文件的 O(1) 宣传句：稀疏 slice 的有序查找、插入搬移、目录增长以及转换都可能增加工作；有界 slice 与阈值限制了局部成本。浮点 immediate 表示还涉及低位清理，持久化保存逻辑类型而不是架构相关 tagged word。这属于该 unstable 提交的具体设计，不是经典五种类型的跨版本知识。

源码证据： stream.h:35–152、rax.h:40–109、hyperloglog.c:194–204、t_hash.c:115–121、270–306、redis.conf:2245–2308、sparsearray.h:23–98、t_array.c:20–39。Bitmap 可查 bitops.c:854–896 的 byte/bit 定位，以及 redisPopcount（67 行）、bitcountCommand（1622 行）；本文未逐一分析所有位操作或执行相关实验。

四个性能设计问题

  1. 工作是不是本来就很多？ 输出一百万个元素至少要处理和传输这些结果。换线程模型不能消除结果大小。
  2. 工作能否分批？ 渐进 rehash、主动过期预算、复制 buffer 分批 trim 都在限制单次占用。
  3. 能否减少数据搬运和分配？ EMBSTR、kvobj、紧凑集合、跳表节点内嵌成员、共享模板都在这里发力。
  4. 能否隐藏等待？ pipeline 降低 RTT 等待，I/O 线程分担网络侧工作，预取利用内存级并行；它们针对不同等待，不能互相替代。

平均复杂度、摊还复杂度、最坏情况、编码切换成本与 P99 应分别讨论。一个“平均 O(1)”查找系统，仍可能在扩容、转换、释放和磁盘争用时产生尾延迟。

学习实验：仅在独立、可丢弃的实例中执行

下列是设计好的验证方案，尚未在此机器上运行。 不连接生产实例，不修改源码检出目录的工作树；构建和运行产生的试验文件、日志、配置及持久化数据均放到系统 TEMP 的独立目录。任何测试实例只监听受控本地地址，不暴露到网络。

A. 看编码切换，不先测极限 QPS

  • 使用不同长度和格式的 String，记录 OBJECT ENCODING 与 MEMORY USAGE；比较短字符串、较长字符串、严格整数与带前导零的值。
  • 按实际运行配置构造阈值内/外的 Hash、Set、ZSet、List，分别观察增长、删除后的编码和延迟；不要把配置文件示例当成实例当前值。
  • 加入宽整数触发 intset 升级；加入非整数观察是否转 listpack/HT。
  • List 围绕转换边界反复增删，验证滞回与节点条件，而不是假设每次都往返转换。

B. 把 pipeline、I/O 线程与预取分开比较

先固定数据集、读写比例、key/value 长度、连接数和持久化策略。分别改变 pipeline 深度、客户端线程数、I/O 线程数；若测试预取，确认当前源码相关配置与可用统计。

客户端发生瓶颈时，服务端参数收益会被掩盖。当前 redis.conf 也提示 benchmark 客户端要有足够线程；不能从一个单线程饱和的压测程序推断 Redis 多线程无效。记录吞吐、P50/P95/P99、CPU、内存和输出缓冲，而不是只摘一个最佳 QPS。

C. DEL 与 UNLINK

对比相似总字节但不同分配结构的对象，例如一个较大 RAW String 与很多字段的 HT Hash。关注前台删除耗时、其他请求延迟、后台释放队列和实际内存变化。预期差异来自释放 effort，不是仅来自 key 大小；这个预期需实验确认。

D. TTL、持久化与恢复

在不同 TTL 集中程度下观察过期工作与前台延迟；对比抖动后的时序。再分别测试快照期间高写入与低写入的 COW 和 RSS，比较 fsync 策略的性能/风险，不同时修改全部参数。

恢复测试必须使用隔离实例和可丢弃数据。记录故障时刻、日志策略、已确认写、恢复后的数据、副本状态；不把“进程正常关闭再启动成功”当作断电安全性的证明。

E. SCAN 与副本恢复

SCAN 期间进行受控修改并去重结果，验证无快照语义；不能要求并发修改时返回一个精确瞬间集合。对复制测试，控制断线时间和写入速率，检查 offset 是否仍在 backlog 窗口，区分 partial 与 full resync。

2. Redis 是单线程吗？ 普通键空间命令主要主线程执行，系统并非只有一个线程 I/O 线程读写/解析、异步释放、后台子进程
3. 多开 I/O 线程能治长 Lua 吗？ 不能自动分摊脚本执行 先区分网络与串行执行瓶颈
4. pipeline 是事务吗？ 不是，主要摊薄 RTT 和调用成本 批次、输出缓冲、命令穿插与原子性
5. SDS 为什么二进制安全？ 显式长度，不靠 NUL 判断内容边界 调用者仍必须使用带长度的 API
6. EMBSTR 为什么省空间？ 合并对象/SDS 分配，减少间接访问 当前 44 字节是实现阈值，不是协议规则
7. 对象类型和编码有何区别？ 类型定义语义，编码定义表示 同类型随规模/内容改变编码
8. 当前 key/value 如何减少分配？ kvobj 可以嵌入 key、短值和元数据 不代表每种 value 都内联
9. dict 的 O(1) 是绝对的吗？ 平均意义下成立 长 key、冲突链、迁移及分配成本
10. 渐进 rehash 怎样避免长停顿？ 双表共存、分批迁移 一个 bucket 的长链仍可能昂贵
11. SCAN 会重复吗？ 会；它不是快照 去重、并发变化、COUNT 只是提示
12. Hash 一定用哈希表吗？ 小对象可以使用 listpack 大对象、字段 TTL、当前可选模板编码
13. listpack 消除了所有搬移吗？ 没有，它避免特定级联长度更新 连续内存仍可能 realloc/memmove
14. quicklist 随机访问是 O(1) 吗？ 不是普通数组 节点定位、局部 listpack 与压缩成本
15. intset 插入为何不是 O(log N)？ 二分找位置之后还要搬移 整数宽度升级也是批量工作
16. Set 非整数必转 HT 吗？ 当前小集合可转 listpack 依数量、长度和配置条件
17. ZSet 为什么两种索引？ 按 member 与按 score/rank 的需求不同 共享跳表节点，并保持索引一致
18. span 有什么用？ 支持跨层累加名次 当前底层字段复用需看版本
19. TTL 到点必然释放内存吗？ 逻辑过期、索引删除、回收不同步 主动预算、访问检查、副本与 lazyfree
20. LRU 为什么是近似的？ 采样与候选池降低全局维护成本 精度、采样成本、LFU 的概率计数/衰减
21. UNLINK 一定异步释放吗？ 高 effort 且条件满足才排后台 64 是 effort 阈值，不是字节数
22. RDB 后台为何还会抖动？ fork、COW 和资源争用仍有成本 高写入率、内存余量、页表和磁盘
23. AOF everysec 最多丢一秒吗？ 通常目标是秒级，不是硬上界 慢 fsync、刷写与故障类型
24. AOF 重写怎样不停写？ 当前状态生成 BASE，新增写进入 INCR manifest 切换与一组文件的可恢复性
25. PSYNC 为什么要 replid？ offset 只有放在同一历史中才有意义 当前/次历史与 backlog 窗口
26. WAIT 后就强一致了吗？ 不是，它等待处理确认 不同于落盘；失败转移仍有边界
27. MOVED 与 ASK 有何区别？ 所有权路由与迁移中临时路由 ASKING、多 key 与 TRYAGAIN
28. MULTI/EXEC 会回滚吗？ 不提供通用执行错误回滚 入队失败、WATCH 失败和运行错误区别
29. 有 TTL 的 Redis 锁就安全吗？ 还要 owner 校验、租期与故障模型 旧持有者继续工作、fencing、复制丢写
30. Stream 直接保证 exactly-once 吗？ 不自动保证外部业务副作用 PEL、ACK、重投及下游幂等/事务

三条源码阅读路线

路线 A：命令执行与访问成本

networking.c → server.c:processCommand/call → t_string.c:getGenericCommand → db.c:lookupKey → kvstore.c/dict.c → 输出缓冲处理。

每一步问：是否分配？是否遍历？是否写元数据？是否需要同步或 I/O？有没有批次/时间边界？

路线 B：一种类型的编码生命周期

object.h 的编码定义 → 对应 t_*.c 的创建/转换 → 底层容器 → 修改/删除路径 → 对象释放 → RDB/AOF 的保存恢复。

例如研究 Set 时同时读 t_set.c 和 intset.c/listpack.c/dict.c；否则只能看到命令表面而看不到成本变化。

路线 C：跨越进程/节点的确认边界

写命令 → call 的传播管理 → aof.c 的 write/fsync → replication.c 的流、offset 与等待 → 断线恢复 → Cluster 的路由状态。

每一步问：成功确认代表数据到了哪里？出现超时是否撤回？换主后历史是否仍相同？业务到底能接受多大的丢失或读旧窗口？

回答时避免的七个绝对化说法

  1. “所有操作都是 O(1)。”
  2. “开多线程以后命令都并行。”
  3. “到了过期时间立刻删除并还内存。”
  4. “UNLINK 永远后台、永远瞬间完成。”
  5. “AOF everysec 硬保证最多丢一秒。”
  6. “事务、Lua、WAIT 或 SET NX 中任一个就足以保证业务强一致。”
  7. “源码里有的特性，所有稳定版本就都默认启用。”

更好的句式是：在这个版本、这种编码、这些配置和失败假设下，机制提供什么；它省了什么，剩下的风险在哪里。
