#### 全链路串讲与线上排查 {#interview-network-diagnostics}

<article class="qa-item" id="qa-keepalive-heartbeat" data-level="scenario" markdown="1">
<p class="qa-question">Q152 · HTTP keep-alive、TCP keepalive 和业务心跳分别检测或节省什么？</p>
<div class="qa-answer" markdown="1">

HTTP 持久连接让多个请求复用传输连接，减少反复建立连接的开销；TCP keepalive 用传输层探测帮助发现长时间空闲连接上的部分故障；业务心跳则可以检测应用协议是否仍按预期响应。三者不是同一个开关。[25–26]

TCP 探测收到回应，最多说明相应传输端点能够响应，不证明业务线程、数据库或依赖服务健康。应用心跳可以携带协议状态并设置更贴近业务的期限，但同样可能受到队列、调度和网络延迟影响，误判后重连还可能引发重复请求。

半关闭表示一方向不再发送，另一方向仍可能传输；RST 表示连接被复位，不等于完成正常 FIN 流程。活性检测、正常关闭和请求成功确认分别属于不同状态判断。选择超时要结合故障恢复与误判成本，不存在适用于所有链路和业务的固定秒数。

</div>
</article>

<article class="qa-item" id="qa-network-other-protocols" data-level="scenario" markdown="1">
<p class="qa-question">Q153 · ICMP、FTP、SMTP、P2P 和链路差错检测解决什么？ping 成功为什么不保证服务可用？</p>
<div class="qa-answer" markdown="1">

ICMP 承担相应网络差错报告与诊断，ping 通常使用 Echo 请求／答复。主机允许 Echo 不说明应用端口正在监听，拒绝 Echo 也不说明所有应用通信失败；防火墙、路由和服务状态要分别判断。traceroute 利用 TTL／Hop Limit 到期等反馈推断路径，但探测包可能与业务流采用不同路径，返回超时也不唯一证明那个跳点丢弃业务数据。

FTP 的控制与数据通道分离，主动和被动模式在数据连接的发起方向上不同，因此会与 NAT、防火墙产生不同交互；SFTP 基于 SSH，是不同协议，不是 FTP 简单加密后的别名。SMTP 主要组织邮件提交和服务器间转发，收取邮件常使用 IMAP／POP3 等协议。协议解决传输与交互，不自动完成垃圾邮件、身份冒用或业务内容真实性判断。

P2P 让参与者同时承担部分资源提供和获取职责，可以分摊中心负荷，却仍需要发现、调度、完整性和滥用防护，并面对节点离线与 NAT 可达性。链路校验和 CRC 检测某些传输错误，纠错码增加冗余以恢复一定错误，两者都不等于密码学认证。共享介质还需要协调多址访问，例如竞争、时分或频分；现代交换式全双工以太网不宜机械套用旧式共享半双工以太网的碰撞模型。

</div>
</article>

<article class="qa-item" id="qa-linux-topology-network-scope" data-level="scenario" markdown="1">
<p class="qa-question">Q154 · CPU 数、内核版本和网络诊断工具各测什么？curl 成功能证明任意端口健康吗？</p>
<div class="qa-answer" markdown="1">

物理封装、核心和逻辑 CPU 是不同层次，进程实际可用执行资源还受亲和性、cpuset 与配额限制。简单数 cpuinfo 行不一定反映容器可用预算；top 的线程视图也不等于这些线程此刻都在并行执行。Uname 报内核信息，发行版信息与用户空间软件版本另有来源。

网络观察需分层：ss 看 socket 状态，lsof 把打开对象与进程关联，ethtool 查看相应网卡能力与链路信息，ping 观察 ICMP 往返，dig 查询 DNS，curl 使用所选应用协议。监听并不等于请求处理正常，ICMP 不响应也不等于 TCP 必然失败，HTTP 返回成功更不证明同一地址上任意服务协议健康。

连接测试需要对齐地址族、目标端口、网络命名空间、TLS 身份及具体应用语义。权限可能使进程归属信息不完整，代理和 DNS 缓存也可能改变观测路径。多个读数应围绕同一时间窗口与故障假设结合，不能由一个工具输出直接宣布网络或服务根因。[76–78,88–89]

</div>
</article>

<article class="qa-item" id="qa-packet-capture" data-level="scenario" markdown="1">
<p class="qa-question">Q155 · 抓包排障：ss、netstat 与 tcpdump 各自能看到什么，应该按什么顺序看？</p>
<div class="qa-answer" markdown="1">

先看本机状态还是先抓包，取决于问题现象。`ss` 是查看套接字状态与统计的工具，能列出连接及其状态（例如大量 `TIME-WAIT`、`CLOSE-WAIT`、`SYN-SENT`）与收发队列长度，并支持按状态和端口过滤；[367] `netstat` 提供类似能力但更老。[367] 这一步能回答“连接有没有建立、卡在哪个状态、队列有没有积压”，成本低且不侵入。

`tcpdump` 工作在链路上，能看到实际报文、重传、握手与挥手、分片标志、窗口与选项，是判断“网络层面到底发了什么”的依据；[368] 它的局限是只能看到本机可见的流量、需要过滤表达式控制量级，并且加密流量只显示到 TLS 记录层，应用内容需要密钥或应用日志配合。

推荐的排查顺序是：先用应用与系统指标定位受影响的服务与时间窗，再用 `ss` 看连接状态分布与队列，再针对具体五元组抓包，最后回到应用日志对齐订单／请求 ID。要区分“本机没有发出”与“对端没有回复”：抓包显示已重传但无 ACK 属于路径或对端问题，显示本机队列积压而报文很少则更像应用写入不畅或下游反馈窗口为零。任何抓包都要注意数据敏感性与存储开销，生产环境应限制过滤条件与时长。

</div>
</article>

<article class="qa-item" id="qa-long-connection-pool" data-level="scenario" markdown="1">
<p class="qa-question">Q156 · 长连接、连接池与 TIME-WAIT 过多分别该怎么处理？</p>
<div class="qa-answer" markdown="1">

先分清三种现象。`TIME-WAIT` 大量出现在主动关闭方，是正常回收路径：等待两倍报文最大生存时间以避免旧报文干扰新连接；[25] 数量高通常说明该端发起关闭多、连接生命周期短或连接复用不足，处理方向是减少无效短连接、复用连接池、必要时用内核的 `TIME-WAIT` 复用开关（例如 `tcp_tw_reuse`，只在安全条件下允许复用）。[369] `CLOSE-WAIT` 堆积则是应用收到了对方 FIN 却没有关闭本地描述符，属于代码或框架缺陷，只能修应用。

长连接与连接池要一起设计：池上限、空闲回收、最大生存时间、连接保活与失效检测、以及“取出连接前是否验证可用”。不设上限的池会把压力转移到被连方（数据库连接数、文件描述符），而过早回收会让每次请求都新建连接、放大握手与 `TIME-WAIT` 成本。[351] 中间设备（NAT、四层代理、负载均衡）常有空闲超时，池的空闲上限要小于它们，否则取出的连接可能已经被对端或中间设备静默关闭，表现为第一次请求失败、第二次成功。

因此“连接数不够”不能只靠调大上限解决：先确认是上游并发过高、下游响应变慢导致的占用时间变长，还是连接泄漏（取用后未归还）。用占用时长分布、等待队列长度与后端连接数一起判断，比单看 `TIME-WAIT` 计数更可靠。

</div>
</article>

<article class="qa-item" id="qa-retry-backoff" data-level="scenario" markdown="1">
<p class="qa-question">Q157 · 超时、重试与退避：重试风暴是怎样产生的，怎样避免？</p>
<div class="qa-answer" markdown="1">

重试把“偶发失败”变成对下游的额外负载。当上游超时阈值短于下游恢复时间，客户端一边重试一边继续接收新请求，失败流量成倍叠加，可能把已经过载的下游推向更长时间的不可用；并发重试还会互相加剧，因为每次失败都触发更多尝试。[371]

退避与抖动是基本手段：失败后按指数增长等待时间（1 秒、2 秒、4 秒……），并在等待上叠加随机抖动，避免大量客户端在同一时刻同时重试形成尖峰。[370] 更关键的是设置重试预算：按请求总量限制重试比例（例如每 100 个请求最多 10 次额外尝试），超过就快速失败并把背压向上传递；服务端侧用限流、排队上限与优先级区分可重试与不可重试流量。[371]

还要保证语义正确：只有幂等的操作可以自动重试——同一请求重复执行不改变最终状态；非幂等写入要用请求 ID 去重或改为“先查询后写入”；读写路径可以只重试读，写失败交给业务层决定。超时值要与下游的分位延迟对齐，而不是取经验固定值；被测方等待、排队与已提交是三种不同状态，超时只说明“没有在期限内拿到结果”，不代表对方没有执行。

</div>
</article>

<article class="qa-item" id="qa-load-balancing" data-level="scenario" markdown="1">
<p class="qa-question">Q158 · 四层与七层负载均衡有什么区别？健康检查与会话保持怎么配？</p>
<div class="qa-answer" markdown="1">

四层负载均衡按连接转发（地址与端口等），不理解应用协议，因此通用、开销低，但无法按 URL、头部或方法路由，也无法为每个请求选择不同后端；七层负载均衡解析 HTTP 等协议，可以按路径、域名、头部路由，做改写、压缩和缓存，代价是代理要维护更多状态与连接（客户端连接与后端连接分离）。[366]

健康检查决定“哪些后端可接收流量”。四层常用端口或 TCP 握手探测，七层可以用 HTTP 路径与期望状态码；检查失败后的摘除与恢复都有滞后，因此配置要处理两点：检查间隔与失败阈值决定了故障后仍会被转发的请求量；恢复时如果后端刚启动还冷，直接放全量流量可能让它再次失败，需要慢启动或权重渐增。健康检查本身也要避免副作用（探测路径不应触发写操作）。

会话保持（同一用户固定到同一后端）在多实例有状态服务中常被使用，但它是把状态放在了负载均衡器上：后端故障或扩容会打断会话，权重调整也可能迁移用户。更稳的做法是把会话外置（共享存储或令牌），让负载均衡无状态；确需保持时，四层按连接哈希、七层按 Cookie 插入等方式实现，并明确超时与失效行为。长连接的负载均衡还要考虑连接级粒度：连接建立后流量不再重新分配，扩缩容只能影响新连接。[366]

</div>
</article>

<article class="qa-item" id="qa-browser-url" data-level="scenario" markdown="1">
<p class="qa-question">Q159 · 输入 URL 到网页显示，除了 DNS、TCP、TLS、HTTP，还发生了什么？</p>
<div class="qa-answer" markdown="1">

浏览器先解释 URL、策略与缓存，再选择是否解析名称、建立或复用连接，通过相应 HTTP 版本取得资源。重定向、代理、缓存命中、Service Worker 和连接复用都可以改变实际路径，不能把一张固定流程图当作每次访问的网络实录。

资源到达后，浏览器解析 HTML 形成 DOM，处理 CSS 得到样式关系，布局计算元素几何，再绘制和合成画面。脚本可以修改 DOM、样式或发起新请求；是否阻塞解析、何时执行与脚本类型及加载属性有关。图片、字体等资源到达也可能影响布局，因此“首个响应完成”“DOMContentLoaded”“load”和“用户可交互”不是同一时刻。

缓存验证依赖 Cache-Control、ETag、Last-Modified 等相应规则，304 可以让客户端复用已有正文；没有发出新请求的缓存命中与收到 304 又不同。诊断时分别观察名称解析、建连、握手、等待响应、资源下载及渲染主线程，才能区分网络与页面计算的瓶颈。本篇的离线 reader 不意味着真实网站没有这些加载阶段，也不把文档回归当作实际站点性能测量。

</div>
</article>
