#### 编译模型、ODR 与 ABI {#interview-cpp-compilation}

<article class="qa-item" id="qa-odr-inline" data-level="principle" markdown="1">
<p class="qa-question">Q70 · 什么是单一定义规则？为什么头文件里的 inline 函数和模板不会重复定义？</p>
<div class="qa-answer" markdown="1">

单一定义规则有两层：一个翻译单元内任何可定义项至多一个定义；[315] 对函数、变量、类等实体，整个程序只能有一个定义，违反者不要求编译器诊断，也就是未定义行为，链接期可能只是“碰巧选中一个”。[314] 这正是不同翻译单元里同名但实现不同的函数能编译通过、运行时行为却不可预测的原因。

例外是标记为 `inline` 的函数与变量、类内定义的成员函数、函数模板与类模板成员、`constexpr` 函数等：它们允许在多个翻译单元中出现定义，但要求所有定义来自相同的 token 序列，也就是语义必须完全一致。[314,316] 头文件中的 `inline` 函数靠这条例外避免重复定义；模板则按“同一特化的多个实例化合并为一个”的方式处理，因此模板定义必须对每个使用点可见（这也是模板通常写在头文件里的原因）。[325]

实践含义：放进头文件的普通函数定义要标 `inline`（或写在类内、或做成模板／`constexpr`），否则多翻译单元包含就会重复定义；反过来，如果内联函数依赖的宏、配置或类型定义在不同翻译单元里不一致，就构成对规则的违反，症状是随机崩溃或行为随链接顺序变化。内部链接（`static` 函数、匿名命名空间）能避免冲突，代价是每个翻译单元一份代码与地址不一致带来的调试问题。

</div>
</article>

<article class="qa-item" id="qa-abi-stability" data-level="principle" markdown="1">
<p class="qa-question">Q71 · 为什么 C++ 库的 ABI 容易不兼容？extern "C" 稳定在哪里？</p>
<div class="qa-answer" markdown="1">

C++ 的二进制接口包含名称修饰（命名空间、参数类型、模板实参都编码进符号名）、对象布局与对齐、虚函数表布局、异常处理与运行时类型信息、内联与模板实例化结果，以及标准库类型（容器、字符串）的实现细节。名称修饰由实现定义，Itanium C++ ABI 是常见约定但不是标准，[317] 因此换了编译器、标准库或编译选项，符号与布局都可能变化。

这些细节共同构成“源码兼容不等于二进制兼容”：给类加一个成员会改变布局，替换 `std::string` 的实现会改变对象布局与接口，修改头文件里的内联函数体会让已编译的调用方继续执行旧代码；libstdc++ 因此维护 ABI 版本与兼容政策，用新增符号与版本化来避免破坏旧二进制。[318] 需要在不同构建之间长期复用的库，通常只暴露不透明句柄加工厂函数，或用 Pimpl 把成员布局藏在实现文件里。

`extern "C"` 改变的是语言链接：名字不做 C++ 修饰、按 C 约定调用，因此不同编译器与语言之间可以按符号名互相找到函数。[319] 它不改变结构布局、对齐、内存所有权，也不改变异常边界——异常与析构不能跨到无法展开 C++ 栈的一侧，跨语言接口仍要显式约定类型大小、调用约定与谁分配谁释放。结论是需要跨构建稳定就用 C 接口或明确文档化的 ABI，纯 C++ 接口按“同一构建体系内、一起重编译”来设计。

</div>
</article>

<article class="qa-item" id="qa-header-dependency" data-level="scenario" markdown="1">
<p class="qa-question">Q72 · 头文件依赖与 Pimpl：编译时间、ABI 与内联该怎样取舍？</p>
<div class="qa-answer" markdown="1">

C++ 的编译模型里“包含头文件”等于把声明、内联定义、宏与平台条件编译一起引入：被广泛包含的头文件一改动就会触发大量重编译，同时把私有成员与第三方头文件暴露给所有使用者，形成编译期耦合与宏污染。[288]

减少依赖的常用手段是前置声明、把实现放进源文件、把公开头文件缩到最小，以及 Pimpl：私有成员改成指向不完整类型的指针，实现类定义在源文件中。这样成员布局与依赖被挡在库内，代价是一次指针间接访问、一次额外分配或生命周期包装，还必须显式定义析构与移动操作（销毁点需要完整类型）。[288] 收益是 ABI 更稳——增删私有成员不再改变公开类的大小，调用方不必跟着重编译。

与内联的冲突是本质的：模板与需要内联的函数必须在使用点可见，因此“减少头文件依赖”与“跨翻译单元内联”目标相反。可行的折中是按变化频率划分——频繁改动的实现细节藏到源文件或 Pimpl，稳定的类型与算法核心留在头文件内联，热点路径另外评估是否需要链接时优化；公开 ABI 的类则不允许成员布局漂移。

</div>
</article>
