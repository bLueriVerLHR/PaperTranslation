#### 并发协议与执行资源 {#interview-concurrency}

<article class="qa-item" id="qa-data-race" data-level="basic" markdown="1">
<p class="qa-question">Q73 · 数据竞争与一般的竞态条件有什么区别？STL 容器一定不能并发访问吗？</p>
<div class="qa-answer" markdown="1">

C++ 数据竞争要求同时满足三个条件：两个动作潜在并发且相互冲突，至少一个动作非原子，二者之间又没有所需的 happens-before 关系。冲突不只包括读写同一内存位置，也包括对象生命周期的开始或结束与相应访问重叠。满足这些条件的数据竞争导致未定义行为。一般的竞态条件则更宽：即使所有共享访问都是合法原子操作，业务结果仍可能取决于不希望出现的交错。[219]

容器保证需要落到具体访问协议。没有并发结构修改时，规定的只读或按只读处理的成员调用可以并发进行；标准还要求避免不同元素内容修改间的数据竞争，但明确排除 `vector<bool>`。`map` 的 `operator[]` 可能插入元素，不能直接当成通用的只读查找接口。元素内部指向的共享可变对象，也不受不同元素保证的保护。[17]

预先定长的 `vector<int>` 中，各线程修改不同元素，不需要为这种元素访问额外串行化；一边 `push_back` 一边读取元素却是另一种协议。锁也须覆盖需要保持一致的不变量：查找结束就解锁，再通过借用指针修改对象，仍可能与随后删除该对象的线程冲突。容器调用、观察路径和目标生命周期因此需要一起分析。

</div>
</article>

<article class="qa-item" id="qa-atomic-volatile" data-level="basic" markdown="1">
<p class="qa-question">Q74 · atomic、volatile 和互斥锁分别解决什么问题？</p>
<div class="qa-answer" markdown="1">

原子操作对同一原子对象的相应访问呈现不可分割的效果，并按内存序参与同步规则；这不表示执行线程不能被调度器抢占。`volatile` 约束相应访问的实现行为，却不建立线程间同步。互斥锁则通过互斥访问和解锁／后继加锁的同步，将多个状态的检查与更新组织成一个临界区。[52, 219, 220]

`load` 读取，`store` 写入，`exchange` 更新并返回旧值；CAS 比较期望状态与当前状态，成功时更新，失败时将观察到的状态写回 `expected`。弱 CAS 还允许虚假失败，因此循环中需要根据更新后的期望状态重新计算条件。整数特化另提供 `fetch_add/sub`、位更新以及自增自减等操作，相应 `fetch` 操作返回更新前的值；这些接口并不对每一种 `atomic<T>` 都成立。一般模板也有平凡可复制、可构造及可赋值等类型要求，而非支持任意用户类型。[220]

原子性不使多步判断自动合并。例如先 `load` 确认计数小于上限，再 `fetch_add`，两个线程仍可能同时通过检查，使结果越过上限。条件检查和更新需要放入同一个 CAS 状态转换或锁保护范围，失败与重试也须重新考虑容量条件。单次原子更新解决的是某个状态转换，不是整个业务事务。

原子操作不保证在所有类型和平台上无锁，无锁操作也不等于组合算法没有重试或端到端一定更快。互斥与原子的选择取决于不变量涉及多少状态、是否需要等待、失败路径如何恢复，以及数据访问的竞争方式，而不是 API 名称。[220]

</div>
</article>

<article class="qa-item" id="qa-thread-local" data-level="basic" markdown="1">
<p class="qa-question">Q75 · thread_local 的语义与代价是什么？</p>
<div class="qa-answer" markdown="1">

`thread_local` 声明的对象每个线程一份实例，存储期与线程相同：命名空间作用域的线程局部变量在首次使用前完成初始化，线程结束时按构造逆序销毁；[303] 块作用域的线程局部变量在控制流首次经过声明时初始化，且这个初始化是线程安全的。[342] 因此它可以用来表达“确实按线程划分”的状态，例如线程本地缓存、随机数状态或诊断上下文。

代价来自实现：访问线程局部存储通常要经过每线程的内存块，动态模型下首次访问可能触发运行时解析；带动态初始化与析构的实例还要登记线程退出时的清理。线程数量多、对象多或频繁创建线程时，这些成本会体现在启动时间与内存占用上。

实践边界比语义更重要：线程池复用的工作线程不会重置线程局部状态，上一次任务留下的缓存、错误码或递归深度会带到下一次任务，因此长期服务要么显式清理，要么避免用它保存业务状态；动态库卸载与线程退出顺序在不同实现上的行为也不一致，销毁时机不宜作为逻辑依赖。更可控的替代是显式把状态沿调用链传递（便于测试），或按任务／连接构造对象，用原子量与锁保护真正共享的状态。

</div>
</article>

<article class="qa-item" id="qa-memory-order" data-level="principle" markdown="1">
<p class="qa-question">Q76 · release/acquire 怎样发布普通数据？为什么 relaxed 标记不够？</p>
<div class="qa-answer" markdown="1">

发布者先写普通数据，再对标记执行 release；读取者通过 acquire 读到这次发布的值，或读到符合规则的 release sequence 中的值，才与相应发布建立同步关系。写入普通数据、发布标记、获取标记和后续读取由此形成 happens-before 路径。仅在两端分别写上 release 与 acquire，并不保证读取者已经观察到目标发布。[219, 221]

下面是一次性发布的教学片段。假设对象在两线程开始前已正确初始化，发布后不再修改 `payload`，且双方都活到协议结束：

```cpp
int payload = 0;
std::atomic<bool> ready{false};

// 发布者
payload = 42;
ready.store(true, std::memory_order_release);

// 消费者
if (ready.load(std::memory_order_acquire)) {
    use(payload);
}
```

把标记的两端都改成 relaxed，仍保留标记的原子性以及同一原子对象的修改序和一致性约束，却不建立这里所需的 `payload` 发布关系。若消费者据此读取仍可能与发布者写入冲突的普通数据，就不能仅凭标记原子性排除数据竞争。反复发布、重用缓冲区或在读者访问期间再次写入，还需要额外的状态与所有权协议。[219, 221]

这些内存序的作用范围也不同：

| 内存序 | 本例相关的语义 |
|---|---|
| `relaxed` | 原子访问及单对象一致性，不负责发布相邻普通数据 |
| `release` | 发布先前写入，仍需满足相应获取操作读到发布的条件 |
| `acquire` | 在满足读取来源条件时，获取相应发布之前的效果 |
| `acq_rel` | 读改写操作同时具有获取与发布语义 |
| `seq_cst` | 具有相应获取／发布语义，并参与顺序一致原子操作的单一全序 |

`load/store` 等接口默认采用 `seq_cst`，但这个全序不是所有普通读写的任意全局顺序。将程序解释为简单线程交错，还要求不存在数据竞争，并满足使用顺序一致原子和相应互斥同步等条件；混用弱内存序不能直接套用这一结论。合法内存序也依操作而定，例如普通 `load` 不能用 release，普通 `store` 不能用 acquire。内存序描述的是抽象机关系，不只是某条 CPU 指令前后的重排限制。[219–221]

</div>
</article>

<article class="qa-item" id="qa-condition-variable" data-level="principle" markdown="1">
<p class="qa-question">Q77 · 条件变量为什么要检查谓词？notify_one 是否保存了一次任务？</p>
<div class="qa-answer" markdown="1">

条件变量推动等待者重新检查共享状态，不保存任务或通知配额。任务和条件存在于队列、计数器等状态中，常规协议用同一互斥量协调状态更新与谓词检查。`wait` 原子地释放锁并进入等待，唤醒后重新取得锁；返回既可能由通知引起，也可能是虚假唤醒。[222]

`cv.wait(lock, predicate)` 对应“谓词为假时继续等待”。即使确实收到了通知，另一工作线程也可能先取走最后一项任务，因此唤醒不等于取得任务。反过来，若任务在本次检查前已经入队，谓词为真就能直接继续，并不要求先前通知仍被保存。[222]

条件变量通知不保存任务：状态更新、出队与完成计数必须置于同一锁协议中。仅把标记改为 atomic 不足以替代这个协调：等待者检查为假之后，发布者可能在它真正进入等待前改写标记并通知，随后等待者仍进入睡眠。如果没有下一次状态变化，就可能一直等不到新的通知。原子标记避免了标记自身的数据竞争，却没有自动修复检查与等待之间的窗口。

</div>
</article>

<article class="qa-item" id="qa-atomic-instructions" data-level="principle" markdown="1">
<p class="qa-question">Q78 · atomic 的常见操作有哪些？atomic&lt;bool&gt; 一定用 LOCK 指令吗？</p>
<div class="qa-answer" markdown="1">

不一定。原子操作规定的是语言层语义，不对应一种固定硬件指令，更不意味着线程不会被操作系统中断。生成什么指令取决于操作、内存序、架构和编译器；某些原子加载可以使用满足要求的普通加载，读改写则可能使用专门指令或重试循环，不必每次都有 x86 的 `LOCK` 前缀。GCC 的 `__atomic` 内建函数在必要时还可能调用运行库。[62]

常见操作包括 `load`、`store`、`exchange` 和 `compare_exchange`：前两者读写值，`exchange` 替换并返回旧值，CAS 则比较并条件替换。CAS 失败会把读取到的值写回 `expected`，弱 CAS 还允许伪失败；重试循环既要使用更新后的预期值，也要重新计算依赖该值的待写入结果。`fetch_add` 等接口只适用于相应特化，不能推广到所有原子类型。GCC 的整数读改写内建接口排除 `bool`，因此用 `__atomic_fetch_and` 操作 `bool` 的示例不能当作通用实现。[62]

内存序决定原子操作与其他访问之间的关系：`relaxed` 保留原子性，但不单独发布普通数据；`acquire`／`release` 在满足读写关联条件时建立同步；`acq_rel` 用于适用的读改写，`seq_cst` 还为相应操作提供全序。C++11–20 的 `consume` 有依赖排序语义，实际编译器常提升为 `acquire`，这里不据此推导一条通用快速路径。某项操作无锁也不等于整个算法无等待，例如 CAS 循环中的某个线程仍可能不断重试。[16, 62]

</div>
</article>

<article class="qa-item" id="qa-cas-aba" data-level="principle" markdown="1">
<p class="qa-question">Q79 · CAS 为什么会有 ABA 问题？带标签的双宽度操作能解决什么？</p>
<div class="qa-answer" markdown="1">

`compare_exchange` 比较的是值：只有当前值与期望值相等才写入新值。[298] 它无法表达“自上次读取以来没有变化”。如果结构从 A 变成 B 又变回 A——例如节点被弹出、释放，之后地址被复用给了另一个节点——读者基于旧信息的比较交换会成功，但它推理时依赖的“还是原来那个节点”已经不成立，在无锁栈或队列中会导致丢节点、重复插入或访问已释放内存。[299]

缓解方式各自有代价。其一是不要立即复用同一地址语义：把弹出的节点标记为删除、延迟释放或交给隔离区，代价是内存占用上升；其二是把版本计数与指针打包成更宽的原子量，每次修改递增版本，“值相等但版本不同”就不再是同一个 ABA 情形，代价是这类更宽的操作未必无锁（用 `is_lock_free()` 查询），[339] 还会遇到版本回绕与对齐／高位可用性的实现依赖；其三是在算法层面避免“取出后重新比较同一指针”的用法，或改用不依赖单字比较交换的原语。

结论是 ABA 源自把值比较当作身份比较；把回收策略设计好通常比在比较交换上打补丁更根本。

</div>
</article>

<article class="qa-item" id="qa-safe-reclamation" data-level="principle" markdown="1">
<p class="qa-question">Q80 · 无锁结构里节点什么时候才能安全释放？hazard pointer、引用计数与 RCU 各适合什么？</p>
<div class="qa-answer" markdown="1">

无锁结构要把“逻辑移除”和“物理释放”分开：一个读者可能刚读到指针就被换出，任何写者都无法仅凭自己的状态确定再没有别的线程会访问这个节点。直接释放会让并发读者访问已释放内存，这是无锁代码最常见的缺陷，也是 [ABA 问题](#qa-cas-aba) 之外的另一个回收问题。

三类常见策略的取舍不同。引用计数（例如 `shared_ptr`）让每个持有者参与计数、最后一个释放，问题是“读指针并增加计数”必须是原子的，否则窗口仍然存在，通常需要更宽的原子操作或专门的 hazard 机制，并且每次访问都有原子操作与缓存行争用成本。hazard pointer 让读者在访问前把自己的引用发布到本线程的 hazard 槽，回收者扫描所有槽确认无人引用后再释放：[300] 读者侧是发布加屏障、不需要原子读改写，适合读多写少的结构，代价是每线程固定槽位、回收时要扫描，且发布顺序必须正确。RCU 让读侧几乎零开销（读侧临界区不能阻塞），写者更新指针后等待所有先前读者离开宽限期再释放，[301] 适合读极多写极少且能容忍短暂陈旧视图的数据，代价是宽限期与延迟回收的实现负担。

选择依据是工程判断而不是规范结论：读侧能否阻塞、读者是否必须看到最新值、可接受的回收延迟与内存上界、是否已有可用的库实现。无论选哪种，内存序都要配合：发布新节点用释放语义，读者首次读取用获取语义，否则即使回收正确也可能读到尚未初始化完成的字段。[16]

</div>
</article>

<article class="qa-item" id="qa-future-capacity" data-level="scenario" markdown="1">
<p class="qa-question">Q81 · future、线程池和有界队列分别承诺什么？请求超时是否等于任务取消？</p>
<div class="qa-answer" markdown="1">

future 提供结果和错误的共享状态接口，不必对应专有线程。线程池复用执行资源，工作线程数约束同时执行的任务，却不自动约束排队闭包、输入缓冲区和结果对象的总内存。有界准入层管理接收容量；只有容量定义覆盖了相应状态，才有助于限制在途工作的占用。[2, 4–5]

客户端停止等待或请求超时，不表示工作线程中的函数已经终止。尚未接收、已经排队、正在执行和外部副作用已经发生，是不同的取消边界。清除排队任务不终止运行中任务，更不能撤销已提交的数据库写入；释放请求上下文前，还需要确认后台工作是否继续借用其中的数据。

在满足稳定、有限平均量等条件时，Little 定律联系平均在途数量、吞吐与停留时间；持续增长的队列不能直接当作稳定状态测量。配额扣除和归还还须形成闭合协议：接收失败、任务异常、排队取消和正常完成各自都有一次性的归还路径。只在正常执行结束时归还，会使其他终态泄漏配额；过早归还则可能让仍在运行的任务失去容量约束。[4, 10]

</div>
</article>

<article class="qa-item" id="qa-thread-pool-tuning" data-level="scenario" markdown="1">
<p class="qa-question">Q82 · 线程池的线程数、队列容量与拒绝策略该怎样定？</p>
<div class="qa-answer" markdown="1">

三者必须一起定，因为线程池的行为由“何时建线程、任务如何排队、满了怎么办”共同决定。以 Java `ThreadPoolExecutor` 的文档化语义为例：提交任务时若运行线程数小于核心数就新建线程，否则入队；只有队列已满且线程数小于最大线程数时才再建线程，仍然满就交给拒绝策略。[337] 这直接说明“无界队列加最大线程数”里最大线程数不会生效（任务总是先排队），只有有界队列才会触发扩容与拒绝，因此队列容量的选择就是过载行为的选择。

线程数来自并发度而不是直觉。CPU 密集型任务的并行度受核数限制，等待型任务可以超过核数，但真正决定排队长度与延迟的是到达率与处理时间；用 Little 定律做一致性检查：<math><mi>L</mi><mo>=</mo><mi>λ</mi><mi>W</mi></math>，其中 λ 是到达率、W 是平均处理时间、L 是系统中的平均任务数，池容量与队列长度必须能容纳这个 L，否则就是拒绝或无限等待。[10]

拒绝策略是容量决策的一部分：直接失败把背压交给上游并让调用方看见；在调用者线程执行相当于自动降速，但会占用繁忙线程；丢弃最旧或最新适合可丢数据。选择取决于任务能否重试、延迟还是吞吐优先、上游是否有重试预算。无上限队列会把过载转化为内存增长与延迟堆积，比明确拒绝更难恢复。

最后是边界：池化不产生容量，只复用线程；下游（数据库连接、外部服务、磁盘）的容量通常更小，池大小应按下游配额决定；线程局部状态、任务嵌套提交与顺序性要求都会限制池的使用方式（同池等待需要单独分析）。

</div>
</article>
