<article class="qa-item" id="qa-redis-rdb-lifecycle" data-level="basic" markdown="1">
<p class="qa-question">Q214 · SAVE、BGSAVE 和自动快照怎样区分？启动时是否总优先加载 RDB？</p>
<div class="qa-answer" markdown="1">

SAVE 由相应服务进程同步生成快照，期间不能把普通请求处理当作照常进行；BGSAVE 通过 fork 后的子进程保存，父进程继续服务。子进程通常先写临时 RDB，成功后替换旧文件。自动保存依据配置的时间和修改量等条件触发，不是每次写入立刻落一份 RDB，也不是时钟一到就保证快照已经完成。[34]

fork 形成父子相应内存视图，写时复制让未修改页可以共享，父进程后续修改相应页时才产生分离副本。这提供快照状态的基础，而不是父子地址空间“从一开始完全不共享”。子进程稍后保存成功，也不表示文件包含父进程在完成前的所有新修改；状态边界与完成时刻要分开。

后台仍有成本：fork／页表处理可能造成停顿，页修改带来复制与内存峰值，子进程与父进程还共享 CPU 和存储等资源约束。进程方案有隔离作用，但不能由此推出子进程故障、磁盘满或系统内存不足永远不影响服务，更不能推出线程在原理上无法提供另一种快照协议。[34]

同时启用 AOF 和 RDB 时，正常启动按相应配置优先用 AOF 路径恢复，而非总加载 dump.rdb；7.0 起的多文件 AOF 还依赖清单和对应基础／增量文件，基础文件可以采用 RDB 格式。这是在 AOF 恢复中读取其基线，不等于独立 RDB 覆盖了 AOF 选择。[34] 文件存在、可加载、恢复到所需业务状态及满足损失窗口仍是不同判断。

</div>
</article>

<article class="qa-item" id="qa-redis-expiry-replication" data-level="principle" markdown="1">
<p class="qa-question">Q215 · 过期键怎样进入 RDB、AOF 和复制？从节点是不是自己随时删除过期键？</p>
<div class="qa-answer" markdown="1">

过期时间以绝对时间戳保存，服务器离线不会让 TTL 暂停。复制运行时，主节点的相应过期／淘汰决策沿复制流和 AOF 传播删除；固定 7.2.6 的 propagateDeletion 根据释放方式选择 DEL 或 UNLINK，并组织两条传播路径，而不是让各副本依自己的时钟任意改变复制数据集。[43,107,267]

副本仍保存过期元数据，某些普通读可把逻辑过期键看作不存在，同时等待主节点的删除来回收物理记录；主节点发送的写、加载及特殊标志路径不能一概按普通读处理。副本被提升后承担主节点的过期职责，所以“副本完全没有过期判断”与“副本总是独立物理删除”都不准确。[107,258]

RDB 是否包含一个已经到截止时间的键，也要区分保存、加载和版本。7.2.6 所核对的 rdbSaveDb 遍历现存字典项，取得过期时间交给 rdbSaveKeyValuePair 写入，并没有先按当前时间过滤所有项。因此物理上仍在字典中的过期记录可能进入文件，不能沿用所有版本的 RDB 保存都会忽略过期键的口诀。[267]

普通主节点加载独立 RDB 时，所核对条件会跳过相应已过期记录；副本接收主节点快照，以及加载 RDB 格式的 AOF 基线，则有不同条件。AOF 基线须给后续增量提供对应键空间，不能先按加载时钟随意删掉基础记录。纯命令格式的 AOF 重写路径也写现存值及其 PEXPIREAT，不能仅凭“重写”推出统一的预过滤规则。[267]

例如备份中键的绝对截止时间已经过去，普通恢复不会从备份保存时刻重新赠送一整段原 TTL；但“文件里有该键”不等于“普通恢复后还能读到该键”。时钟跳变、角色和加载格式都影响判断。这里核对的是固定源码选段和文档规则，没有执行恢复或时钟实验，也不把它提升为全部加载／传播路径的审计。

</div>
</article>

<article class="qa-item" id="qa-redis-psync" data-level="principle" markdown="1">
<p class="qa-question">Q216 · Redis 全量与部分重同步怎样工作？PSYNC、复制偏移和 backlog 有什么关系？</p>
<div class="qa-answer" markdown="1">

副本连接／重连后，以 PSYNC（partial resynchronization，部分重同步）携带已知复制历史 ID 和处理偏移，请求延续历史；初始数据无可延续基线、历史不匹配或缺口不在可用 backlog 内，就走全量重同步。旧 SYNC 只有全量能力，不能把它当成现代连接一律使用、以后永远只增量的固定流程。[107]

全量先取得数据集基线，接着补上生成和传送基线期间的变更，再持续应用复制流。常见磁盘路径生成 RDB、传送并加载；diskless 路径可由子进程直接发送而不先写中间 RDB 文件。父进程继续处理并缓存相应变更不等于全过程零停顿，fork、复制缓冲、带宽及副本加载仍有资源和时延代价。[107]

复制 offset 按流的字节进展计数，不是业务事务条数。相同整数只有结合相同历史才有意义。副本晋升后生成新的主历史 ID，同时保留旧 ID 及可接受偏移边界，以便其他副本在合法范围内延续旧历史；旧主若在分区另一侧继续写，不能因为偏移相同就把两条历史合并。

backlog 是有限的连续历史窗口，不是无限备份。若实际可用窗口为 B 字节，复制流平均产生率为正数 r、断连时长 T，理想稳定速率模型的缺口约为 rT，容量条件给出 <math xmlns="http://www.w3.org/1998/Math/MathML"><mi>T</mi><mo>≤</mo><mfrac><mi>B</mi><mi>r</mi></mfrac></math>。这说明为什么写流越快，同一窗口能容纳的断连越短；不保证满足这个估算就必定部分同步，历史匹配、窗口保留和真实速率仍需核对，也不能把配置字节数当作任何时刻的精确可重播范围。

复制默认异步，读副本要接受相应延迟；WAIT 按当前连接先前写入的偏移等待确认，不是全局读后写一致或磁盘同步屏障。7.2.6 在事务／脚本等不能阻塞的上下文中，WAIT 也不会按普通阻塞调用等待。返回值须检查，超时不能撤销已发生的写，故障切换仍可能选中不含该写的状态。[107,268]

</div>
</article>

<article class="qa-item" id="qa-redis-sentinel" data-level="principle" markdown="1">
<p class="qa-question">Q217 · Sentinel 怎样发现节点、判定下线并执行故障转移？quorum 是否就是选主多数票？</p>
<div class="qa-answer" markdown="1">

Sentinel 从配置的受监测主节点出发，用 INFO 等信息发现副本，通过受监测实例上的__sentinel__:hello 消息发现同组其他 Sentinel 并传播配置。它向客户端提供当前主节点定位，业务连接仍直接访问相应 Redis 实例，不把 Sentinel 当数据代理；也可监测多个主从组，但不是通用的 Cluster 分片管理器。[108]

监测不是瞬间知道机器已死亡：一段配置时间内没有可接受 PING 回复，某个 Sentinel 形成 SDOWN 主观判断；受监测主节点再汇集足够近期故障意见达到 quorum，才形成 ODOWN。此客观下线状态针对主节点，不是对所有副本／Sentinel 都套同一升级流程，网络故障和长阻塞也可能引发判断。[108]

quorum 用于故障判定，实施故障转移还须获得多数授权；quorum 高于多数时需要相应更高门槛。五个 Sentinel、quorum 为二，两份不可达意见可促成 ODOWN，但至少三份授权才足够执行相应切换。投票先授权一个 Sentinel 协调转移，不是所有 Sentinel 直接给业务副本投票、得票最多的副本必然晋升。

协调者先排除不适合的副本，再按优先级、已处理复制偏移、run ID 等规则选择；优先级零不被选为新主，较小的非零优先级先于单纯比较偏移。随后提升所选副本，重新配置其他副本跟随，并让客户端更新定位。优先级与偏移排序不能找回从未到这些候选的数据。[108]

旧主恢复后按当前配置改为副本，而不是自动恢复原主地位。Sentinel 能组织重新配置，不意味着网络分区中的旧主在任意瞬间都已停止接受业务；客户端路由、写入资格及异步传播仍有窗口。故障检测、授权、选择和数据持久性是不同步骤，不能把自动切换等同于不丢写。

</div>
</article>

<article class="qa-item" id="qa-redis-cluster-routing" data-level="principle" markdown="1">
<p class="qa-question">Q218 · Redis Cluster 怎样路由和迁槽？MOVED、ASK 与集群总线有什么区别？</p>
<div class="qa-answer" markdown="1">

Cluster 把键映射到 16,384 个槽，再维护槽到负责节点的映射，客户端据此直接连接目标。相应 CRC16 结果确定槽；有效 hash tag 让只取出的那段键名参与映射，例如同一 `{user42}` 标记的相关键可同槽。普通多键操作／脚本受同槽约束，但把很多业务都标成一个 tag 也可能制造热点。[44]

这与传统一致性哈希的环上节点／虚拟节点映射不是同一组织。固定槽给键到槽与槽到节点之间加了可显式调整的层，增减节点主要安排相应槽及其键迁移；它仍有迁移与元数据成本。哈希环也能与复制、故障协议组合，因此不能把是否有环说成是否具有自动故障恢复的根本原因，下面分析可见机制而非推断全部历史设计动机。

MOVED 提示节点所知的槽负责者，客户端重发并可刷新映射，不代表本次业务已经执行。迁移尚未结束时，源节点处于 MIGRATING，存在的键仍可在源处理；源处不存在的键用 ASK 临时引向 IMPORTING 目标。客户端在目标同一连接先发 ASKING，再发这次被重定向的请求，不永久替换后续槽路由，否则下一次可能错过还留在源的键。[44]

迁移工具逐步搬键，再完成槽归属及配置传播；大键会放大迁移阻塞、网络和内存成本，跨键操作在迁移期还可能遇到暂时错误。不能把新增一个空节点当成数据已经自动均匀搬完，也不能将所有超时当成原请求未执行后无限重试。

集群总线用于节点间心跳、故障意见、配置及相应传播，不是普通客户端命令流。Cluster 以自己的故障检测／副本授权等协议处理主节点故障；无可用合适副本时不能凭槽号生成丢失数据。网络分区的少数侧在相应超时后拒绝写，是限制风险并牺牲部分可用性，不是瞬间同步所有节点或回滚已确认写。[44] Sentinel 不提供一层通用的 Cluster 强一致修复。

</div>
</article>

<article class="qa-item" id="qa-redis-pubsub-stream" data-level="principle" markdown="1">
<p class="qa-question">Q219 · Pub/Sub、List 队列与 Stream 的投递边界有什么不同？XACK 表示业务只执行一次吗？</p>
<div class="qa-answer" markdown="1">

Pub/Sub 面向当前订阅关系推送，不保留断线后可补读的普通消息历史；接收端报错或断开，不能指望服务端重新投递，属于相应至多一次语义。它适合允许丢通知的即时传播，而不是仅凭 PUBLISH 成功就完成可靠任务。一客户端同时订阅匹配频道与模式，还可从不同关系收到同一发布的多条通知，至多一次不能读成应用永远看不到重复内容。[109]

List 弹出会将元素从原队列移走；若取出后、业务完成前消费者崩溃，单纯弹出没有待确认状态可供恢复。可设计转入处理中队列、成功后移除及超时重领，但这些是需要实现的协议；另一个方向，Stream 保存带 ID 的记录，普通读取与消费者组分工也是不同方式。

常规需要确认的消费者组读取，会把已交付项登记到 PEL 待确认列表；XACK 移除该组的待确认关系，不等于删除原 Stream 记录，更不提交外部数据库。只持续用 XREADGROUP 的 `>` 读新消息，不会自动处理所有旧 pending。XPENDING 观察相应状态，XCLAIM 或 6.2 起的 XAUTOCLAIM 可把闲置项交给另一消费者；闲置超时不是证明旧消费者死亡，原消费者仍可能恢复并继续业务。[110]

业务已提交、ACK 前崩溃，重领可重复执行；先 ACK、业务未提交就崩溃，则可能漏做。幂等业务键、去重记录与事实修改需在相应可靠事务／协议中协调，不能先单独写“已处理”标记就跳过尚未完成的工作。消息 ID 帮助定位，不自动建立这个外部提交边界。

持久化、复制、保留／裁剪、待确认恢复和毒消息处理还决定任务能否最终完成；记录被裁剪也不能仅凭 PEL 就保证原内容仍在。7.2.6 应使用其已有确认／认领能力，较新 8.2 的删除协调、8.6 的生产去重等能力不回填给它，生产去重也不直接证明业务副作用端到端恰好一次。[110]

</div>
</article>

<article class="qa-item" id="qa-redis-lua-boundary" data-level="principle" markdown="1">
<p class="qa-question">Q220 · Lua 脚本怎样原子组合命令？报错、超时或客户端断开会撤销已有修改吗？</p>
<div class="qa-answer" markdown="1">

Lua 脚本把检查与数据操作放进服务端的一次执行边界，普通客户端命令不能插入其中，因此能减少客户端多次读改写之间的竞态和往返。原子执行说明交错受到控制，不保证脚本要么全部成功、要么没有效果，更不提供跨 Redis 与外部服务的整体提交。[36,106]

固定 7.2.6 的脚本命令路径会检查权限等条件并调用实际命令；Lua 随后失败时，错误路径组织回复及清理执行上下文，不把已经执行的写入统一回滚。因此先写一个键、后因另一个键类型不符报错，前一个修改不能假定消失。redis.call 将相应错误抛给脚本，redis.pcall 把错误值交回脚本处理，也不会自动撤销之前的写入。[106,259]

应在写入前检查必要的参数、数据类型和业务条件，并约束后续可能失败的路径；这减少部分失败窗口，不证明任何资源故障都已消除。客户端超时或断开也不能代替结果确认，重发脚本可能重复修改，业务幂等需单独设计。EVALSHA 遇到缺失脚本要处理 NOSCRIPT／重新加载，不能把 SHA 身份当成已经执行成功的证明。

访问的键名应显式通过 KEYS 等输入声明，普通参数走 ARGV；不能任意从值中生成隐藏键名。在 Cluster 中还受同槽和路由等限制，脚本不会形成所有节点的全局事务。[44,106] 慢脚本阻碍相应处理，超过时长阈值也不是自动安全回滚；SCRIPT KILL 只能用于尚未修改数据的相应脚本。工作量应可控，外部副作用留给明确的可靠协议。[106]

</div>
</article>

<article class="qa-item" id="qa-redis-hotkey-memory" data-level="scenario" markdown="1">
<p class="qa-question">Q221 · Redis 只容纳事实库一小部分数据时，怎样尽量保留热点？大键、热点键和内存碎片是否同一个问题？</p>
<div class="qa-answer" markdown="1">

先判断请求集中在哪个工作集，而不是把能缓存的记录比例直接当命中率。LRU 近似近期访问，LFU 用概率计数和衰减近似频率，TTL 表达有效期；热点变化、容量和对象大小都会影响驻留。[33] 若数据几乎均匀随机，策略无法凭空创造一个很小的热门集合；若访问集中且热点能装下，小缓存也可能覆盖大量请求。

为分开条数、流量与内存，假定当前有效驻留集合固定为 S，一次请求指向记录 i 的概率为 pᵢ，所有记录概率总和为 1。忽略并发填充、失效及失败时，模型命中概率就是 <math xmlns="http://www.w3.org/1998/Math/MathML"><mi>H</mi><mo>=</mo><munder><mo>∑</mo><mrow><mi>i</mi><mo>∈</mo><mi>S</mi></mrow></munder><msub><mi>p</mi><mi>i</mi></msub></math>，因为命中恰是这些互斥记录事件之一。若各对象有固定可归摊占用 mᵢ，可用于这些对象的预算为 B，驻留还须满足 <math xmlns="http://www.w3.org/1998/Math/MathML"><munder><mo>∑</mo><mrow><mi>i</mi><mo>∈</mo><mi>S</mi></mrow></munder><msub><mi>m</mi><mi>i</mi></msub><mo>≤</mo><mi>B</mi></math>。共享余项及不能逐对象独立归摊的真实开销另算，这是解释模型，不是 RSS 容量测量。

只有在等大、均匀独立请求、恰好有效驻留 20 万条等理想前提下，2000 万条事实库的这个模型才给出 <math xmlns="http://www.w3.org/1998/Math/MathML"><mi>H</mi><mo>=</mo><mfrac><mn>200000</mn><mn>20000000</mn></mfrac><mo>=</mo><mn>1</mn><mo>%</mo></math>。现实的 pᵢ、可驻留对象与回源成本不同，所以不能把 1% 当实测命中或普遍上限；高代价对象也可能值得保留，目标未必只是最多命中次数。[264]

热点键是访问集中，大键是对象／回复数据量大；小计数可极热，大冷集合可少用。前者可能卡在单节点串行执行，后者放大扫描、拷贝、回复、迁移及释放；String 等类型也不能笼统说所有操作连同数据传输都恒定成本。读热点可合并请求或加局部缓存，代价是失效和陈旧度；拆对象改变操作与同槽约束，异步删除仍消耗后台工作和峰值内存，不是免费消失。

删除后分配器可能留页复用，RSS 不必立即下降；高 RSS／当前分配比值也可能由历史峰值及混合占用造成，不能仅据这个比值断言故障原因。[105] 元数据、复制／AOF 缓冲、输出和写时复制另有占用，因此 maxmemory 和有效载荷之和都不是整进程预算。调整策略后应按目标工作负载观察命中、尾时延、回源与内存，以上推导不宣称已经测得收益。
