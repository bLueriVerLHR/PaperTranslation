#### Redis 定位、数据类型与执行路径 {#interview-redis-foundations}

<article class="qa-item" id="qa-redis-purpose" data-level="basic" markdown="1">
<p class="qa-question">Q206 · Redis 除了缓存还能做什么？关系型与非关系型数据库能否按“慢而一致／快而不一致”分类？</p>
<div class="qa-answer" markdown="1">

Redis 是以键定位数据、提供数据结构命令的服务，除了缓存，还可保存计数、会话、集合关系、排行榜、限流状态或事件流。选择它的理由应是访问形态和恢复要求匹配，而不是“在内存里就一定快”。短命令访问热数据可以少走存储访问和应用端整对象处理，但网络往返、大对象扫描、慢脚本、持久化及输出压力仍会影响时延。[104,106]

可重建缓存丢失后能从事实来源重新生成；若 Redis 是唯一事实存储，丢失、提前淘汰或重复执行就可能直接改变业务结果。后者必须另行约定持久化、备份、复制和失败处理，不能沿用允许任意逐出的缓存配置。noeviction 也只改变容量压力下的处理，不代表已经获得不丢数据的持久性。[33–34]

关系模型用表、关系、连接与约束组织数据，非关系模型则包含键值、文档、宽列和图等不同选择。数据模型、事务接口、隔离、复制及扩展是不同维度；关系数据库也会缓存热页，Redis 也有持久化和原子操作，所以 SQL／NoSQL 不能被直接分成“慢而一致／快而不一致”。比较应先固定操作和故障语义，再比较相应产品。[34,36,97]

例如排行榜按成员查分数、按分数查区间，ZSet 比反复取出整个 JSON 再排序更贴近目标操作；这不保证任何规模都更快，也不提供与数据库订单的跨服务原子提交。复制帮助保留副本，分片帮助分散键空间，两者也不自动消除写入丢失或热点。数据结构和部署方式减少的是特定成本，业务不变量仍需自己的协议。[44,104]

</div>
</article>

<article class="qa-item" id="qa-redis-types-encodings" data-level="basic" markdown="1">
<p class="qa-question">Q207 · String、Hash、List、Set、ZSet 和 Stream 怎样选？数据类型是否等于底层编码？</p>
<div class="qa-answer" markdown="1">

先按需要执行的操作选择类型，而不是把所有对象都序列化成一个大字符串。Redis 7.2.6 已有的常见模型可以这样区分：[104]

| 类型 | 语义与典型用途 | 不能顺带推导的保证 |
|---|---|---|
| String | 字节序列；整体值、缓存对象或符合数值命令要求的计数 | 不要求是自然语言文本，也不是任意字符串都能 INCR |
| Hash | 字段—值映射；对象属性和局部字段更新 | 不等于关系表、任意嵌套对象或每个字段都支持该版本的独立 TTL |
| List | 有序字符串序列、两端操作；任务候选队列 | 弹出成功不等于消费者完成，也不自动提供崩溃后确认协议 |
| Set | 不重复成员及集合运算；标签、成员关系 | 不承诺成员排序或按分数排名 |
| ZSet | 唯一成员关联分数；排行榜、范围和名次 | 分数可以重复，同分还要按成员次序区分 |
| Stream | 带 ID 的追加记录和消费状态；事件处理 | 确认与外部业务提交不是同一个动作 |

类型是接口语义，编码是内部布局。同为 Hash，小对象可以紧凑保存，大对象改用字典；不能因为命令叫 Hash 就推断每个对象内部永远是一张哈希表。阈值涉及元素数量和大小，越界转换需要工作，紧凑布局也可能以扫描／搬移换取更少指针和分配。[105]

Redis 7.0 的 Hash／ZSet 紧凑配置使用 listpack，7.2 还增加 Set 的相应 listpack 配置；旧 ziplist 规则不能跨版本直接套用。Bitmap／Bitfield 是对字符串的位级操作，HyperLogLog 用于近似基数，GEO 提供地理查询语义；是否是独立键类型、值的内部编码和命令能力仍应分别看。最新文档中 JSON、向量及其他扩展的导航项，不证明旧版标准实例都具备它们。Hash 字段过期等新能力也不能回填给 7.2.6。[104–105]

<article class="qa-item" id="qa-redis-event-loop" data-level="principle" markdown="1">
<p class="qa-question">Q208 · Redis 的事件循环、I/O 线程和 serverCron 各做什么？请求怎样从字节变成命令？</p>
<div class="qa-answer" markdown="1">

按 Redis 7.2.6 的普通请求路径看，客户端字节先进入输入缓冲，协议解析形成命令与参数，再查找／检查命令、执行数据操作、组织回复并写出。一次 socket 读不必恰好得到一条完整命令，半条请求和多条请求都要靠缓冲与解析状态处理。文件事件保存相应描述符、就绪掩码和回调，事件循环借多路复用取得就绪集合，再调用相应读写处理；时间事件用于周期工作，两者不是为每条命令开一个线程。[114,260]

6.0 配置已经提供 socket 读写与读解析的 I/O 线程选项，不能把它解释为普通命令全部并行执行。[263] 固定 7.2.6 的 I/O 线程主要分担 socket 读写等工作；默认不启用多线程 I/O，启用后通常先分担写出，读与协议解析还受 io-threads-do-reads 配置控制。它不把任意慢命令或 Lua 计算搬到可并行执行的工作池。[257] 下面是 Redis 7.2.6 固定提交 `ae6a2aa95cd094b032e7a69b8b59f64dd1ed085f`，`src/networking.c` 2567–2571 行，`processInputBuffer` 内的原文摘录。处于相应读线程阶段时，它标记待执行命令并退出该轮，而不是直接在这里执行命令。[114]

```c
            if (io_threads_op != IO_THREADS_OP_IDLE) {
                serverAssert(io_threads_op == IO_THREADS_OP_READ);
                c->flags |= CLIENT_PENDING_COMMAND;
                break;
            }
```

该判断只把待执行状态交回相应阶段，不能据此把整个进程称为只有一个线程。后台线程可处理相应释放／I/O 工作，持久化子进程可以利用另一个核；多实例或分片还可分散独立键的负载。若瓶颈是同一热点上的串行计算，增加 I/O 线程不会自动解除它，分片也需要数据能被合理拆开。[257]

serverCron 在固定版本组织统计、客户端、数据库、持久化子进程及复制相关维护，频率与 hz 和动态调整有关。[117] 服务初始化注册的是周期维护的时间事件，过期处理再以预算分批推进，而不是对每个键创建准点删除的定时器。[258,260] 慢命令、大回复及脚本仍会占用执行或输出资源；该模型不推广为以后所有版本与模块的唯一实现，也不构成多核收益测量。

</div>
