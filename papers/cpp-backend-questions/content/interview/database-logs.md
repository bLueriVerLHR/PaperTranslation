#### 日志、复制与恢复 {#interview-database-replication}

<article class="qa-item" id="qa-mysql-query-path" data-level="basic" markdown="1">
<p class="qa-question">Q180 · MySQL 的 Server 层和存储引擎怎样协作？查询缓存还在执行链上吗？</p>
<div class="qa-answer" markdown="1">

MySQL 的 Server 层提供连接、认证、SQL 分析、优化和执行组织等公共服务，存储引擎负责相应记录、索引与物理存储操作。以一条普通 SELECT 为例，连接建立后，请求经过解析和名称／语义检查，优化器选择访问路径与连接顺序，执行器再按计划向引擎取记录，完成过滤、连接、聚合等操作并返回结果。这是职责划分，不意味着每条 SQL 都沿完全相同的物理步骤执行；预处理、优化改写和具体语句类型会改变细节。[92,96,239]

例如按订单索引查找记录时，Server 层决定采用哪个访问计划，InnoDB 执行相应索引访问并按其事务规则提供记录。事务、锁、MVCC 和崩溃恢复能力受引擎支持范围限制，不能因为 SQL 接口相同就认为换成 MEMORY 或 MyISAM 后仍保留 InnoDB 的全部保证。[92,237–239]

旧资料常在解析前画一个通用查询结果缓存，并描述表更新时使缓存结果失效；这不是 MySQL 8.0／8.4 的现行执行链。官方 MySQL 8.0 SELECT 文档明确说明查询缓存已移除，SQL_CACHE 也已移除，SQL_NO_CACHE 不再具有相应效果。[100]

查询结果缓存保存的是相应查询结果，InnoDB buffer pool 主要保存数据和索引页。即使页已在内存里，执行器仍要完成查询计算，引擎仍要处理相应可见性判断；页命中不等于直接返回此前同一 SQL 的结果。移除查询缓存也不等于移除 buffer pool，更不等于禁止应用在明确失效和一致性协议下使用自己的结果缓存。

</div>
</article>

<article class="qa-item" id="qa-mysql-memory" data-level="principle" markdown="1">
<p class="qa-question">Q181 · Buffer pool、连接级内存和刷脏怎样影响容量？缓存命中率高是否就没有性能问题？</p>
<div class="qa-answer" markdown="1">

Buffer pool 使 InnoDB 的热数据和索引页可以直接从内存读取。页被修改后成为脏页，随后按刷脏规则写回；它既不是只读缓存，也不是每次提交都立即写出全部修改页。[31,97] 替换采用带新旧区域的 LRU 变体：新读入页先放到旧区入口，而不是直接挤到最热端；再次访问及晋升时间条件影响它是否进入热区。默认旧区约占 3/8，扫描抵抗页给出的默认晋升保护窗口为 1000 毫秒。这能降低一次性扫描挤走工作集的风险，却不保证任何负载都不会污染缓存，也不是可直接照抄的调优结论。[240]

内存容量不能只看 buffer pool。还要计入日志缓冲、连接和线程状态、排序等活跃操作的工作区、临时结果以及其他组件。为避免重复相乘，可把同一时刻的分配粗分为互不重叠的几项：

<math display="block"><mrow><msub><mi>M</mi><mtext>预算</mtext></msub><mo>≈</mo><msub><mi>M</mi><mtext>共享</mtext></msub><mo>+</mo><munderover><mo>∑</mo><mrow><mi>i</mi><mo>=</mo><mn>1</mn></mrow><mi>C</mi></munderover><msub><mi>B</mi><mi>i</mi></msub><mo>+</mo><munder><mo>∑</mo><mrow><mi>j</mi><mo>∈</mo><mi>A</mi></mrow></munder><msub><mi>W</mi><mi>j</mi></msub><mo>+</mo><msub><mi>M</mi><mtext>余项</mtext></msub></mrow></math>

这里 C 是当前连接数，Bᵢ 是第 i 个连接不含活跃工作区的基础分配，A 枚举此刻活跃的操作，Wⱼ 是其工作区；共享项只计一次，余项留给未归入这些类别的开销。这是容量解释模型，不是进程常驻内存的精确恒等式。连接缓冲可以按需增长，排序也有自己的分配规则；一条复杂查询还可能有多个操作。把所有缓冲上限乘以 max_connections 可能高估实际常态，反过来只给每连接留一个固定小缓冲又会漏掉并发峰值。[242,253]

高命中率只说明相应页读取较少需要存储访问。大量内存扫描仍消耗 CPU，锁等待仍能阻塞请求，脏页和 checkpoint 推进也可能限制持续写入。放大缓存若挤压系统内存、引起换页，还可能恶化尾时延。容量预算、刷脏吞吐与提交持久性是不同问题，不能用更多 RAM 替代 redo／binlog 的相应持久化保证。[31,97,229–230,253]

</div>
</article>

<article class="qa-item" id="qa-logs" data-level="principle" markdown="1">
<p class="qa-question">Q182 · redo、undo 与 binlog 分别做什么？写了日志是否就不会丢数据？</p>
<div class="qa-answer" markdown="1">

InnoDB 的 redo 记录用于重做相应修改，支持数据页尚未全部写回时的崩溃恢复；undo 支持撤销，并为一致性读重建某些历史版本；MySQL 服务层的 binlog 保存变更事件，用于复制及配合备份进行日志恢复。redo、undo 与 binlog 的层次、格式和保留目标不同，不是三份可任意互换的同一日志，也不是把所有日志都永久保存便得到完整备份。[31,45–46]

预写日志要求在相关脏页写回之前，先使所需重做信息达到相应持久状态；它将恢复信息的持久化与数据页最终写回分离，允许后者延后。产生 redo、进入日志缓冲、写入日志文件和完成持久化同步是不同阶段，不能把事务修改一产生就理解为一次独立磁盘写入。[31]

MySQL 8.4 的 `innodb_flush_log_at_trx_commit` 控制提交相关的日志写入与同步，常见区别如下。[229]

| 值 | 提交及周期处理的区别 | 需要注意的边界 |
| --- | --- | --- |
| 0 | 周期性将日志缓冲写出并同步 | 最近尚未写出或同步的事务可能因崩溃丢失 |
| 1（默认） | 提交时写出并同步相关日志 | 仍依赖操作系统和设备正确履行同步承诺 |
| 2 | 提交时写出，周期性同步 | 写入文件或操作系统缓存不等于已经抗掉电 |

0、2 的周期默认约一秒，但调度及其他刷出活动使它不是精确频率或严格损失上限。组提交可以让一组提交共享相应同步工作，因而高并发优化不必然等于降低持久性，也不能把设置 1 解释成每个事务都独占一次物理刷盘。[229]

开启 binlog 时还要单独考虑 `sync_binlog`：0 由操作系统安排同步，1 在提交前同步相应提交组，较大的 N 按 N 个 binlog 提交组同步，而不是简单按 N 个事务计数。引擎与 binlog 的协调、存储设备是否诚实报告完成、故障是进程退出还是掉电，以及复制确认的阶段，共同决定已经向客户端确认的结果能否保留。“写了日志”或“收到复制事件”都不足以单独证明不会丢失。[229–230]

</div>
</article>

<article class="qa-item" id="qa-mysql-replication-path" data-level="principle" markdown="1">
<p class="qa-question">Q183 · MySQL 主从复制的流程和三种日志格式是什么？为什么副本会有延迟？</p>
<div class="qa-answer" markdown="1">

MySQL 的传统复制以源端 binlog 为变更流，副本先接收，再应用。源端须启用相应二进制日志，复制拓扑中的 server_id 应唯一；副本还要有可访问的源端连接及与初始化数据对应的起点。MySQL 8.4 默认开启 binlog，但启用日志不等于所有 SQL 都产生复制事件，读取和被排除的事务不能一概算入。[46,250,252]

复制连接建立后，源端的 binlog dump 线程发送事件；副本 I/O 接收线程把事件写入 relay log；应用端再读取这些事件并执行相应变更。单线程应用是一种配置，多线程副本则由协调线程分发事务、worker 执行，不能把所有版本和配置都画成固定的“两线程”。收到、写文件、同步到持久存储和应用后可查询是不同进度。[249]

日志文件名与位置标识流中的起点；使用 GTID 时，事务身份及已执行集合有助于判断哪些事务还需复制，同一 GTID 在已提交后会被自动跳过。常见未带标签的 GTID 由来源 UUID 和事务序号组成，8.4 也支持带标签的形式。GTID 不提供缺失的初始数据，不补回已经清除而仍需读取的日志，也不自动给业务请求建立幂等性。[250]

语句格式重放 SQL，日志可能较紧凑，但非确定性或执行上下文差异需要处理；行格式描述行修改，更直接表达数据变化，大批量修改则可能产生很多事件；混合格式按规则在两者之间选择。MySQL 8.4 默认行格式，切换格式的相关配置已进入弃用方向，旧版三种格式不是未来版本永久不变的承诺。[98]

延迟可以积在接收侧，也可以积在应用侧。网络或带宽受限、源端大事务、副本存储／CPU 能力、锁等待与事务依赖，都可能限制追赶。若瓶颈是应用端等待同一热点记录，增加接收带宽并不能解除它；增加 worker 也受可并行事务和资源约束。排查应分别确认连接及日志进度、应用错误和资源等待，而不是只看“线程正在运行”。读写分离中的写后立即读需要源端读取、等待所需应用进度或其他明确协议，分担读取不会自动保留会话一致性。[98–99,249]

</div>
</article>

<article class="qa-item" id="qa-mysql-semisync" data-level="principle" markdown="1">
<p class="qa-question">Q184 · 异步、半同步与同步复制有什么区别？半同步是否保证副本已完成事务？</p>
<div class="qa-answer" markdown="1">

异步复制不以获得副本确认作为源端提交返回的前提，因此客户端已收到成功时，副本仍可能没有相应事务。若源端故障并提升落后副本，未复制到该副本的已提交变更可能丢失。MySQL 半同步则按配置等待所需数量的副本确认：相应事件已写入并同步到它们的 relay log；不要求已在副本执行和提交，所以确认后立即读副本仍可能看到旧值。[99]

半同步的等待点还要区分。AFTER_SYNC 在源端 binlog 同步之后、存储引擎提交之前等待副本确认；AFTER_COMMIT 先完成源端引擎提交再等确认，此时其他客户端可能已经看到源端变更，而提交客户端尚未收到成功。这两个顺序影响故障与切换边界，不能仅凭“等过 ACK”就推断同一种源端可见性。[99]

确认超时可以退回异步，而不是必然撤销刚才的事务。因此开启半同步不代表每次提交都得到相同保护。还必须明确确认数量、当时的工作状态、哪些副本持有所需日志，以及选出的副本如何应用到目标进度；任意提升一台落后副本仍不能宣称零丢失。旧源端重加入也需处理分歧和重复执行，不能只恢复网络连接。

“同步复制”不是足够完整的保证名称：是等待日志持久化、等待事务应用，还是按成员与故障模型达成某种一致性协议，需要分别说明。等待更多副本通常增加跨节点延迟与故障耦合，本地刷盘、复制确认和业务可读性也各有边界；不能用一个同步开关同时替代这些判断。

</div>
</article>

<article class="qa-item" id="qa-database-backup-recovery" data-level="scenario" markdown="1">
<p class="qa-question">Q185 · 备份、复制、redo 和 binlog 怎样配合恢复？有副本为什么还需要备份？</p>
<div class="qa-answer" markdown="1">

复制维护跟随变更的副本，备份保留可恢复的历史基线，两者目的不同。误删和错误更新通常也会被复制过去，因此健康副本可能忠实保留了错误结果；它可以帮助故障切换，却不能代替历史恢复点。redo 主要用于引擎崩溃后恢复相应页与事务状态，binlog 表达可复制／重放的变更，两种日志都不是完整备份的通用替代品。[31,46]

MySQL 的时间点恢复通常先恢复目标之前的完整备份，再按正确顺序应用备份之后的 binlog，把状态推进到选定事件边界。备份和日志起点必须对齐，所需日志必须完整可用。以误删为例，先确定误操作附近的事件位置，再选择安全停止点；不能仅凭大致时钟时间盲目截断事务，或从任意日志位置开始重放。备份工具提供的位置也不能随意替换成恢复时 InnoDB 显示的位置，后者可能遗漏较晚的 DDL 或非 InnoDB 变更。[244]

跳过错误操作后继续回放后续事件，还可能遇到依赖被跳过结果的变更。这是恢复方案需额外核对的业务语义，不是“删掉一行日志就回到正确状态”的保证。逻辑备份表达模式和数据，物理备份保存相应存储文件与恢复状态；兼容性、生成成本和恢复路径不同。并发写入下的一组普通文件副本，不自动构成一致备份。

恢复方案应明确可接受的数据损失窗口和恢复时间，也要覆盖权限、对象定义与应用版本。备份存在、文件校验通过和完整恢复演练是不同证据，前两者不能证明恢复出的系统可用。本篇只说明机制，没有对真实数据库执行备份、日志重放或故障恢复。

</div>
</article>

<article class="qa-item" id="qa-replica-read-consistency" data-level="scenario" markdown="1">
<p class="qa-question">Q186 · 读写分离后，为什么刚写入就读不到？该怎样保证关键读取的一致性？</p>
<div class="qa-answer" markdown="1">

复制默认是异步的：主库提交后立即向客户端返回，从库按自己的进度重放，因此从库上存在一个“还没追上”的窗口，窗口长度取决于主库写入速率、从库回放能力与网络。[145] 读写分离把读请求发到从库后，用户的“我刚提交”就可能读不到，这不是数据丢失，而是读取位置落后于写入位置。

可用的对策按代价递增：把写完立即需要读的请求固定走主库（例如写请求返回时带上标记，或对同一会话短时间内强制读主库），代价是这部分读没有扩展收益；从库上按 GTID 或位点等待追到指定位置再读，代价是延迟不可控且可能超时；用会话粘性或分片键把同一实体固定在同一节点，减少跨节点可见性问题。任何一种都要明确“最终一致”的时间上界，并给业务提供补偿查询路径，而不是只在客户端加重试掩盖。

判断与监控要对齐复制状态：看从库的延迟指标与复制线程状态，并把延迟与业务时段关联；长事务、大事务、DDL、单线程回放与从库上并发的读压力都会拉长窗口。[145] 报告问题时区分“复制延迟”“读到了旧快照”与“应用缓存未失效”三种情形：前者看从库的复制位点与追平时间，中者看读视图或事务的建立时机，后者看缓存键与失效记录；三者的证据不同，处理方式也不同。

</div>
</article>
