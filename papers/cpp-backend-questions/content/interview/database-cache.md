#### 缓存与 Redis 应用 {#interview-cache}

<article class="qa-item" id="qa-redis-concurrency" data-level="basic" markdown="1">
<p class="qa-question">Q197 · Redis 的命令执行具有串行性，为什么应用仍会出现并发错误？</p>
<div class="qa-answer" markdown="1">

串行处理单条命令，不等于串行处理一个客户端的整段业务。假设初值 10，A 执行 GET 得到 10，B 也得到 10；A 算出 11 后 SET，B 最后又 SET 11。服务端每条命令都顺序执行，最终仍只体现一次加法。这是客户端拆开的读改写发生交错，不是 Redis 内部同时修改同一结构造成的数据竞争。[36]

若需求就是整数加一，可直接使用 INCR。没有其他改值、过期或失败，且数值在支持范围内时，两次成功 INCR 把 10 推进到 12，不应沿用“多个客户端使用 INCR 也会因并发丢失更新”的说法。String 只是载体，数值命令还要求内容可解释为相应整数，并有类型、溢出及容量错误边界。[261]

多步条件可以用 WATCH 后的重新读取与有条件 EXEC，或者用脚本把检查和修改放进一个执行边界；只给一串盲目写入套 MULTI，也不能补回在此前读取时丢失的条件。超时后的重试又是另一层问题：第一次 INCR 已生效而回复丢失，重发可能多加一次，原子递增本身不提供业务请求去重。[36,106]

固定 7.2.6 的普通命令执行、I/O 线程、后台线程和持久化子进程各有不同职责，不能把整个进程概括成一个线程，也不能把 I/O 并行推成任意命令并行。[114,257] 大集合、慢脚本和大回复仍会形成排队／输出压力；单命令原子性也不能跨 Redis 与数据库建立整体事务。

</div>
</article>

<article class="qa-item" id="qa-expiry-eviction" data-level="basic" markdown="1">
<p class="qa-question">Q198 · 键过期与内存淘汰有什么区别？设置 TTL 是否意味着准点回收内存？</p>
<div class="qa-answer" markdown="1">

过期回答“键是否仍在有效期内”，淘汰回答“容量压力下保留哪些键”。TTL 到期后，逻辑有效性与物理清理不必同刻发生；主节点相应访问路径检查过期状态，主动过期则以预算分批检查和回收，并非为每个键设置准点删除的定时器。Redis 7.2.6 还区分快／慢主动周期，其工作量受配置和时间预算影响，不能把旧资料的固定 100 毫秒当成每个键的回收保证。[43,258]

因此“24 小时后是否过期”应先明确问的是截止时间判断，还是内存已释放。相应时间判断成立时，普通访问可以把逻辑过期键视为不存在，即使它的物理记录尚未回收；时钟、角色和特殊访问上下文另有条件。反过来，内存淘汰可以删除仍未过期的缓存，所以 TTL 也不是保证至少驻留那么久的租约。[258]

7.2.6 的主要淘汰选择可以分成候选范围与近似选择规则：[33,257]

| 配置族 | 候选及选择 |
|---|---|
| allkeys-lru／allkeys-lfu／allkeys-random | 从全部相应键中按近似近期访问、频率或随机选择 |
| volatile-lru／volatile-lfu／volatile-random | 只从带过期时间的键中采用相应规则 |
| volatile-ttl | 只从带过期时间的键中优先选择剩余 TTL 较短的候选，也是近似选择 |
| noeviction | 不为容量压力逐出键，相关需要更多内存的命令会失败 |

maxmemory-policy 是选择这些行为的配置项，不是与 LRU 并列的第五种算法。volatile 族没有合格候选时，不会自动回收任意永久键；noeviction 也不等于所有读写都停止。LRU 不是每次都给全部键作精确排序，而是从采样候选中比较访问历史；LFU 也用压缩的概率计数与衰减近似近期频率，不是保存完整的永久访问总数。采样更充分或保留更多历史仍有成本，二者都不能预知未来热点，TTL 更短也不必代表业务价值更低。较新文档的 LRM 等策略不回填到 7.2.6。

复制与 AOF 等缓冲可占用不计入淘汰比较的内存，逐出本身还会产生需要传播的变更；maxmemory 不是整个进程 RSS 的硬上限。[33] 分配器留存及后台释放也影响何时交还物理内存。策略应与可重建性、有效期和失败处理一起选择，业务唯一事实不能因“省内存”而被当成任意可逐出的缓存。

</div>
</article>

<article class="qa-item" id="qa-persistence" data-level="principle" markdown="1">
<p class="qa-question">Q199 · RDB 与 AOF 的恢复方式和代价有什么区别？AOF everysec 是否是绝对的一秒保证？</p>
<div class="qa-answer" markdown="1">

RDB 保存一个状态快照，恢复时加载该状态；AOF 保存重建状态的基线及后续变更，恢复时按其结构重建。单独 RDB 通常会丢掉最后有效快照之后未另行保存的修改；AOF 的风险窗口取决于同步策略和实际持久边界。不能把它们分成“RDB 一定丢／AOF 一定不丢”，文件大小和恢复速度也受数据量、格式及重写状态影响。[34]

Redis 7.0 起使用多文件 AOF：清单组织基础文件和增量文件，基础可为 RDB 或 AOF 格式。重写根据当前数据生成新的基线，例如计数已加一百次，重建当前值通常不必再保留这一百个历史动作；它不是复制旧日志或提供完整审计历史。重写期间父进程继续写相应新增量，完成后通过新的清单协调切换，不能只取一个看起来最新的文件作为完整备份。[34]

追加到用户态缓冲、写给内核和同步到持久存储是不同阶段。appendfsync always、everysec 和 no 分别采用相应每批同步、周期同步或交由操作系统安排的取舍；always 也有组提交，不必等于每条命令单独一次 fsync。everysec 以约一秒更新风险解释常见情形，但 I/O、调度、其他配置和故障类型仍有边界，不是所有故障最多丢精确一秒的承诺。[34]

后台快照／重写借助子进程和写时复制，父进程写入相应页时增加复制与内存占用；fork、页表和存储竞争仍会影响资源。RDB 较紧凑、AOF 常有更多持续写入，是典型取舍而非实测倍率。持久化文件损坏、空间耗尽和恢复策略也要处理；持久化、历史备份与故障切换分别解决不同问题，误操作也可能进入两种持久化状态。

</div>
</article>

<article class="qa-item" id="qa-redis-transaction" data-level="principle" markdown="1">
<p class="qa-question">Q200 · Redis 事务、WATCH 和 pipeline 分别提供什么？失败会全部回滚吗？</p>
<div class="qa-answer" markdown="1">

MULTI 让后续相应命令先入队，QUEUED 表示排队而非已完成业务修改；EXEC 再顺序执行，其他客户端命令不插在这一执行批次中间。DISCARD 在执行前丢弃队列，不是执行后的撤销操作。客户端在 EXEC 前断连与 EXEC 已被服务端处理、只是回复丢失，也不能按同一种失败恢复。[36]

WATCH 提供乐观条件检查。需要先 WATCH 相关键，再读值并计算，随后 MULTI 入队修改并 EXEC；若在观察窗口内发生相关变化，EXEC 返回相应空结果而不执行该批，客户端重新读取后决定是否重试。WATCH 不会锁住键阻止别人写。7.2.6 也把相应过期／淘汰计入这种变化，旧版本 6.0.9 之前的过期例外不能照搬；观察和队列状态属于连接，连接复用必须正确收尾。[36]

错误有两个关键阶段：入队时发现参数数量等错误，现代版本会在 EXEC 拒绝该事务；执行时才遇到类型错误，则返回各条命令的结果，其他已排队命令仍会执行，先前成功修改不统一回滚。不能只看 EXEC 返回了数组就认定每项成功，也不能把错误回复当成整批完全无效果。[36]

Redis 确有这种隔离的执行边界，但没有通用运行时回滚，持久性还取决于配置。因此“原子执行”等于“所有命令都成功”及“Redis 事务完全没有任何隔离性”都是不准确的概括。用户业务的不变量必须结合类型、参数、错误及重试设计，不能用事务名称代替 ACID 各项判断。

pipeline 把多个请求先发出，再统一取回复，以减少逐条等待的网络往返；只成批发送不保证与其他客户端不交错，也不保证错误时撤销整批。若下一条请求取决于上一条返回值和客户端计算，也不能只靠盲目管线化消除该依赖；批量过大还会增加排队回复的内存。[262] 可把事务命令管线化以减少等待，但隔离来自事务而不是 pipeline；脚本、Cluster 同槽及跨服务关系仍需分别定义。[36,44,106]

</div>
</article>

<article class="qa-item" id="qa-replication-cluster" data-level="principle" markdown="1">
<p class="qa-question">Q201 · 主从复制、Sentinel 和 Cluster 是同一套高可用机制吗？</p>
<div class="qa-answer" markdown="1">

不是同一层。复制维护数据副本，Sentinel 监测一个或多个主从组并协调故障切换，Cluster 则把键空间分给多个主节点，并使用自己的节点通信及故障处理。[44,107–108]

| 机制 | 主要职责 | 不自动提供 |
|---|---|---|
| 主从复制 | 全量／部分同步与持续传播，可分担允许陈旧的读 | 仅靠复制自动选主、全局分片或绝不丢写 |
| Sentinel | 主节点定位、故障判断、切换授权及重新配置副本 | 业务请求代理、键分片或同步复制 |
| Cluster | 16,384 槽的归属、客户端路由、迁槽与相应故障转移 | 单热点自动分散、跨槽通用事务或所有分区均可写 |

更多副本可扩展部分读能力，不等于增加单主写能力；更多分片也要求键和负载能被拆开。hash tag 让相关键同槽，可满足相应多键操作条件，却可能集中热点。副本传播不替代保留历史、抵抗误操作的备份，故障检测也不证明最新状态已保存。

主回复成功后，变更尚未到候选副本就故障，提升副本仍可能丢失已确认写。WAIT 按当前连接先前写入等待相应副本确认，应检查返回数量；超时少于目标不撤销已经执行的写，也不是各副本都完成持久同步或始终选择这些副本的保证。[268]

限制写入所需的副本数／滞后可约束部分风险窗口，但并非逐笔同步提交；缩短故障检测时间也有误判／抖动代价。[107] Sentinel 不是给 Cluster 补出“全局只能有一个主”的修复层——Cluster 本来就允许多个各负责槽的主节点。持久化、备份、监测和拓扑维护要分别审查，不能用部署名称代替数据损失与可用性约定。

</div>
</article>

<article class="qa-item" id="qa-cache-failures" data-level="scenario" markdown="1">
<p class="qa-question">Q202 · 缓存穿透、击穿与雪崩的流量形态分别是什么？</p>
<div class="qa-answer" markdown="1">

穿透常指反复请求事实来源中不存在的对象，缓存也没有可命中的结果，每次都回源；击穿通常是一个真实热点的缓存失效，大量并发请求同时重建；雪崩则是大量键集中失效、被清除，或缓存服务整体不可用，许多请求一起压向后端。普通冷启动未命中与恶意不存在请求也要区分，不能把所有 miss 都叫穿透。[11–12]

负缓存把“已查询且不存在”保存成可辨认的结果，不能与“还没查到缓存”使用同一个空值约定。有限 TTL 限制新增对象被旧负结果遮住的时间，也需要处理新增后的失效、不同租户／查询条件及错误响应。布隆过滤器可由应用或合适扩展维护；若正确包含全部可存在对象，阴性可挡掉部分无效查询，阳性仍可能误判而需回源。漏插、错误删除或同步落后会破坏这个前提；它判断的是维护的对象集合，不是精确判断此刻缓存命中。预热真实热点也不会消除无限新增的无效键。[269]

击穿可先查缓存，miss 后合并同键重建：一个请求回源，其他请求等待或读取允许的旧值；取得重建资格后还应再查一次，避免前一个请求已经填好却重复查库。等待有上限，重建报错要结束相应等待并清理状态，多实例还要明确合并范围。NGINX 的 cache lock 提供同键填充和等待的具体例子，但超时／lock age 也可能放行后续请求，不能据此承诺任何情况下都只有一次回源。[266]

刷新可把重建提前，随机 TTL 可分散计划性集中失效，局部缓存可保留一部分可接受旧数据；它们分别有后台峰值、失效传播与陈旧度成本。缓存整体故障时，随机 TTL 无济于事，应限制全局回源并发与等待、熔断／降级，必要时拒绝低价值请求，而非让每个 miss 无限重试。对同一个热点键只改变哈希路由，通常也不会把它自动摊到多个节点。

容量、预热和多级缓存是按工作集作的选择，不保证热点永远在场。应一起观察命中、回源并发／时延、等待超时及失败，检查保护是否把压力转移到另一资源。这里的负载与故障交错是机制分析，不是某个生产环境的实测故障比例。

</div>
</article>

<article class="qa-item" id="qa-cache-consistency" data-level="scenario" markdown="1">
<p class="qa-question">Q203 · 更新数据库后删除缓存，是否就能保证强一致？普通事务能原子更新两者吗？</p>
<div class="qa-answer" markdown="1">

不能。普通数据库事务只提交它管理的事实数据，不会顺带与另一个 Redis 服务原子提交。cache-aside 通常先查缓存，miss 时查事实来源并填充；更新先提交数据库，再使对应缓存失效。它免去直接双写两个新值的部分顺序问题，但官方模式说明也明确不保证缓存与事实库始终一致。[264]

删缓存若早于数据库提交，读者可在这段窗口查到旧数据并重新填入。即便改成提交后删除，仍有另一反例：读者先 miss 并读到旧值，写者随后提交新值并成功删除，最后读者才把旧值填回。每一步都成功也不能消除交错；从延迟副本回源、提交后崩溃或删除失败还会增加窗口。加版本号、读写分离或定时刷新本身都不证明窗口已关闭。

可靠失效应把“要通知什么”也纳入失败处理。例如同一事实数据库事务同时保存业务修改和 outbox 事件，提交后由 relay 发送失效通知，失败可重试，避免只在提交后临时发一次而丢失意图。仍需消息被最终送达、消费者正确处理，并处理重复／顺序；relay 在发送后、记录成功前崩溃就可能再发一次。这改善的是可恢复传播，不是立即同步的跨服务提交。[265]

版本化填充需要可信、可比较的业务版本，以及能原子拒绝旧结果的规则。仅对已有缓存值比较大小，删除后没有留下有效版本底线，旧读者仍可能被接纳；版本底线自身的丢失／淘汰也要处理。互斥方案则要求所有相关读写者使用同一协议，并正确处理租约失效，不能只给某个写路径套一把锁。

延迟双删希望再挡住一次较晚回填，但回填可能比第二次删除更晚，删除也可能失败，所以固定睡眠不是全时间安排的证明。TTL 能限制部分陈旧驻留，却不自动阻止持续从旧来源重新填充。若确实要求读后立即看到已提交的新值，应明确读写协调或绕过缓存，并核对事实来源自己的读语义；代价包括更多回源、等待和故障时的可用性取舍。上述反例与协议边界为条件性分析，未运行一致性实验。

</div>
</article>

<article class="qa-item" id="qa-distributed-lock" data-level="scenario" markdown="1">
<p class="qa-question">Q204 · Redis 锁为什么要带唯一令牌和期限？锁过期后旧持有者还能写资源吗？</p>
<div class="qa-answer" markdown="1">

两者解决不同问题：唯一令牌标识本次持有的所有者，使释放与续期只作用于自己的锁；正期限在持有者崩溃或长时间无响应时自动解锁，避免键被永久占用。在单实例模型中，`SET key token NX PX ttl` 把不存在检查、所有者令牌和正期限放进一条命令。若拆成 SETNX 成功后再 EXPIRE，进程在中间崩溃可能留下无期限键。令牌应在不同客户端／获取尝试之间足够唯一，不能大家都写同一个固定值；网络超时后也要考虑加锁已生效、只是回复丢失，而不能盲目认定未持有。[35]

释放必须原子比较当前令牌再删除。单独 GET 核对成功后再 DEL，中间可能租约失效并由别人重新取得，旧客户端就会误删新锁。7.2.6 可使用下面的教学脚本；较新文档的 DELEX 是 8.4 能力，不能回填给它。[35]

以下是适用于相应版本的教学 Lua 片段，用来解释原子比较删除，不是上游源码摘录：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
```

期限帮助回收无人释放的资格，却不能终止旧进程。例如 A 暂停到租约过期，B 取得新锁并写入，A 恢复后仍可能继续发出写请求。续期也须验证当前所有者并原子延长，不能把“进程还活着”当成锁仍有效；续期成功还不能撤销已飞行的旧请求，墙上时钟变化也是期限模型的边界。[35]

fencing token 针对这种延迟旧写：资源按可信单调资格号原子检查并写入，在接受较新资格后拒绝较旧资格的请求。检查与写入不能拆开，生成资格号与故障切换也不能允许回退；仅在客户端比较数字，或把随机解锁令牌称为 fencing 号，都不提供这一保证。它与业务幂等、当前资格验证等仍是不同协议要求。

异步副本还可能尚未收到锁键，原主就故障，提升后的副本向 B 授出锁，而 A 仍以为自己持有。持久化、更多副本或一次 WAIT 可改善某些风险，不能直接作为全故障模型下的互斥证明。[35,268] 应先判断锁用于减少重复成本，还是保护不能违背的不变量，再决定受保护资源必须承担什么验证。

</div>
</article>

<article class="qa-item" id="qa-redis-blocking" data-level="scenario" markdown="1">
<p class="qa-question">Q205 · Redis 为什么会“卡住”？慢命令、大 key 与 fork 各有什么表现？</p>
<div class="qa-answer" markdown="1">

Redis 的命令执行仍是串行的：7.2.6 允许网络读写由 I/O 线程并行，但命令在主执行路径上依次处理，一个命令执行期间独占这条路径，任何耗时较长的命令都会推迟其他客户端的请求（事件循环与 I/O 线程的分工见 [Redis 事件循环](#qa-redis-event-loop)）。因此阻塞通常来自三个方向：O(N) 命令在大集合上运行（`KEYS`、`SMEMBERS`、`HGETALL`、无限制的 `LRANGE`、带大量元素的 `SORT`／`ZUNIONSTORE`）、删除或过期巨大 key 时的释放开销，以及持久化与内存操作触发的 fork 及其写时复制带来的内存与延迟尖峰。[356]

诊断有专用入口：`SLOWLOG` 记录超过阈值的命令及其耗时，`LATENCY` 相关命令与延迟监控能把尖峰归因到具体事件（fork、过期循环、命令执行），`INFO` 的统计与内存指标可以看是否有巨大对象与分配峰。[356] 判断“是不是大 key”要按类型看元素数量与序列化大小，而不是只看 key 本身。

缓解要落到数据结构与访问方式：用 `SCAN` 系列分批遍历、用 `HSCAN`／`SSCAN` 替代整集合读取、用 `UNLINK` 或分批删除替代一次性 `DEL` 大集合、把大 key 拆分成多个子 key，并把过期时间打散以免集中过期。fork 与写时复制无法完全避免，但可以通过控制最大内存、减少写入频率（选择更合适的持久化策略与刷盘节奏）与留出内存余量来降低尖峰幅度；同时要给关键请求设置客户端超时与降级路径，避免一次阻塞放大成全站超时。[356]
