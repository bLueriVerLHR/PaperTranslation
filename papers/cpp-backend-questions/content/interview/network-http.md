#### HTTP、WebSocket 与消息边界 {#interview-network-http}

<article class="qa-item" id="qa-stream-framing" data-level="basic" markdown="1">
<p class="qa-question">Q141 · TCP“粘包／拆包”是什么？一次 send 为什么不对应一次 recv？</p>
<div class="qa-answer" markdown="1">

“粘包／拆包”指应用消息与读取批次不一致：多条消息可能一次读到，一条消息也可能分多次读到。TCP 提供有序字节流，没有承诺一次 `send` 对应一次 `recv`，所以这不是传输错误。发送缓冲、分段、接收缓冲与调度影响读写粒度，却都不能替应用定义消息边界。[25]（§2.2）

例如应用依次提交消息 A、B，接收端可能先读到 A 的前半部，再读到 A 的剩余部分连同 B；也可能一次读到 A+B。发送调用自身也可能只接受部分字节，发送方必须保存已提交位置并继续处理剩余部分。可读事件只说明某类读取能够推进，既不保证完整帧已经到达，也可能表示 EOF。[78]

常见分帧方式有固定长度、长度前缀和分隔符。固定长度要求双方约定相同记录尺寸；分隔符需要转义或明确禁止正文出现分隔符；长度前缀则要求约定字段宽度、字节序，以及长度是否包含头部。对长度为 L 的正文和固定 H 字节头部，解码过程是：

1. 累积至至少 H 字节，再读取长度字段；未收齐头部时继续等待。
2. 校验 L 的合法范围、最大消息限制和 `H+L` 的溢出，不因对方声明巨大长度就无条件分配。
3. 缓冲不足 `H+L` 时保留当前帧状态；足够时消费一帧，并继续解析已经到达的后续帧。
4. 遇到 EOF 时区分刚好结束于帧边界和未完成帧；同时限制累计缓冲、等待期限与输出积压。

关闭 Nagle 算法、增加发送间隔或一次提交完整对象，都不会把字节流变成消息流。序列化解决字段表示，分帧解决消息界限；格式本身已有可确定边界时可以复用它，但不能只凭“用了序列化库”就假定接收器无需保留状态。

</div>
</article>

<article class="qa-item" id="qa-http-methods" data-level="basic" markdown="1">
<p class="qa-question">Q142 · GET、POST、PUT、DELETE 与幂等有什么关系？重试是否一定安全？</p>
<div class="qa-answer" markdown="1">

HTTP 方法定义请求语义。安全方法的意图基本为只读，不是保证服务完全没有日志等副作用；幂等表示多次相同请求的预期服务端效果与一次相同。GET 等安全方法、PUT 和 DELETE 具有相应幂等语义，POST 不默认具有此保证。[26]（§9.2）

幂等不要求每次响应状态码相同，例如删除后再次删除可以返回不同状态，而最终资源状态一致。GET 与 POST 的差别也不是“一个明文、一个加密”；传输保护由 HTTPS 等机制提供，路径、请求体和日志分别还有暴露边界。

支付创建一类 POST 请求可以通过业务幂等键、唯一约束及一致的结果记录建立安全重试协议。连接在请求发出后中断时，客户端未收到结果不等于服务端没执行；避免重复业务动作依赖协议，而不是仅把失败请求再发送一次。

</div>
</article>

<article class="qa-item" id="qa-http-status-redirect" data-level="basic" markdown="1">
<p class="qa-question">Q143 · 常见 HTTP 状态码怎样解释？重定向、代理转发和 URL 编码有何区别？</p>
<div class="qa-answer" markdown="1">

状态码描述 HTTP 响应语义，不直接替代业务状态。200 表示相应请求成功，201 表示创建了资源，204 没有响应内容；304 用于条件请求中复用缓存，不是携带新正文的普通成功响应。400 表示请求问题，401 涉及认证挑战，403 表示拒绝，404 表示没有找到相应资源或不愿披露；500、502、503、504 分别涉及服务端错误、网关收到无效响应、暂时不可用和网关等待上游超时。[26]

重定向通过 Location 等信息让客户端另发请求，通常改变客户端可见的目标；代理或服务端内部转发由中间层处理，不要求浏览器重新导航。301／302 的历史行为允许部分客户端将 POST 改为 GET，303 引导到检索，307／308 保留方法与请求内容；301／308 与 302／307 的永久／临时语义也不同。不能把所有 3xx 都当作同一种可透明重试的跳转。

URL 百分号编码表达字节，不是加密。非 ASCII 文字需要明确字符编码与所在 URL 组件，再按规则编码；路径、查询与表单编码的规则不是完全相同，例如 `+` 不在所有 URL 位置都表示空格。URI 是更一般的标识概念，URL 强调定位；输入规范化、解码次数和权限判断不一致可能产生安全问题。

</div>
</article>

<article class="qa-item" id="qa-http-versions" data-level="principle" markdown="1">
<p class="qa-question">Q144 · HTTP/1.0、1.1、2 与 3 有哪些关键差别？HTTP/2 消除了所有队头阻塞吗？</p>
<div class="qa-answer" markdown="1">

HTTP/1.0 通常每次交换建立连接，也有持久连接扩展；HTTP/1.1 默认支持持久连接，并具有 Host、消息分帧等规则。流水线允许多个请求连续发出，但响应顺序会让前面的慢响应阻塞后续结果，所以流水线不等于独立多路复用。

HTTP/2 将请求和响应映射到独立流，在同一 TCP 连接上交错传送二进制帧，并用 HPACK 压缩字段。它减少 HTTP/1.x 的部分应用层串行约束，却没有消除 TCP 有序字节流的队头阻塞：前面的 TCP 数据丢失时，后续字节仍等待恢复，即使它们属于另一条 HTTP 流。[82]

HTTP/3 基于 QUIC。QUIC 对流分别组织有序交付，丢包通常只阻塞含有缺失数据的流，而不是要求所有流等待同一字节流的缺口；若一个丢失包包含多个流的数据，这些流仍会受影响。[85] 连接共享拥塞、资源和应用依赖也会造成相互影响，因此 HTTP/3 不等于“完全没有阻塞”。协议升级还要考虑部署支持、加密、代理和实际负载，版本号本身不是性能排名。

</div>
</article>

<article class="qa-item" id="qa-websocket-frames" data-level="principle" markdown="1">
<p class="qa-question">Q145 · WebSocket 与普通 HTTP 请求有什么区别？掩码、消息分片与 Ping/Pong 是什么？</p>
<div class="qa-answer" markdown="1">

WebSocket 在建立协议后提供持续的双向消息通道，服务端可以主动发送消息，不必为每条消息等待新的普通 HTTP 请求。RFC 6455 的常见 HTTP/1.1 路径通过 Upgrade 握手切换协议；它不表示所有后续消息继续按 HTTP 请求／响应格式交换。[83]

帧头包括 FIN、opcode、长度及相关标志，消息可以跨多个帧，续帧仍须按协议重组。客户端发送的帧必须掩码，服务端发送的帧不得掩码；掩码用于协议防护，不是加密，保密通道依赖 `wss` 等 TLS 保护。控制帧包括 Close、Ping 和 Pong，控制帧不能分片，负载最多 125 字节，并可穿插在分片消息之间。[83]

Ping/Pong 可以辅助活性检测，却不证明后端业务健康；接收方还要限制帧大小、完整消息大小、解压成本和排队量。WebSocket 有消息边界不代表任意大小消息都可以无条件缓冲，也不提供断线后的业务确认与自动去重。

</div>
</article>

<article class="qa-item" id="qa-http-framing-security" data-level="principle" markdown="1">
<p class="qa-question">Q146 · 消息长度歧义（Content-Length 与 Transfer-Encoding）为什么会造成请求走私？</p>
<div class="qa-answer" markdown="1">

HTTP/1.1 的报文边界由长度信息决定：有 `Content-Length` 就按它读取实体，用 `Transfer-Encoding: chunked` 就按分块编码读取；该规范同时规定了对同时出现或不合法组合的处理要求。[365] 当链路中有两个解析者（例如前置代理与后端服务），而两者对同一条请求的边界判断不一致时，第一个解析者认为的“请求结束”位置与第二个不同，后面被当作下一条请求的字节就会被重新解释——这就是请求走私类问题的成因。

实践要点有三：一是不要自己实现 HTTP 解析，也不要在代理层“清洗”后再转发一个边界含义不同的报文；二是理解规范对这类组合的要求（例如同时出现两种长度信息时被视为错误或按规范指定的优先级处理），不同实现的宽容度是风险来源；[365] 三是保持链路两端软件对同一规范版本的严格一致，并在接入层拒绝含可疑头部组合的请求。

这与 TCP 的“粘包／拆包”是不同层次的问题：TCP 只提供字节流，框架按自己声明的长度切分消息；如果长度字段本身可以有两种互相矛盾的解释，那么无论 TCP 还是分块编码都无法保证两个解析者看到同一组消息。安全影响属于网关与代理的边界设计问题，不能靠应用层重试掩盖。

</div>
</article>

<article class="qa-item" id="qa-http-cache" data-level="scenario" markdown="1">
<p class="qa-question">Q147 · HTTP 缓存的 Cache-Control 与 ETag 各解决什么？代理缓存和浏览器缓存有什么不同？</p>
<div class="qa-answer" markdown="1">

RFC 9111 把缓存分成共享缓存与私有缓存，并规定了响应指令的语义：哪些响应可以存、能存多久、是否必须向源服务器再验证。[364] `Cache-Control` 的 `max-age`、`no-store`、`private`/`public`、`s-maxage` 等指令决定可缓存性与新鲜期；`ETag`／`Last-Modified` 提供验证依据，条件请求得到 `304` 时客户端复用已有正文，`Vary` 则决定键要不要区分请求头。

浏览器缓存（私有）与中间代理缓存（共享）的差别在于谁能存：`private` 只允许单用户缓存，`no-store` 完全禁止落盘，`s-maxage` 专门约束共享缓存的新鲜期。[364] 这一区分直接关系到安全和容量：把用户相关的响应标成 `public` 会让共享代理把它发给别人；反过来，把静态资源标成 `private` 会让每个用户各存一份，浪费带宽。

工程上应把缓存看作“协议 + 键设计”两件事：协议字段决定允许与验证，键（URL、`Vary` 头）决定命中。诊断“改了内容但用户还看到旧页面”时，要按层分别看：源站是否发了可缓存响应、代理是否按 `Vary` 分键、客户端是否走了条件请求复用了未失效的副本；`304` 表示验证通过而非“没有请求”，与“本地缓存直接用、根本没联网”是两种不同的证据。

</div>
</article>

<article class="qa-item" id="qa-rpc-vs-http" data-level="scenario" markdown="1">
<p class="qa-question">Q148 · RPC 与 HTTP 接口该怎样选？gRPC 相比 JSON/HTTP 改变了什么？</p>
<div class="qa-answer" markdown="1">

两者的差别主要在接口约定与数据编码，而不是“谁更快”。RPC 风格把方法名、参数与错误当成接口的一部分，通常由 IDL 生成客户端与服务端代码，调用形态接近本地函数；HTTP/JSON 风格把资源与动作放在 URL、方法和状态码上，文本可读、可被浏览器与网关直接使用，跨语言成本低。

gRPC 在 HTTP/2 之上定义了消息成帧：请求与响应是长度前缀的二进制消息，通过流传输，状态用 HTTP 状态与尾部元数据分别表达。[358] 这带来双向流、头部压缩与多路复用的能力，也让二进制编码（Protobuf）比文本更紧凑；代价是需要 HTTP/2 通路、调试时不能直接读文本、中间代理与负载均衡要支持尾部头部与长连接语义。

选择依据：内部服务间、接口稳定且需要代码生成与流式能力时，gRPC 类方案合适；对外开放、需要浏览器直接访问、依赖 HTTP 缓存语义或希望用通用工具排障时，HTTP/JSON 更直接。两者都不是性能保证：吞吐还取决于序列化成本、连接复用、并发模型与下游容量；把“换成 RPC”当作性能修复方案之前，应先确认瓶颈在协议层还是业务与后端。

</div>
</article>
