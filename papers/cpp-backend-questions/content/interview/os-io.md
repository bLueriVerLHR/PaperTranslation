#### 文件、权限与 I/O {#interview-os-io}

<article class="qa-item" id="qa-inode-links" data-level="basic" markdown="1">
<p class="qa-question">Q108 · inode 保存什么？软链接、硬链接及打开文件后删路径有什么区别？</p>
<div class="qa-answer" markdown="1">

inode 关联类型、权限、所有者、大小、链接数及时间等元数据，文件名通过目录项与对象关联。inode 号只在相应文件系统范围内区分对象，不能脱离设备身份当全局唯一键。atime 是访问，mtime 是内容修改，ctime 是状态改变，不等于创建时间；创建时间还依赖接口和文件系统支持。[73]

硬链接给同一文件对象增加一个目录入口，通常不能跨文件系统；软链接自身保存目标路径，可以跨文件系统，也可能悬空。解除一个名字不等于立刻摧毁正在被访问的对象，其他硬链接或打开引用仍可能维持它。[74] 描述符又关联打开文件状态，dup 或 fork 可能共享偏移，另一次独立 open 通常有自己的打开状态。目录写入与查找权限影响删除路径，不是只看目标文件有没有写权限。[66, 73–74]

</div>
</article>

<article class="qa-item" id="qa-linux-permissions" data-level="basic" markdown="1">
<p class="qa-question">Q109 · rwx 对文件和目录分别意味着什么？chmod 777 能解决所有权限错误吗？</p>
<div class="qa-answer" markdown="1">

普通文件的 r、w、x 分别表达读、写、执行权限；目录的 r 用于读取目录项，x 用于路径查找，w 影响增删目录入口。路径上的祖先目录、所属用户与组、ACL、挂载及安全机制都会影响操作，不能只看最后一个文件。sticky、setgid 等位还有另外规则，例如共享临时目录的 sticky 位限制谁可删除入口。[73–74]

chmod 改模式位，chown 改拥有者，umask 限制新建时允许的权限，这三者不是一个设置。777 会开放过多权限，也不解除只读挂载、不可变标志或其他访问控制；账户修改、sudoers 调整和服务安全配置属于有风险的管理操作。诊断应先确认执行身份与失败的具体路径和动作，再按最小权限设计，不把题库中宽泛授权命令当默认修复步骤。

</div>
</article>

<article class="qa-item" id="qa-user-authentication-authorization" data-level="basic" markdown="1">
<p class="qa-question">Q110 · su、sudo、用户组与权限怎样区分？认证成功等于可以执行所有动作吗？</p>
<div class="qa-answer" markdown="1">

认证确认身份，授权决定该身份允许的操作。su 切换相应用户上下文，登录式切换还调整环境；sudo 按配置策略授予指定命令或身份的执行能力。两者并不都等于“无条件成为 root”，允许哪些动作、怎样认证和是否审计都由实际策略决定。

文件访问结合有效身份、组、模式位及其他控制，目录搜索、读取和修改权限还有不同意义；服务账户、交互用户与容器内身份也不能只看显示名称就认定等价。[73–74] 身份变化后的 HOME、PATH 和环境继承会影响执行的程序与配置。

增加用户、改密码、改组或 sudoers 都是真实账户与安全配置修改，不是普通只读诊断。最小权限应与具体工作职责相连，权限错误先定位失败动作与执行上下文，而不是采用一条泛化授权命令。身份核查与更改账户策略属于不同的状态操作。

</div>
</article>

<article class="qa-item" id="qa-mmap" data-level="principle" markdown="1">
<p class="qa-question">Q111 · mmap 与 read 有何区别？共享映射的写入是否立即持久化？</p>
<div class="qa-answer" markdown="1">

`mmap` 建立文件或其他对象到虚拟地址空间的映射，程序通过内存访问使用内容；`read` 将字节读入调用者提供的缓冲区。映射可以减少某些额外复制和接口调用，但仍可能触发缺页、页缓存访问、存储 I/O 和页面管理开销，不能概括成“没有 I/O 的零拷贝”。[22]

`MAP_SHARED` 允许修改在相应共享映射间可见，并关联到底层文件；`MAP_PRIVATE` 是私有写时复制映射，修改不写回原文件。内存可见性、线程间同步与持久化是三个不同问题，使用共享映射不会让普通数据写入变成原子事务，控制写回时机还涉及 `msync` 等接口。

映射的生命周期也不同于文件描述符：建立映射后关闭描述符通常不会解除映射。与此同时，其他操作截断文件后访问越过实际文件范围的映射页面，可能产生 `SIGBUS`。资源包装器必须分别管理映射范围、文件状态和并发访问关系。

</div>
</article>

<article class="qa-item" id="qa-io-model" data-level="principle" markdown="1">
<p class="qa-question">Q112 · 同步／异步与阻塞／非阻塞是一组同义词吗？</p>
<div class="qa-answer" markdown="1">

阻塞／非阻塞描述一次调用在当前条件下是否等待；同步／异步通常描述操作完成与结果通知的组织方式，具体术语要结合接口定义。非阻塞 `read` 可能立即返回“当前不可读”，并不表示操作已经在后台完成；异步提交则可以稍后通过完成通知取得状态。

I/O 多路复用等待的是一组描述符的就绪条件。`epoll_wait` 自身可以阻塞等待事件，而被监视的 socket 常设置为非阻塞；收到就绪事件后，应用仍执行读写并处理短读、短写、错误和 `EAGAIN`。[21]

异步接口同样可能在队列准入、提交或其他路径出现等待，也不自动消除缓冲区生命周期要求。对于后端设计，关键是哪个执行者等待、谁推进完成、谁在完成之前持有数据，而不是给整个程序贴一个“异步所以高性能”的标签。

</div>
</article>

<article class="qa-item" id="qa-epoll" data-level="principle" markdown="1">
<p class="qa-question">Q113 · epoll 的 LT、ET 与 EPOLLONESHOT 有什么区别？ET 一定更快吗？</p>
<div class="qa-answer" markdown="1">

LT 在相应就绪条件持续满足时仍可报告事件；ET 改变通知组织，不能指望未处理的数据一定会在下一次等待中继续提醒。常见 ET 协议使用非阻塞描述符，在重新等待前读取或写入到 `EAGAIN`，并保存未完成的连接状态。[21]

“读到 EAGAIN”不等于一条连接可以无限占用事件循环。大量连续数据会使其他连接饥饿；可以用应用就绪队列和处理预算继续推进未完成工作，而不是有剩余数据却直接等待下一条边缘通知。短写也必须保留剩余输出，不能假设一次 `write` 完成整个响应。

`EPOLLONESHOT` 在一次事件后暂时禁用相应描述符的事件报告，应用处理完成后重新启用。它能帮助安排事件处理所有权，却不自动保护连接对象生命周期或其他业务状态。ET 可能减少重复通知，但额外状态管理、重新注册和调度成本决定实际结果，不能直接断言总比 LT 快。

</div>
</article>

<article class="qa-item" id="qa-zero-copy" data-level="principle" markdown="1">
<p class="qa-question">Q114 · 文件发到网络通常有哪些复制？sendfile 的“零拷贝”省掉了什么？</p>
<div class="qa-answer" markdown="1">

传统 read 再 write 的简化发送模型，可能有设备到页缓存的 DMA、页缓存到用户缓冲的 CPU 复制、用户缓冲到发送缓冲的 CPU 复制，以及到设备的传输；具体次数取决于缓存命中、驱动、设备和实现。接收端写文件属于另一段路径，不能把两端都算进一个本地发送接口的固定成本。

sendfile 在内核内组织描述符间传输，省去相应用户态往返数据复制；支持适当路径时可以让内核或设备复用页面。[69]“零拷贝”不表示没有任何 DMA、协议处理、缺页或系统调用。短传输、EAGAIN、源文件范围保持不变以及完成期间的生命周期仍需处理；TLS、压缩、变换或接口限制可能要求不同路径。一次返回写入多少，也不是对端已持久化多少。[69]

</div>
</article>
