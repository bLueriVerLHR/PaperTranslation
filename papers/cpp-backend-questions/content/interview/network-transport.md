#### 传输层协议、端口与连接容量 {#interview-transport-headers}

<article class="qa-item" id="qa-tcp-udp" data-level="basic" markdown="1">
<p class="qa-question">Q127 · TCP 与 UDP 的核心区别是什么？“UDP 快、TCP 慢”是否足够？</p>
<div class="qa-answer" markdown="1">

TCP 提供面向连接、可靠且有序的字节流；UDP 提供数据报服务，本身不承诺交付、顺序或去重。“TCP 慢、UDP 快”不足以选型：首先要确定应用需要怎样的交付语义，以及丢失、超时和拥塞由谁处理。[25,139,270]

| 比较项 | TCP | UDP |
|---|---|---|
| 交付单位 | 字节流，不保留应用写调用的消息边界 | 数据报，保留报文边界，但接收缓冲不足仍可能截断 |
| 传输状态 | 建立连接，维护序号、确认、重传及窗口等状态 | 基本协议没有同一套连接建立和恢复状态；socket 仍有本地状态 |
| 丢失和乱序 | 尝试恢复缺失字节并按序交给应用，失败时连接仍可能终止 | 由需要这些保证的上层协议处理 |
| 负荷约束 | 接收端流量控制与网络拥塞控制同时约束发送 | 不能因基本头部没有窗口，就让应用无限制发送 |

TCP 的流量控制保护接收端，拥塞控制限制网络中的在途负荷。ACK 说明相应字节已被传输端点接收，不等于应用已读取，更不等于订单或数据库事务已提交。超时后重试一个业务动作，仍需要请求标识、结果关联与幂等协议。[25,79]

UDP 基本头部较短、无需 TCP 握手，可能适合允许舍弃过时数据的交互；但这不构成同一业务的速度证明。上层增加可靠交付、加密、拥塞控制和消息重组时，相应成本不会消失。连接复用、往返时延、丢包和业务处理共同决定实际表现；应比较完整协议与工作负载，而不是只比较 TCP／UDP 名称。

</div>
</article>

<article class="qa-item" id="qa-tcp-udp-header-fields" data-level="basic" markdown="1">
<p class="qa-question">Q128 · TCP 与 UDP 头部有哪些字段？校验和能代替可靠传输或加密吗？</p>
<div class="qa-answer" markdown="1">

TCP 头部表达端点、流位置、连接控制和接收窗口；UDP 基本头部只有源端口、目的端口、长度与校验和。TCP 无选项时是 20 字节，四位 Data Offset 按四字节单位计头长，普通编码下最多 60 字节；UDP 基本头部固定八字节。它们都不包括外层 IP 头。[25,139]

| 字段 | TCP | UDP |
|---|---|---|
| 源、目的端口 | 各 16 位，结合 IP 地址等上下文区分端点 | 各 16 位，表达数据报端点 |
| 序号、确认号 | 各 32 位；序号定位字节，确认号在 ACK 有效时表示下一期待位置 | 没有同一套序号和确认字段 |
| 头长／长度 | Data Offset 表示 TCP 头长，不是整个段长 | 16 位 Length 包含 UDP 头和数据，RFC 768 基本最小值为八 |
| 控制标志 | SYN／FIN 控制两个方向的建立和结束，ACK 使确认号有效，RST 复位，另有 PSH／URG 等语义 | 没有相应连接控制字段 |
| 接收窗口 | 16 位通告值，扩大的解释另依赖选项协商；不是发送方 `cwnd` | 没有基本接收窗口字段 |
| 校验和 | 16 位，覆盖相关伪头部、TCP 头和数据；必须计算并验证 | 16 位，覆盖相关伪头部、UDP 头和数据；规则受 IP 版本影响 |
| 紧急指针、选项及填充 | 紧急指针在 URG 有效时解释；选项可承载 MSS、窗口缩放、SACK 等能力 | 基本头部没有这些字段 |

PSH 不是应用消息边界，URG 也不表示任意一段业务数据更重要。选项是否出现及怎样解释还依赖协商和协议规则，不能从字段存在推出所有组合都合法。SYN、FIN 各占一个序号位置；累积 ACK 越过已连续收到的位置，但不证明应用已读取或业务已提交。[25]

伪头部把 IP 地址、协议号和相应长度纳入校验，以帮助检测错误交付；它是校验时组织的输入，不是额外插入的 TCP／UDP 负载。TCP 校验和不是可选字段；RFC 768 中以零表示未生成 UDP 校验和的约定属于历史 IPv4 语境，不能无条件推广到 IPv6。校验和没有秘密密钥，不提供防恶意篡改的认证，更不负责重传和去重。[25,139]

多字节整数字段还须按协议字节序编解码。大端把高有效字节放在低地址／先传位置，小端相反；例如 16 位值 `0x1234` 的网络字节序是 `12 34`。`htons`／`ntohs`、`htonl`／`ntohl` 在主机序和相应网络序之间转换，不能先转换后又重复交换。[281] 这也不意味着任意自定义负载和文件都强制采用大端；应用须明确自己的字段编码，不能把含本地填充、对齐和本机字节序的结构体直接当作通用线上格式。

</div>
</article>

<article class="qa-item" id="qa-udp-connect" data-level="basic" markdown="1">
<p class="qa-question">Q129 · UDP 调用 connect 后是不是变成可靠连接？UDP 怎样接收错误和完整报文？</p>
<div class="qa-answer" markdown="1">

不会。UDP `connect` 主要给本地 socket 设置默认发送目标，并限定通常接收的对端；它不执行 TCP 握手，也没有增加可靠交付、有序性或重传。应用可使用 `send`／`write` 而不逐次提供目标，Linux 仍允许通过带目的地址的 `sendto`／`sendmsg` 指定其他发送目标。因而“connect 后只能向一个地址发送”也不是 Linux 的一般接口结论。[76–77]

关联固定对端可以简化调用和请求状态管理，接收过滤也能减少无关报文，但地址过滤不是密码学身份认证。它更不能自动证明 CPU 开销下降或业务性能提高；那些结论还需要具体实现和负载证据。

UDP 保留数据报边界，普通接收操作一次取得一个数据报。缓冲区不足时可能截断并丢弃剩余部分，不会在下一次读取中自动续出同一个报文；Linux `recvmsg` 的返回标志等信息可以帮助发现 `MSG_TRUNC`。零长度数据报也是合法的，所以返回零不能照搬 TCP 的 EOF 解释。报文边界存在，不等于任意大小报文都能完整接收。[77]

Linux 的未 connect UDP socket 也可以收到异步网络错误，错误可能对应先前发送的报文，而不是刚刚提交的那条；启用 `IP_RECVERR` 后可通过 `MSG_ERRQUEUE` 读取相应错误队列。[77] 没收到错误不证明报文到达，成功发送也不证明目标应用已处理。需要业务确认时，应另行规定响应、请求关联、超时与重试，而不是把本地 socket 关联称作可靠连接。

</div>
</article>

<article class="qa-item" id="qa-socket-lifecycle" data-level="basic" markdown="1">
<p class="qa-question">Q130 · TCP 服务端和客户端的 socket 流程是什么？非阻塞 connect 与 select 应怎样解释？</p>
<div class="qa-answer" markdown="1">

典型 TCP 服务端的流程是 `socket → bind → listen → accept → 连接上的读写 → 关闭`。`listen` 使原 socket 成为监听端点，`accept` 取出一个待接收连接并返回新的已连接描述符；原监听描述符不因此变成该客户端连接，也不因此停止监听。客户端创建 socket 后 `connect`，未显式绑定时，内核通常选择本地地址和临时端口。[76,88–89,280]

非阻塞 TCP `connect` 返回 `EINPROGRESS` 表示建立过程尚未完成。等待可写后读取 `getsockopt(SOL_SOCKET, SO_ERROR)`，零表示此次连接成功，非零表示相应失败；可写本身不是成功证据。流程还需要连接期限和失败清理。不同地址族的错误语义不完全相同，不能把所有非阻塞调用都套用 TCP 的一个返回码。[76]

对于 `select`，调用前准备三个描述符集合和超时，`nfds` 是最高被监测描述符数值加一，调用后检查实际就绪项。集合被原地修改，Linux 还可能修改超时，因此循环应重新准备下一轮输入。常用固定 `fd_set` 只能表示小于 `FD_SETSIZE`、通常为 1024 的描述符数值；即使只监测一个数值很大的 fd，也会越界，而不只是“最多监测 1024 条连接”。[78]

就绪表示某类操作能够推进，不表示完整业务动作成功：监听 fd 可读后，连接仍可能先被另一线程取走或遇到错误，所以非阻塞 `accept` 仍须处理 `EAGAIN`；已连接 TCP fd 可读可能是数据、EOF 或实际错误，可写也不保证任意大的写入不会阻塞。非阻塞读写要按实际返回值维护剩余字节，处理 `EINTR`、`EAGAIN` 和失败，不能把一次通知当作一条完整消息。[78,280]

建立连接、交付完整应用消息和关闭所有持有者是不同生命周期阶段。关闭路径应明确谁拥有监听 fd、已连接 fd、缓冲与定时器，避免只处理正常通信而遗漏超时、半关闭和错误路径；`exceptfds` 也不是全部 socket 错误的统一集合。[78]

</div>
</article>

<article class="qa-item" id="qa-listen-queues" data-level="principle" markdown="1">
<p class="qa-question">Q131 · 半连接队列、accept 队列与 SYN flood 有什么关系？调大 backlog 能解决过载吗？</p>
<div class="qa-answer" markdown="1">

半连接队列通常指尚未完成握手的请求状态，accept 队列保存已经建立、等待应用 `accept` 的连接。Linux 2.2 以来，`listen` 的 backlog 针对后一类队列，超过 `somaxconn` 的值会被截断；未完成握手的状态有不同控制，SYN cookies 又会改变保存方式。backlog 既不是两队列之和，也不是服务端能维持的全部连接数。[88]

SYN flood 通过大量无法及时完成的打开请求消耗状态或处理能力。SYN cookies 将部分建立信息编码到服务端序号，收到后续有效确认时再恢复相应状态，减少提前保存半连接的需要。但链路带宽、包处理和建立后的应用资源仍可能被耗尽，不能把 cookies 或第三次握手说成完整防攻击保证。[25,88]

增大队列可以在容量范围内吸收短时突发，却不提高处理器本身的服务速率。若新建连接持续到达得比 `accept` 更快，等待会积累；若接收连接很快而业务处理很慢，积压会转移到应用和输出队列。客户端等待与重传又可能放大负荷。

因此应分别分析握手、接收连接和处理请求的瓶颈，再决定准入、限流、等待期限与处理容量。队列满时观察到的丢弃、重试或连接结果还受具体内核行为和配置影响，不能只看一个 backlog 数字就宣布容量已经扩大。

</div>
</article>

<article class="qa-item" id="qa-connection-capacity" data-level="principle" markdown="1">
<p class="qa-question">Q132 · 一个服务端最多只能有 65,535 个 TCP 连接吗？端口、四元组和文件描述符怎样限制容量？</p>
<div class="qa-answer" markdown="1">

不是。对同一 TCP 查找上下文，一条连接由本地 IP／端口和远端 IP／端口组成的四元组区分。同一监听端口可接收许多不同远端的连接，并非每接收一次就必须占用另一个本地服务端口。16 位端口有 65,536 个编号、零号又有特殊接口语义，但无论如何，端口编号总数不是全机连接上限。[25,89]

客户端从一个本地地址向固定远端 IP／端口主动打开时，可用临时端口才更容易成为瓶颈：新连接必须获得可用的本地组合，已有连接、TIME_WAIT 和绑定／复用规则会限制它。若改变本地地址或远端组合，上限又会改变。经 NAPT 时，网关的映射资源可能先达到限制，不能只数客户端的端口。[76,277]

服务端实际容量还取决于进程和系统描述符、内核连接状态与缓冲、应用每连接对象、CPU、带宽及排队。高并发不能直接把 IPv4 地址数乘端口数当作可部署容量，因为大多数理论组合并不对应可用资源或真实客户端。

连接池减少反复建连的开销，却保留空闲连接及其状态；请求多路复用又可能让少量连接承载大量业务。比较容量时应区分同时连接数、活跃连接数、新建连接率和请求吞吐，再说明负载与每连接资源成本，不存在仅由端口位数得到的通用最大值。

</div>
</article>

<article class="qa-item" id="qa-ip-fragmentation" data-level="principle" markdown="1">
<p class="qa-question">Q133 · IP 分片与 MTU 是什么关系？为什么 TCP 要在 MSS 层就分段？</p>
<div class="qa-answer" markdown="1">

链路层对单个帧有尺寸上限，即最大传输单元（Maximum Transmission Unit，MTU），IP 数据报超过该上限时必须分片，接收端再重组；分片信息放在 IP 头里，重组依赖每片的偏移、标志与标识字段。[363] 分片把“一个数据报”的风险摊给了路径上的每个设备：任一片丢失就要重传整个数据报，重组缓冲占用接收端内存，中间设备策略也可能直接丢弃或禁止分片。

TCP 因此避免依赖 IP 分片：最大报文段长度（Maximum Segment Size，MSS）选项让双方在握手时通告自己能接收的最大 TCP 报文段长度，通常由本端 MTU 减去 IP 头与 TCP 头长度推导，使每个报文段装进一个不分片的 IP 数据报。[372] 路径上 MTU 可能更小，所以还有路径 MTU 发现：发送方设置禁止分片位，靠 ICMP“需要分片”报文逐步调低估计值；若 ICMP 被过滤，就会出现“小包通、大包丢”的典型故障，此时要么修复 ICMP 通路，要么用固定较小的 MSS 配置。[362]

判断时要区分层次：MSS 是 TCP 选项、MTU 是链路属性、IP 分片是网络层行为；应用层看到的“大报文收不到”可能来自三者中任意一层的限制，也可能来自中间设备。抓包确认时应看是否有分片标志位和 ICMP 差错，而不是只看应用层超时。

</div>
</article>
