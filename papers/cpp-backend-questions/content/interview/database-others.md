#### PostgreSQL 与 SQLite：机制对比 {#interview-database-others}

<article class="qa-item" id="qa-sqlite-locking" data-level="basic" markdown="1">
<p class="qa-question">Q194 · SQLite 的锁与 WAL 模式：嵌入式数据库的并发边界在哪里？</p>
<div class="qa-answer" markdown="1">

SQLite 直接把数据库放在单个文件里，用文件锁协调多进程访问：锁状态分为共享、保留、待定与排他等层次，读取需要共享锁，写入先取保留锁表示“打算写”，真正落盘前升级到排他锁；升级时若已有其它读者就可能导致 `SQLITE_BUSY`，需要应用自行重试或缩短事务。[355] 因此传统回滚日志模式下，写会阻塞读、读也会阻塞写，并发能力受限于单写者语义。

WAL（write-ahead logging）模式把修改先追加到单独的 WAL 文件，再把页变更合并回主库文件：读操作按自己看到的一致快照读 WAL 与主库，因此读者不阻塞写者、写者也不阻塞读者，但同一时刻仍然只有一个写者；[354] 需要定期做检查点把 WAL 内容合并回主库并截断日志，检查点本身会与写操作竞争，长读事务（持有的快照过旧）会阻止检查点推进、让 WAL 持续增长。[354]

工程含义很直接：SQLite 适合单机、进程内、读多写少或写入可串行的场景（本地缓存、配置、边缘节点、测试与原型）；把多个服务实例挂在同一网络文件系统上并发写入不是它的设计目标，此时应换用客户端／服务端数据库。使用时要显式设置忙等超时或实现重试，避免把 `SQLITE_BUSY` 当异常；对写入频繁的场景还要监控 WAL 大小与检查点进度，避免磁盘被未合并的日志填满。

</div>
</article>

<article class="qa-item" id="qa-pg-mvcc" data-level="principle" markdown="1">
<p class="qa-question">Q195 · PostgreSQL 的 MVCC 与 MySQL 有什么不同？为什么它需要 VACUUM？</p>
<div class="qa-answer" markdown="1">

MySQL 的 InnoDB 把最新版本放在聚簇索引里，历史版本通过 undo 日志与回滚段按需构造，读操作沿版本链找到可见版本，旧版本由清理线程回收（见 [MVCC](#qa-mvcc)）。[30,45] PostgreSQL 的做法相反：更新一行时写入一个全新的行版本，旧版本仍留在表里，行的可见性由创建与删除它的事务标识决定，因此同一张表在物理上同时存在多个版本。这个差异决定了后续一切：读不需要构造历史版本，但表会持续“变胖”，必须有人回收死亡版本。

回收者就是 VACUUM：常规清理标记可复用的空间，能避免表无限增长并更新可见性信息供索引扫描使用；自动清理（autovacuum）按阈值与代价参数在后台运行。[352] 与清理相关的是事务标识回卷问题：PostgreSQL 用 32 位事务标识判断版本新旧，标识用尽后必须把很旧的标识“冻结”为永久可见，因此清理不能被长期推迟，否则数据库会拒绝写入——这也是必须监控 `age` 与自动清理进度、并对长事务设上限的原因。[352]

隔离语义上两者的默认行为也不同：PostgreSQL 的默认隔离级别是读已提交，每条语句看到各自的新快照；可重复读使用事务级快照，并在遇到写冲突时以序列化错误终止其中一个事务，这不是 MySQL 那种“读已提交／可重复读”的同一套措辞。[353] 所以跨数据库讨论“MVCC 是否阻塞读写”时，要先说明是哪一个产品与版本、哪种隔离级别与哪种读，否则结论不成立。

</div>
</article>

<article class="qa-item" id="qa-pg-vacuum-wraparound" data-level="scenario" markdown="1">
<p class="qa-question">Q196 · PostgreSQL 的事务标识回卷是什么？长期不清理会发生什么？</p>
<div class="qa-answer" markdown="1">

版本可见性靠事务标识比较，而标识空间是有限的 32 位：当标识接近用尽时，必须把足够旧的元组标记为已冻结，让它们对新事务恒久可见，否则“旧”与“新”的判定会翻转，数据看起来会消失或出现。[352] 因此 PostgreSQL 要求定期清理，并把防止回卷当作必须监控的运行约束，而不是可选优化。[352]

机制上要区分三件事：清理是否跟得上（死亡元组能否及时回收、表是否膨胀）、冻结是否推进（事务标识年龄是否受控）、以及清理是否被阻塞（长事务、长查询或复制槽持有旧快照，会让清理无法回收它们之后仍可能需要的版本）。[352] 表现上，年龄持续上升时可能只是表变大、查询变慢；接近阈值时数据库会发出警告并最终拒绝新的写入，需要停机式或高成本的维护。

运维做法是监控最老的表年龄与自动清理频率、给自动清理留足 I/O 预算、限制长事务与空闲事务的时长、避免复制槽长期不使用，并在批量操作后主动触发清理与统计信息更新。[352] 这与 MySQL 的 undo 清理在思路上类似（都要防止历史版本无限积累），差别在于 PostgreSQL 的历史版本就在主表里，所以清理滞后直接体现为表与索引的物理膨胀。[352]

</div>
</article>
