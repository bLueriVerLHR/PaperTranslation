#### 跨语言对比：内存、泛型与并发 {#interview-cross-language}

<article class="qa-item" id="qa-gc-vs-raii" data-level="basic" markdown="1">
<p class="qa-question">Q86 · 追踪式垃圾回收与引用计数／RAII 各有什么代价？</p>
<div class="qa-answer" markdown="1">

引用计数在计数归零时立即释放：回收时机可预测、没有全局停顿，也容易与 RAII 结合（离开作用域即释放）。代价是每次复制与销毁都要更新计数（跨线程共享时需要原子操作）、每个对象多一份计数空间，而且无法回收环。Python 的主机制就是引用计数，另用周期性回收补充处理循环引用。[326,327]

追踪式回收从根出发遍历可达对象：能处理环，分配通常更快（可以顺序分配并整理内存），但回收时机不确定，需要按停顿与吞吐的取舍选择收集器并调参；会移动对象的收集器还禁止把对象地址长期交给本地代码（需要句柄或固定）。[328]

语言层面的差别比性能更重要：依赖 GC 的语言无法用析构函数保证“必须立即释放”的资源立刻归还（文件句柄、锁、连接），因此需要确定性的作用域机制显式关闭，[330] 而终结器已被证明难以正确使用，`Object.finalize` 已标记为弃用并计划移除，不能作为资源释放方案。[329]

C++ 走的是另一条路：释放时机由类型与作用域决定，代价是所有权必须显式表达，环状所有权要用弱引用等约定手工打破；好处是资源与析构顺序可以精确控制，且不依赖运行时收集器。

</div>
</article>

<article class="qa-item" id="qa-erasure-monomorphize" data-level="principle" markdown="1">
<p class="qa-question">Q87 · Java 泛型的类型擦除与 C++ 模板的单态化各带来什么后果？</p>
<div class="qa-answer" markdown="1">

Java 的泛型在编译后擦除类型参数：`List<String>` 与 `List<Integer>` 在运行期是同一个类，类型参数不作为运行期信息存在。[331] 后果是不能用基本类型作为类型实参（需要装箱）、不能 `new T[]` 或对类型参数做 `instanceof`（要传入 `Class<T>` 或用通配符）、泛型类的静态成员在实例间共享、擦除后签名相同的方法不能靠类型参数重载，而桥方法与编译器插入的强制转换承担类型安全；换来的是与旧代码兼容、不产生按实参组合的代码副本。[332]

C++ 模板按实参单态化：每个实参组合生成一份代码，因此可以依赖具体类型做内联、特化与编译期计算，也没有装箱与运行期转换；代价是二进制体积与编译时间增加、跨翻译单元可能产生重复实例化（由链接期合并解决），以及模板错误在实例化点报出。[325]

两者的共同点是都在编译期做类型检查，差别在于检查之后还剩什么信息：Java 留下统一的运行期表示与转换，C++ 留下具体类型的代码。由此可以推出一条实用的判断——“C++ 模板更快”不是自动成立的结论，只有调用点确实被内联、优化确有价值时才成立；“Java 泛型没有开销”也不完全成立，装箱与桥方法在热路径上仍有成本，实际影响要靠测量而不是类型学判断。

</div>
</article>

<article class="qa-item" id="qa-volatile-cross-language" data-level="principle" markdown="1">
<p class="qa-question">Q88 · Java 的 volatile 与 C++ 的 volatile 是同一个东西吗？</p>
<div class="qa-answer" markdown="1">

不是。Java 的 `volatile` 是并发语义：对 volatile 字段的读写具有可见性并建立 happens-before 顺序（禁止相关重排、保证读到最新写入），但不把复合操作变成原子——`i++` 仍然需要额外同步；内存模型在 Java 语言规范第 17 章定义。[333,334]

C++ 的 `volatile` 只表示“这些访问是可观察的副作用”：同一线程内不能被优化掉或合并，因此适合内存映射寄存器与信号处理相关的访问，但它不建立线程间同步、不保证原子性，也不阻止数据竞争；需要同步时要用 `std::atomic` 与内存序，Core Guidelines 的 CP.8 规则正是“不要用 volatile 做同步”。[324,288]

所以“用 volatile 当多线程标志位”在 C++ 里是错误的做法，在 Java 里却是常见写法（只是要注意复合操作）。粗略对应可以这样记：Java 的 `volatile` 约等于 C++ 中偏重可见性与顺序的 `atomic` 用法；C++ 的 `volatile` 表达的是“每次都要真实访问”的语义，在 Java 中没有直接对应物。两者不能互相替代，也不能把一种语言的直觉搬到另一种语言。

</div>
</article>

<article class="qa-item" id="qa-hash-collision-strategy" data-level="principle" markdown="1">
<p class="qa-question">Q89 · 哈希冲突处理：Java HashMap 的树化与 C++ unordered_map 有什么不同？</p>
<div class="qa-answer" markdown="1">

共同前提是冲突处理方式由实现决定：C++ 标准对无序容器只要求平均常数时间，最坏情况取决于实现与哈希质量，也不保证迭代顺序；[297] Java 的 `HashMap` 文档同样只承诺容量与负载因子参数下的平均行为，并提示迭代性能受初始容量与负载因子影响。[335]

差别在冲突集中的处理。Java 8 起，当同一桶内节点数达到阈值（源码中 `TREEIFY_THRESHOLD = 8`）且表已扩到足够大时，桶内链表会转成红黑树形态，使该桶的查找从线性降为对数级；节点数降到较小阈值（`UNTREEIFY_THRESHOLD = 6`）再退回链表。[336] 这缓解了劣质哈希与碰撞攻击下的最坏查找，但树化节点占用更多内存，并且要求键可比较或用平局比较规则决定顺序。C++ 的 `unordered_map` 由实现选择链地址或开放寻址，标准没有树化要求，可移植的控制点只有负载因子相关接口与自定义哈希／相等比较。[341]

工程结论适用于两者：哈希分布均匀是前提而不是保证，容易受外部输入影响的服务需要在哈希函数里加入随机化或使用抗碰撞哈希，这属于数据结构之外的决策；容器选择还要同时看迭代顺序、引用与迭代器失效规则、内存开销（见 [rehash 的失效范围](#qa-unordered-rehash)）。

</div>
</article>
