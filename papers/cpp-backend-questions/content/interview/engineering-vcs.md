#### 版本控制、传输与作业 {#interview-engineering-vcs}

<article class="qa-item" id="qa-git-state-history" data-level="basic" markdown="1">
<p class="qa-question">Q256 · Git 工作树、暂存区、提交与 reset 如何区分？merge、rebase、stash 应怎样理解？</p>
<div class="qa-answer" markdown="1">

工作树是当前文件，暂存区是准备写入下次提交的状态，提交是已记录的快照与历史关系。普通 diff 比较工作树与暂存区，暂存区 diff 比较待提交内容与相应提交；查看 diff 和 log 不会自动同步远端。

对提交的 reset 可以移动当前分支：soft 保留暂存区和工作树，mixed 更新暂存区而保留工作树，hard 还改写工作树，可能损失本地修改或覆盖阻挡恢复的未跟踪路径。按路径 reset 则主要调整相应暂存内容，不应混同为分支回退。[151]

Merge 汇合历史，可能快进或产生合并提交；rebase 把选定变化重放到另一基底，通常改变提交身份；cherry-pick 引入选定提交的变化，不把整段祖先历史都合入。冲突需要按目标语义解决，“保留任一侧”不是一般正确方法。已共享历史的改写还影响协作者，必须与单纯本地整理区分。[152]

Stash 暂存局部修改便于切换上下文，不代替长期备份；未跟踪和忽略文件是否包含取决于选项，恢复也可能冲突。[157] 清理、硬重置、删分支和强制推送都属于实际状态修改；它们改变的对象和可恢复边界不同于只读查看差异与历史。

</div>
</article>

<article class="qa-item" id="qa-shell-redirection-jobs" data-level="scenario" markdown="1">
<p class="qa-question">Q257 · 标准输入输出、重定向顺序和后台任务有什么关系？nohup 是服务管理器吗？</p>
<div class="qa-answer" markdown="1">

标准输入、输出、错误通常对应描述符 0、1、2，管道默认把前一程序的标准输出接到下一程序标准输入；标准错误与命令退出状态另外处理。重定向复制的是当时的描述符关系，顺序改变就可能改变目标。

在常规 POSIX 类 Shell 中，`command >out 2>&1` 先把输出指向文件，再让错误共享该目标；`command 2>&1 >out` 先复制原输出到错误，再仅改变输出，错误不因此自动跟到文件。`>` 通常还会截断目标，所以改变日志路由也可能同时删除原有内容。

`&` 让命令在后台执行，并不保证 SSH 断开、终端关闭或主机重启后持续可用。nohup 处理挂断信号及相应终端流，不自动实现监控、重启、权限与日志轮转。管道整体状态还受 Shell 与选项影响，最后一段成功可能掩盖前面失败；可靠批处理需要表达错误传播和退出协议，而不是只看是否出现预期文字。

</div>
</article>

<article class="qa-item" id="qa-transfer-archive-boundaries" data-level="scenario" markdown="1">
<p class="qa-question">Q258 · tar、压缩与 rsync 的语义怎样区分？源目录末尾斜线和主机身份为什么重要？</p>
<div class="qa-answer" markdown="1">

归档把文件及相应元数据组织进容器，压缩改变字节表示，二者可以组合但不是同一操作。能列出归档内容不证明能按所需权限、链接和一致性要求恢复；解包还需限制绝对路径、向上逃逸和链接目标，避免覆盖预期范围外的文件。

Rsync 的源目录末尾斜线通常表示复制目录内容而不增加同名目录层；不带斜线则按目录本身组织目标。实际结果还取决于目标是否存在和选项，删除同步、过滤和元数据保留也各有规则。[153] 增量复制不自动形成跨文件的一致快照，也不替代备份历史。

SSH 私钥用于相应客户端身份认证，远端主机密钥用于确认连接的是谁。关闭主机身份验证只是去掉安全检查，不是可靠部署方案；未知或变化的密钥需要通过可信渠道核对。传输源、目标与删除范围决定实际修改边界，连接安全与恢复一致性仍是两个不同问题。

</div>
</article>
