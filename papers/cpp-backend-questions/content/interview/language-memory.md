#### 内存布局、分配与调用约定 {#interview-cpp-memory}

<article class="qa-item" id="qa-layout-alignment" data-level="basic" markdown="1">
<p class="qa-question">Q31 · 结构体怎样对齐？成员大小相加为什么不等于 sizeof？</p>
<div class="qa-answer" markdown="1">

结构体的大小不仅包含成员存储，还可能包含成员间和对象末尾的填充。这些填充使成员地址以及数组中后继对象的起始地址满足对齐要求。类型的对齐要求由 `alignof(T)` 表示，不等同于 `sizeof(T)`；类类型成员也有自己的对齐要求，因此只考察外围最大的基本类型成员并不足以确定布局。过度对齐、基类子对象和编译器打包选项也会影响结果。[54, 57]

例如假定 char、int、short 大小分别为 1、4、2，对齐分别为 1、4、2，普通顺序布局的 `{char; int; short;}` 可以有偏移 0、4、8，末尾再补齐到 12 字节。这是给定 ABI 假设的算例，不是所有平台的答案。调换独立成员次序可能减少填充，却可能改变 ABI；基类、虚基类和位域布局还有专门规则，不能推成“基类一定在地址 0”。把内存结构体直接发送到网络还会暴露填充、端序和版本问题，应按协议字段编码。

成员的地址次序还要按语言版本判断。C++20 对应的 N4861 工作草案规定，非 union 类中具有相同访问控制、非零大小的非静态成员按声明先后具有递增地址，不同访问控制组之间的分配顺序则未指定。[181] 本篇固定的较新工作草案对非变体、非零大小的非静态成员不再附加相同访问控制条件。[166] 因而不能把旧规则无条件推广到新版本，也不能反过来把新规则当成旧版本的保证；两种规则都不意味着相邻成员紧贴，更不规定虚函数管理信息或虚基类的统一布局。

静态数据成员不属于类对象的子对象，因此不会计入每个对象的成员存储。同一类的各对象共享普通静态数据成员；声明为 `thread_local` 时，则每个线程有独立实体，不能概括为整个程序始终只有一份。[182] 其实际映射到什么数据区、何时完成初始化，与这里的对象布局问题分别判断。

位域把字段压入分配单元，但分配、对齐及是否跨单元由实现定义，不能从声明位宽推出可移植的网络字节布局。位域不能取地址，非 const 引用也不能直接绑定到位域；匿名零宽位域用于让下个位域从分配单元边界开始，不是一个可读写的零位成员。[164] 普通内置数组声明的显式长度必须大于零；结构体尾部的 `char data[0]` 因而不是标准 C++ 数组成员，不能把编译器接受扩展与标准合法性混为一谈。[165]

GNU C 的零长度数组扩展与 C99 的柔性数组成员也不相同：前者写成 `[0]`，仍有元素对齐要求，可能增加外围结构体的尾部填充；后者写成 `[]`，具有不完整类型，不能对成员本身做 sizeof，并受非空结构体最后一个成员等限制。[162] 二者都不能直接当成可移植的标准 C++ 非静态数组成员。处理可变长度数据时，C++ 可以把固定头部与另行管理的连续缓冲分开组织，并明确容量、地址及生命周期，而不靠把扩展声明误认作额外存储已经存在。

</div>
</article>

<article class="qa-item" id="qa-storage-duration" data-level="basic" markdown="1">
<p class="qa-question">Q32 · C++ 的存储期和常说的栈、堆、数据段是一回事吗？</p>
<div class="qa-answer" markdown="1">

不是。存储期描述对象所占存储能够持续存在的时间，C++ 区分自动、静态、线程和动态存储期；栈、堆以及 ELF 中常说的 text、data、BSS 则属于实现和可执行格式的组织方式。普通块局部变量通常具有自动存储期，局部 `static` 变量具有静态存储期，`thread_local` 对应各线程的独立实体。“局部”描述作用域，并不意味着静态分配，也不决定物理存放位置。[204] 自动对象可能保存在寄存器中或被优化消除，`const` 对象也不一定位于只读数据区。

典型进程的代码映射承载指令，已初始化静态数据和零初始化数据具有不同的装载表示，线程有各自的执行栈及线程局部状态，动态分配则可能利用多种区域和映射。静态存储期不等于“编译时已经完成全部构造”，相应对象仍可能在运行期间动态初始化。动态分配允许按运行时需求申请存储，但一次申请并不使该存储自动伸缩；改变容量仍需要另行分配，或遵循具体分配接口的约定。

存储期也不同于对象生命周期：池仍拥有一片存储时，其中的对象可能已经析构，随后还可在满足条件的情况下重用该存储。容量分析因而需要区分虚拟地址范围、驻留页面、分配器保留容量和仍存活对象，源码中的 `new` 次数不能直接换算为 RSS。[23, 41, 204]

</div>
</article>

<article class="qa-item" id="qa-allocation-pairing" data-level="basic" markdown="1">
<p class="qa-question">Q33 · new／delete 与 malloc／free 有什么区别？placement new 怎样释放？</p>
<div class="qa-answer" markdown="1">

`new` 表达式组织存储获取与对象初始化，`delete` 表达式组织对象销毁与相应的存储释放；`malloc/free` 提供原始存储接口，不执行普通类的构造函数和析构函数。

分配失败与构造失败是两条不同的路径。普通抛异常式分配失败以 `std::bad_alloc` 报告；`new (std::nothrow)` 的分配失败可以返回空指针，但随后构造函数抛出的异常并不会因此转换为空返回。初始化因异常终止时，若能找到合适的匹配释放函数，就先释放这次构造所用的存储，再继续传播异常；没有无歧义匹配的定制分配形式则未必能自动回收。[205] `malloc` 的分配失败返回空指针。[188]

分配与释放必须匹配：普通 `new T` 对应 `delete`，`new T[n]` 对应 `delete[]`，`malloc` 对应 `free`。直接把 `malloc` 返回的地址交给普通 `delete` 不满足删除表达式的来源要求，属于未定义行为；风险并不只是两个接口的内部实现可能不同。[19, 205]

通常所说的定位 new（`new (address) T(...)`）在已有、足够大且满足对齐要求的存储中构造对象，并不接管底层存储的释放责任。使用结束后，需要析构的类对象先调用相应析构函数，再由存储拥有者按原方式释放。显式调用析构函数不会改变原始分配接口的配对规则。C++20 对部分隐式生命周期类型的规则同样不取消这一要求；重用存储时，旧指针能否继续使用还取决于对象生命周期和相应的重用条件，而不只取决于地址是否相同。[19, 57]

</div>
</article>

<article class="qa-item" id="qa-memory-errors" data-level="basic" markdown="1">
<p class="qa-question">Q34 · 泄漏、悬挂、野指针、越界和内存不足有什么区别？置空能全部解决吗？</p>
<div class="qa-answer" markdown="1">

泄漏是需要释放的资源失去正确回收路径；悬挂指针或引用原来有效，但目标生命周期已结束；野指针常指未初始化或无合法指向的指针；越界是访问超出允许范围；内存不足则是分配或后续使用资源失败。它们涉及的有效性条件不同，单纯的空指针判断无法同时解决这些问题。

把指针初始化为有效地址或空指针，可以避免使用未初始化的指针值，但不会延长目标的生命周期。释放后将一个拥有者指针置空，也只改变这一处变量，不会更新其他别名、迭代器、异步回调或引用。RAII 使资源随拥有者销毁而释放；观察者能否安全使用目标，仍取决于所有权、容器失效规则和任务持有关系。[18, 42]

非空指针不等于有效对象。返回局部自动对象的地址、让异步任务保存借用地址，以及容器重分配使观察者失效，都可能造成悬挂。共享拥有者可以在使用期间保留目标，却不自动同步目标上的并发读写；注销回调也未必等待已经开始的调用结束，因此对象销毁还需要与回调退出建立明确的同步关系。[15, 16, 18]

计算缓冲容量时，长度相加或相乘若发生溢出，实际分配可能小于访问所需范围。`strncpy` 也可能不补零，且仍要求足够的目标容量，不能作为通用的安全替代品。代码审查与静态分析可以补充路径检查，动态检测则受实际执行路径和工具检测范围限制；没有报告错误不等于已经证明不存在缺陷。[146, 147]

</div>
</article>

<article class="qa-item" id="qa-strict-aliasing" data-level="principle" markdown="1">
<p class="qa-question">Q35 · 严格别名规则是什么？memcpy 和 bit_cast 为什么可行？</p>
<div class="qa-answer" markdown="1">

如果程序通过一个“不是该对象可访问类型”的泛左值读取或修改对象的存储值，行为是未定义；这条规则让编译器可以做基于类型的别名分析，假定不同类型的访问不会指向同一对象。[340] 可访问类型包括对象自身类型及其 cv 限定版本、对应的有符号／无符号类型、聚合类型与其成员、共同初始序列，以及字符类型或 `std::byte`。[340]

常见的类型双关写法都越过了这条线：把 `float` 的地址 `reinterpret_cast` 成 `int*` 再解引用、或在一个 `union` 里写入一个成员再读取另一个（除公共初始序列与字符检查外）都不保证有意义；`reinterpret_cast` 只改变访问时使用的类型，不创建对象，也不放宽别名规则。

可行做法是用字节复制：`std::memcpy` 把源对象表示复制到目标类型对象，或 C++20 的 `std::bit_cast`，后者要求两个类型尺寸相同且都是可平凡复制类型，语义是构造目标类型对象并复制其对象表示。[291] 复制之后按目标类型访问是合法的，这也是序列化与类型双关的推荐写法（优化器通常能识别 `memcpy` 而不再生成真实调用，但这不是保证）。

边界有两点：`bit_cast` 只是按对象表示转换，不同端序的机器会得到不同数值，因此它适合类型双关而不适合作为跨平台线格式的编解码；需要在既有存储上“开始”一个新类型对象的生命期时，要显式构造（placement new）或使用 C++23 起的 `std::start_lifetime_as` 一类工具，而不是靠强制转换。

</div>
</article>

<article class="qa-item" id="qa-copy-rule-five" data-level="principle" markdown="1">
<p class="qa-question">Q36 · 结构体能直接赋值吗？自己写字符串类时怎样避免浅拷贝和自赋值问题？</p>
<div class="qa-answer" markdown="1">

能否直接赋值取决于类型是否有可用的赋值操作。普通含整数的结构体通常按成员赋值；包含 const、引用或不可赋值成员时，相应默认赋值可能被删除。复制一个拥有资源的裸指针只复制地址，不复制资源，若两个对象都负责 delete，就会重复释放；非拥有观察指针的共享却未必有错。[174] 深复制可以建立独立缓冲、分开原来混淆的拥有关系，却不是通用的数据竞争消除器：复制时读取正在被另一线程修改的源，或随后并发读写同一个新对象，仍需要同步。[16]

独占字符串类的接口需要明确文本长度、零结尾和分配释放匹配；若支持增长，还需要维护容量。复制建立独立缓冲，移动转移拥有关系并留下合法的源状态。拷贝赋值可以先取得新资源，再通过不抛异常的 `swap` 提交，使分配失败时原值不变，也能正确处理自赋值；先删除旧缓冲再分配则会破坏这一保证。这种先复制后提交的策略会暂时同时保留新旧缓冲，并非没有额外存储成本。空串、空输入和移动后状态同样属于接口约定。普通业务类通常可以让 `string`、`vector`、`unique_ptr` 等成员承担资源管理，采用 Rule of Zero，而不必为每个类手写五个特殊成员。[13, 42]

下面的原创 C++11 教学类只保留零结尾文本的最小拥有接口。构造参数必须指向有效零结尾字符串；空指针作为错误拒绝，空字符串则是正常值。缓冲由 unique_ptr 的数组特化负责析构，因此不需要再手写 delete[]。[167]

```cpp
#include <cstring>
#include <limits>
#include <memory>
#include <stdexcept>
#include <utility>

class OwnedText {
public:
    explicit OwnedText(const char* source = "") {
        if (!source) throw std::invalid_argument("null text");
        const std::size_t length = std::strlen(source);
        if (length == std::numeric_limits<std::size_t>::max())
            throw std::length_error("text too large");
        data_.reset(new char[length + 1]);
        std::memcpy(data_.get(), source, length + 1);
    }

    OwnedText(const OwnedText& other) : OwnedText(other.c_str()) {}
    OwnedText(OwnedText&&) noexcept = default;

    OwnedText& operator=(OwnedText other) noexcept {
        data_.swap(other.data_);
        return *this;
    }

    const char* c_str() const noexcept {
        return data_ ? data_.get() : "";
    }

private:
    std::unique_ptr<char[]> data_;
};
```

复制构造分配独立缓冲，赋值的值参数先取得新拥有关系，再以不抛异常的 swap 提交。若复制分配失败，异常发生在进入赋值函数体之前，原对象尚未改变；自赋值也先取得独立副本，不会读取已经释放的地址。移动后的空句柄被 c_str 解释为空文本，可继续复制、赋值和销毁。返回的字符指针仍是借用，不能在对应缓冲被替换或释放后使用；此类没有实现容量增长、嵌入零字符或完整 std::string 接口。[55, 167]

</div>
</article>

<article class="qa-item" id="qa-call-abi" data-level="principle" markdown="1">
<p class="qa-question">Q37 · 函数参数一定从右到左入栈吗？函数调用与递归会发生什么？</p>
<div class="qa-answer" markdown="1">

不一定。实参求值顺序是语言规则，参数放在哪些寄存器或栈位置是 ABI，二者不能混为一谈。某些传统 x86 调用约定有相应入栈顺序，现代 ABI 常先使用寄存器，编译器还可能内联或优化掉调用。对于本篇固定的较新工作草案，普通函数调用的各参数初始化（包括相关计算与副作用）相互具有不确定先后而非交错求值的约束，也没有规定全部按源码从左到右执行；旧版本的求值规则须另行判断，不把当前草案整段回溯到 C++11。[207]

以默认 Windows x64 ABI 为例，参数列表前四个位置上的普通整数或指针参数按位置对应 RCX、RDX、R8、R9，调用者还须预留寄存器参数的影子空间；第五个及后续参数使用栈，浮点、聚合和变参另有传递规则。这里的参数位置不是表达式求值的先后。调用方为调用后仍需要的易失状态负责，被调用方使用相应非易失寄存器时须按约定保存、恢复，不是所有寄存器都一律压栈。[206]

实际调用传递参数、建立返回路径，并按约定保存需要的状态；正常返回时，需析构的自动对象结束生命周期，相关状态恢复，控制返回调用者。返回值的传递也遵循 ABI，而不是所有结果都经过栈。局部变量则按语言规则初始化和销毁，并非每个变量都必须有独立栈槽。

递归通常使多个尚未返回的调用帧同时存在，递归深度与每帧空间共同决定栈容量风险。终止条件缺失可能造成无界递归，有限但过深的递归也可能耗尽栈；若很大的自动数组实际放在栈上，即使没有递归也可能触及容量上限。尾调用消除不是通用的 C++ 保证。普通循环反复调用且每次已经返回，不会仅因调用次数多就持续累积栈。显式工作栈可以避免依赖同样深度的函数调用栈，但待处理状态所需的存储并不会因此消失。

</div>
</article>

<article class="qa-item" id="qa-memory-fragmentation" data-level="principle" markdown="1">
<p class="qa-question">Q38 · 内存碎片怎样形成？为什么长期服务的分配行为与分配器策略有关？</p>
<div class="qa-answer" markdown="1">

分配器只能在已有大块上按对齐与尺寸切分，且不能移动已分配对象（C／C++ 不提供搬迁和压缩，指针就是地址）。于是反复申请与释放不同尺寸会让空闲空间被切成互不相邻的小块，总量足够但缺少可用连续块（外部碎片）；按尺寸类取整分配又会留下用不到的尾部（内部碎片）。`malloc`／`free` 的接口只承诺分配与释放语义，具体策略由实现决定，碎片是分配器策略与负载共同作用的结果。[292]

glibc 的实现可以说明这类策略为什么可调：小请求来自堆，较大请求走内存映射，阈值与整理行为由环境变量或 `mallopt` 调整，`malloc_trim` 才尝试把空闲内存还给内核。[292] 这些接口的存在本身就说明“释放”不等于“立即归还”。

对长期运行的服务，碎片表现为内存占用随时间上涨、分配延迟尾部变差，极端情况下长期存活对象把地址空间钉住，导致看似总量充足却无法完成大块分配。缓解手段与代价分别是：固定尺寸对象池或尺寸类分配器（把碎片转成可控的内部碎片、稳定延迟，但浪费内存并要处理并发回收）；减少尺寸种类与小对象数量（改动数据结构）；分池管理大块与小块；必要时用分配器参数整归还策略（与具体实现绑定）。判断是否泄漏要看增长形态与分配栈，不能只看驻留内存指标。

</div>
</article>

<article class="qa-item" id="qa-memory-pool" data-level="scenario" markdown="1">
<p class="qa-question">Q39 · 简单内存池怎样设计？只保存空闲块列表够吗？</p>
<div class="qa-answer" markdown="1">

一个简单的定长池可以拥有一片存储，将其分为等宽槽，并用空闲链或预分配的索引栈记录可用槽。底层起始地址满足对齐要求还不够，槽间距也必须是所需对齐的整数倍，才能使每个槽都正确对齐。若空闲链接嵌在槽内，槽的大小和对齐还须同时容纳链接结构。申请取出一个槽，归还将其放回；这两个操作管理的是存储，对象的构造和析构另行处理。槽大小、对齐、容量耗尽时的行为以及并发访问条件共同构成池的接口约定。[57]

底层存储的拥有记录与空闲槽索引承担不同职责。只在析构时遍历当前空闲块，会遗漏仍被借出的存储；仅保存所有块的地址，也不意味着池可以在使用者尚未退出时释放它们。底层存储可以先交给 RAII 拥有者，再建立空闲索引，使索引初始化失败时仍有可靠的回收路径。重复归还、外来地址和大小溢出的处理也属于设计边界。[42]

槽的状态依次经历“空闲槽 → 预留槽 → 已构造对象 → 析构完成 → 空闲槽”。对象构造抛出异常时，预留槽应归还，但尚未建成的完整对象不执行析构；其已构造完成的子对象按语言规则清理。正常归还则发生在最后一次使用及对象析构之后，使空闲链接不覆盖仍存活对象的数据。并发池还需同步这些状态转换。[42, 55, 57]

空闲结构自身的分配也会影响收益。若每次归还都为 `list` 节点重新分配内存，就会削弱减少分配器调用的目标；嵌入链接或预分配索引可以避免这类额外申请。池可能降低固定工作负载的分配开销，但也会保留容量、产生内部碎片并增加生命周期约束，不能推导为所有程序都会更快。

</div>
</article>

<article class="qa-item" id="qa-class-optimization" data-level="scenario" markdown="1">
<p class="qa-question">Q40 · 栈一定比堆快吗？怎样优化一个 C++ 类而不改变语义？</p>
<div class="qa-answer" markdown="1">

栈分配不一定比堆分配快。常见自动对象的存储可以复用函数栈帧，而一般动态分配还要维护分配器状态，因而可能增加分配和释放的工作量。但总成本还包括对象构造、页面访问、数据访问模式以及编译器优化；连续组织的堆对象也可以具有良好局部性，栈上的存储则同样可能触发页面处理。比较需要对齐对象大小、生命周期和访问方式，不能从存放位置推出固定的性能倍数。[188, 206]

类的优化应落到具体成本。减少重复分配和批量处理可以减少分配器调用；移动独占资源可以避免复制其缓冲；紧凑布局可能减少数据占用，但也会改变 ABI。小标量按值传递可能比引用更合适，大对象的只读访问常用 `const` 引用；`unique_ptr` 与 `shared_ptr` 则分别服务于独占和共享所有权，不能仅因接口方便就引入共享计数。[13, 15, 18, 42]

友元与成员函数的选择首先决定接口和访问关系，`const` 约束相应成员函数的访问语义，`inline` 也不强制编译器进行内联展开。这些声明本身都不是加速证明。优化仍须保持异常保证、对象生命周期、ABI 和并发协议；若减少工作量的方式改变了这些条件，就不能称为语义不变的优化。[172, 198]

</div>
