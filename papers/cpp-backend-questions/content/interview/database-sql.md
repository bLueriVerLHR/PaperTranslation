<article class="qa-item" id="qa-sql-aggregation" data-level="basic" markdown="1">
<p class="qa-question">Q160 · SELECT、WHERE、GROUP BY、HAVING、ORDER BY 和 LIMIT 分别做什么？怎样写一个完整聚合查询？</p>
<div class="qa-answer" markdown="1">

SELECT 决定输出表达式，WHERE 筛选输入行，GROUP BY 按相应键形成分组，HAVING 筛选分组结果，ORDER BY 排列输出，LIMIT 限制返回范围。理解聚合时可沿“FROM／JOIN 形成输入 → WHERE 过滤 → GROUP BY 分组 → HAVING 过滤组 → 输出与排序 → LIMIT”的逻辑关系分析；这不是执行器必须逐阶段物化的物理计划，优化器仍可以在保持语义的前提下改写和下推。INSERT、UPDATE 和 DELETE 则分别增加、修改和删除数据。[91]

假设 `orders` 的 `id` 为非空主键，`customer_id` 表示客户，`amount` 是采用适当精度的非空、同币种金额，`status` 表示订单状态。下面的原创例子求已支付订单至少三笔的客户，按总额降序返回前十名，同总额用客户 ID 明确打破平局。

```sql
SELECT customer_id,
       COUNT(*) AS paid_count,
       SUM(amount) AS paid_total
FROM orders
WHERE status = 'paid'
GROUP BY customer_id
HAVING COUNT(*) >= 3
ORDER BY paid_total DESC, customer_id ASC
LIMIT 10;
```

WHERE 先排除未支付订单，所以 COUNT 和 SUM 都只处理已支付的输入；HAVING 再判断各客户的组是否至少三行。先对全部订单求总额、最后再按状态挑组，并不是同一个问题。`COUNT(*)` 计行，`COUNT(column)` 只计该表达式非 NULL 的行，不能随意替换。没有 ORDER BY 时不能依赖物理行顺序，GROUP BY 本身也不承诺输出有序；LIMIT 若没有确定次序，不能稳定表达同一批“前十名”。

MySQL 8.4 默认启用 ONLY_FULL_GROUP_BY。未聚合输出列通常应属于分组键，或满足 MySQL 能识别的函数依赖、单值限制等允许条件；例如不能在只按客户分组后任意选一个订单 ID，并指望 ORDER BY 指定是哪一笔。关闭该模式也不会自动定义组内取值规则。完整聚合查询除了写齐子句，还必须明确每一行输出表示什么、哪些值可被确定，以及平局和 NULL 怎样处理。[223]

</div>
</article>

<article class="qa-item" id="qa-sql-joins" data-level="basic" markdown="1">
<p class="qa-question">Q161 · INNER JOIN、LEFT JOIN 与 RIGHT JOIN 有什么区别？外连接条件放 ON 或 WHERE 是否一样？</p>
<div class="qa-answer" markdown="1">

INNER JOIN 只保留连接条件为真的行组合；LEFT JOIN 还为每条未匹配的左侧行生成一条右侧列为 NULL 的补齐行，RIGHT JOIN 对称地保留右侧。调整条件和输出列后，右连接可以改写为交换两侧的左连接，但不能忽略 SELECT * 等投影的列顺序变化。连接不是自动去重：一个客户匹配四笔订单，就会产生四个相应组合。[102]

沿用客户和订单的例子，下面的原创查询保留全部客户，并统计各自已支付订单。假设 `orders.id` 是非空主键，因此没有匹配时该计数为零，而不是把补齐行计成一笔订单。

```sql
SELECT c.id, c.name, COUNT(o.id) AS paid_count
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.id AND o.status = 'paid'
GROUP BY c.id, c.name
ORDER BY c.id;
```

这里 ON 决定哪些订单可以匹配，未找到已支付订单的客户仍有补齐行；COUNT(o.id) 忽略补齐的 NULL，因而得到零。若改成 COUNT(*)，这条补齐行会被计为一行，而不是零笔订单。若把 `o.status = 'paid'` 移到 WHERE，补齐行的条件为未知、不是为真，无支付订单的客户便被过滤。ON 与 WHERE 因而不能在外连接中不加条件地互换。[101–102]

再同时连接两张各有多条匹配记录的一对多表时，结果可能出现组合乘积，继而重复累加订单金额。应按问题所需的维度先聚合，或在只问“是否存在”时采用 EXISTS 等表达。DISTINCT 删除相同的结果行，但不能恢复已经重复累加的金额，也不是修复错误关联条件的通用方法。

</div>
</article>

<article class="qa-item" id="qa-mysql-types-null" data-level="basic" markdown="1">
<p class="qa-question">Q162 · MySQL 类型怎样选？NULL、字符集、排序规则和隐式转换有哪些边界？</p>
<div class="qa-answer" markdown="1">

先明确数据域，再选择表示。MySQL 的整数类型表达相应范围内的整数，DECIMAL 表达十进制定点数，FLOAT／DOUBLE 表达近似数。要求确定十进制精度的金额通常适合恰当精度、标度的 DECIMAL 或明确单位的整数，同时仍须规定溢出和舍入规则；使用定点列也不意味着任意混合浮点表达式都保持原来的精度。日期时间、字符、二进制、JSON 和空间数据各有专门语义，全部存成字符串会把范围和比较错误推迟到后续处理。[103,225]

CHAR 与 VARCHAR 在长度组织、填充和尾空格行为上有差别，比较还受排序规则影响。字符集决定编码，排序规则影响相等和排序，例如是否区分大小写；字符数、编码字节数与可见文字数量也不是同一个预算。唯一约束、连接和索引定位都使用相应比较语义，不能只凭字符串看起来不同就认定键不同。

NULL 表示缺失或未知，不等于零或空字符串。普通 `= NULL`、`<> NULL` 的结果为未知，应以 IS NULL／IS NOT NULL 判断是否缺失；MySQL 的 `<=>` 是另有定义的 NULL 安全比较。WHERE 只保留条件为真的行。比如 `3 NOT IN (1, NULL)` 不为真：3 不等于 1，但与 NULL 的比较未知，不能据此认定 3 不在集合中。NOT EXISTS 检查的是子查询是否有符合条件的行，二者只有在相应 NULL 与匹配条件下才可等价改写。COALESCE 提供替代值时，也必须确认未知值与所替代的零、空字符串是否真的表达同一业务含义。[101,225]

类型不同不意味着比较总是报错。MySQL 可以把字符串与数值转换后比较，既改变匹配集合，也可能改变索引定位方式；严格模式不是所有 SELECT 比较的统一拒绝开关。列类型、参数绑定类型、字符集和排序规则应共同符合预期数据域。[225]

这些列类型规则不能直接推广到所有数据库。SQLite 的普通表通常结合值的存储类别与列的类型亲和性处理数据，而不是全面采用 MySQL 式严格列类型；SQLite 3.37.0 起另提供 STRICT 表。相同的类型名称不足以证明跨产品具有相同约束或转换行为，这里涉及 MySQL 的选型和比较时应保留产品前提。[227]

</div>
</article>

<article class="qa-item" id="qa-database-keys-normalization" data-level="basic" markdown="1">
<p class="qa-question">Q163 · 主键、唯一键、外键和普通索引有什么区别？范式与反范式怎样取舍？</p>
<div class="qa-answer" markdown="1">

在 MySQL 中，主键是表所选的非空、唯一标识，可以由多列组成，但一张表只有一个主键约束；UNIQUE 约束限制相应键值重复，外键表达引用完整性，普通索引则提供访问路径而不禁止重复。可空 UNIQUE 可以出现多个 NULL 键值，不能因此视为与非空主键完全相同。InnoDB 通常用主键组织聚簇索引，但主键的逻辑约束与索引的物理组织仍是两件事，不能把这一映射推广为所有数据库的存储规则。[47,224]

范式讨论的是业务定义的函数依赖。在经典无 NULL 的关系模型中，<math><mi>X</mi><mo>→</mo><mi>A</mi></math> 表示所有合法数据实例里，属性集 X 的值相同就必须有相同的 A 值；某个小样本恰好不重复不能证明这种依赖。能决定全部属性的是超键，去掉任何属性便不再能做到这一点的是候选键；属于至少一个候选键的属性称为主属性，不只是属于最终选定主键的属性。[228]

| 范式 | 核心要求 | 所消除的典型问题 |
| --- | --- | --- |
| 1NF | 各属性的数据域按用途视为原子值 | 用重复组或一串同类业务值替代相应关系；“二维表”或“有主键”本身不是这项定义 |
| 2NF | 满足 1NF，非主属性不部分依赖于任何候选键 | 复合候选键的一部分已经决定某个非主属性，导致该事实被重复保存 |
| 3NF | 对每个非平凡的单属性函数依赖，决定因素是超键，或被决定的属性是主属性 | 常见的非主属性经其他属性传递依赖于键所造成的冗余 |

非平凡依赖指被决定属性不在左侧属性集中；属性集决定自身已有属性，不是这里讨论的冗余来源。例如，假定同一订单的同一商品只出现一个明细，且明细的候选键只有 `(order_id, product_id)`。当前商品名称由 `product_id` 决定，是非主属性对候选键真子集的依赖，因此不符合 2NF，宜把当前名称放入产品关系。再如客户可以有多笔订单，每客户只有一个当前电话；订单同时保存客户 ID 和当前电话时，订单 ID 决定客户 ID、客户 ID 再决定电话，重复保存会带来更新异常。3NF 的正式条件涉及所有候选键，不能机械缩写成“每列只能依赖所选主键”。[228]

拆分要保持所需信息及合理的约束检查，而不是按字段数量随意拆表。订单发生时的历史联系方式可能是独立业务事实，不能以去重名义改成只读取客户最新电话。反范式为读路径保留派生或冗余值，可能减少连接、计算，却增加写入、同步和恢复成本；必须说明哪个值是事实来源、哪些可重建，以及更新失败和并发时怎样维护它们。

</div>
</article>

<article class="qa-item" id="qa-database-view" data-level="basic" markdown="1">
<p class="qa-question">Q164 · 视图是不是保存了一份查询结果？视图能否更新，权限由谁决定？</p>
<div class="qa-answer" markdown="1">

普通视图保存查询定义，不是额外维护的一份持久结果表。在 MySQL 中，MERGE 把适合合并的视图定义并入外层查询，TEMPTABLE 使用临时结果，UNDEFINED 允许选择适合的处理方式。执行时形成临时中间结果，不等于数据库为这个普通视图持久维护了可复用的物化结果，也不保证视图比直接查询底层表更快。[93]

部分 MySQL 视图可以更新，但结果要能按其规则对应到底层行；聚合等定义没有可以任意反向修改的行映射，使用 TEMPTABLE 的视图也不能据此成为可更新对象。经可更新视图写入最终改变的是相应底层数据，而不是一张另外保存的视图数据表。[93]

WITH CHECK OPTION 要求经视图插入或更新的行继续符合相应条件。例如视图只显示某个范围内的记录，没有这项检查时，更新可能使该行不再出现在视图中，却并非删除了底层行。LOCAL 与 CASCADED 区分涉及下层视图时的检查范围，MySQL 默认 CASCADED；这项约束针对经视图的相应写入，不会自动限制具有底层表权限的其他写入路径。[93]

调用者仍需拥有对应的视图操作权限；SQL SECURITY DEFINER／INVOKER 再决定相关底层对象检查采用定义者还是调用者上下文。封装列与筛选条件只有配合实际授权才形成访问边界：同时开放底层表权限，就不能声称用户只能读取视图筛选后的内容。权限和定义者账户的变化也可能影响使用，这些具体规则应按产品处理。[93]

</div>
</article>

<article class="qa-item" id="qa-stored-routines-triggers" data-level="principle" markdown="1">
<p class="qa-question">Q165 · 存储过程、函数和触发器有什么作用？它们会自动形成独立事务吗？</p>
<div class="qa-answer" markdown="1">

存储过程把一组数据库操作封装成可调用的接口，可通过参数和结果集与调用方交换数据；存储函数返回相应值，用于允许它出现的表达式；触发器由指定表的数据事件激活，而不是由客户端像过程那样直接调用。它们把规则放到数据附近，可以减少部分客户端往返，却也使写入的实际调用链、部署和权限检查更复杂。[243,251]

这些对象不会自动创建能独立提交的嵌套事务。在 MySQL 中，存储程序里的 BEGIN…END 是复合语句块；过程若需开始事务，应使用相应 START TRANSACTION，同时仍受已有事务和隐式提交规则限制。函数和触发器不能这样开始事务，也不能独立提交或完整回滚事务；过程从函数或触发器调用时，不能借此绕开调用环境的限制。触发器中的 ROLLBACK TO SAVEPOINT 是手册允许的例外，因为它不结束事务，但也不形成独立内层事务。[95,243,251]

动态 SQL 也不是各类例程共有的能力：SQL 级 PREPARE／EXECUTE 可以用于过程，不能用于函数或触发器。函数不能向客户端直接返回普通结果集，函数或触发器也不能修改正在被触发它的语句读写的那张表。这些限制影响怎样拆分数据库接口，不能只按“代码都写在数据库里”把三者互换。[243]

触发器的执行和触发语句关联。BEFORE 失败会阻止对应行操作，AFTER 在相应前置触发器与行操作成功后执行；触发器错误会使整个触发语句失败。事务表可以撤销该语句的相应修改，非事务表则可能留下错误前已经发生的修改。外键动作不会激活触发器；行复制在副本上不会把源端行事件再当成普通语句激活其触发器，语句复制的路径不同，所以“所有数据变化都会重新跑一遍触发器”并不成立。[243,251]

触发器不能代替外部服务的可靠消息协议。数据库回滚无法撤销任意已经发出的网络副作用；需要跨系统传播结果时，可在本地业务事务中记录待投递事件，再由独立发送流程处理重试，并由接收方去重。这是协调边界的设计思路，不是普通触发器天然提供的跨服务原子性。

</div>
</article>
