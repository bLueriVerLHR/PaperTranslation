#### 事务、隔离级别与锁 {#interview-database-transactions}

<article class="qa-item" id="qa-database-acid" data-level="basic" markdown="1">
<p class="qa-question">Q173 · ACID 四项特性分别是什么？为什么事务不能自动保证全部业务一致性？</p>
<div class="qa-answer" markdown="1">

ACID 指原子性、一致性、隔离性与持久性（atomicity, consistency, isolation, durability），描述事务保证的不同侧面，不是一个“绝不出错”的标签。

| 特性 | 含义 | 不能由此直接推论的事 |
| --- | --- | --- |
| 原子性 A | 受该事务机制管理的修改整体提交或整体撤销 | 任意语句失败都已经自动回滚整个事务；外部通知也自动撤销 |
| 一致性 C | 按正确事务协议维护已经定义的状态约束 | 数据库自动知道未表达的余额、授权、金额守恒等业务规则 |
| 隔离性 I | 按所用隔离级别限制并发可见性与冲突 | 事务互相完全没有影响，不等待、不冲突，也不观察其他提交 |
| 持久性 D | 提交结果在约定故障模型及持久化条件下保存 | 任意刷盘配置、硬件失效或异步复制切换都保证零丢失 |

原子性尤其不能与错误处理混淆。InnoDB 某些错误只回滚当前语句，事务此前成功的修改还在；死锁则回滚整个事务。假设转账扣款已成功、入账错误只撤销该条语句，应用却继续 COMMIT，便可能提交仅扣款的状态。问题不是事务“部分提交”，而是应用把错误的修改集合当成了完整业务事务。必须根据错误与事务状态决定回滚或重试范围。[233]

唯一、外键等数据库约束只能检查已表达的规则。转账还需要正确的余额条件、授权与并发协议；把两条 SQL 放进事务而省略这些检查，仍可能提交错误结果。向外部服务通知或扣费也不会因为本地 BEGIN 自动参加原子提交，混用非事务表则有额外边界。[95]

并发异常包括读到未提交值的脏读、再次读取同一行看见不同已提交值的不可重复读，以及同一条件下匹配集合变化的幻读；读后无条件写回还可能丢失更新，多个事务对不同记录的决定可以形成写偏斜。快照、锁、约束及事务协议限制的是不同情况，一致性不等于每次读取最新值，隔离性也不能只用前三类读异常概括。[30,32,94,226]

</div>
</article>

<article class="qa-item" id="qa-database-isolation" data-level="basic" markdown="1">
<p class="qa-question">Q174 · 四种隔离级别怎样区分？InnoDB 的 RR 能否一句话概括为“没有幻读”？</p>
<div class="qa-answer" markdown="1">

隔离级别规定相应并发保证，但相同名称不表示每种数据库采用相同读写机制。InnoDB 默认 RR，普通读取的重要区别如下；此表不是锁定读和所有写操作的完整行为表。[94]

| 级别 | InnoDB 中相应普通读的特点 | 关键边界 |
| --- | --- | --- |
| READ UNCOMMITTED（RU） | 允许读取其他事务未提交的修改 | 可能出现脏读，不是较新的值就必然可靠 |
| READ COMMITTED（RC） | 每次一致性读取得相应新快照 | 两次读取间的提交可以改变值及匹配集合 |
| REPEATABLE READ（RR） | 相应一致性读复用首次建立的读视图 | 自己的修改另有可见性；锁定读与写入不是同一种历史读取 |
| SERIALIZABLE | 提供更强的串行化保证，并按相应条件使用锁定读 | 不能理解为数据库全局只运行一个事务或所有 SELECT 一律同样加锁 |

例如，假定甲在同一 RR 事务中首次一致性读得余额 100，随后乙把它改为 80 并提交，甲没有修改该行。甲再次普通一致性读仍可得到 100；若采用 RC，新的一致性读则可见这个已提交的 80。甲后续 FOR UPDATE 或 UPDATE 不能无条件按原来的 100 推理，必须依据相应锁定与修改规则。这是基于读模型的推导，不是把事务中所有语句都固定到同一快照。[30,94]

RR 普通一致性读由快照保持历史可见集合；范围锁定读和更新则在相应条件下使用记录、间隙或 next-key 锁限制插入。讨论“是否有幻读”要先说是在重复普通快照读、锁定范围，还是把读写混合为业务操作；快照稳定并不自动保证所有业务不变量。InnoDB 的 SERIALIZABLE 在关闭 autocommit 时可将普通 SELECT 转为相应锁定读，而独立的只读 autocommit SELECT 又有自己的处理规则。[30,32,94]

产品差异也说明不能只背现象表：PostgreSQL 17 将 RU 按 RC 处理，RR 实现已经防止幻读，但仍允许串行化异常；SERIALIZABLE 在快照隔离基础上监测相关依赖，可能报告串行化失败，应用需重试事务，而不是仅把所有读取改为与 InnoDB 相同的锁定读。更强保证会增加锁等待、监测或失败重试等不同成本，不等于取消并发执行。[226]

</div>
</article>

<article class="qa-item" id="qa-mysql-transaction-control" data-level="basic" markdown="1">
<p class="qa-question">Q175 · autocommit、SAVEPOINT、DDL 与 ROLLBACK 怎样相互作用？MySQL 支持嵌套事务吗？</p>
<div class="qa-answer" markdown="1">

MySQL 没有普通的嵌套事务：重复 START TRANSACTION 会隐式提交已有事务，SAVEPOINT 只是同一事务内的回滚点，许多 DDL 也会隐式提交。以下按 MySQL 的事务表语义区分这些交互。[95,234] autocommit 开启且没有显式多语句事务时，相应语句通常各自构成事务，并不意味着“没有事务”；START TRANSACTION 将操作组织到显式事务，COMMIT 提交，ROLLBACK 撤销受其管理的修改。关闭自动提交后，也不能以为每条成功语句已经单独持久提交。事务边界与当前语句是否成功、日志是否已同步是不同问题。

SAVEPOINT 标记当前事务中的位置，ROLLBACK TO SAVEPOINT 撤销该位置之后的相应修改，但不终止事务，也不保证释放这段操作取得的所有 InnoDB 行锁；手册对新插入行的撤销另有锁释放说明。RELEASE SAVEPOINT 只是移除保存点，不提交或回滚数据。外层 COMMIT／完整 ROLLBACK 才结束相应事务并清除保存点，保存点因此不是能独立提交的嵌套事务。[234]

MySQL 不提供靠重复 START TRANSACTION 自动嵌套的普通事务；新的开始操作可以隐式提交已有事务。许多 DDL、授权和管理语句也会造成隐式提交。CREATE／DROP TEMPORARY TABLE 是重要例外：相应操作不隐式提交，却不能由用户 ROLLBACK 撤销；“不隐式提交”和“可随外层事务撤销”不是同一个属性。[95]

DELETE 按条件删除行，事务表上的相应数据修改可以参与用户事务；TRUNCATE 走 DDL 路径，在 MySQL 中有隐式提交边界，DROP 则删除对象定义。即使数据库支持内部原子 DDL，也不等于可以把任意 DDL 与 DML 放入用户事务统一回滚。混用非事务表及外部副作用同样超出普通本地回滚保证。[95]

语句出错时还应判断是仅语句撤销还是整个事务已被回滚，不能吞掉异常后继续提交剩余工作。连接复用也必须有明确的事务收尾和会话状态管理，避免把未结束的事务交给下一个业务操作。[233]

</div>
</article>

<article class="qa-item" id="qa-mvcc" data-level="principle" markdown="1">
<p class="qa-question">Q176 · MVCC 为什么能减少读写阻塞？RR 的快照是在事务开始时建立的吗？</p>
<div class="qa-answer" markdown="1">

MVCC（multiversion concurrency control，多版本并发控制）让普通一致性读选择对其读视图可见的版本，不必为了读取历史已提交状态而等待每个正在修改该行的事务。InnoDB 聚簇记录中的 `DB_TRX_ID` 标识最近插入或更新它的事务，`DB_ROLL_PTR` 指向 undo 信息；当前版本不适合该次读取时，可以由 undo 重建更早的内容，直到取得相应可见版本。快照并不是在开始事务时复制整份数据库。[30,237]

因此，一个事务持有修改该记录的排他锁，另一个事务仍可能通过普通一致性读取到此前版本。这里减少的是相应读写阻塞，不是所有锁：更新与更新之间仍需处理冲突，唯一性和外键检查也有自己的要求。锁定读、UPDATE 和 DELETE 不能直接按普通快照读解释。[30,32]

在通常的 REPEATABLE READ 一致性读中，读视图由第一次相应 InnoDB 一致性读建立，不应一律写成普通 BEGIN 的时刻；显式一致性快照操作另有规定。READ COMMITTED 的一致性读则逐次取得新的快照。事务自身先前修改的行对自己可见，所以“所有 SELECT 都看到数据库在同一个历史瞬间的完整状态”也不成立。[30]

代价是保存并查找旧版本，以及在不再被需要时清理。update undo 只有在没有相应读视图仍可能需要它时才能回收；长时间保持快照的只读事务也可能阻碍这部分清理。删除还涉及标记和随后 purge，并非每次 DELETE 立刻移走全部物理记录。多版本改善某类并发读取，同时把一部分成本转到历史保留、版本重建和后台回收，不是无成本地消除幻行与业务并发问题。[45,237]

</div>
</article>

<article class="qa-item" id="qa-database-lock" data-level="principle" markdown="1">
<p class="qa-question">Q177 · InnoDB“行锁”锁的是什么？为什么有间隙锁和数据库死锁？</p>
<div class="qa-answer" markdown="1">

InnoDB 的事务记录锁作用于索引记录，而不是按应用中“返回了哪一行”直接决定锁集合。对同一记录，不同事务的共享锁 S 可以共存，排他锁 X 与其他事务的 S、X 冲突；但普通一致性读可以通过 MVCC 读取历史版本，不能泛称“加了 X 就不允许任何其他事务读取”。表级意向锁 IS、IX 表示相应行级加锁意图，使整表锁与行锁之间能检查兼容性，不等于已经把全表排他锁住。[30,32]

间隙锁限制相应区间中的插入，next-key 锁结合一条索引记录与它前方的间隙。例如相邻键为 10、20 时，记录 20 的 next-key 区间为 <math><mrow><mo>(</mo><mn>10</mn><mo>,</mo><mn>20</mn><mo>]</mo></mrow></math>，而不是“记录及其后方间隙”。只锁住既有记录不能阻止 15 这样的新键进入区间，范围保护因此需要处理不存在的键；但实际取得哪些锁，仍取决于访问路径、条件与隔离级别。[32]

这里的唯一索引例外指锁定查找等相关操作：通过唯一索引按完整且确能唯一定位的键值查找已存在记录，通常可以只锁记录；可空 UNIQUE 的 NULL 值不能直接当成这种唯一定值，未命中键、非唯一范围和复合唯一键只指定部分列也不能简单套用。RC 对普通搜索和扫描通常不采用同样的间隙锁规则，外键及重复键检查仍有例外。索引不合适时，扫描和锁定范围可能扩大，不能仅据 WHERE 的文字条件推断最终只锁一行。[32]

若事务甲先持有记录 A 的 X 锁，再等待乙持有的 B；乙先持有 B，再等待甲持有的 A，便形成等待环。这体现相应资源冲突、占有且等待、不能任意抢占和循环等待条件。统一访问顺序、缩短事务以及改善访问路径可以降低风险，但行锁、较低隔离级别或超时都不保证消灭死锁，也不能牺牲原有业务不变量。[232]

默认启用的死锁检测会选择受害事务并回滚整个事务，此时应按完整业务事务组织重试。锁等待超时则默认只回滚发生超时的语句；启用 `innodb_rollback_on_timeout` 才改变为整事务回滚。两者不能统一当成“最后一条 SQL 没成功”。处理错误前要明确其余修改与锁的状态，按业务约束决定整体撤销、重新读取和有限重试，并避免重试重复发出外部副作用。[233]

</div>
</article>

<article class="qa-item" id="qa-innodb-2pc" data-level="principle" markdown="1">
<p class="qa-question">Q178 · redo 日志与 binlog 怎样保证一致？崩溃恢复时如何判断一个事务该提交还是回滚？</p>
<div class="qa-answer" markdown="1">

两条日志记录的内容与用途不同：redo 日志是存储引擎的物理/页级修改记录，用于崩溃后把数据页恢复到一致状态；binlog 是服务层记录的变更事件，用于复制与时间点恢复。[31,46] 一个事务在两者都落盘后才算“提交完成”，否则可能出现数据已改而复制流里没有这次修改（或反过来）的不一致。

MySQL 在内部用两阶段提交把两者对齐：事务先在 InnoDB 中 prepare，binlog 写入并同步后，再在 InnoDB 中提交。[345] 这套内部协议与面向多数据源的 XA 分布式事务是两回事，不要把它当成应用层可加入的全局事务。崩溃恢复时，服务端扫描最新的 binlog 文件，收集事务的 `xid` 并计算最后一个有效位置，然后让 InnoDB 完成那些“已成功写入 binlog”的预备事务，并把 binlog 截断到有效位置；未提交也不在预备状态的事务则回滚。[345,350] 这样 binlog 反映的内容与 InnoDB 数据一致，副本不会收到已被回滚的语句。[345]

配置决定这套机制的强度：`sync_binlog=1` 让 binlog 每次提交都落盘，InnoDB 日志默认同步；若关闭同步，机器掉电可能丢掉 binlog 尾部，恢复时若发现 binlog 比预期短，会报错并提示需要从新快照重建复制。[345] 因此“写了 redo 就不会丢”与“binlog 一定完整”是两条不同的保证，判断持久性要同时看两个日志的刷盘设置。

</div>
</article>

<article class="qa-item" id="qa-innodb-deadlock-debug" data-level="scenario" markdown="1">
<p class="qa-question">Q179 · 线上出现死锁该怎样定位与处理？为什么应用必须能重试？</p>
<div class="qa-answer" markdown="1">

InnoDB 的死锁检测默认开启：检测到环时它会选择代价较小的事务作为牺牲者回滚，并返回错误给该事务的客户端；如果关闭检测（`innodb_deadlock_detect`），则靠锁等待超时来打破僵局。[347] 因此“每次死锁都有事务被回滚”是预期行为，应用必须能重试被回滚的事务，把死锁当成可恢复的并发冲突而不是致命错误。[347]

定位应看具体证据：`SHOW ENGINE INNODB STATUS` 显示最近一次死锁（涉及的事务、SQL、持有的锁与等待的锁），要长期留证可以开启 `innodb_print_all_deadlocks` 把全部死锁写入错误日志。[347] 恢复到“谁锁了什么、以什么顺序等待”之后，常见根因是不同事务以相反顺序更新多行或多表、缺少合适索引导致扫描并锁定更多区间、或者事务过大使持有时间长于预期；死锁概率与隔离级别无关，因为读操作不会因此改变写冲突。[347]

处理分两层：应用侧统一重试策略并保持幂等（见 [超时与重试](#qa-retry-backoff)），数据库侧把大事务拆小、固定更新顺序、为条件列建索引以减少锁定范围（相关机制见 [行锁与间隙锁](#qa-database-lock)）。把死锁频次当指标看，比在告警里逐个手工排查更能发现结构性设计问题。

</div>
</article>
