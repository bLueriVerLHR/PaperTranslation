#### 执行计划、容量与并发写入 {#interview-database-tuning}

<article class="qa-item" id="qa-mysql-explain" data-level="scenario" markdown="1">
<p class="qa-question">Q187 · 慢 SQL 应怎样定位？EXPLAIN 和 EXPLAIN ANALYZE 分别能证明什么？</p>
<div class="qa-answer" markdown="1">

先确定慢的是哪一类 SQL、什么参数范围，以及在怎样的并发下出现。一次请求的时间可能消耗在获取连接、锁等待、扫描计算、存储访问或传输结果上；计划只能解释其中一部分。还应同时看频率和总资源消耗：一条偶发的长查询，与大量中等代价查询压满资源，需要不同的处理。

EXPLAIN 描述优化器选出的计划，普通计划中的行数不是实际执行计数。常见字段可这样读：[96,241]

| 观察项 | 能说明什么及其边界 |
|---|---|
| type | 访问形态；ALL 与 index 分别可能是全表／全索引扫描，不能只按标签排名判断总耗时 |
| possible_keys、key | 候选定位索引与实际选择；key 也可能是用于覆盖扫描、却不在 possible_keys 中的索引 |
| key_len、ref | 使用的键字节及比较对象；推断用了哪些联合键部分还要结合类型、字符集和可空性 |
| rows、filtered | 估计检查行数及条件通过比例；后续连接的估计输入约为 rows 乘以 filtered 的百分比，不是最终实际结果数 |
| Extra 或相应结构化属性 | 覆盖访问、ICP、额外排序／临时结果等信息；不同输出格式不必具有同名字段 |

统计信息、数据倾斜和条件相关性可能造成估计误差。即使出现 Using index，遍历大量索引项和传输大量结果仍有成本；覆盖还受相应可见性处理限制。filesort 表示额外排序路径，不等于一定用磁盘文件，结果规模超过可用排序内存时才可能需要相应临时文件。[237,241–242]

EXPLAIN ANALYZE 会实际执行其支持的语句，并显示迭代器耗时、返回行数和 loops，不是完全无副作用的静态观察；支持的多表 UPDATE／DELETE 等路径还可能真实修改数据，使用前必须获得相应授权并控制数据与负载。[96] 迭代器时间包含子节点而不包含父节点，多个循环时显示的时间是每次循环的平均值。因此不能把整棵树时间直接相加，也不能把一个多次调用节点的显示时间当作所有调用的总成本。

定位之后再按瓶颈选择措施：减少读取列与候选行、调整索引或连接形态、改善估计依据、缩短锁持有，或者限制过高并发。修正计划、一次受控执行和稳定负载下的性能结论是三种不同证据；本篇只作静态解释，没有运行这些数据库操作。

</div>
</article>

<article class="qa-item" id="qa-mysql-pagination-insert" data-level="scenario" markdown="1">
<p class="qa-question">Q188 · 插入、排序和深分页怎样优化？游标分页为什么还需要唯一顺序和索引？</p>
<div class="qa-answer" markdown="1">

插入、排序和分页应分别减少请求开销、额外排序及无用扫描，但不能改变所需的提交和读取语义。多行 VALUES 可以把多条插入的客户端请求与解析开销合并，适量批次也可分摊提交成本；额外索引仍要维护，大事务仍扩大日志、锁持有和恢复成本。批次大小、参数及持久化要求必须一起考虑，不能把官方示例的倍率当成本机收益，或为加速而默认关闭约束。[254]

排序有两条基本路径：利用适用的有序索引，或者对候选结果额外排序。前者也受成本选择制约，例如取很宽的行、大量回表时未必更划算。联合索引能否支持 ORDER BY，还要检查前置列是否被相应条件固定、剩余列顺序和升降方向是否匹配；混合 ASC／DESC 不能无条件用任意同列索引代替。[28–29,242]

OFFSET 深分页往往先取得并丢弃前面的记录。即使顺着有序索引读取，跳过很多行也不是免费操作；若还要排序或残余过滤，候选处理量可能更大。连续向后读取时，可以改为从上一页的键值边界继续。以下原创示例假设 created_at 非空、id 唯一且排序键在读取期间稳定；租户、时间和 ID 均已绑定，有与访问形态相配的索引。它只给出语义，不是实测计划。

```sql
SELECT id, created_at, amount
FROM orders
WHERE tenant_id = ?
  AND (created_at > ? OR (created_at = ? AND id > ?))
ORDER BY created_at ASC, id ASC
LIMIT 20;
```

时间参数需要两次绑定相同值，id 打破相同时间的平局。若只比较时间，上页末尾同一时间的其他记录可能被漏掉；上述条件先取更晚时间，再取同一时间而 id 更大的记录。可以考虑以 tenant_id、created_at、id 组织联合索引，再按返回列和实际成本判断是否需要覆盖；写出条件本身不保证优化器一定选择预期访问路径。[28–29,91]

键值继续分页通常不能直接跳到任意第 N 页。唯一顺序也不等于跨请求的固定快照：新插入可能落在已经越过的边界之前，删除会减少记录，排序键更新可能造成遗漏或重读。应先约定是接受实时变动、固定业务截面，还是维持一致快照；长期事务快照也有保留历史和占用资源的代价，不能只为分页便利而忽略它。[30,237]

</div>
</article>

<article class="qa-item" id="qa-database-sharding" data-level="scenario" markdown="1">
<p class="qa-question">Q189 · 分区、分库分表与读写分离分别解决什么？扩容会增加哪些一致性成本？</p>
<div class="qa-answer" markdown="1">

表分区把一张逻辑表按规则分成分区，分库分表把数据路由到不同物理表或节点，读写分离则把部分读取交给副本。分区裁剪可能减少候选范围，分片可能分散容量与负载，副本可能分担读取；增加分区不等于增加服务器，增加副本也不等于把源端写入自动分摊到多个节点。

MySQL 8.4 原生分区支持限于 InnoDB 和 NDB，相应约束有产品边界。例如分区 InnoDB 表不支持外键；分区表达式涉及的列必须包含在每个唯一键中，也包括主键。若业务要求 `id` 本身全表唯一，不能简单把主键从单列 `id` 改成 `id` 与分区列组成的复合键后就认定约束保持不变，因为后者允许相同 `id` 配不同分区列。[245–246]

分片键决定哪些操作能在一片内完成。按用户路由有利于用户内查询，却可能把跨用户转账、全局排行榜和唯一性检查变成跨片操作。按哈希平均分配记录数，也不保证热点用户的请求量平均。跨片排序分页要汇总候选并维护全局顺序，迁移则还要协调路由切换和在途读写；普通单库事务不能被直接当成跨片事务。

读副本仍有应用延迟，写后读与故障切换需要明确进度和副本选择协议。[98–99] 选择扩容方式前，应指出要缓解的是容量、读取还是写入瓶颈，以及哪些约束可留在本地、哪些需要跨节点维护。协调、热点与迁移成本都可能限制扩展，节点数不能直接换算成线性吞吐。

</div>
</article>

<article class="qa-item" id="qa-online-ddl" data-level="scenario" markdown="1">
<p class="qa-question">Q190 · 大表加字段或改索引为什么会阻塞查询？在线 DDL 怎样才能真正在线？</p>
<div class="qa-answer" markdown="1">

MySQL 用元数据锁（metadata lock，MDL）保证结构一致性：事务或语句访问表时会对表加元数据锁，并在事务结束前保持，因此其它会话对该表的 DDL 必须等待这些锁释放；反过来，等待中的 DDL 会阻止后续到来的读写请求获取元数据锁，于是短 DDL 也可能把整张表的访问堵住。[348] 这就是“加一个字段导致接口超时”的常见链条：一条长事务或未提交的会话持锁，DDL 排队，后续查询全部排在其后。

判断与预防要按证据来：用性能模式中的 `metadata_locks` 表查看谁持有锁、谁在等待，[348] 并在变更前先确认没有长事务或空闲会话占着表。DDL 本身也应选择合适算法：支持在线变更的操作会尽量减少锁时间，但并非所有操作都能完全在线（例如改列类型往往仍需重建表）；社区工具的做法是建副本表、分批拷数据、再短暂改名切换，把长时间持有放在副本上，代价是额外空间、触发器或 binlog 同步的复杂度，以及切换瞬间的一致性窗口。

把“在线”理解为“锁时间短”而不是“没有影响”更准确：即使不阻塞，重建表仍会消耗 I/O 与 CPU、增加主从延迟（见 [复制与延迟](#qa-mysql-replication-path)），变更窗口要按业务低谷与容量余量安排，并在变更后核对延迟与错误率，而不是只看命令是否返回成功。

</div>
</article>

<article class="qa-item" id="qa-sharding-problems" data-level="scenario" markdown="1">
<p class="qa-question">Q191 · 分库分表之后会带来哪些新问题？全局 ID、跨分片查询和分布式事务怎么处理？</p>
<div class="qa-answer" markdown="1">

分片把单机容量与写入压力分散，但也把“一个数据库”的保证拆掉了：应用与运维要知道数据在哪个分片，单机可用的 SQL 在分片后不一定等价（表名变化、分页、排序、聚合与分组都可能失效），跨库事务变得更难处理。[357] 这不是实现细节，而是水平扩展的固有代价：原本由单机事务与单一执行计划承担的一致性，现在要由应用或中间件重新组织。

三类问题各有常见对策。全局 ID：用统一发号器（数据库号段、Snowflake 类时间戳 + 机器号方案）或让分片键自身保证唯一，避免依赖单表自增；跨分片查询：把分页与聚合改成按分片并行执行再归并（注意每片取足够数据才能正确排序分页），或把常用查询维度做成冗余表、宽表与离线的汇总数据，牺牲写入成本换取读路径简单；分布式事务：能避免跨分片写就避免（把同一事务涉及的行设计到同一分片），必须跨分片时用 XA 或柔性事务（TCC、Saga、本地消息表）实现最终一致，并明确补偿与幂等。[357]

评估是否该分片要先看真实瓶颈：单表行数本身不是分片的充分理由，索引命中率高、缓冲池能放下热数据的表即使很大也能工作；真正驱动分片的是单机写入吞吐、单表维护（DDL、备份、清理）成本与存储上限。分片键要选基数足够、查询最常用的维度，因为它决定后续所有路由、扩容与数据迁移的成本。[357]

</div>
</article>

<article class="qa-item" id="qa-db-connection-pool" data-level="scenario" markdown="1">
<p class="qa-question">Q192 · 数据库连接池和最大连接数该怎样定？连接泄漏怎样发现？</p>
<div class="qa-answer" markdown="1">

数据库连接是有成本的共享资源：服务端为每个客户端连接分配线程与内存，`max_connections` 就是允许的同时客户端连接上限（默认 151，且实际生效值不超过文件描述符上限减去固定余量）。[351] 因此“池上限 × 实例数”必须小于服务端能承受的连接数，否则扩容应用实例会先打满数据库，表现为连接被拒、认证失败或排队超时。

池大小按并发占用推导而不是按直觉：如果单个查询的平均执行时间是 W、请求到达率是 λ，则平均占用连接数约为 λW（Little 定律[10]）；池必须覆盖峰值占用，并把溢出变成可控的等待（有上限的排队）而不是无上限堆积。把池调大只能提高同时执行的查询数，若下游是 I/O 或锁瓶颈，更多并发会让单次延迟上升、反而降低吞吐。

连接泄漏与连接污染的排查方式不同。泄漏表现为池占用随时间上涨、等待超时增加，常见原因是取用后没有归还（异常路径未释放）、或把连接传给了生命周期更长的对象；连接污染则表现为偶发的“状态错乱”（未提交事务、临时表、会话变量、锁未释放），处理方式是在归还时回滚事务并按需重置会话，而不是只在业务代码里补 `commit`。监控上应同时看池内空闲/活跃/等待数、等待时长与数据库端的连接数与线程状态，才能区分“池太小”和“取用后不归还”。

</div>
</article>

<article class="qa-item" id="qa-sql-concurrent-update" data-level="scenario" markdown="1">
<p class="qa-question">Q193 · 怎样防止库存读改写丢失更新和重复请求？参数化 SQL 是否解决所有注入问题？</p>
<div class="qa-answer" markdown="1">

丢失更新常来自把一次读改写拆成互不保护的步骤。例如两个请求都读到库存 10，各自扣 1 后都写回 9，最终只体现一次扣减。可以采用悲观并发控制，在同一事务中先按正确条件锁定记录，再读取和修改；也可以用版本条件更新实现乐观并发控制，把检查与修改放进一条语句。以下原创示例按 InnoDB 事务表解释：product_id 是非空唯一键，参数按相应列类型正确绑定，库存和 version 为非空、适当范围内的整数，扣减参数为正整数，递增不会溢出，且没有改变该协议的触发器。参数依次为扣减数量、商品 ID、期望版本和同一扣减数量。

```sql
UPDATE inventory
SET quantity = quantity - ?, version = version + 1
WHERE product_id = ? AND version = ? AND quantity >= ?;
```

WHERE 同时检查版本和余量，SET 在条件满足时完成扣减并递增版本。若两个请求都持有版本 5，第一个成功修改并提交为 6，第二个经所需等待后再按当前记录检查版本 5 时就不匹配，不能把旧计算无条件覆盖上去；若第一个回滚，则不能据此断言第二个必失败。版本方案称为乐观并发控制，不代表引擎写入时不加锁，也不是等到应用提交时才由数据库自动发现所有冲突。[32,94,247]

应先确认语句成功，再读取驱动返回的行数。唯一商品键和上述数值前提下，一行表示该条件修改发生，但显式事务仍需成功提交；零行可能是不存在、版本冲突或余量不足，并不区分原因。一般 UPDATE 默认报告实际改变行数，而 CLIENT_FOUND_ROWS 可改为匹配行数；不能把任意更新的零行都解释成版本冲突。此例匹配后必改变版本，才避免了“匹配但原值不变”的歧义。[247–248] 重试仍要限制次数并判断事务状态；死锁和默认锁超时的回滚范围不同。[233]

版本控制也不能解决业务重复请求。若扣减已提交而响应丢失，重发方无法只凭旧版本失败判断第一次是否成功。应给业务请求稳定的幂等键，用唯一约束竞争同一请求，并在适当事务范围内协调该键、业务修改与结果记录；重复请求返回原有结果，而不是重新扣减。幂等键还需约束请求内容，不能让同一键悄悄代表不同商品或数量。

正确的值参数绑定把 SQL 结构与数据分离，不是靠删除几个危险关键词。MySQL 的参数标记用于数据值，不能替代表名、列名或 SQL 关键词；动态标识和排序片段应从明确允许集合中选择。把用户文本先拼进 SQL 再 PREPARE，并不会把已拼入的语法变回数据。参数类型和业务数据域、访问权限也仍要检查，参数化不能代替授权。[255]

</div>
</article>
