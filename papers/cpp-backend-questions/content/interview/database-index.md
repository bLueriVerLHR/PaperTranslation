#### 存储引擎、索引与访问路径 {#interview-database-index}

<article class="qa-item" id="qa-mysql-engines" data-level="basic" markdown="1">
<p class="qa-question">Q166 · InnoDB、MyISAM 和 MEMORY 怎样比较？InnoDB 是否不支持全文索引？</p>
<div class="qa-answer" markdown="1">

三者在事务、并发机制与故障后状态上不同：InnoDB 提供事务、MVCC 与崩溃恢复，MyISAM 和 MEMORY 不提供同一套事务能力，主要以表级锁组织并发；按 MySQL 8.4 的能力说明，InnoDB 支持全文索引，因此“InnoDB 不支持全文索引”并不成立。[92] 比较某种负载的快慢前，应先对齐这些边界。

| 引擎 | 事务与并发机制 | 存储与索引要点 |
| --- | --- | --- |
| InnoDB | 提供事务、MVCC、记录及相应范围锁、崩溃恢复 | 行数据采用聚簇组织，二级索引通过聚簇键定位；支持全文和空间索引 |
| MyISAM | 不提供 InnoDB 式事务，主要采用表级锁 | 行数据与索引的组织不同，不能照搬 InnoDB 的回表或缓存解释；支持全文索引 |
| MEMORY | 不提供相同事务能力，主要采用表级锁 | 表数据保存在内存，重启后表定义仍可保留但行数据为空；默认 HASH，也可选择 BTREE 索引 |

MEMORY 的定义保存在数据字典中，不能把表定义存在与行数据仍存在混为一谈。哈希索引适合完整键的相应等值定位，不提供普通有序范围或键前缀遍历；B-tree 则可承担相应范围与顺序访问。InnoDB 的自适应哈希索引是内部优化，并不意味着用户可以给任意 InnoDB 表选择与 MEMORY 相同的通用 HASH 索引。“数据在内存”也不自动意味着具有持久性或事务回滚能力。[29,92,238]

“InnoDB 不支持全文索引”已不适用于现行版本：官方特性表说明 MySQL 5.6 起支持 InnoDB FULLTEXT，5.7 起支持相应空间索引；FULLTEXT 面向 CHAR、VARCHAR、TEXT 等支持的文本列，不能把任意普通索引当全文检索。版本、列类型和实际访问运算仍需匹配。[92,224]

引擎选型应对齐数据重要性、事务边界、恢复方式、锁竞争和查询形态。“读多用 MyISAM、写多用 InnoDB”跳过这些条件，也没有给出可公平比较的工作负载，不能据此保证快慢。

</div>
</article>

<article class="qa-item" id="qa-btree-index" data-level="principle" markdown="1">
<p class="qa-question">Q167 · 为什么数据库索引常用 B+ 树？InnoDB 主键索引与二级索引有何不同？</p>
<div class="qa-answer" markdown="1">

B+ 树适合同时需要精确查找、范围访问和有序遍历的页式存储。内部节点用分隔键和子页指针引导查找，叶层保存有序记录；查到范围起点后，可以沿叶层继续扫描，不必为每一条记录重新从根定位。多路分支比二叉结构容纳更多子页，因而可能减少访问层数。哈希索引适合完整键的等值定位，却不能由哈希值顺序直接得到原键的有序范围。

假设理想均匀满载树的内部节点各有 b 个子节点，每个叶页存 c 条记录，其中 b 至少为 2、c 为正整数；从根到叶共 h 层，则记录数满足 <math><mi>N</mi><mo>=</mo><mi>c</mi><msup><mi>b</mi><mrow><mi>h</mi><mo>−</mo><mn>1</mn></mrow></msup></math>，所以 <math><mi>h</mi><mo>=</mo><mn>1</mn><mo>+</mo><msub><mi>log</mi><mi>b</mi></msub><mrow><mo>(</mo><mfrac><mi>N</mi><mi>c</mi></mfrac><mo>)</mo></mrow></math>。在固定 b、c 的条件下，层数随 <math><msub><mi>log</mi><mi>b</mi></msub><mi>N</mi></math> 增长。这是空间组织模型，不是每次查询必有 h 次磁盘 I/O：上层页可能已在缓存，叶页也可能命中缓存；实际填充、分裂、页大小和访问局部性还会改变成本。[236]

在 InnoDB 中，聚簇索引的叶记录承载行数据。表有主键时以主键组织；确实没有主键时，选取第一个所有键列都非空的 UNIQUE 索引，否则生成以内部行 ID 为键的聚簇索引。一个表的行数据只有这一套聚簇组织，但可以有多个二级索引。二级记录包含聚簇键，用它再次查找行数据的过程通常称为回表；因此聚簇键较宽会放大各个二级索引。键序也不等于文件中的页一定物理相邻，更不保证没有 ORDER BY 的结果顺序。[47,91]

覆盖索引包含查询所需列，可能省去单纯为取列值而进行的聚簇查找，但事务可见性检查仍可能要求访问聚簇记录。维护索引还要付出写入、页分裂、空间和缓存占用的代价；页留有可用空间也并非“浪费最小”的无条件保证。[236–237]

索引分类有不同维度：主键、唯一和普通索引描述约束角色，聚簇和二级描述行的组织与定位，有序、哈希、全文和空间索引则描述访问结构或用途，不能把它们当成一组互斥名称。MySQL 的空间索引采用 R-tree，FULLTEXT 提供文本检索；其他产品又有不同索引族。例如 PostgreSQL 17 的 GIN 按组成值建立倒排条目，GiST 是依算子类支持不同搜索策略的框架，并不是 MySQL 可照搬的索引类型选项。[224,235–236]

</div>
</article>

<article class="qa-item" id="qa-composite-index" data-level="principle" markdown="1">
<p class="qa-question">Q168 · 联合索引为什么有最左前缀？范围条件后面的列是否完全没用？</p>
<div class="qa-answer" markdown="1">

联合 B-tree 索引按键元组的字典序排列。例如 `(tenant, created_at, id)` 先按租户，再按时间，最后按 ID。固定租户后，时间范围对应这一前缀下的有序区域；只给时间条件时，不同租户的相应记录分散在多个前缀下，不能直接当作一次普通连续范围查找。这是最左前缀的结构原因，不是要求 WHERE 中的普通等值条件按索引列顺序书写。[28]

在 MySQL 手册介绍的多段键范围提取中，可以沿连续的等值键部分继续收窄区间，遇到相应不等范围后则不再按同一方式继续使用后面的键部分。因此固定 `tenant`、限制 `created_at` 后，附加 `id` 条件不一定进一步收窄所扫描的键区间；这并不意味着 `id` 没有作用。[29]

后续列可以过滤已经扫描到的候选项，也可能使查询覆盖所需列。当还需要取得完整行且满足索引条件下推（ICP）的适用条件时，引擎可以先用二级索引中的字段检查一部分条件，排除不匹配项后再访问聚簇记录。缩小扫描区间、减少回表和完全覆盖取列是不同收益，不能用一句“范围之后失效”把它们合并。覆盖取列也不取消 MVCC 所需的可见性检查。[231,237]

MySQL 8.4 在特定条件下还可以采用 Skip Scan：枚举缺失前缀的不同值，为各个前缀分别构造范围。它有适用限制和枚举成本，不是所有缺首列查询都能受益，但足以说明“没有首列条件就绝不访问此索引”过于绝对。[29]

将高选择性字段一律放最左也不充分。常用等值组合、租户隔离、范围、排序、分页及写入成本共同决定列顺序；合适的键序有时还能避免另行排序。设计首先应说明如何定位区间、预计扫描多少候选项，以及扫描后还需过滤和读取哪些列。

</div>
</article>

<article class="qa-item" id="qa-index-choice" data-level="principle" markdown="1">
<p class="qa-question">Q169 · !=、IS NULL、函数和类型转换会让索引“一定失效”吗？</p>
<div class="qa-answer" markdown="1">

不一定。“能否形成可用的索引区间”“索引能否过滤或覆盖”“优化器最后是否选择它”是三个问题。MySQL 8.4 的 B-tree 范围优化可以处理相应 `!=`、`<>`、`IS NULL` 和 `IS NOT NULL` 条件；NULL 也不是索引一律不存储、不检索的值。因此这些符号不是绝对失效清单。若条件匹配表中大多数行，即使能形成范围，所选扫描方式仍可能不同。[29]

函数条件要看索引实际保存的键。只在原列上建立普通索引，不代表能直接按任意 `f(column)` 定位；MySQL 8.4 支持符合限制的函数键部分，生成列索引或保持语义的改写也可能提供另一条路径。字符串前缀索引则以较短键换取空间，可能降低区分度，不能代替完整列值的所有用途。表达式、长度、类型与排序规则都须匹配实际需求。[224]

隐式转换也不能统一判断。例如 MySQL 比较索引字符串列 `str_col` 与数值 `1` 时，`'1'`、`' 1'`、`'1a'` 等不同字符串都可能转换为同一数值，原字符串索引不能用于这种数值等值定位；改成字符串参数则是另一种比较语义。严格模式并不使普通 SELECT 的所有这种比较都变为报错。参数应绑定到预期数据域，改写还必须确认没有改变业务匹配规则。[225]

`LIKE 'abc%'` 在满足相应类型与比较条件时可形成前缀范围；`LIKE '%abc'` 通常不能获得这样的普通 B-tree 起点，但仍可能扫描较小的覆盖索引，或利用其他条件先缩小候选集合。条件文本顺序与索引顺序不同、缺少联合索引首列、范围后还有键列，也应按 [联合索引的最左前缀](#qa-composite-index) 的访问机制判断，而不是归入同一张禁用清单。[29,231]

索引能够定位大量匹配行却需要逐条回表取得宽记录时，全表扫描可能成本更低；少数值的列也不等于永远不值得索引，实际分布、组合条件和覆盖需求都重要。合适索引还可能减少排序或某些聚合需要处理的数据，但不使任意 COUNT、MIN、MAX 自动变成常数时间。额外或过宽索引增加写入和缓存成本，重建也有资源代价，不能把定期重建当作固定获益操作。EXPLAIN 描述所选计划，不能单凭静态 SQL 语义推导实际耗时。[29,96]

</div>
</article>

<article class="qa-item" id="qa-index-condition-pushdown" data-level="principle" markdown="1">
<p class="qa-question">Q170 · 索引条件下推（ICP）与覆盖索引怎样减少回表？两者有什么不同？</p>
<div class="qa-answer" markdown="1">

没有 ICP 时，存储引擎沿索引找到行位置后就把整行读出来交给服务层，再由服务层判断 `WHERE` 里剩下的条件；启用 ICP 后，服务层把“只用索引列就能判断”的那部分条件下推给存储引擎，引擎先按索引项判断，只有通过才去读整行。[346] 这减少了回表次数与层间交互次数，适用对象是范围/等值/ref/ref_or_null 扫描，InnoDB 上只对二级索引有意义（聚簇索引本来就把整行读进缓冲，省不了 I/O），并且子查询、存储函数、触发器相关的条件不会下推。[346]

覆盖索引解决的是另一个问题：如果查询需要的列都在索引里，引擎可以只读索引、完全不回表，此时 `EXPLAIN` 显示 `Using index`；而 ICP 生效时显示 `Using index condition`，两者不是一回事，也不会同时为同一读取路径表达同一件事。[346]

工程判断要区分“减少回表次数”与“减少读取总量”：ICP 让不满足条件的行不产生回表 I/O，但索引扫描本身仍要走过这些索引项；覆盖索引减少的是每行读取的字节数，代价是索引更宽、写入与内存开销上升。选择时要看选择性与列宽：前缀很窄但过滤性强的条件下推收益明显；查询列少且热点高时覆盖索引更划算。两者都依赖优化器选择该索引，因此仍需看 `EXPLAIN` 的实际计划，而不是只看索引是否存在。

</div>
</article>

<article class="qa-item" id="qa-primary-key-choice" data-level="principle" markdown="1">
<p class="qa-question">Q171 · 自增主键、UUID 与页分裂：主键选择怎样影响写入与索引大小？</p>
<div class="qa-answer" markdown="1">

InnoDB 把行按聚簇索引组织，二级索引里保存的是主键值而不是行地址。[47] 因此主键长度会放大到每个二级索引条目上：长主键（例如 36 字节的字符串 UUID）不仅让聚簇索引更大，也让所有二级索引更大，缓冲池里能放下的行更少；短且单调的主键在空间与比较成本上更有利。[47]

写入模式上，自增值让插入集中在索引右侧，页填满的方式更规则；随机分布的主键（随机 UUID、哈希值）会让插入分散到整个 B+ 树，更多页面被反复打开、分裂与回填，写放大与脏页分布更差。这是 B+ 树插入与页分裂的机制推断，属于通用索引行为，具体收益取决于键分布、页填充率与并发写入强度，不能把“UUID 一定慢数倍”当成恒定结论。

`AUTO_INCREMENT` 的取值分配还受并发与复制格式影响：MySQL 8.4 默认使用 interleaved 锁模式（取值可交错分配），该模式随着行格式复制成为默认而成为默认设置；其它模式在语句级复制下有不同约束。[349] 也就是说自增值只能保证唯一与递增趋势，不保证连续，更不保证按提交顺序生成，应用不应依赖它做排序或业务编号。

折中方案是按业务需要选：需要短小且有序时用自增或时间有序的 64 位标识；需要无中心生成时用带时间前缀的有序 UUID 变体（如 UUIDv7 类方案）以减少随机性；需要对外隐藏规模时用单独的映射表或编码后的 ID，而不是直接把随机字符串当聚簇主键。

</div>
</article>

<article class="qa-item" id="qa-lsm-compaction" data-level="principle" markdown="1">
<p class="qa-question">Q172 · LSM 怎样组织日志、memtable 和 SSTable？为什么需要 compaction？</p>
<div class="qa-answer" markdown="1">

典型 LSM（Log-Structured Merge，日志结构合并）将新写入记录在内存结构中，并按持久性配置写日志；内存结构冻结、刷成不可变有序文件，读取综合内存与相关文件中的版本。Compaction 合并有序记录，整理旧版本和删除标记，以控制查询和存储成本。[149–150]

日志应对尚未刷入文件的更新恢复，SSTable 保存有序记录，文件清单描述有效文件集合；它们不是同一种状态。RocksDB 文档还区分是否启用 WAL 与是否同步日志，不能由“API 已返回”无条件推出断电不丢失。[149] 删除标记需遮蔽旧值，只有满足快照可见性和旧版本覆盖等条件时才可清理，否则旧文件中的数据可能重新出现。

写放大表示物理写入相对逻辑更新的额外工作，读放大来自查询多个候选结构，空间放大来自旧版本、重叠文件和合并期间的临时存储。层级与分层合并在这些量之间取舍，后台处理不足还可能触发写入停顿。[150] 与 B+ 树相比，批量顺序整理可能有利于写入，却增加合并与读取成本；收益取决于键分布、缓存和读写形态。这里是官方动态架构文档的机制说明，未审计某个 RocksDB 发行版或运行引擎。

</div>
</article>
