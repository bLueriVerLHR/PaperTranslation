### 云端通用引擎：请求驱动的调度与状态管理

#### vLLM：从请求进度到实际输入批

vLLM 的一条生成请求经过协议处理、输入预处理、引擎核心、调度器、执行器、GPU worker、采样和输出处理。`vllm/v1/engine/async_llm.py` 的 `AsyncLLM` 连接前端与引擎；`engine/core.py` 的 `EngineCore.step` 串起调度、执行和状态回写；`core/sched/scheduler.py` 的 `Scheduler.schedule` 决定本步计算量；`worker/gpu_model_runner.py` 的 `GPUModelRunner` 构造设备输入和注意力元数据。

进程边界把协议解析、tokenizer、流式输出与核心执行解耦，但消息、序列化、忙轮询和错误传播都有成本。worker 消费引擎定义的调度输出，无需从原始 HTTP JSON 自行推断状态。`core/sched/output.py` 的 `SchedulerOutput` 包含新请求、已有请求的增量、各请求的 token 数、块更新、结束与抢占、草稿和 KV 连接器信息，是这一边界上唯一需要对齐的数据。

固定版本的 V1 调度注释明确不以“预填充阶段／解码阶段”作为调度主抽象，而以已完成进度追赶当前应计算的 token 总数。前缀命中缩短待计算区间，分块预填充由预算截断，投机草稿增加待验证 token。这里“无阶段”只描述调度进度模型；算子层仍需识别不同查询长度和执行形状。

{{include:excerpts/vllm-budget.md}}

代码首先计算“应达到的进度减去已经计算的进度”，再分别施加长预填充阈值和本轮预算。若只保留请求数上限，一条 8192 token 的新请求与一条只需 1 个 token 的生成请求会占用同样的一个名额，执行时间却完全不同。以本轮可用输入预算 512、长预填充阈值 512 为例，前者只能推进一个块，无法一次算完整个输入；后续轮次继续从 `num_computed_tokens` 接上。这是可从状态轨迹复核的分解；时延表现要另行测量。

只加分块仍不够：没有完成进度会重复计算已经处理的区间，没有输出占位又可能在异步结果回传前错误地安排后续工作。因此三项进度与多项预算共同构成调度时必须同时满足的约束；代价是每轮都要回写状态并重新组批，长请求的总计算量并不减少。

下面是连接块分配的教学伪代码，函数名与变量名为解释性简化，属教学伪代码：

```python
needed = tokens_with_spec + output_placeholders - computed_tokens
scheduled = clip_by_token_budget_and_other_limits(needed)
blocks = kv_manager.allocate_slots(request, scheduled)
if blocks is None:
    defer_or_preempt(request)
```

异步输出占位表达已提交但尚未回传的生成结果，不能当作已经确认的 token；采样完成后还要处理接受／拒绝、停止、取消和资源释放。真实调度受请求数、token、编码器、草稿和模型长度等多种预算约束，不能只靠一个 batch size 解释。

#### 分页、前缀哈希与引用计数

连续 KV 预分配容易在短请求中浪费容量，也难以在变长请求间复用空间。vLLM 把逻辑序列映射到定长物理块，`KVCacheManager` 管请求的块，`BlockPool` 管可分配块与缓存，注意力后端通过 `block_table` 找到数据。这是 [PagedAttention](https://arxiv.org/abs/2309.06180) 的内存管理主线；它与 FlashAttention 的片上分块属于不同层次。

同一 token 段在不同上下文中通常产生不同 KV，因此前缀哈希需要串入先前块的身份。`core/kv_cache_utils.py` 的 `hash_block_tokens` 和附加键生成函数还处理 LoRA、多模态与嵌入等影响状态的上下文。缓存共享既要语义一致，也要命名空间与版本一致；不能只按一段文本的相等性共享。

引用计数防止活跃请求使用的块被随意回收。零引用块可留作缓存，待重新分配时淘汰；共享数据被修改前还要判断可写性或执行写时复制。`BlockPool.touch`、`get_new_blocks`、`is_block_writable` 和 `KVCacheManager.free` 因而分属命中、分配、写入与释放不同动作。SGLang 同样需要保护在用数据，不能把引用计数说成它独有的能力。

分页减少碎片，不减少有效 KV 元素本身。序列长度、并发和 KV 头数共同扩大占用；块大小更小可减少尾块浪费，却增加索引与管理成本。`KVCacheSpec` 还要描述不同层的全注意力、窗口、MLA 或状态型布局，混合模型的命中边界必须是相关组都可恢复的边界。

#### 真实问题：长请求把短请求的输出拖慢

一条长预填充独占执行时，其他请求即使只差一个生成 token，也会等待整个长计算完成。分块预填充让长输入分多步推进，与增量生成共享预算；运行中请求优先、长预填充阈值和请求准入共同控制干扰。它通常以延长长请求的预填充完成时间，换取其他请求更稳定的生成间隔。

方案验证应同时记录首 token 时间（TTFT）、输出 token 间隔（TPOT／ITL）、尾分位及公平性。减小块不一定更好：会增加轮数、调度和 kernel 启动开销。vLLM 的部分分支会跳过本轮不能推进的请求继续尝试其他请求，这可提高利用率，与严格 FCFS 相比则会出现偏差；若长请求持续被跳过，需要以等待时间和优先级策略辨认饥饿。

如果 KV 块不足，V1 可抢占请求、释放状态并在之后重算。重算成本取决于被释放的上下文，恢复因此有代价。单独的 KV offload 与连接器路线可以搬运冷状态；旧版调度器中基于 swap 的描述不适用于当前抢占路径。频繁抢占应优先检查准入、最大输出、KV 预算和并发，增加 token 预算可能使问题更严重。

#### 后端接入：能力协商与元数据一致性

`attention/selector.py` 的 `get_attn_backend` 把设备、头维度、dtype、KV 精度、窗口、sink、MLA 和并行等条件交给平台选择，`attention/backends/registry.py` 注册实现。支持单项能力与支持所有组合是两件事；一个后端需要声明支持范围，也需要对不支持组合回退或拒绝。

执行器生成 `query_start_loc`／累积长度、`block_table`、位置和 KV 写入槽位。变长打包消除 padding 浪费，分页寻址避免 KV 重排，但序列边界必须同时传到 kernel。固定长度、变长连续 KV、分页 KV 是不同接口，FlashAttention 并不要求所有调用都使用分页或打包。

后端能力声明把数学条件与输入接口连在一起：不等长因果对齐决定查询的历史边界，GQA 映射决定多个查询头读取哪个 KV 头，窗口、dtype 和步长决定有效读取范围及数值解释。单个规则张量上的 kernel 正确性只覆盖其局部接口；多请求打包还依赖序列边界和槽位映射。若这层映射跨越了请求边界，算子即使正确执行了同一个注意力公式，也会把别的请求的数据混进来。
