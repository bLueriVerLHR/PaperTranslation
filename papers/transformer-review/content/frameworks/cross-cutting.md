### 贯穿框架的机制：资源预算与状态一致性

各框架的差别不只在 kernel 的速度，还在于请求怎样变成一次设备执行。一次执行依次经过几个环节：调度器选出这一批，缓存管理器给出物理槽位，模型执行器写入新的 K、V，采样器选出输出，控制层提交状态并回收完成或取消的请求。vLLM、SGLang、FastGen 与极简实现的组织规模不同，但同一条链上必须相容的三件事是一样的：每条请求算到了哪一步、每个物理页归谁、输出按什么顺序交付。

#### 连续批处理：每一步重新组批

如果一批请求固定不变，短请求提前结束后，它占用的算力和缓存位置要闲置到整批完成。连续批处理在生成步之间让完成的请求退出、新到的请求进入，因此每一步的批组成都不同。它复用空出的预算，并不意味着每个请求都更快：新进入的请求会扩大本步的工作量，排队顺序也会改变已有请求的间隔。

调度同时受两类约束。第一类是计算预算：若第 i 条请求本步处理 <math><msub><mi>t</mi><mi>i</mi></msub></math> 个位置，则总和不超过本轮 token 预算。第二类是缓存容量：页大小为 <math><mi>q</mi></math>、第 i 条请求的历史长度为 <math><msub><mi>s</mi><mi>i</mi></msub></math> 时，不考虑共享，所需页数约为 <math><mo>∑</mo><mo>⌈</mo><msub><mi>s</mi><mi>i</mi></msub><mo>/</mo><mi>q</mi><mo>⌉</mo></math>，不能超过物理页预算。一条只处理少量新 token 的解码请求仍持有很长的历史，因此这两类预算不能互相替代。vLLM 的 `scheduler.py` 与 nano-vllm 的调度摘录分别展示了进度与块分配怎样连接。

长预填充在一步内产生大量计算，增量解码只产生少量计算，却反复占用历史状态。把一条很长的提示直接插入解码批，其他请求就要等这一步做完。分块预填充把长输入切成多步执行，代价是新请求需要更多轮次才能完成预填充，首 token 时间不一定下降。公平性也不会自动出现：一直优先解码会推迟新请求，一直追求大块矩阵的效率又会拉长已有请求的间隔。

调度策略因此要在利用率、首 token 时间、生成间隔与饥饿风险之间取舍。代码里的预算是某种资源的具体代理：同样处理 <math><msub><mi>t</mi><mi>i</mi></msub></math> 个 token，短上下文与长上下文的注意力读取量不同，切换模型或适配器还要额外开销。一次选批只保证那一次决策合理，服务层面的最优策略还需要到达分布。

#### 分页与共享前缀：分配对象与计算对象

分页 KV 用块表把逻辑位置映射到物理页，请求不必预留整段最大长度的连续空间。页尾仍会浪费：长度为 <math><msub><mi>s</mi><mi>i</mi></msub></math> 的请求占 <math><mo>⌈</mo><msub><mi>s</mi><mi>i</mi></msub><mo>/</mo><mi>q</mi><mo>⌉</mo></math> 页，浪费的槽位为 <math><mi>q</mi><mo>·</mo><mo>⌈</mo><msub><mi>s</mi><mi>i</mi></msub><mo>/</mo><mi>q</mi><mo>⌉</mo><mo>−</mo><msub><mi>s</mi><mi>i</mi></msub></math>。减小 <math><mi>q</mi></math> 会降低尾部浪费，却增加块表条目与管理频率；按 token 分配把这一取舍推到更细，索引和预留成本并没有消失。

前缀共享让不同请求引用同一批历史页。共享之后，总容量取决于唯一的物理页，把各请求的逻辑长度直接相加会高估。但每个新查询仍要读取相关历史，所以共享减少的是存储和重复预填充，不减少读取。长公共系统提示、有路由局部性、命中状态仍在设备上时，两者可以叠加；共享区很短或额外归约开销较大时，收益会减弱。

状态身份由模型权重、适配器、token 前缀、位置约定以及图像等非文本输入共同决定，字符串相似度提供不了这层身份；租户与权限命名空间还决定能不能共享。SGLang 的基数树负责逻辑前缀与分叉，物理页对齐决定哪些边界可以安全复用；vLLM 用块哈希把身份映射到块级对象。页未填满时，后续写入需要独占或写时复制，否则一个请求会改掉另一个请求仍然依赖的历史。

#### 图重放：把稳定的执行骨架与每步变化的内容分开

小批量解码会提交大量短 kernel，主机端两次提交之间的间隙可能占据可观的时间比例。CUDA Graph 把一段可捕获的执行整体重放，省掉主机反复构造提交序列的开销；它不减少长上下文要读的 KV 数据量。固定地址的缓冲允许每步改写内容，形状分档与补位让不同批量映射到已有的图，分段图则把动态操作留在图外。

分页与图重放并不冲突：物理页的选择可以通过稳定地址上的块表内容变化来表达。真正的约束在于后端是否允许这些元数据在重放中更新。nano-vllm 的图执行、SGLang 的分段图与 TensorRT-LLM 的图 runner 分别体现了这种划分。

每保留一个档位，就要多花捕获时间并常驻一份缓冲；把有效批量补到更大的档位，又会产生无效计算。若瓶颈在主机提交，图重放直接有效；若瓶颈已经是 KV 带宽或通信，减少提交只能改善剩下的那部分。

#### 重叠执行：用事件确认完成，用引用确认归属

主机准备下一批、设备执行当前批、CPU 处理上一批输出，三者可以重叠，但它们看到的不是同一时刻的状态。下一批若覆写上一批仍在读取的块表，数据本身合法，映射却已经属于别的请求。双缓冲避免读写同一块，事件确定设备何时完成，引用计数或锁定保证物理页在完成前不被回收；这三件事都不能由一个 `non_blocking=True` 标志替代。

取消请求最能看出区别。业务状态可以立刻标记取消，物理内存却要等在途访问结束才能释放；先释放再分配给新请求，就会出现地址有效、内容已变的错误。投机执行同样把临时候选与已确认状态分开：接受的前缀提交，拒绝的后缀回滚，异步参与者在统一完成点回收。重叠的收益，正是用更复杂的状态生命周期换来的。

#### 采样、结构化输出与多 rank 一致性

投机解码的概率校正在上一章推导，这里只看执行接口。草稿器、验证器和采样器分别消耗时间与 KV；候选越长，请求在确认前持有的临时位置越多。接受率高不保证收益，因为小模型执行、额外的验证形状与管理开销仍可能超过省下的调用。框架的 proposer、worker 或双 context 路线必须把接受决定接到实际进度上。

结构化输出为每条请求维护语法状态，在采样前生成合法 token 掩码。批内 logits 的行必须与请求、语法状态一一对应，选中的 token 确认之后才推进解析状态。语法合法不等于业务正确，类型检查和语义判断仍在生成之外。

张量并行的每个 rank 持有模型的一个分片，却共同表示同一条序列。若各 rank 独立采样或独立接受草稿，就可能得到不同的后缀，后续集合通信随之错位。因此输出选择、取消与状态版本要在约定的边界上一致；专家并行与流水线并行还多一层路由与在途微批的对应关系。并行降低了单卡压力，也扩大了必须同步的范围。

#### PD 分离：减少队列干扰，增加状态传输

预填充与解码的资源形态不同，放到不同实例可以分别组批，长输入与持续生成不再互相干扰。交接时，解码端除了输入 token 还需要各层可继续使用的 KV。若有效状态为 <math><mi>M</mi></math> 字节、持续带宽为 <math><mi>B</mi></math>，纯传输至少要 <math><mi>M</mi><mo>/</mo><mi>B</mi></math>；协议、排队与确认会再加等待，计算重叠则改变传输占关键路径的比例。

同样的字节形状不说明状态相容。两端的权重、适配器、位置、精度和布局必须对应；发送端的页在传输期间受保护，接收端在数据确认之前不能执行依赖该页的查询。连接器超时会触发重算，重算与在途传输还要避免重复提交。净收益等于减少的干扰减去新增的交接成本，短提示、低并发或弱互连未必需要这种组织。

分层缓存把冷状态移到主存或存储，PD 把状态移到另一个实例，两者都是数据移动，目标不同：前者减少昂贵介质上的驻留，后者分离计算负载。每增加一层状态位置，就多一层身份、命中、恢复与故障处理；容量变大也不代表读取时延消失。

#### 训练与 rollout 交替：权重版本是一致性边界

RL rollout 与训练共享资源时，引擎的 sleep／wake 与权重安装负责交接资源，不属于训练优化器本身。权重更新会改变各层对历史的表示，旧 KV 一般不能继续作为新模型的历史，因此要么按版本失效，要么重算。安装之前还要结束或隔离在途批，避免同一条轨迹混入两个参数版本。

训练状态分片、推理 KV 分页和环境快照保存的是不同对象，却都要回答三个问题：谁拥有这块内存、它何时有效、何时释放。框架之间可比的地方就在这些答案上；把它们合并成一个“缓存”功能名，会丢掉这些区别。
