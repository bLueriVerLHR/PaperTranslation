#### LightLLM：token 级分配与逐模型内核

LightLLM 的 TokenAttention 以 token 为粒度管理 KV 位置，`lightllm/common/kv_cache_mem_manager/` 与 `req_manager/` 分离物理分配和请求映射。它减少固定页末端未用槽位，却增加细粒度索引、分配和搬运组织；“没有块内碎片”只说明碎片这一项，服务内存利用率另受其他因素影响。

模型目录中的 Triton 内核及 autotune 配置体现逐硬件、逐形状调优。细粒度分配使不同长度请求的最后几个 token 不必独占一整页，却使注意力内核读取更多位置映射，并可能降低连续访问程度。若一个 token 的 KV 数据很大，索引字节的相对占比可能较小；若请求本来很长，尾部浪费占比已经很低，细化粒度的容量收益也随之下降。因此 token 级与块级方案的差异同时落在碎片、间接寻址和访问组织上，分配粒度越小也会带来间接寻址与访问组织的代价。

`server/` 的路由、多级缓存、PD 分离和 RL 接口连接更高层的执行。Windows 检出对带冒号的调优配置路径存在限制，本地工作树不完整；因此这部分以固定提交中的 Git 对象为来源，不能把检出缺失当成框架没有内核，也不能在当前机器声称完成部署验证。
