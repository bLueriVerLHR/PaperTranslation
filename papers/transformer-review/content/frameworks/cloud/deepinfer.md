#### DeepInfer：面向单一模型的生产推理引擎

DeepInfer 是 DeepSeek 于 2026 年 10 月以 Apache-2.0 协议开源的推理引擎，用于线上 DeepSeek-V4.1-Flash 服务。它的代码起点是 vLLM 的早期分支，项目说明中也提到参考了 SGLang 与 TensorRT-LLM 的做法。一个自然的问题是：既然已有通用引擎，为什么还要维护一套自己的实现。要回答这个问题，需要先看清推理引擎每一步究竟在安排什么。

##### 推理引擎的执行循环

请求送入引擎后进入等待队列，随后被分批送入设备做预填充，算出第一个 token 后转入解码，每一步生成一个 token，直到满足停止条件。如果按固定的一批请求推进，就必须等这一批全部结束才能接入新请求，短请求提前结束所空出的算力只好闲置到整批完成。连续批处理取消了这次等待：每生成一步，已完成的请求退出，新到的请求加入。批的组成因此每一步都不同，调度也就必须每一步重新作出四项决定。其一是这一步执行哪类计算，即把新请求的上下文一次算完（预填充），还是为已有请求各生成一个 token（解码）；两者的计算形态差别很大，前者是长序列上的大矩阵乘，后者是短查询读取长历史。其二是哪些请求进入这一步，即从等待队列按预算接收多少条、从运行队列取哪些继续。其三是每条请求这一步处理多少 token，预填充可以一次算完，也可以按 token 预算切成多个 chunk，解码则要决定每条请求验证多少条投机草稿。其四是每条请求读取多长历史、占用哪些物理位置，历史长度决定注意力读取多少 KV，物理位置指分页 KV 的块号、滑动窗口的环形槽位，以及新 token 写入的槽位。

完成这四项决定后，就得到了这一步的设备执行计划。承担这项工作的部件称为调度器（scheduler）。它本身不执行数学运算，输出是一组描述：哪些序列组成这一批、每条贡献多少查询、每条需要读取多长的键，以及块表与槽位映射。这组描述称为元数据（metadata），在 CPU 侧内存中组织好后再拷贝到设备。原因是 kernel 的启动参数（例如 `cu_seqlens_q`、`block_table`、`position`）位于主机侧，设备上的内核无法访问 Python 对象。

调度不能被省略，原因有三。请求异步到达与结束，批必须逐步重组；KV 容量有限，准入、预留与回收都需要统一管理，必要时还要抢占；预填充与解码对算力和带宽的需求不同，混在同一步内会互相拖慢。调度器的作用，就是把当前存活的请求整理成一次设备执行。

##### 负载特征与改造目标

项目公开的负载数据如下：单集群每天处理约 155 万亿个 token，平均每请求输入约 77K 个 token，其中 96% 命中缓存；KV 缓存保留 3 天（代理流量）到 7 天（对话流量）；解码使用 64～128 张卡的宽专家并行（Wide Expert Parallelism，Wide-EP）；硬件覆盖 NVIDIA SM100 与 Ascend 950。

这些数据决定了哪些环节需要改写，也改变了前述四项决定的权重。命中率达到 96%，意味着吞吐主要由未命中部分的预填充决定，命中路径的组织比单个算子的极限速度更重要。平均输入达到 77K，使预填充与解码的资源形态明显分开，两段分别扩缩容才有实际收益。Wide-EP 把专家分散到几十个 rank，任何集合通信都要求全体参与，于是“全组在同一步执行同类计算”成为硬性约束。两种硬件并存，则要求同一套模型语义在两种指令集与通信库上都能实现。

##### 系统结构

引擎只有一个工作循环，即 `LLMEngine.step`。每调用一次，完成一次调度、设备执行、采样与回收，产出一批已确认的输出。

| 层次 | 代码入口 | 本步由它决定 | 状态归属 |
|---|---|---|---|
| 编排 | 未随包开源 | 请求路由、命中长度、容量与扩缩容 | KV 存储集群与目录 |
| 引擎 | `engine/llm_engine.py::LLMEngine.step` | 步循环、请求生命周期、延迟释放 | 序列对象、输出池 |
| 调度 | `csrc/engine/scheduler.hpp` | 本步执行哪类计算、哪些请求入选、处理多少 token、占用哪些块与槽位、何时抢占与回收 | 块池、状态池 |
| 执行 | `worker/worker.py`、`worker/model_runner.py` | 元数据组装、图重放、滞后元数据的校正、采样 | 图缓冲、pinned 内存 |
| 模型与算子 | `model_executor/models/v4_modules/`、`layers/tilelang_ops/{cuda,asc}`、`vendor/` | 层结构、注意力、MoE、低精度格式 | 权重、KV 与状态 |

三层之间通过三个对象传递信息：调度输出 `SchedulerOutputs`，包含本步序列、`prompt_run` 标记、预算、已完成与忽略的请求，以及异步调度下对每行 token 数的估计；逐序列元数据 `SequenceMetadata`；以及在搬运 KV 时描述搬运范围的 `BlockLoadPlan`，其中 `paged_range`、`ring_range`、`zero_fill` 三类段分别对应分页块、环形槽位与补零，源块号为 `-1` 表示该段填零。

调度器以 C++ 头文件实现（1168 行，随扩展一起编译），这是整个结构中最基础的一个选择。解码步的设备时间在毫秒量级，而每一步要处理几十到上百条序列的进度、块分配与元数据组装。若这些逻辑留在 Python 中，解释器开销会随批大小线性增长，并且恰好落在设备等待的时间里。代价是调试需要跨 `nanobind` 边界，扩展必须随版本重新编译，调度逻辑也无法热更新。仓库中大量设计说明写在头文件注释里，原因也在于此。

##### 调度与设备空闲

在没有重叠的情况下，一步的执行顺序如下：CPU 调用调度器得到元数据，将其拷贝到设备并启动前向；设备完成前向后启动采样；采样结果留在设备内存中，必须拷回主机，CPU 才知道每条序列本步输出了什么 token、接受了几条草稿、是否有请求结束。只有得到这些信息，下一次调度才能决定谁继续、谁退出、块是否需要释放、每条序列还差多少 token。由此形成一条固定的依赖链：

```text
设备: 前向 N ────► 采样 N ──►（空闲）────────────► 前向 N+1
CPU : 调度 N ──► 启动前向 ──► 等采样结果 ──► 调度 N+1 ──► 启动前向 N+1
```

空闲来自等待采样结果这一次同步。提高 kernel 效率无法消除这段空闲，因为它源于控制流上的依赖：调度器的输入包含上一步的输出。批越大，前向越长，CPU 等待的时间也越接近一次调度与后处理的完整耗时。在 Wide-EP 下这一现象更明显，因为全体 rank 必须同时进入下一步，一个 rank 的 CPU 延迟会使整组设备停在同一位置。

DeepInfer 的处理方式是不让下一次调度等待上一步的采样结果，代价是调度器必须在结果未知的状态下工作。

{{include:../excerpts/deepinfer-step-order.md}}

这段顺序使三件事错开：前向 N 在设备上执行时，CPU 处理第 N−1 步的后处理；采样 N 启动后，CPU 返回执行调度 N+1。这样，调度器看到的始终是上一步的结果。由此产生两处需要单独处理的信息。第一处是批的组成，即这一步有哪几行、每行对应哪条序列，它由 CPU 侧的记账决定：已完成的请求退出，等待队列按预算接收，CUDA Graph 档位不足时补占位行；这些判断依赖已经回传的第 N−1 步结果，以及为第 N 步尚未返回的 token 预留的位置（代码中为 `num_cached_tokens + total_inflight_tokens + nextn + 1`）。第二处是每行的长度，即本步验证多少 token、读取多长历史，它依赖上一步实际接受了多少条草稿，只有设备知道。

DeepInfer 用一张 `remap` 表描述第一处信息，把第二处留给设备计算。

{{include:../excerpts/deepinfer-zos-remap.md}}

`remap[i] = -1` 表示第 i 行是新行，CPU 已知其输入 token；其余值表示它是上一步第 `remap[i]` 行的延续，其输入可直接复用设备上已有的输出。此时 `SchedulerOutputs.seqlens_q` 只是调度时的估计值，最终长度由两个设备内核依据上一步的接受数与置信度改写：`compute_seqlens_q_by_confidence_rates` 处理查询长度，`compute_seqlens_k_zos` 处理历史长度。

校正的 H2D 拷贝与内核排在前向之前，回读事件也一并排入同一流，但 CPU 直到启动前向、完成上一步的后处理之后才去等待它。等到时，拷贝与内核已经完成，等待几乎不占时间。回读只用于一处：使 CPU 侧元数据与设备一致，从而可以启动采样。

{{include:../excerpts/deepinfer-mtp-varlen.md}}

这个内核也说明了为什么调度不能提前完成：每条序列需要验证多少草稿，取决于上一步逐位置的接受率，而这一信息只在设备上。内核先按 `remap` 连乘得到累积接受率，新行的累积率置零，不参与分配；然后用秩统计按预期收益把总预算分配给各行。项目文档将这一步描述为累积乘积、全局排序与融合散写，而固定提交的实现以秩计数代替排序，避免了一次全量排序。

这种做法的代价有三项。输出晚一步交付，调用方在第 N 步拿到的是第 N−1 步的结果，流式输出因此多一步延迟。每一步多一次 H2D 拷贝与一次 D2H 回读，后者只在变长验证时必要。pinned 的 `seqlens_q` 源缓冲会被就地改写，不能被多个读者共享。最容易出错的地方是身份对应关系：同一张 `remap` 表必须从准备、校正一直用到采样，对应错一次，读到的就是另一条请求的状态。

##### 缓存与重放

预填充是一步中开销最大的部分，重复预填充等于把已算过的上下文再算一遍。若 KV 缓存分布在各计算节点的本地内存中，命中就要求路由把同一前缀的请求送到同一台机器，而路由还要服从负载均衡，两者在生产环境中相互冲突。DeepInfer 把块级 KV 放入独立的 3FS 存储集群，使任何预填充机器都能命中任何前缀，容量扩缩容也与计算节点解耦。代价是一次跨网络的 KV 读取，以及随之而来的故障处理。官方给出的配置是每台存储服务器 20 块 30.73 TB SSD，至少 40 GB/s 读与 5 GB/s 写，按 10+2 纠删码组织，回收由 3FS 自身的 GC 与 LRU 水位控制，TTL 为代理流量 3 天、对话流量 7 天。对话流量的长尾命中更重，官方称 TTL 取 3 天将损失 0.5%～1% 的命中率。

窗口注意力带来第二层缓存。在 YoCo 结构中，解码（consumer）层的块级 KV 可由编码器末层的隐状态投影得到，滑动窗口的 KV 则必须逐层现算。精确恢复需要把最后约 2,560 个 token 重新跑过 20 个解码层，DeepInfer 改为只重放末尾 128 个 token，并把可见域限制在重放区间内。

{{include:../excerpts/deepinfer-yoco-clip.md}}

`clip_prefix` 是一个经过夹紧的差值：保留区间从 `data_len - keep_tokens` 开始，`clip_prefix` 表示当前 chunk 位于保留区间之前、可以丢弃的 token 数，上界 `q_len - 1` 保证即使整块都在保留区间之前，仍保留最后 1 个 token。这条下限有实际作用：分块预填充时若一块被完全裁掉，本步没有任何行参与计算与状态写入，后续的进度推进与命中长度计算都无从进行。命中策略与之配套：先用块级 KV 得到命中长度 `L1`，它是 128 的整数倍；再检查 `L1 - 128` 到 `L1` 之间是否存在 SWA 缓存，若不存在则退一个块重算；允许的最大命中长度还需扣除窗口与投机回溯，即 `L - 134`。

收益是预填充计算近似减半，代价则很具体：得到的是近似 SWA KV，只在窗口内自洽；截断开启时 `prompt_logprobs` 被强制关闭，因为压缩后的行无法还原逐位置概率。这两条限制同时出现在代码与文档中，属于设计者主动接受的近似。

##### 专家并行下的负载与同步

解码阶段每个 token 只激活少量专家，专家权重却分散在几十个 rank 上，单步时间由最慢的 rank 决定。DeepInfer 采用 EPLB：为热点专家保留冗余副本，按最近若干步的专家负载周期性重排，权重通过 NVLink 上的对称内存交换。官方参数为预填充从每卡 4 个冗余专家起，统计窗 100 步，每 1000 步重排，测得不均衡度（最慢 rank 与均值之比）为 1.074（EP4／DP4）与 1.045（EP2／DP2）；解码从每卡 1 个冗余专家起，统计窗 1000 步，每 10,000 步重排，测得不均衡度 1.090。

Wide-EP 还带来一个约束：一个实例内的所有 GPU 属于同一通信域，注意力又按数据并行组织，DP 数与 EP 数相等，全体 rank 因此必须在每一步执行同类计算。`csrc/engine/scheduler.hpp` 用两次投票满足这一约束：在按步数计数的 ALL 点与 ANY 点各执行一次 `MIN` 归约，第一次决定是否切换到预填充，第二次确认组内确实排出了预填充，否则退回解码。第二次投票是必要的：若只依据“存在等待请求”投票，全组可能同时无法排出请求（槽位已满、块不足），而空的预填充步会清零步计数，下一步继续投票、继续为空，形成循环。代价是每一轮集合通信，以及没有任务可做的 rank 也要跟着走完这一步；收益是全体 rank 执行同类计算，使专家并行的集合通信有确定的参与者。

##### 与 vLLM 的差异

将两侧的固定提交并列比较，可以区分哪些是继承、哪些是改写。vLLM（`b0e21b30`）已有 `AsyncScheduler`，同样用 `-1` 占位符与设备侧缓冲表示尚未返回的采样结果；也有 `vllm/distributed/eplb`，其默认策略在文档中说明改编自 DeepSeek 的 EPLB。因此 DeepInfer 在这些概念上并非首创，差异体现在实现形态与所服务的约束上。

| 维度 | vLLM（`b0e21b30`） | DeepInfer（`774ce244`） |
|---|---|---|
| 调度器位置 | Python，`vllm/v1/core/sched/` | C++ 头文件与 `nanobind`，调度期间释放 GIL |
| 本步计算类型 | V1 调度注释明确不以预填充／解码阶段为主抽象，按进度差推进 | 显式 `prompt_run`，并在 DP 组内用两次投票统一 |
| 异步调度 | 可选项，受投机方法与执行器组合限制 | ZOS，与变长验证、图档位、YoCo 截断耦合；本提交默认关闭 |
| 投机验证 | 固定 `num_spec_tokens` 的占位列表 | DSpark 置信度调度，逐序列长度由设备内核分配 |
| 前缀缓存 | 引擎内块哈希，可选 KV 连接器 | 外部 3FS 存储与入口匹配，SWA 单独分层 |
| 针对模型结构的优化 | 以通用机制为主 | YoCo 有界重放、稀疏注意力的索引、engram 压缩词表 |
| 硬件 | CUDA、ROCm、XPU、CPU 等 | SM100 与 Ascend 950，算子按后端分别实现 |
| 发布范围 | 完整服务与工具链 | 引擎与模型侧，KV 存储、PD 部署与负载均衡未包含 |

由此可以概括这套实现的作用：通用引擎中已有的机制，按照自身模型的层结构、硬件的指令与通信库、存储的组织方式重新组合，并把生产参数（TTL、EP 规模、冗余专家数、不均衡度、验证长度收益）公开到可以复算的程度。

##### 与其他框架的分工

与 SGLang 相比，DeepInfer 保留了显式的阶段划分，没有采用“前缀树加程序接口”的路线：SGLang 的收益来自缓存感知的调度与前端表达力，DeepInfer 的收益来自在固定模型上把每一步的元数据准备得更完整。与 TensorRT-LLM 相比，它不做引擎级的图编译与插件生态，模型实现保留在 Python 层，性能主要依靠专用算子与调度重叠。与 ktransformers、PowerInfer 相比，它针对的问题在于设备利用率不足，而显存容量并不构成限制。与 nano-vllm、mini-sglang 这类教学实现相比，它的复杂度正来自这些实现有意省略的部分：跨机缓存、阶段投票、近似重放与多后端算子。

##### 证据范围

本文没有编译 DeepInfer，没有下载 V4.1-Flash 权重，也没有在 SM100 或 Ascend 950 上运行。文中性能与命中率数据均为项目文档的报告值，机制结论来自固定提交的静态阅读。`vendor/` 下的 FlashMLA、DeepGEMM、DeepEP、DeepSelect 未拉取，相关判断只引用文档表述。另有一处文档与代码不一致：README 将异步调度列为默认开启，而 `deepinfer/environ.py` 中 `DEEPINFER_ZERO_OVERHEAD_SCHEDULING` 默认为关闭，示例脚本也未统一打开（`examples/yoco/yoco_equiv.py` 显式设为 `0`）。判断某一部署的实际行为，应查阅实际环境变量与启动参数。
