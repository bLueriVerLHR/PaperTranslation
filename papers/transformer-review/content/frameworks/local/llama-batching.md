#### 逻辑批、物理批与序列状态

一次 `llama_decode` 提交的是逻辑 batch，`llama_batch_allocr` 根据记忆状态与 `n_ubatch` 拆成物理批。调大 `n_batch` 增加一次可提交的输入，调大 `n_ubatch` 才直接改变某次执行的工作区和形状。两者不能互换解释。

{{include:../excerpts/llama-batch-contract.md}}

接口把拆批和缓存适配交给 memory 实现，返回可检查状态的上下文；逻辑批与一次设备执行分属两个层面。假设一次输入有 2048 个 token、物理批上限为 256，逻辑提交仍可保持完整，执行则需要按合适边界分成多轮。这样减小的是某一轮的工作区和计算形状，这条输入的总 KV 与模型权重不受影响。

如果只允许“一个逻辑批对应一个物理批”，应用要么自行拆提示并处理位置／序列状态，要么承受大批的峰值需求；前者把内部约定泄漏到 API 使用者，后者限制容量。上下文接口集中承担准备、推进和应用状态的责任，不同 memory 类型实现相同调用边界。代价是更多子批执行与状态管理；`init_batch` 的返回值仍需检查，任意拆分未必都能成功。

`src/llama-memory.h` 的 `seq_rm`、`seq_cp`、`seq_add` 等接口按序列与位置操作状态，支持分支、删除和部分模型的位置调整。缓存快照和 slot 内公共前缀提供另一类复用，与 vLLM 的块哈希、SGLang 的基数树不同。位置平移是否有效仍取决于模型和相应实现，能否无损改位置要看具体结构。

长输入的内存峰值由常驻权重、KV 与当前算子工作区共同形成。逻辑批描述一次请求组织的数据，物理微批描述一次实际执行的切片；减小物理微批可以降低工作区峰值，却增加切片和执行次数。更多层放到 GPU 会改变 CPU 计算、显存容量和设备间传输，权重文件大小只覆盖其中一项。仓库的 `tools/fit-params/`、`llama-bench` 与 `perplexity` 分别对应配置选择、速度测量和部分质量评估，这些工具的职责也反映了容量、性能和输出质量的不同约束。
