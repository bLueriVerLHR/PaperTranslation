#### DeepSpeed：容量问题与推理批组织分属两侧

DeepSpeed 同时包含训练与推理能力。训练侧的 [ZeRO](https://arxiv.org/abs/1910.02054)通过在数据并行参与者之间划分优化器状态、梯度和参数来减少每卡冗余；不同 stage 划分的对象不同，参数按需聚合又增加通信。CPU／NVMe 卸载进一步将容量压力转移到搬运与带宽。这里只辨认其系统职责，不展开完整 ZeRO 训练实现。

训练内存由模型状态与动态激活共同占用。注意力 IO 优化减少大中间矩阵的存储，激活重计算减少前向结果的长期保留，状态分片则把参数、梯度或优化器状态分散到多个 rank。三者作用于不同项，组合收益也受剩余最大占用约束。分片后计算阶段需要的完整或局部参数通过通信形成，内存压力因而可能转为集合通信压力；微批、累积步数与聚合时机改变状态的复用次数和通信频率。

推理侧 `deepspeed/inference/v2/engine_v2.py`、`ragged/`、`allocator.py`、`scheduling_utils.py` 组织不规则批、状态和执行。[DeepSpeed-FastGen](https://arxiv.org/abs/2401.08671)的 Dynamic SplitFuse 把长预填充拆开，并把预填充块与增量生成 token 混入预算内的一次执行。它控制的是步内工作量及生成请求的等待，作用于推理侧的批组织，与训练参数分片无关。服务封装还涉及独立的 MII 项目，不能从本地 DeepSpeed 目录推断已经拥有全部 MII 实现。

`put` 先做可调度性判断，再清空本轮批描述，按 UID 取得或建立持久序列状态，准备 KV 和本轮进度，最后把批元数据发往设备。结构上区分了跨轮次存活的 state manager 与每次执行重新组织的 ragged batch；后续模型准备与前向消费的是后者，原始服务请求在这一步之前已完成转换。

若把每条序列 padding 到本批最长长度，组批较直接，却在长度差异大时浪费输入计算；ragged 表达让有效 token 和序列描述共同决定执行，额外承担索引与元数据成本。若去掉准入检查但没有上层等价保证，KV 或跟踪序列容量不足可能在分配／组批阶段才失败。因此 `do_checks=False` 把容量约束的证明责任交给已完成检查的调用方。这一推理路径的容量约定与 ZeRO 的训练状态分片是不同问题。

固定 token 数有助于约束步内负载，但并不保证每步耗时相等：KV 长度、注意力模式、MoE 路由、缓存命中和通信仍会改变成本。比较 SplitFuse 与其他框架的分块预填充，应观察 TPOT 分布与首 token 时延，不能只看名称是否相同。
