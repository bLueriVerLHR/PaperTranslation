### DeepSeek 自研栈：模型形状、硬件换代与部署规模共同决定

DeepSeek 公开的基础设施仓库不是一套通用框架。它们要解决的问题是具体的：模型里有 MLA、稀疏注意力、细粒度专家这些不在通用形状内的结构；硬件在一代之内从 Hopper 换到 Blackwell，又多了 Ascend 分支；部署规模把专家并行、流水线并行和长上下文同时压到一套服务上。这三件事决定了栈的形状。

#### 三个约束，三条设计原则

**模型结构先行。** MLA 的潜在状态加解耦位置键（第 2 章）、DSA 的索引器选择、每 token 只激活一小部分专家的 MoE，这些结构交给通用 kernel 要么多一次展开与重排，要么退化成稠密计算。于是一条原则贯穿所有仓库：kernel 按模型结构写，接口为模型让路。

**硬件换代不可回避。** 指令集在换代时会改（张量内存、块级原子、缩放格式），把同一份源码留给编译器去猜，得到的往往是保守代码。第二条原则是把控制权下到指令层：内联 PTX、显式寄存器预算、warp 特化，以及对 PTX 与 SASS 输出的直接检查。

**部署规模要求可替换的后端。** 通信、存储、调度各自面对不同的域（NVLink、RDMA、SSD），任何一套都不能绑死。第三条原则是让上层接口稳定、下层实现可换：DeepEP 在 V2.5 里去掉了 NVSHMEM，改用 NCCL 的设备侧接口；3FS 把元数据放进外部事务型存储；DeepJIT 让同一份源码在不同设备上运行期生成代码。

三条原则的代价写在明处：算子与模型同版本发布（FlashMLA 2026-09-30 的版本移除 Hopper、改 KV 格式、与旧模型不兼容），运行环境必须保留 CUDA 工具链与 C++ 编译器，每换一代硬件就要重做一遍指令选择。

#### 栈的全景

| 仓库 | 位置 | 作用 | 一句话的差异 |
|---|---|---|---|
| FlashMLA | 单卡算子 | MLA 解码／预填充，稀疏、FP8／FP4 KV、融合小算子 | 逐模型逐架构发版，含 Ascend 内核 |
| DeepGEMM | 单卡算子 | FP8／FP4／BF16 矩阵乘、融合通信的 Mega MoE、索引器打分 | 安装不编译，运行期按设备生成 |
| DeepSelect | 单卡算子 | DSA 的 Top-k 选择与采样核 | 把不可微的选择做成独立 kernel |
| DeepJIT | 横向设施 | xPU kernel 的运行期编译 | 缓存、转储 PTX 与 SASS |
| DeepEP | 多卡通信 | EP 的 dispatch／combine、冗余专家权重交换 | 对称缓冲区 + 设备侧发起 |
| EPLB | 多卡编排 | 专家复制与放置的均衡算法 | 两套策略，按组数与节点数选择 |
| DualPipe | 训练编排 | 双向流水线，计算与通信全重叠 | 气泡减半，参数翻倍 |
| 3FS、smallpond | 存储与数据 | 分布式文件系统与其上的数据处理 | 无状态元数据 + 链复制 |
| DeepInfer | 引擎 | 推理调度与执行 | 异步调度、滑动窗口重放 |

#### 读这一组仓库的顺序

单卡先看指令层（`instruction-level.md`）：同名算子在不同硬件上差在哪，为什么他们要直接写 PTX。再看两个算子库各自的取舍：FlashMLA 的版本绑定，DeepGEMM 的运行期编译。多卡部分（`load-balancing.md`）把三处均衡分开：token 选哪些专家、专家放到哪张卡、微批怎样排进流水线。最后是存储与数据，以及已经单独成稿的 DeepInfer。

#### 覆盖范围与证据边界

这里收录的是承担计算、通信、编排、存储与引擎职责的仓库。模型权重仓库（DeepSeek-V3／V3.2／V4 等）只作对照，不算框架；Ascend 分叉（DeepGEMM-Ascend、DeepEP-Ascend）只提及存在，未检出、未阅读，不对其实现作判断。

九个仓库均按固定提交只读检查，提交号记在 `source-repositories.json`。本节没有构建、安装或运行任何上游代码，也没有跑 benchmark；引用的吞吐与时延都是仓库报告值，随文保留 GPU 型号、CUDA 版本或集群规模。断言与来源的对应、以及哪些结论属于推断，记在 `reference/deepseek-stack.md`。
