### 3FS 与 smallpond：一套存储支撑三类负载

训练与推理对存储的要求分成三类：数据加载要随机读、检查点要并行写、推理的 KV 缓存要低延迟大容量。3FS 用一套文件系统同时覆盖这三类，smallpond 则是跑在它上面的数据处理层。[54][55]

#### 3FS 的四个设计决定

| 决定 | 实现 | 影响 |
|---|---|---|
| 接口用文件语义 | FUSE 挂载，另提供用户态直接读写接口 USRBIO | 应用不必学新 API，但 FUSE 路径有额外上下文开销 |
| 元数据无状态 | 元数据服务背后是事务型键值存储（如 FoundationDB） | 元数据节点可水平扩展；依赖外部存储的可用性 |
| 强一致 | 链式复制（CRAQ），读可以分摊到链上多个副本 | 写沿链传递，读的吞吐随链长增加；应用代码不需要处理副本 |
| 存储与计算分离 | 存储节点只挂 NVMe SSD，客户端通过 RDMA 访问 | 容量与带宽按节点横向扩展，访问局部性被抽象掉 |

代码构成也反映了这种分工：主体是 C++（`src/client`、`src/storage`、`src/meta`、`src/fuse` 等），另有一个 Rust 工作区承担块引擎、回收工具与用户态接口的绑定。

```text
# 文件：3FS/Cargo.toml（固定提交 22fca045）
# 1-9 行
[workspace]
members = [
  "src/client/trash_cleaner",
  "src/storage/chunk_engine",
  "src/lib/rs/hf3fs-usrbio-sys"
]
default-members = [
  "src/client/trash_cleaner",
  "src/storage/chunk_engine",
]
```

Rust 只出现在这三处，说明它的引入是有边界的：块存储引擎、垃圾回收和 FFI 绑定，没有重写整个系统。这类“局部换语言”的做法在小团队里常见，收益是有内存安全保证的模块，代价是构建链里多一套工具。

维护者报告的性能条件是具体的：180 个存储节点、每节点两张 200 Gbps InfiniBand 网卡与 16 块 14 TiB NVMe，500 多个客户端各一张 200 Gbps 网卡，聚合读吞吐约 6.6 TiB/s，且测时有训练流量在跑。这些数字属于报告值，与客户端数量、块大小和副本策略都相关，不能直接折算成单卡或单机的带宽。

#### smallpond 只做一层壳

smallpond 是 Python 库，把 DuckDB 当作单机执行引擎、Ray 当作调度层、3FS 当作数据面，用 Parquet 在阶段之间落盘，不常驻服务。这样的组合让数据处理复用现成的 SQL 引擎与调度器，自己只负责把“任务图 + 文件布局”翻译成两边都能执行的计划。

3FS 的 GraySort 结果同时是这套组合的说明：110.5 TiB 数据分 8192 个分区，两个阶段（按键前缀做 shuffle、分区内排序）读写都走 3FS，25 个存储节点加 50 个计算节点，用时 30 分 14 秒，平均 3.66 TiB/min。这个用例把存储的元数据吞吐也压到了极限，因为每个分区都是一次独立的文件读写。

#### 和推理侧的关系

3FS 在推理中的角色是 KV 缓存的外部容量层。第 5 章区分过显式 KV 与潜在状态：把冷请求的 KV 落到 3FS，能换来显存里更多的活跃序列，代价是取回时要付网络与反序列化。这条路径是否划算，取决于命中率与取回延迟；存储的名义带宽不能代替这两项。

本节只读源码与文档，没有部署集群、没有跑 fio 或 GraySort；所有吞吐与时长均为仓库报告值，集群配置随报告一并保留。
