### DeepGEMM：运行期编译的 GEMM 与 MoE 原语

矩阵乘是 MoE 与前馈的算术主体，也是量化格式落地的地方。DeepGEMM 把 FP8、FP4、BF16 的矩阵乘、融合通信的 MoE 计算、索引器打分放在同一个代码库里，用一套接口跨架构提供。[52]

#### 安装不编译，kernel 在运行时生成

安装阶段只构建宿主扩展，源文件只有一个。设备侧 kernel 由 DeepJIT 在首次调用时按目标设备编译。

```text
# 文件：DeepGEMM/setup.py（固定提交 5081f851）
# 32 行，37-38 行
sources = ['csrc/python_api.cpp']
build_include_dirs = [
    f'{CUDA_HOME}/include',
    f'{CUDA_HOME}/include/cccl',
    'deep_gemm/include',
    'third-party/deep_jit/include',
    'third-party/cutlass/include',
]
```

这个选择换来了两件事：一个 wheel 覆盖 SM90 与 SM100，不需要为每张卡准备预编译产物；代价是首次调用有编译延迟，运行环境必须保留 CUDA 工具链与支持 C++20 的编译器。仓库把这条取舍写在需求里：CUDA 12.9 以上、PyTorch 2.3 以上、CUTLASS 4.0 以上，编译器需要 C++20 的 `<format>`。

#### 同一接口，两套硬件契约

接口形状统一成 `D = C + A @ B`，缩放因子的布局却不相同：

| 项 | SM90 | SM100 |
|---|---|---|
| 内存布局 | 只支持 NT | NT、TN、NN、TT 全支持 |
| 缩放因子格式 | FP32 | 打包的 UE8M0，四个因子压进一个整数 |
| 对齐要求 | TMA 对齐且转置 | 同左 |

缩放因子之所以要打包，是因为逐块量化的粒度变细之后，因子本身的字节数开始占带宽；UE8M0 只用指数表示缩放，既省位宽又便于在张量核的缩放指令里直接使用。换架构时接口不变、数据布局与指令变了，这是“跨架构同一 API”的真实含义。

#### 与 CUTLASS 的关系

仓库自述借用了 CUTLASS 与 CuTe 的概念，但不重度依赖其模板与代数，核心 kernel 数量有限。这一取向对读者有利：warp 划分、流水线级数、共享内存布局这些手段在小而完整的代码里更容易读；不利之处是要自己维护新架构的适配，而不能坐等上游。新加入的融合 MoE 计算把通信与矩阵乘叠在一起，需要与 DeepEP 的缓冲区约定对齐，跨仓库的耦合因此加深。

维护者报告 2025 年 4 月在 H800 上达到 1550 TFLOPS，此后的版本又加入了 FP4 与索引器打分。这些数字是仓库报告值，条件随提交变化；本节没有编译或运行，只核对了构建方式、接口约定与布局要求。
