### 优化先定位对象：输入、模型与执行系统

Zhou 等把 LLM 高效推理分成数据、模型、系统三个层次，并把计算量、内存访问与内存占用拆成不同成本。[11] 这套分类的用处在于先认出瓶颈长在哪：输入压缩改变模型实际看到的内容，结构与数值压缩改变模型表示，引擎优化重新组织既定的计算和状态。三者可以叠加，各自的质量条件却不同，用一个“加速”盖住全部会丢掉判断依据。

#### 省掉输入会在别处补回来

冗长的检索文档或重复提示推高预填充工作量，也留下后续生成要访问的 KV。摘要、去重、筛选、提示压缩能把输入压下来，代价是可能删掉决定答案的那段证据。[11] 文档问答里这两件事直接对立：相关材料的条件与解释链被截断之后，模型跑得更快，能支撑的回答范围同时缩小。这个代价与只调整 kernel 访存组织的情况完全不同：后者没有删掉任何 token。

模型侧的量化、剪枝、蒸馏和结构设计，分别动精度、参数、知识传递和计算图。省下权重空间与省下每个请求的 KV 是两件事；某些结构改动还要配套训练或格式转换。系统侧的融合、缓存、批处理和调度一般不以改变目标模型为目的，也拿不到“逐位相同”的保证：浮点归约顺序、随机数来源和执行顺序都有各自的约定。[11]

#### 容量、首 token 和持续输出要分开量

长提示先撞上首 token 等待，长输出持续累积解码步骤与 KV，占用与排队取决于同时存活的请求数。综述分别给出首 token 时延、逐输出 token 时延、整段生成时延、模型大小、KV 大小与吞吐的定义。[11] 用数字感受一下预填充的形状：提示从 4K 涨到 32K，成对交互的位置对数涨 64 倍，首 token 等待随之上升；而这一步一旦过去，后续每步解码只多读 32K 个历史位置。交互式应用里用户很快看到首 token、后面却卡顿，与离线批处理吞吐高、单请求等待长，是同一组量的不同组合。

于是各方案的职责可以逐条对上：分页减少容量碎片，连续批处理提高多个请求共享执行资源的机会，分块预填充限制长请求对单轮执行的影响，前缀复用省掉重复输入的计算。缺掉某个机制时出现的问题，要用碎片、空闲名额、长步阻塞、重复计算分别解释，笼统归到“GPU 利用率低”上会丢掉定位依据。后面读框架时，就沿这几条职责看实现。
