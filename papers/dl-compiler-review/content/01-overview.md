# 编译栈的分层与研究对象 {#stack-layers}

一个模型从 Python 源码走到硬件指令，中间要经过若干次表示变更：算子集合与图形状被改写，张量计算被切成适合片上存储的块，块的读写模式被绑定到线程与寄存器，最后落成目标指令。不同项目把这些变更放在不同位置——有的做成可检查的中间表示与变换管线，有的压进模板实例化，有的藏在一个装饰器后面。本书关心这条链上每一层各自负责什么、代价落在哪里，以及真实负载里哪些约束会先暴露。

## 编译这一层要决定什么 {#what-a-compiler-decides}

把一次矩阵乘法或一个注意力块交给设备执行，最终必须落下四个决定：计算切成多大的块、块之间按什么次序执行、每个元素由哪个线程负责、数据在存储层次之间怎么搬。这四个决定互相牵制。块切得大，片上存储放不下中间结果，必须回到显存往返；块切得小，每次搬运的有效载荷不足，带宽花在开销上。线程映射只要和数据的物理排布错开一拍，一次内存事务就要拆成多次。搬运与计算的次序安排不当，硬件只能在读数和算数之间空转。

四个决定之上还有一个更基本的问题：哪些信息在编译期已知。形状固定、步长可推导、对齐满足、缩放因子是常量，编译器就能把偏移、边界判断和缓冲区大小全部静态算出来。任何一项推迟到运行期，同一段计算要么生成两条路径并在入口处选择，要么退化为通用循环，要么在运行时补齐元数据。深度学习负载里形状经常来自上游算子的输出，批大小随请求变化，这使得“编译期已知”成为一个需要主动争取、而不是天然成立的前提。

## 三个阶段与它们的分界 {#three-phases}

按“谁有权修改已经做出的决定”来分，这条链可以切成三段。

**前端**决定程序以什么形式进入编译器。一种做法是给出一个受限的编程模型（块级程序、计算块级程序），让使用者只写数据流，剩下的留给后端；另一种做法是让框架的执行过程可被记录成图。前者的难点是表达受限之后哪些优化仍能成立，后者是捕获的完整性与守卫何时失效。

**中间表示与 Pass**决定改写怎样被表达和验证。这里要回答：IR 里装了什么事实（类型、作用域、内存层次、别名、依赖），谁能注册新的操作与变换，分析结果如何维护，以及“源码里有某个 Pass”与“默认管线会启用它”之间的差距。图级改写、循环级改写、调度原语、方言分级都属于这一段。

**后端**决定这些选择落到哪条指令、哪个寄存器。布局与指令的对应关系可以用模板与类型在编译期证明，也可以由寄存器分配器在机器 IR 上选择；硬件差异要么被压进后端的转换，要么被推回源码，要么由平台适配层承担。

三段之间存在来回反馈，并非一次性的流水作业：后端资源（寄存器、共享内存、占用率）会让前端看起来合理的决定不再成立，中端的合法性事实又限制了前端能承诺的东西。本书在每一章都尽量指出这条回路上代价落在哪一段。

## 本书的对象与位置 {#five-pathways}

| 对象 | 主要位置 | 它交出的核心决定 | 主要代价 |
|---|---|---|---|
| Triton | 前端：块级 DSL | 布局、共享内存、流水由固定后端管线决定 | 表达受限；布局问题要进 TTGIR 才看得见 |
| TileLang | 前端：计算块级 DSL | 线程绑定、片布局、流水由三档推导与代价模型决定 | 默认代价模型不等于实测最优；后端差异需注解或下沉 |
| PyTorch／Inductor | 前端捕获 + 后端生成 | 图能否被捕获、模式能否被认出 | 守卫与图断裂；匹配失败即退化 |
| TVM | 中端：调度与降低 | 调度由使用者或搜索给出，IR 逐层降低 | 测量与搜索成本；调度合法性要求 |
| LLVM | 中端 + 后端 | SSA、循环与向量化事实、寄存器分配 | 分析维护成本；语言语义约束比 IR 优化更强 |
| MLIR | 中段基础设施 | 方言与层间转换的组织方式 | 跟随版本演化的 API 成本 |
| CuTe | 后端：布局代数与模板实例化 | 布局、原子与指令在编译期被证明 | 需要静态知识；换架构重选参数 |
| 昇腾（MindSpore／torch-npu） | 前端适配 + 后端图编译 | 开源部分只到图与结点，算子编译在运行库内 | 可用内核集合与匹配条件互相约束 |

LLVM 与 MLIR 与前六者是不同性质的对象：它们不实现某种注意力，而是被别的栈使用或借用的基础设施。把它们放进同一本书，是为了让“切分点、可检查性、调度决策、目标绑定、可见性、动态信息、代价承担方”这七个问题能在一处对照，而不是暗示它们与 TVM、Triton 处在同一层。

## 比较用到的问题 {#comparison-axes}

对照这些对象时，本书反复追问同一组问题：

1. **切分点在哪里。** 编译器从这里接管程序，也在这里承担“已知信息不足”的后果。
2. **中间表示是否可检查。** 能否打印、匹配、写自定义变换，决定了调试成本落在人身上还是落在管线里。
3. **调度决策由谁做出。** 由使用者显式写出、由搜索挑选、由后端固定策略决定，还是由类型系统或布局推导在编译期推导。
4. **目标绑定发生在什么时候。** 同一份源码换一个设备，需要改动的是调度、是布局、还是整段程序。
5. **内存与同步是否可见。** 共享内存、寄存器、流水缓冲和栅栏是否出现在源码层面，决定了性能问题的可诊断性。
6. **动态信息如何处理。** 形状变化时是重新编译、走通用路径，还是在入口处判断后选择。
7. **代价由什么承担。** 编译时间、模板展开深度、搜索开销、需要的静态知识，都要与运行期收益一起计入。

后续各章按三段顺序展开：先看前端如何获得程序（Triton、TileLang、PyTorch 与计算图四章），再看中间表示与改写（IR、TVM，以及 LLVM 的中端两章），然后是后端（LLVM 寄存器分配、CuTe、昇腾三章），再用一条算子路径横向对照，以代价与退化收尾。
