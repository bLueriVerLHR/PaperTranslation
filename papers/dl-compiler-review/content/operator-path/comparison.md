## 对照：决策位置与代价的分配 {#operator-path-comparison}

把六条路并排放在一起，差异集中在四个问题上。

| | 融合决策在哪里 | 使用者交出什么 | 合法性由什么判定 | 条件不成立时 |
|---|---|---|---|---|
| Triton | 使用者的循环 + 后端固定管线 | 块形状、递推、`warp_specialize` 请求 | 后端 pass 的前提条件 | 仍生成代码，性能下降 |
| TileLang | 使用者的图块数据流 + 布局与流水推导 | 块形状、数据流、可选注解 | 推导约束与后端能力 | 布局冲突或后端缺失，编译期报错 |
| CuTe | 示例模板的选择 | 分块、布局、指令原子 | 编译期整除与静态形状条件 | 实例化失败 |
| PyTorch | 图上的模式改写 | 不改代码，交出可捕获的执行 | 模式是否匹配 | 保留原图，不融合 |
| TVM | 后端配置与分派 | 目标与调度（或交给外部模板） | 调度合法性 + 外部库能力 | 退回逐算子实现 |
| 昇腾（MindSpore） | 图上的模式改写 | 不改代码 | 模式条件与设备内核是否可得 | 结点选不到内核 |

**决策位置决定了可用信息。** 在图级做改写时，编译器看得到形状、语义与算子边界，看不到寄存器与共享内存；在块级编程里，使用者看得到数据流与块形状，看不到整张图。两类系统都因此在某个位置“跳出去”一次：Triton 把 `warp_specialize` 与布局处理交给使用者写，TVM 与 Inductor 把“用哪个后端、哪套模板”交给配置。这条缝不可能消掉，只能选择把它放在哪里：放在源码里，使用者必须理解硬件；放在配置里，使用者必须理解匹配条件。

**失败路径是进入生产的前提。** 六个栈都保留了退化机制，差别只在退化的位置：Triton 与 CuTe 的失败停在编译期（一个报错，一个放弃优化），TileLang 的失败也停在编译期（布局冲突或后端缺失），PyTorch 与昇腾的失败停在匹配阶段（保持原图继续执行），TVM 的失败停在分派阶段（退回逐算子实现），MindSpore 另有图内的 Python 回退结点（昇腾那一章）。对使用者而言，决定可用性的往往是退化后的行为能否接受，最好情况下的性能说明不了这一点。

**可移植性的实际形态与直觉相反。** 需要最少改动的做法是在图上识别模式，因为模式表达的是“哪些算子构成一次注意力”，与设备无关，换设备只需要后端提供融合后的实现。跟设备绑得最紧的是库级模板，每代硬件要准备一份对应实现——CuTe 的三份注意力示例分属不同架构正是这个原因。块级与计算块级程序处在中间：前者比模板可移植，后者进一步把布局与流水交给推导与后端注册，但 Triton 教程里那段只对特定块形状与特定架构生效的重标定分支说明，一旦要压榨性能，设备差异仍会渗回源码；TileLang 把差异集中到后端方言与推导，代价是每个后端仍需自己的算子和调优。

**同一个算子在各处被改写成了不同东西。** 在 Triton 里它是一段带递推的循环，在 TileLang 里是一组图块算子加一条流水声明，在 CuTe 里是一次模板选择，在 PyTorch 与昇腾里是一个被认出来的图模式，在 TVM 里是一个可能交给外部代码的图算子。这些形态都可以用框架自己的话说成“融合注意力”，但它们对使用者的要求、对版本的依赖与失败后的行为各不相同。LLVM 与 MLIR 不直接出现在这张表里，但每条路最终都要经过它们中的一个或两个：前者提供寄存器与指令，后者提供可加层的管线。判断一个栈是否适合某个负载，落点就在这里，而不在某一项基准数字上。
