## 多后端复用到哪一层为止 {#tilelang-backends}

“同一份内核跑在多种加速器上”是一个需要拆开核对的承诺。TileLang 把后端组织成显式注册表：一个 `BackendModule` 声明自己接受哪些 target、使用哪条 pass 管线、设备与宿主代码如何生成、执行与回调如何绑定。CUDA 后端注册的就是上一节读到的 `CUDA_PIPELINE`，外加基于 nvcc 的设备编译与二进制缓存；ROCm、Metal、Ascend 各自注册自己的管线与代码生成，生态后端（MetaX、摩尔线程、海光等）在独立仓库维护，不随发行包一起发布。

用注册表而不是在 lowering 里写条件分支，换来的是两件事：后端可以带自己的 pass 序列（Ascend 的持久化核划分与 CUDA 的 TMA 流水不是同一套改写），公共部分仍然共用同一份布局推导与 IR。代价是后端之间的能力差异不再体现在编译错误里，而是体现在“这个后端缺哪个 pass、哪条 lower 路径”上，使用者需要按目标查阅相应文档。

语言层同样按后端分化。共享的那一层给语义（区域、注解、`T.Kernel`、`T.Pipelined`、`T.Parallel`），硬件旋钮由各方言包装函数追加：CUDA 的 `T.gemm` 多出完成屏障与双 CTA 选项，ROCm 多出 packed MFMA 的 `k_pack`，Ascend 多出 Cube 单元标志，拷贝类接口在 CUDA 侧还有 TMA、gather/scatter 与 cluster 入口。语义与旋钮分处两层，使内核主体保持可读，硬件差异集中在包装函数里。

复用边界在真实项目里比宣传语窄。DeepInfer 的 `deepinfer/model_executor/layers/tilelang_ops/` 按 `cuda/` 与 `asc/` 各维护一份实现，同一个“按置信度累积率分配验证预算”的算子在两处是不同代码：CUDA 版按序列一维网格开块，用 `T.pdl_sync()` 衔接两段内核、`T.alloc_reducer` 做秩统计；Ascend 版按向量核数做持久化划分，用 `T.SimtVF`／`T.SimdVF`、`S.vcmp`、`S.vcadd` 等向量内在函数、核间同步标志和显式共享内存缓冲重写，连数据切块尺寸都要按 8 与 64 对齐重新推导。分派器（`tilelang_ops/ops.py`）按平台模块名加载后端目录，缺失的算子以 `KernelUnavailableError` 报出，测试在非 CUDA 后端上转为跳过。

可复用的是语言、编译链、调试工具与“把数据流和调度分离”的组织方式；同一份源码、同等成熟的算子覆盖则不在其中。这也解释了它与另外两条路的分工：Triton 把硬件差异压在编译后端的转换里，使用者写一份程序；CuTe 只做 CUDA 布局代数，靠模板适配不同架构。三者对“跨硬件”给出的答案分别是改变换、改后端、改代码，选择哪一种取决于要覆盖的硬件数量、算子复杂度，以及愿意付多少逐后端维护成本。

还有一层边界属于性能而非可移植性：计算块级生成没有取代手工最内层优化。DeepInfer 的部署问答称，对外版的 FlashMLA 因缺少一处手调 SASS，解码内核慢 5%～10%，而端到端差距最多 5%；同一文档又把 Mega MoE 这类大融合内核归为通用解法。在指令级细节与极端形状上，手写库仍是基准。

本节只做固定提交的静态阅读：没有安装、编译或运行 TileLang，也没有运行任何内核基准。关于收益与代价的判断来自代码结构、官方文档与上游作者的论文表述，不能替代实测。
