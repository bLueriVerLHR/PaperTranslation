## 8. 异构算力编排：设备抽象、切分与干扰 {#heterogeneous-gpu}

CPU 的共享有成熟机制：配额限制时间片，权重决定争用时的比例，超用表现为变慢。加速器的共享没有同等成熟的抽象。Kubernetes 对 GPU 的处理停留在“计数”，一张卡是一个不可分割的单位；而生产集群的实际需求往往是把一张卡按空间切给两个负载，或者把一周内闲置的算力让给离线任务。这一章讨论三种切分方式的隔离强度与代价，并用一个已部署系统的数据说明收益与风险分别落在哪里。

### 8.1 计数式抽象

Kubernetes 用扩展资源表达异构设备：节点通过状态更新上报“有 4 个 `nvidia.com/gpu`”，Pod 在申请量里写 1，调度器据此匹配[1]。设备插件把这件事标准化，以 gRPC 接口向 kubelet 上报设备列表、执行分配，并返回设备路径与驱动目录供容器挂载[1]。

这套机制能回答“这台机器还有没有卡”，不能回答“这张卡是什么型号、与哪些卡在同一互连域、是否已被切分”。书中对此的评价是：设备插件只实现了入门级功能，能用但不好用；更复杂的描述需要动态资源分配（dynamic resource allocation，DRA）这类新机制，其接口随版本与厂商变化[1]。对可靠性工程，这意味着“资源够用”与“性能达标”之间存在一个由调度表达力决定的缺口。

### 8.2 三种切分方式

时间片复用把卡在不同负载之间切换。它的隔离最弱：上下文切换要保存与恢复显存状态，切换开销大；对延迟敏感的负载，等待切换就是尾时延。

空间复用让多个进程同时驻留在同一张卡上，按流式多处理器（streaming multiprocessor，SM）份额分配算力。它提高了空间利用率，但不提供性能保证：多个进程共享同一组 SM、同一份显存带宽与同一套缓存。

实例切分把一张卡划分成若干独立实例，每个实例有独立的显存切片与计算通道。它的隔离最强，代价是切分粒度固定，无法按需细分，且不同代际的卡支持程度不同。

三者的选择不是纯粹的技术偏好，而是由“能否接受干扰”决定的。在线推理不能接受不可预测的干扰，因此倾向实例切分或独占；离线训练可以接受变慢，因此可以空间共享。

### 8.3 一个生产系统的数据

MuxFlow 报告了字节跳动在超过 18,000 张异构 GPU 上的部署结果，值得逐条读，因为它同时给出收益与风险的量级。

问题的起点是利用率。该文统计了推理集群一周的数据：超过 99% 的 GPU 的 GPU 利用率与 SM 活动度低于 60%，约 90% 的 GPU 显存使用率低于 60%[5]。原因是请求频率随时间波动，而即便在高峰，为满足时延要求也会把批大小限制在较小值。

收益侧的数字是：GPU 利用率从 26% 提升到 76%，SM 活动度从 16% 提升到 33%，显存使用率从 42% 提升到 48%[5]。这三个数字的差异本身说明了瓶颈位置：利用率提升最多，SM 活动度提升有限，说明空间共享把“卡被占用但算力空闲”的时间填上了，而没有把算力本身用满。

风险侧的设计分两层。作业级用一套用户态运行时约束离线负载的显存分配与核函数发射，使在线负载受到的干扰可控；GPU 级用探针维护一个状态机，按多维指标判断共享是否会损害在线负载，必要时驱逐离线负载[5]。这层设计的必要性来自空间共享的固有缺陷：多个进程共享同一张卡时，一个进程的异常会传播到同卡的其他进程。

错误传播的统计值得单独记录。该文分析了生产集群中所有传播性错误，发现 99% 由 SIGINT 与 SIGTERM 信号引起，这些信号通常来自 Kubernetes 停止容器的动作；处置办法是拦截信号并主动释放 CUDA 上下文，对剩余的长尾情形则按错误模式识别后重置执行上下文[5]。这条结论把第 5 章的容器终止机制与 GPU 可靠性接在了一起：容器停止的默认行为在共享显卡上会变成跨负载的故障源。

### 8.4 干扰从哪里来

干扰有四条路径，它们的可控性依次下降。显存容量是硬边界，超了就失败，不存在“慢一点”的中间状态。显存带宽是共享资源，多个负载同时读写会互相拖慢，且没有按份额分配的机制。SM 占用可以被限流，代价是被限流的负载变慢。主机侧资源（CPU、内存带宽、PCIe 通道）在容器层面可用控制组限制，但加速器与主机之间的数据搬运仍然竞争同一条链路。

Borg 在 CPU 上的测量提供了参照：共享 cell 的平均 CPI 比专用 cell 高约 3%，每多一个任务使其他任务 CPI 上升 0.3%，而这些相关性只解释了 5% 的方差[4]。GPU 上的情况更差，因为缺少细粒度的隔离机制，可观测的干扰指标也更少。可行的做法是把保护放在运行时：监测在线负载的关键指标，一旦劣化就驱逐离线负载，而不是试图事前算准能塞几个。

### 8.5 可接受的劣化

一个容易被忽略的参数是“允许多少劣化”。MuxFlow 报告了一个业务侧的判断：按算法工程师的说法，多数在线负载的时延劣化 20% 仍能满足要求[5]。这个数字是混部策略的边界条件：它决定了在保护机制触发之前，可以接受多大的干扰。

这个判断必须由业务方给，而不是由平台方推算。原因是时延与业务指标的关系不是线性的，20% 的劣化对某些场景没有影响，对另一些场景会直接影响转化。把它写成 SLO 的一部分（例如“P99 时延劣化不超过 20%，且不超过 SLO 上限”），才能进入第 2 章的错误预算体系。

### 8.6 混合型号与碎片

生产集群很少只有一种卡。型号不同意味着显存容量、互连拓扑与编译产物都不同，而一个训练作业通常要求所有参与节点同型号，否则集合通信会因为带宽差异而整体降速。这条约束把资源池切成多个按型号独立的子池，每个子池各自承担碎片损失。

碎片的机制与第 3 章的装箱问题相同，但约束更硬：普通服务的 Pod 可以落到任何满足资源的节点，训练作业的 rank 必须满足同型号、同拓扑。因此同一个碎片率在混合型号集群上的实际可用容量更低。可行的做法是按型号统计“能装下最大作业的连续空间”，而不是看总体空闲量。

还有一个容易被忽略的绑定：编译产物与型号绑定。为某一代卡编译的内核无法在另一代上运行，镜像与卡型的组合因此成为一个隐含的调度约束。把它写成节点标签与镜像标签的匹配规则，比在运行时发现“镜像不支持该卡”要便宜。

### 8.7 抽象层缺什么

把上面的内容收拢，当前的编排抽象在三个地方不足。第一，无法表达“这张卡与那张卡在同一互连域”，于是拓扑约束只能靠标签近似。第二，无法表达“这张卡被切成两个实例”，于是资源计数与实际可用容量不一致。第三，无法表达“这个负载可以与别人共享但优先级更低”，于是共享决策只能由调度器之外的系统完成，例如 MuxFlow 那样的双层保护。

这三项缺失都不是配置问题，而是抽象的表达力问题。平台团队通常用自定义资源与自定义调度器补齐，代价是维护一套与上游不同的语义。是否值得补，取决于共享带来的收益是否超过维护成本；按第 3 章的算式，这个收益在两成到三成的机器数量级。
