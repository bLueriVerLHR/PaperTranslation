出处与说明

本书为原创技术综述，围绕语言与内存、并发执行、C++20 无栈协程、操作系统与网络、存储缓存及服务工程组织机制。配套 《C++ 后端问答》 单独按问题检索，不作为本书连续论述的替代。

线程池案例固定为 Barak Shoshany 的 BS::thread_pool 5.1.0，提交 bd4533f1f70c2b975cbd5769a60d8eaaea1d2233。案例保留既有 Windows x64、Clang 23.1.2、C++17/C++20、-O0 的部分接口契约记录；这些记录不覆盖全部并发交错、上游完整测试或性能。源码分析不把线程池视为完整后端框架，容量数字是说明性假设。

第一篇 语言、对象与内存

后端请求把数据、对象和外部资源串在一起。连接已经关闭，不表示后台任务已经结束；一段内存仍然可访问，也不表示其中的旧对象仍有效。对象模型规定合法访问的起点，所有权决定状态能存活多久，容器与内存布局再影响这些状态如何移动和被观察。

本篇沿对象、接口和存储布局建立这些关系。并发、协程与网络随后延长访问时间或改变执行位置，但不会使生命期规则失效。配套的 《C++ 后端问答》 按问题索引相关机制，与这里的连续论述分别阅读。

对象生命期与资源不变量

一个请求中的连接、输入缓冲区、解析结果和数据库事务具有不同的生命期。网络连接断开时，后台计算可能仍在执行；解析函数返回时，指向输入缓冲区的视图可能仍被任务引用。C++ 的对象模型首先规定对象何时存在、哪些操作有效，而服务协议还要规定谁能在什么时候访问它。拥有一段地址、拥有一个对象与拥有对象正在使用的外部资源，是三个不同关系。

存储期描述存储持续多久，生命期描述对象何时完成相应初始化、何时结束。自动对象通常随作用域退出而销毁，动态对象的销毁则由所有者安排。为对象分配了内存，不表示其中已经有任意类型的有效对象；同样，析构之后地址仍可打印，不表示原对象还能使用。把对象放进容器或交给异步任务，都必须维持这些条件，不能用“内存还没有被系统回收”替代生命期证明。

资源获取即初始化（Resource Acquisition Is Initialization，RAII）将资源的取得和释放接到对象的构造与析构。构造成功建立不变量，析构负责释放资源，异常栈展开和正常离开作用域因此可以复用同一清理路径。构造失败时，该对象自身没有完整构造完成；已构造的成员和基类仍按规则清理。这解释了为什么资源宜尽早交给具有明确析构行为的成员，而不宜在多个可能抛异常的步骤之间保留裸所有权。[42]

下面是原创教学片段，假定 Connection 的析构函数关闭连接，open_connection 返回独占所有权；它展示释放关系，不是某个网络库的实现：

void process_request() {
    auto connection = open_connection();  // unique_ptr<Connection>
    auto request = parse(*connection);    // 失败时可抛异常
    auto response = execute(request);
    connection->send(response);
}

若 parse 抛异常，已经建立的连接所有者仍会销毁；但这不意味着 send 的部分传输、execute 已提交的事务也被撤销。资源清理保证、对象不变量和业务原子性需要分别成立。基本异常保证要求失败后对象仍有效且不泄漏资源；强异常保证还要求观察到的状态保持不变，常通过“在私有状态准备，再以不可失败的步骤提交”实现。外部系统已经接受的副作用通常不在这种本地提交边界内。

对象的多态接口同样需要销毁协议。通常通过基类指针删除派生对象时，基类需要虚析构函数；明确禁止通过基类销毁的接口则可以采用受保护的非虚析构函数。语言规定动态分派行为，不规定所有平台都必须具有同一种虚表布局。应用二进制接口（application binary interface，ABI）才涉及具体平台的参数传递、对象布局和符号约定；以某次调试观察推断所有编译器布局，会混淆语言规则与实现。[19–20]

对象模型由此形成服务中第一条约束链：构造建立可用状态，所有者维持生命期，访问者遵守借用和同步条件，销毁必须发生在最后一次合法访问之后。后面的线程池闭包与协程帧，只是把这条约束链延伸到了函数返回之后。

所有权、移动与异步接口

函数参数不仅传递数据，也表达一段访问关系。值参数建立独立对象，引用和指针通常表达借用，unique_ptr<T> 表达独占所有权的转移，shared_ptr<T> 表达加入共享所有权组。接口若只需要在调用期间读取对象，要求共享所有权会增加不必要的持有关系；接口若将访问延迟到返回之后，单靠引用参数又不能保证目标继续存在。

std::move 不搬运资源，它把表达式转换成可参与相应右值重载选择的形式。真正的资源转移发生在随后选中的移动构造、移动赋值等操作里。一个具名的右值引用变量作为表达式仍是左值；对 const 对象使用 std::move 也不会去掉 const。因此，接口是否复制、转移或拒绝参数，需要结合类型和重载分析，不能从调用处出现 std::move 就推出零复制。[13–14]

异步提交使这种区别变得可见。下面两个原创教学闭包借助假定的 enqueue 接口说明持有关系，未规定其线程安全、容量或错误语义：

void unsafe_submit(std::string request) {
    enqueue([&request] { consume(request); });
}

void owning_submit(std::string request) {
    enqueue([request = std::move(request)] { consume(request); });
}

第一种闭包保留对局部参数的引用，函数返回后再执行就可能访问已销毁对象。第二种闭包拥有自己的字符串，原参数的生命期不再限制该字符串的使用。但如果字符串内容换成 string_view、原始指针或引用包装器，按值捕获的只是借用描述，不会复制被引用的数据。移动闭包解决的是闭包成员如何持有，不会递归地把所有间接引用变成所有权。

共享所有权还必须分清控制块、句柄和业务对象。不同线程操作各自的 shared_ptr 句柄，可以共享同一控制块；对同一个句柄的相应并发修改仍需要同步。多个句柄都能保证 Session 存活，不表示它们可以同时无锁修改 Session::count。弱观察句柄 weak_ptr 可以打断所有权环，但 lock() 只是取得一段临时所有权，不是业务状态的互斥锁。[15–16]

结果通道也属于接口契约。返回一个 future，通常表示调用方可以在之后取得结果或错误，而不是工作已经完成，更不是每个 future 都拥有一条独立线程。调用方销毁结果句柄、等待超时、执行器拒绝接收和任务本身取消，都是不同事件。服务必须给每种事件规定资源归属，尤其要说明后台工作是否仍持有请求缓冲区，以及错误由谁消费。[4]

模板包装层还可能改变接口行为。满足推导条件的转发引用与 std::forward<T> 可以保留实参的值类别；无条件 std::move 则可能提前消耗调用方对象。转发并不延长生命期，也不保证同一参数只被消费一次。接口设计的核心不是尽可能多地使用智能指针或转发，而是使持有期限、可变性和失败路径能从调用关系中得到解释。

容器布局、地址稳定与内存成本

容器选择同时决定查找路径、内存布局和失效规则。连续数组适合顺序访问及按下标定位，节点结构便于保留某些元素地址，有序索引支持范围遍历，哈希表围绕键的散列分布组织定位。抽象复杂度描述操作次数的增长关系，实际时延还取决于缓存命中、分配、比较成本和访问局部性，不能只用一个复杂度标签排出所有工作负载的优劣。

以通常的 vector<T> 为例，元素连续存放；容量不足时，重分配需要建立新存储，将元素移动或复制过去，再释放原存储。原有元素的指针、引用和迭代器因此失效。reserve 可以减少预期增长中的重分配，但它自身改变容量时也会导致失效。没有重分配也不等于所有观察都稳定，中间插入、删除及旧 end() 有各自的失效边界。[18]

均摊成本与单次时延因此需要分开。假设一个教学数组每次将容量扩大为原来的两倍，从空数组增长到最终规模时，历次搬移量构成几何级数，总量与最终规模同阶。这个模型解释尾部追加为何可能有均摊常数成本，却不保证某次触发扩容的请求具有常数时延，也不规定标准库采用这个增长系数。提前预留容量把一部分工作移到准备阶段，同时可能保留暂时用不到的空间。

异步路径进一步放大失效问题。解析器若把 vector<char> 的内部区域暴露为视图，随后接收更多网络数据而触发扩容，尚未执行的任务可能持有旧地址。解决方式可以是冻结已交出的缓冲、转移独立缓冲的所有权，或保存可在当前存储上重新定位的偏移；这些方式分别增加分配、复制或协议复杂度。将 vector 换成另一种容器之前，仍需说明新结构保证的是哪些地址和哪些操作。

内存占用也不等于元素数量乘以元素大小。容器可能保留额外容量，节点可能携带链接和分配器元数据，闭包、结果共享状态和协程帧还会间接持有其他对象。虚拟地址范围、实际驻留页与逻辑有效载荷是不同统计口径。只限制运行线程数，不能限制排队对象和等待 I/O 的请求总内存；操作系统篇和容量准入案例将分别解释这些口径与约束。[41]

当数据超过内存时，同一原则延伸为分块、外部排序与流式处理：一次只保持可承受的工作集，以额外扫描或归并换取空间界限。某个中间步骤降低内存占用，不自动降低端到端时间，因为数据移动和重复读取可能随之增加。内存设计需要把对象生命期、容器失效与系统工作集放在同一条数据路径上分析。

第二篇 并发、执行器与线程池

后端执行层把中央处理器（central processing unit，CPU）计算、输入／输出（input/output，I/O）等待和结果交付接起来。线程数量、队列长度和请求数量分别约束不同资源，合法的内存访问也不自动建立业务上的完成顺序。本篇先建立并发状态模型，再用同一个固定版本线程池跟踪完整执行路径。

并发状态与执行资源

并发描述多个任务可以交错推进，并行描述任务在同一时刻获得多个执行资源。单线程事件循环可以并发管理很多请求，却不能同时执行这些请求的计算；增加工作线程可以提供并行机会，却也增加同步和调度成本。线程、任务和请求不是一一对应的对象，一个请求可能跨多个任务，一条线程也可能先后推进许多请求。

共享状态的正确性首先是语言层问题。潜在并发的冲突动作中，若至少一个不是原子动作，且缺少所需的先行发生关系，就可能形成导致未定义行为的数据竞争；对象生命期的开始、结束也参与相应冲突规则。即使所有字段都是原子类型，多步业务操作仍可能发生一般意义上的竞态。例如两条线程分别检查余额后扣减，单次读取和更新合法，不表示组合操作满足余额不为负的不变量。[219–220]

互斥量把多个状态转换组合成临界区；发布／获取原子操作则可以在满足读取来源条件时建立数据发布关系。下面是一次性发布的原创教学片段：假定两个对象在并发访问开始前已初始化，发布后不再修改 payload，并且它们一直存活到访问结束。

int payload = 0;
std::atomic<bool> ready{false};

// 发布者
payload = 42;
ready.store(true, std::memory_order_release);

// 消费者
if (ready.load(std::memory_order_acquire)) {
    use(payload);
}

只有获取操作读到了相应发布的值，才能由发布者写入、发布、获取和消费建立这里的顺序关系。将标记两端改成宽松内存序，仍保留标记自身的原子性，却不建立这条普通数据发布路径。反复复用缓冲区时，还需避免下一轮写入与上一轮读取重叠；一个布尔标记不是完整的循环队列协议。[221]

条件变量处理的是等待状态变化，而不是保存通知。任务存在于队列里，完成条件存在于计数与标记里；等待者持锁检查谓词，等待操作原子地释放锁并进入等待，返回后重新取得锁并检查状态。虚假唤醒和其他线程抢先消耗工作，都使“收到通知即取得任务”的解释失效。锁必须覆盖相关不变量，而不只是某一次容器调用。[222]

执行器把这些语言层关系接到实际资源上。工作线程数约束可同时运行的任务数，队列容量约束尚未取走的工作，连接池约束外部资源占用，结果通道连接完成者与等待者。若一个父任务占着唯一工作线程等待排在同池中的子任务，执行槽也会成为等待环中的资源；这类死锁不要求出现两把互斥锁。

下面的五个连续案例以 BS::thread_pool 5.1.0 为固定实现，沿提交、入队、取任务、交付结果和退出逐步分析同一组状态。它们展示具体库如何实现执行层协议，不把一个线程池扩张为网络循环、容量管理或完整服务。协程篇随后改变等待时保存状态的方式，但不会取消上述所有权和同步条件。

1. 服务中的执行模型

请求、任务与线程是三个层次

后端服务接收请求，但不必为每个请求创建一个新线程。请求可以经过网络读取、业务判断、计算和结果返回，其中某些步骤需要等待外部资源，某些步骤占用 CPU。线程池把可执行工作封装成任务，交给已经存在的工作线程；它提供执行资源复用，不自动定义请求的超时、数据权限或响应顺序。

以压缩响应为例：网络层接收数据，线程池执行压缩，结果再交回响应通道。一个请求可能产生多个任务，一个任务也可能合并多项小计算。任务边界首先应说明输入所有权、输出取得方式和执行期间依赖的资源，而不是仅把函数包进 lambda。

BS::thread_pool 在固定提交中以头文件实现线程池。模板选项分别启用优先级、暂停及同池等待死锁检查，默认 tp::none 不启用这些能力。创建池时指定线程数；未指定时按实现提供的硬件线程信息决定，启用原生扩展还可能考虑进程亲和性。[1, 7] 这些是库的默认选择，不是服务的最优容量证明。

CPU 工作与阻塞工作需要不同的预算

固定工作线程数能限制同时运行的任务数量，但线程如果阻塞于数据库或网络，就无法执行队列中的其他工作。CPU 密集任务、长时间阻塞任务和延迟敏感任务共享一个池时，会互相影响。分离执行资源、采用异步 I/O 或限制并发外部调用，是服务设计的选择，不是该线程池已经提供的网络框架功能。

例如，四个工作线程都在等待远端响应时，排在后面的短计算也无法启动。增大线程数可能缓解这一特定等待，却增加上下文切换、资源竞争和外部服务负载。线程数应与任务耗时、阻塞比例和机器资源一起评估，不能将 hardware_concurrency() 的返回值视为吞吐上限或性能建议。

接口对应的完成语义

接口 交给池的工作 调用方获得什么 需要另行处理什么
detach_task() 一个无参数任务 没有结果 future 任务自身错误报告、外部生命周期
submit_task() 一个无参数可返回值任务 单任务 future 结果取得、异常消费与等待位置
submit_loop() 按块封装的索引循环 一组完成句柄 各索引数据的独立性、分块粒度
wait() 不提交新工作 等待池状态满足谓词 上游是否已经停止提交

提交函数返回只表示任务已被接收，不表示函数已经执行；队列先进先出也不表示结果完成顺序一致。多线程可能同时执行多个任务，耗时不同会改变完成顺序。若业务要求按请求序号提交结果，需要在执行层之外维护相应协议。[2, 5]

2. 工作队列与同步协议

入队在锁内，任务执行在锁外

detach_task() 使用 tasks_mutex 保护队列插入，然后调用 task_available_cv.notify_one() 唤醒一个工作线程。以下是固定版本的短摘录，省略了优先级分支：[2]

{
    const std::scoped_lock tasks_lock(tasks_mutex);
    tasks.emplace(std::forward<F>(task));
}
task_available_cv.notify_one();

锁保护的是队列和关联状态，不是任务的全部执行时间。worker 在锁内等待、出队并增加运行计数，随后解锁再调用任务。[3] 如果用户代码一直在队列锁内运行，其他工作线程和提交者就会等待同一把锁，原本独立的任务也会被串行化。解锁执行还允许任务提交新工作，但不保证这些新工作与父任务之间没有等待环。

这一结构是集中式队列，不是每个 worker 各自持有双端队列的工作窃取。默认队列为 std::queue<task_t>；启用优先级后改为 std::priority_queue<pr_task>。优先级比较器只比较数值，没有使用提交序号，因此不能据此承诺同优先级稳定顺序。[3, 9]

条件变量通知不保存任务

worker 等待的是“队列非空且没有暂停取任务”，同时考虑停止条件。wait(lock, predicate) 在释放锁进入等待、被唤醒后重新获得锁，并再次检查谓词。通知只是推动等待者重查状态；任务由队列保存，不能用通知次数代替队列中的工作数量。[3]

这解释了两个经常混淆的场景。任务先入队、worker 后进入等待时，worker 会看到非空队列，不需要依赖一条此前通知仍被保存。发生虚假唤醒，或另一个 worker 已经取走最后一个任务时，谓词不成立，当前线程继续等待。正确性来自状态与锁的配合，而不是假设每次唤醒必定对应一个可执行任务。

计数必须覆盖状态转移

worker 出队时，在同一个临界区内增加 tasks_running；任务执行结束后，下一轮循环重新拿锁并减少计数，再判断是否应通知等待完成的调用者。这样，“排队任务”和“正在执行的任务”之间的转移不会向同一锁下的完成检查暴露一个两者都为空的间隙。[3]

计数还有初始化阶段的用途。create_threads() 在启动 worker 前先把 tasks_running 设为工作线程数，各线程执行初始化函数后进入循环并减少计数。因此这个字段在启动期间并不只表示正在运行的用户任务，也避免 wait() 把尚未完成初始化的池误判为空闲。[7] 解释计数器时必须跟随其写入和读取位置，不能只根据变量名推断含义。

把锁边界接到对象边界

队列同步不替业务对象提供线程安全。两个任务从队列中被正确取出之后，如果同时修改同一个非原子计数器，仍可能发生数据竞争；如果各自使用同一客户端对象，还需要核实该客户端是否允许并发调用。线程池保护自己的不变量，任务则必须维护共享输入、输出和外部资源的不变量。

细粒度分块可以减少排队和调度成本，但任务粒度过小会放大锁、封装、分配及唤醒开销。粒度过大则可能使某个工作线程长时间占用资源。不同工作负载应比较完成时间和负载分布，不能仅因队列逻辑短就断言它在任意并发度下没有瓶颈。

3. 结果、异常与对象所有权

future 是结果通道，不是工作线程

submit_task() 先创建 task_and_future<R>，将其中的任务移入队列，再把 future 返回给调用者。包装器创建 promise，取得其 future，并把用户函数与 promise 一起移动进任务。[4, 5] future 与工作线程没有一一对应关系：任意可用 worker 都可以执行该任务，结果仍通过同一共享状态交给调用方。

返回值为 void 时，包装器执行函数后调用 promise.set_value() 表示完成；有返回值时，函数结果进入 promise。在启用异常处理的构建中，包装器捕获异常并调用 set_exception()，随后调用方的 future.get() 重新抛出异常。[4] wait() 或 future.wait() 只等待状态，不代替 get() 消费结果和错误。

异常处理的位置改变可观察性

worker 外层也有异常捕获，但其 catch 为空。带 future 的包装器通常已把用户异常放入结果通道；直接 detach_task() 则没有同样的通道，未自行处理的异常可能被 worker 外层捕获后丢弃。[3, 4] 因而，“工作线程没有因普通任务异常退出”与“错误已经被业务记录”是两个不同结论。

服务代码可以使用带结果的接口，在明确的完成路径记录错误；也可以让 detached 任务内部自行报告失败。线程初始化与清理函数位于普通任务的 catch 范围之外，库的接口说明要求它们不抛出异常。[1, 6] 不能把任务异常通道推广为对所有线程生命周期异常的统一保护。

移动闭包与引用捕获

移动捕获可以将一个资源的所有权交给任务，而引用捕获只保存外部对象的引用。下面的例子用 unique_ptr 演示所有权转移，代码是本篇构造的用例：[4]

BS::thread_pool<> pool(2);
auto result = pool.submit_task(
    [p = std::make_unique<int>(21)] { return *p * 2; });
const int answer = result.get();  // 42

工作函数持有资源直到任务销毁，而不是依赖调用栈上的指针仍然存在。相反，[&request] 不延长 request 的生命周期；请求处理函数提前返回、超时逻辑销毁对象或连接关闭，都可能使后续任务访问失效引用。池的析构等待不能自动修复更早发生的外部对象销毁。

还要辨认依赖对象的声明顺序：局部变量按构造的逆序销毁。若被任务引用的数据先于线程池析构，池随后等待任务时可能已失去有效输入。稳妥的接口应明确拥有输入，或通过共享生命周期协议保证资源在任务完成前仍然有效。

清除队列之后的结果

purge() 清除尚未出队的任务，不影响已运行任务。[6] 对包装器持有的 promise 而言，任务未执行却被销毁，会使尚未满足的共享状态失去生产端，future 因而可能报告 broken_promise。这与任务主动抛出的业务异常不同，也不是“取消后成功完成”。

任务取消需要另外定义结果、原因和资源回收。清除队列只改变执行机会，不能回滚已经发出的外部请求、撤销已写入的数据，或中断正在运行的函数。把所有取消场景都映射成一个成功值，会掩盖调用方真正需要处理的状态差异。

4. 等待、暂停与退出

等待池空闲不是停止接收请求

未暂停时，wait() 的完成谓词同时要求运行计数为零、任务队列为空。暂停时则要求运行计数为零，并允许队列仍有未取出的任务。这一差异直接来自实现：[5]

if constexpr (pause_enabled)
    return (tasks_running == 0) && (paused || tasks.empty());
else
    return (tasks_running == 0) && tasks.empty();

pause() 改变的是 worker 是否继续取任务，已运行的函数仍会执行。于是暂停后的 wait() 返回，不能解释为全部提交任务已经完成。若另一条线程还在提交新工作，“此刻池空闲”也不是关闭服务的屏障；上游准入和生产者停止必须由服务自己协调。

同池等待为什么会死锁

一个任务正在执行时，其自身也占用运行计数。若在这个任务中调用同一个池的 wait()，任务等待计数归零，而计数归零又要求该任务先结束，形成循环等待。启用 tp::wait_deadlock_checks 后，等待接口检查当前线程所属的池，并为这种情况抛出 BS::wait_deadlock。[5]

该检查不是通用死锁检测器。单 worker 池中，父任务提交一个子任务，再等待子任务 future：worker 被父任务占住，子任务仍在队列，future 等不到结果。这个等待绕过了池的 wait()，因此不会被上述检查自动识别。跨池互相等待、持有业务锁等待任务也需要单独分析依赖图。

服务可把后续工作表达为完成之后的下一步，而不在有限 worker 中同步等待其依赖；也可将有明确隔离需求的执行资源分开。增加线程只能推迟资源耗尽，并不消除循环依赖。

析构的等待与停止路径

析构先调用 wait()。在使用 std::thread 的路径上，再将 workers_running 置为 false，通知等待者并逐个 join；具有相应标准库能力时采用 std::jthread 与停止令牌路径。[1, 7] 停止条件使 worker 退出取任务循环，不表示正在执行的用户函数被强制中断。

暂停状态尤其需要明确退出策略。库的析构说明指出，暂停时仍在队列里的任务不会执行。[1] 服务若希望排空已接收工作，应先停止生产者、恢复取任务，再等待并释放资源；若策略是舍弃排队工作，就应向结果消费者表达对应失败或取消。析构也没有为任意长任务提供统一完成期限：用户函数永久阻塞时，退出仍可能被拖住。

reset 不是请求级取消

启用暂停能力的 reset() 暂停取任务，等待正在运行的工作，重新创建工作线程，最后恢复原暂停状态。排队任务可以保留并由新线程继续处理；未启用暂停能力的路径则按相应等待语义先等全部工作。[6] 重建线程与清除队列是不同操作，不能把 reset 用作无条件取消请求的替代。

一个可维护的服务关闭协议，应分别说明接收入口、排队工作、运行工作、结果通道和依赖资源如何退出。线程池负责 worker 的生命周期，服务负责这些对象之间的依赖顺序。

5. 容量控制与验证

固定线程数不等于有界服务

固定版本的入队路径直接向任务容器插入，没有以队列容量、租户配额或请求期限作准入判断。[2, 3] 工作线程数限制同时执行的工作，却不能限制待执行闭包占用的内存。当请求到达快于完成速度，任务和它们捕获的数据会累积。

稳定系统中，平均在途数量、到达率和平均停留时间可用 Little 定律联系：[10]

L=λW

这里 L 是所选边界内平均在途工作数，λ 是同一边界的平均到达率，W 是平均停留时间；边界、统计窗口与稳定条件须一致。这是容量分析关系，不是本线程池的性能模型。队列持续增长时，不能任选瞬时测量值就称系统已稳定。

假设一个稳定工作流每秒进入 200 项工作，平均停留 0.1 秒，则平均在途工作数为 20。这个例子只解释数量关系，并未测量该库。在途包括排队还是运行，取决于统计边界；每个任务捕获的内存、队列节点和结果通道还会影响实际容量。

准入、背压与优先级各解决一部分问题

服务可以在提交之前限制在途数量、单租户工作量及输入大小，并在任务结束或提交失败时可靠归还配额。这个包装层还要定义超时、拒绝原因和结果通道，不能只在压力大时丢弃任务而让调用方永久等待。

背压把处理能力反馈给生产者，准入控制决定是否接收工作，优先级决定排队工作的选择顺序。三者不是互相替代的功能。优先级队列在持续高优先级到达时可能推迟低优先级任务；它也不能抢占已经运行的长任务。[9] 若服务需要截止期限、公平性或取消，应分别设计和验证。

从源码协议到小规模契约检查

本篇构造了一组确定性用例，在 Windows x64、Clang 23.1.2 下以 C++17 和 C++20、-O0 编译运行。检查了返回值与仅可移动捕获、任务异常经 future 传播、分块循环覆盖、暂停时 wait 返回但队列未清空、purge 后 broken_promise、同池等待检查以及未暂停析构排空。这些用例均通过，不是上游完整测试或并发压力测试。

例如，暂停语义的用例先创建单 worker 池、暂停并提交任务，再调用 wait()。随后检查队列仍有一项且 future 尚未 ready；恢复取任务后取得结果。它区分了“当前运行任务已结束”和“所有已接收任务都完成”，而不是依赖某次调度恰好慢了一点。[5, 6]

这类检查验证明确的接口现象；静态分析则解释现象由哪些状态和调用关系产生。二者结合比只看 API 名称更可靠，但仍不证明所有交错、所有标准库、异常关闭路径或生产负载均安全。

性能实验应回答具体问题

线程池评测可以控制任务粒度、提交者数量、worker 数量、阻塞比例和结果取得方式，分别记录吞吐、排队时延、尾时延与峰值在途数量。测量还应说明是否包含闭包构造、内存分配和 future 消费。只测一组空任务不能直接预测数据库服务或压缩服务的行为。

本篇未进行吞吐、尾时延、竞态检测或服务部署评测，也未实现工作窃取与网络事件循环。线程池案例说明的是后端执行层的同步、结果和生命周期协议。网络协议、持久化、连接管理与分布式一致性属于不同问题，不能因为任务能够并行执行就视为已经解决。

第三篇 C++20 无栈协程

线程池把任务放到可复用线程上执行；无栈协程进一步允许一个任务在尚未完成时保存状态、交还执行线程，再由后续事件恢复。两者不是互相排斥的调度模型，也不能由相似的顺序代码推出相同的生命期和取消语义。

本篇以 C++20 相关工作草案 N4861 的固定条款解释语言协议，并用原创教学代码建立帧所有权，再分析异步 I/O 如何接入运行时。草案编号不等于正式 ISO 标准版本；这里不分析特定编译器的协程降低实现，也不提供一个已经测试的网络协程库。

无栈协程的语言协议

阻塞式请求处理把“读请求、访问存储、写响应”写成顺序代码，但等待外部结果时，执行这段代码的线程可能无法处理其他请求。回调式处理可以归还线程，却需要把后续动作及其状态显式传给回调。C++20 无栈协程提供另一种表达方式：函数在暂停点保存继续执行所需的状态，之后再恢复，使源代码仍能沿请求顺序组织。它改变的是控制流与状态保存方式，不是操作系统的调度策略。

无栈并非不使用任何栈或内存，而是不为每个协程保存一套可任意暂停的独立原生调用栈。跨暂停点需要继续存在的状态由协程状态承载，常称协程帧；执行某一段协程代码时，仍使用当前线程的执行资源。普通辅助函数不能仅因为被协程调用就任意暂停整个调用链，需要通过协程协议表达等待关系。帧的具体布局及是否发生独立动态分配由实现和允许的优化决定，不能把“每个协程都分配固定大小的堆对象”当成语言保证。[282]

函数体包含相应的 co_await、co_yield 或 co_return，可以使函数成为协程。调用协程时，编译器按返回类型与参数类型确定 promise 类型，建立相关参数副本及 promise 对象，通过 get_return_object() 建立返回对象，然后进入 initial_suspend() 指定的初始等待。这里的 promise 是协程协议对象，不等于标准库的 std::promise<T>；返回对象也不必是 future。[282]

initial_suspend() 返回从不暂停的等待器，可以使函数体在调用时立即推进；返回总是暂停的等待器，则可以让调用先交回返回对象，稍后由运行时启动函数体。这常称立即启动与惰性启动，但惰性不表示参数处理、promise 构造和可能的帧分配都推迟到首次恢复。函数体何时运行与调用本身是否发生工作，需要分别分析。

普通 co_await expression 通常先经过 promise 的 await_transform（若存在），再按适用的 operator co_await 取得等待器，最后调用等待器的三个操作。初始、最终等待及 co_yield 隐式产生的等待另有相应转换规则，不能把普通表达式的每一步机械套到所有等待点。[283]

协议操作 控制流含义
await_ready() 结果为真时不进入暂停分支，直接求取等待结果
await_suspend(handle) 进入暂停分支后执行，用于登记继续执行关系或转交控制
await_resume() 未暂停或恢复后取得等待结果，也可以在这里报告错误

await_suspend 的返回类型进一步决定控制流。返回 void 表示本次协议不请求立即继续当前协程；返回 bool 且为 false 时继续当前协程，为 true 时保持此次暂停；返回一个协程句柄时，控制流恢复到该句柄指向的协程，常用于对称转移。这些选择都不等于创建线程或切换线程，await_ready()==true 也完全可能使一次 co_await 同步完成。[283]

协程在调用 await_suspend 之前已经按语言规则进入暂停状态。因此，若等待器把句柄发布给其他执行者，对方可能在 await_suspend 返回前恢复协程，甚至使等待器被销毁；发布后的代码不能无条件继续访问等待器自身。跨线程发布还需要相应同步和生命期协议，句柄这个普通值不会自动提供这些保证。

co_yield expression 则按语言规则表达为等待 promise 的 yield_value(expression) 所产生的对象。生成器可以借此保存本次产出值，并把控制交给逐步取值的调用方；产出值的存储、引用有效期及下一次推进仍由生成器类型定义。它不自动把元素发送给另一线程，C++20 的底层协程协议也不等于已经提供一个通用标准生成器容器。[286]

co_return value 将结果交给 promise 的 return_value；无值返回使用 return_void，同一 promise 类型不能同时提供两种返回接口。随后控制流结束相关局部对象的作用域并进入最终等待。函数体中未处理的异常按协程转换规则交给 unhandled_exception()，是否保存、终止或之后转交等待者，由返回类型的契约决定。最终等待必须满足不抛异常的要求。[282, 285]

至此，语言已经规定如何暂停、恢复、交付结果和结束，却尚未规定谁等待文件描述符、谁运行定时器、谁把就绪协程放回线程。co_await 若包裹的只是一次阻塞调用，这次调用仍会阻塞当前执行线程；若函数长时间计算而不交还控制，单线程事件循环中的其他请求仍不能推进。下一节先建立帧的所有权，再把语言协议接到实际调度与 I/O 上。

协程帧、返回对象与销毁边界

协程帧使函数在交还线程之后仍能保存状态，也使原本依附于普通调用栈的清理关系变得显式。返回对象、协程句柄和 promise 是不同对象：返回对象向调用者提供任务接口，句柄定位协程状态，promise 定义语言转换中的结果和等待行为。std::coroutine_handle 本身不是拥有型智能指针，复制它不会增加引用计数，销毁句柄值也不会自动销毁帧。[282, 284]

在有效状态上调用 resume()，会在当前调用的执行上下文中推进协程，直到下一次暂停或结束；它不是向某个内建线程池提交任务。done() 要求句柄指向暂停中的协程，返回其是否停在最终暂停点。destroy() 也要求协程处于暂停状态，不能与仍在执行的协程并发调用。非空句柄只说明保存了非空地址，不证明对应帧仍存活，更不证明它现在可恢复。

下面是完整的原创教学程序，采用 C++20 接口，专门展示单线程手动推进和独占帧所有权。它没有 I/O、调度器、父子任务等待或并发取消协议，未编译或运行，不是可直接替换生产协程库的实现。

#include <coroutine>
#include <cstdio>
#include <exception>
#include <utility>

class manual_task {
public:
    struct promise_type;
    using handle = std::coroutine_handle<promise_type>;

    struct promise_type {
        std::exception_ptr error;

        manual_task get_return_object() {
            return manual_task{handle::from_promise(*this)};
        }
        std::suspend_always initial_suspend() noexcept { return {}; }
        std::suspend_always final_suspend() noexcept { return {}; }
        void return_void() noexcept {}
        void unhandled_exception() noexcept {
            error = std::current_exception();
        }
    };

    manual_task(const manual_task&) = delete;
    manual_task& operator=(const manual_task&) = delete;
    manual_task(manual_task&& other) noexcept
        : h_(std::exchange(other.h_, {})) {}

    ~manual_task() {
        if (h_) h_.destroy();
    }

    bool step() {
        if (!h_ || h_.done()) return false;
        h_.resume();
        if (h_.done() && h_.promise().error) {
            std::rethrow_exception(h_.promise().error);
        }
        return !h_.done();
    }

private:
    explicit manual_task(handle h) noexcept : h_(h) {}
    handle h_;
};

manual_task example() {
    int phase = 1;
    std::printf("phase=%d\n", phase);
    co_await std::suspend_always{};
    ++phase;
    std::printf("phase=%d\n", phase);
    co_return;
}

int main() {
    auto task = example();
    while (task.step()) {}
}

按协议推演，example() 先建立返回对象并停在初始等待，尚未执行函数体中的输出。第一次 step() 将其推进到显式等待，局部变量 phase 的值需要跨暂停点保留；第二次推进继续递增并走到最终等待。这里所述顺序来自静态控制流推演，不是运行记录。std::suspend_always 只表示协议始终选择暂停，不负责未来恢复。[284]

final_suspend() 也选择暂停，使完成后的帧继续存在，所有者可以在恢复返回后检查异常，最后由析构函数调用 destroy()。若最终等待改为不暂停，协程可以自行释放帧，外部保存的句柄就可能悬空，当前 step() 里的 done() 与析构协议也不再成立。因此“只换一个等待器”可能改变整个返回类型的所有权契约，而不只是改变调度时机。

上述析构只在约定的单线程、没有外部恢复者的情形下成立：step() 返回时协程已经再次暂停，所有者不会在协程执行期间销毁自己。真实异步任务还可能把句柄交给 I/O 回调，直接照搬这个析构函数会让稍后的回调访问已释放帧。所有者释放任务之前，需要先解决挂起操作及所有可能恢复者的退出或解绑关系。

参数保存也不自动消除借用。按值传入的拥有型字符串可以把数据保留在协程相关状态中；按值传入的视图仍只保存指针和长度。引用参数不延长目标生命期，非静态成员协程也不会仅因调用而复制整个 *this。具有捕获的协程 lambda 若通过短命闭包启动，其函数体可能仍依赖闭包对象，不能假定捕获值已经自动搬进了独立帧。[282]

普通局部对象在正常离开相应作用域时销毁，暂停本身不退出作用域。因而跨等待点持有的连接、锁或大缓冲会一直占用资源。按值持有让生命期更容易成立，却也可能延长资源占用；借用减少复制，则要求外部所有者跨越所有恢复和取消路径。协程并未废除 RAII，而是要求 RAII 的所有者覆盖更长、也更复杂的控制流。

从等待表达式到 I/O 运行时

使协程适用于网络服务，需要把三层机制接起来：语言层保存和恢复函数状态，运行时管理就绪队列及执行上下文，I/O 层报告可推进或已完成的操作。三层可以由同一个库封装，但保证的来源仍然不同。C++20 的 <coroutine> 没有提供通用网络事件循环，也没有规定标准库 std::future 自带可等待接口。[283–284]

以 Linux 上的非阻塞连接为例，epoll 报告就绪，不替应用读取和解析完整消息。一个读取等待器可以先尝试推进读取；若得到当前不能完成的结果，则登记关注的事件和继续执行关系，交回执行线程。事件循环发现就绪后，再重试读取或安排协程继续，由等待结果接口交付字节数及错误。这是运行时的设计路径，不是 co_await 关键字隐含的系统调用。[21]

下面的原创状态示意假定单个事件循环串行处理登记、事件、定时器和恢复，并且登记函数不会内联调用完成回调。它刻意不提供一个缺失生命期协议的多线程 await_suspend 伪实现：

请求持有操作状态与缓冲
  → 尝试非阻塞操作
  → 尚不能完成：登记事件和继续执行关系，暂停协程
  → 事件／超时／取消之一选定唯一终态
  → 写入结果，解除或失效化其他登记
  → 将继续执行关系放入就绪队列
  → 恢复协程，读取结果
  → 所有可能的回调都不再访问状态后，回收操作状态

“选定唯一终态”解决的是同一操作可能被 I/O 完成和定时器同时结束的问题。只有胜出的路径可以交付一次结果并请求一次恢复；落败路径还要释放自身持有的登记或引用。多线程实现通常还需要原子状态转移、结果发布与安全回收，单独对一个完成标记做比较交换，并不能证明等待器和缓冲区在回调期间仍然存活。

就绪也不保证下一次操作必然取得完整数据。其他消费者可能先取走数据，系统调用可能返回部分结果，边缘触发模式还要求将剩余就绪工作处理到适当边界。一次“读取消息”的协程操作，通常需要在多个就绪等待之间保留已读偏移和解析状态；这些字节属于哪个缓冲、下一次接收是否使其失效，仍受前面容器与所有权规则约束。[21, 25]

父任务等待子任务时，运行时还要保存父任务的继续执行关系，安排子任务启动，并在子任务结束后传播结果或异常。若子任务最终等待返回父协程句柄，可以形成语言支持的控制流转移；若把父协程放回执行器队列，则增加一次队列与调度边界。两种方案的线程亲和、栈使用和公平性取决于实际实现，不能从顺序外观推断执行顺序和线程身份。

跨线程恢复尤其会改变隐含前提。resume() 在执行它的上下文中推进协程；恢复后不应假定仍在原线程。线程局部状态、需要同线程解锁的互斥量，以及具有线程亲和的连接对象，都不能无条件跨等待点使用。即使所有协程都在同一线程运行，暂停期间另一个协程也可能修改共享对象；单线程排除了同时执行，不排除业务检查与更新之间的逻辑交错。[284]

超时只说明等待预算用尽，不证明外部操作没有产生效果。运行时可以让取消与完成竞争选择返回结果，但销毁帧之前仍须处理尚未结束的访问；向存储系统发出的写入也可能在客户端停止等待后成功。父任务取消是否传播到子任务、取消后是否等待子任务退出，以及错误由谁观察，都属于库与服务契约，而不是语言统一提供的结构化并发保证。

协程的容量收益因此具有明确条件。它可以使等待 I/O 的请求不必各占一条阻塞线程，却仍保留帧、缓冲、连接和登记状态。已有的准入控制应覆盖这些在途资源，而不只是就绪队列长度；计算密集工作仍需要可用处理器和适当执行器。线程池与事件循环可以分工协作：前者承接受限的计算或阻塞工作，后者推进可暂停的网络状态，并在边界上明确交接所有权、错误和容量。

第四篇 操作系统与异步网络

语言中的任务最终由操作系统线程执行，网络消息最终通过连接传输字节。虚拟内存解释对象存储与物理资源之间的关系，事件通知则连接等待中的操作与可运行的继续执行位置。两者都提供机制，而不直接提供业务请求的完成语义。

进程、线程与虚拟内存

进程为程序提供地址空间及一组操作系统资源，线程则是在其中推进指令的执行流。同一进程的线程通常共享地址空间和许多进程资源，但各有自己的执行上下文和栈。把工作分到线程中，可以避免通过进程间消息复制所有状态，也使一个无效指针或共享对象的数据竞争直接影响同一地址空间内的其他工作。[23]

操作系统调度的是可运行的执行实体，而不是每一个用户态业务请求。线程阻塞等待 I/O 或同步条件时，内核可以调度其他可运行线程；单线程事件循环中的一个普通阻塞调用，却可能使整个循环暂时无法推进。用户态协程保存多个请求的继续执行位置，再由少量线程执行这些位置；只有实际执行它们的线程获得处理器，协程才会推进。

在具有内存管理单元的系统上，程序使用虚拟地址，地址转换和权限控制把它们映射到物理存储。页表记录映射关系，地址转换缓存（translation lookaside buffer，TLB）保存部分转换结果，避免每次访问都完整遍历页表。虚拟地址相邻不要求对应物理页相邻，不同进程也可以将同一物理页映射到各自空间。[41]

因此，申请了一大段虚拟地址，不表示所有页面都已经占用物理内存；对象所需存储、映射范围与驻留页统计也不是同一个数量。访问尚未建立相应映射或权限状态的页面，可能触发缺页处理，其中有些情况需要读取存储，有些只需建立映射或处理写时复制。把每次缺页都解释成一次磁盘读取，会错误估计请求时延与内存压力。[41]

文件访问又引入页缓存。普通缓冲文件读写可以借助内核缓存减少重复设备访问，写入返回与数据达到相应持久化边界之间仍可能存在距离。数据库自己的缓存、进程驻留内存和内核页缓存可能共同影响工作集；只看某一层的缓存命中，不能推出整个请求已经避开存储等待。预写日志和刷盘策略正是在这些不同完成边界之间建立恢复契约。[41]

内存布局还会影响访问路径。同一工作集分散到更多页，会增加地址转换压力；跨线程共享热点状态可能增加缓存一致性通信。大页、对象池、分片和批处理分别改变映射、分配或共享方式，也各有额外空间、回收和负载不均成本。没有对齐硬件、对象大小和访问模式的测量，不能从一种布局的机制优势直接宣称服务整体加速。

这些系统机制与 C++ 生命期规则并行成立：页面仍驻留不使已经销毁的对象重新有效，持有合法对象也不保证相关 I/O 已持久化。后端设计需要同时满足语言有效性、系统资源约束和业务完成语义，而不是用某一层的“成功”代替其他层。

字节流、事件循环与连接状态

传输控制协议（Transmission Control Protocol，TCP）向应用提供可靠、有序的字节流，不保留应用每次发送调用的边界。一次发送的内容可以分多次读取，多个发送也可以由一次读取获得。网络层把字节交给连接，并不表示应用已经取得一条完整请求；消息长度、分隔符、编码和最大报文限制属于应用协议。[25]

以长度前缀协议为教学模型，解析器需要先凑齐固定宽度的长度字段，再按约定字节序解释其值，验证上限，最后累积指定数量的正文。这个长度必须在分配大缓冲之前校验，整数计算也不能溢出。连接关闭时若只取得半个字段或半段正文，属于未完成消息，而不是一个长度较短的合法消息。一次系统调用的成功，只能推进这个状态机的一部分。[25, 281]

等待头部 → 累积头部 → 校验长度 → 累积正文 → 交付完整消息
                ↘ 非法长度／提前关闭／错误：进入相应失败终态
交付后若缓冲仍有字节 → 继续解析下一条消息

在 Linux epoll 模型中，内核维护关注集合和就绪集合，epoll_wait 取得当前事件。就绪表示相关操作可能推进，不是完整业务操作已经结束；应用仍须处理部分读写、错误和当前不能完成的返回。非阻塞调用使一次不能推进的读写交回控制，从而允许同一线程继续管理其他连接。[21]

水平触发（level-triggered，LT）在相应就绪条件持续时仍可报告，边缘触发（edge-triggered，ET）按相应状态变化组织通知。使用 ET 时，只消费一部分数据后直接等待下一次变化，可能使缓冲中剩余数据长期无人处理。典型协议使用非阻塞文件描述符，并在读写返回 EAGAIN 等相应边界后再等待事件。为了公平性而限制单轮处理量时，需要另行保留就绪工作，不能把未处理内容遗忘在等待集合中。[21]

连接状态应包含输入和输出偏移、解析阶段、已登记事件、截止时间，以及能够辨别当前操作身份的信息。文件描述符编号可能被复用，仅凭一个旧编号不能证明回调仍属于原连接。关闭流程除了释放描述符，还要处理事件登记、排队继续执行关系和持有缓冲的任务；共享所有权可以延长连接对象生命期，却不能自动使已经关闭的外部连接重新可用。

协程可以把上述状态机写成较连贯的顺序代码，但消息分帧和部分读写仍然存在。运行时等待“可读”，业务等待“完整消息”，数据库等待“事务完成”，这三个等待操作具有不同的终态和错误。它们的结果接口可以相似，底层保证却不能互相替代。

输出方向同样需要容量协议。对端读取慢时，发送缓冲可能积压；继续无限接收并计算响应，会把压力转移到用户态输出队列。高水位可以暂停接收新的工作或向上游传播背压，低水位再恢复；拒绝、断开和已接受请求的处理需要保留清晰语义。背压改变的是产生与消费之间的速率关系，不只是换一个更大的缓冲。

超文本传输协议（HyperText Transfer Protocol，HTTP）在字节传输之上定义方法和消息语义，传输层安全协议（Transport Layer Security，TLS）提供相应通道的认证、机密性与完整性。通道安全不等于业务授权，方法的幂等语义也不自动使任意数据库写入可安全重试。请求在网络断开之前是否已提交，必须回到服务和存储的状态边界判断。[26–27]

第五篇 数据库、存储与缓存

计算结果只有进入相应存储与提交协议，才获得约定的可见性和恢复性质。索引决定访问哪些数据，事务决定哪些变更一起发生，缓存则在另一条读取路径上复用结果。优化某一层不能自动建立其他层的保证，尤其不能由客户端停止等待推断数据库没有完成修改。

索引结构与存储读写路径

索引不是为每个条件附加一个加速标签，而是按某种顺序或映射保存定位信息。查询能够利用多少定位能力，取决于谓词怎样缩小搜索范围、返回哪些列，以及读取的记录在存储中如何组织。增加索引会增加写入维护与空间成本，不能脱离读写比例和实际查询路径讨论收益。

在 MySQL 8.4 的 InnoDB 中，聚簇索引保存行数据，显式主键通常承担这项角色；没有合适主键时还有相应选择与内部键规则。二级索引记录包含索引列及主键列，可能需要再通过主键访问聚簇索引取得其他列。因此，一个查询在二级索引上完成筛选，不等于已经取得全部结果字段；覆盖所需列可以避免相应回表，但更宽索引也会占用更多空间。[47]

组合索引按列组成的键序组织数据。例如 (tenant_id, created_at, id) 可以把一个租户中的时间范围组织为局部有序区间，同时为同一时间的记录提供进一步顺序。条件能否缩小连续搜索区间、剩余条件能否在索引记录上过滤、是否需要扫描或排序，是不同问题。最左前缀解释常规定位能力，但不能把“不能按首列直接定位”简化成“优化器绝不读取这个索引”。具体计划还取决于可用路径和成本估计。[28]

页式树结构通过多路分支降低访问层数，并保持适合范围扫描的顺序；节点扇出、键宽和页中有效记录比例共同决定路径成本。宽主键还会出现在二级索引记录中，使主键选择的成本传播到其他索引。缓存在内存中的索引页减少了实际设备读取，却没有改变查询必须处理哪些记录的逻辑工作。

日志结构合并树（Log-Structured Merge，LSM）采取另一种写入组织方式。以 RocksDB 的公开架构为例，新写入进入内存表，按配置记录预写日志，内存表刷成有序文件，随后通过合并整理控制文件和版本。顺序记录及批量刷写可以改变随机更新路径，但读取可能需要检查多个有序文件，旧版本与删除标记也要等待合适的回收条件。[149]

合并整理不是免费后台工作。更积极地压缩重叠有序段，可能降低读取候选和空间放大，却增加重写数据；保留更多有序段可以减少一部分写放大，又增加读取或暂存空间。RocksDB 的分层、分级及混合策略具有不同形状，不能把某一个理想模型的放大公式当成所有配置的实测成本。[150]

树结构与 LSM 的对照因此不是“读快”对“写快”的无条件排名。键分布、更新偏斜、范围扫描、缓存大小、持久性配置与合并积压都会改变结果。对服务而言，前台请求还与刷盘和合并共享设备带宽；只观察前台接口的逻辑写入量，可能低估真实数据移动和后续维护工作。

事务可见性、日志与业务原子性

数据库事务把一组读写接到提交或回滚边界。原子性、一致性、隔离性与持久性（atomicity, consistency, isolation, durability，ACID）描述不同性质，其中原子性不意味着其他系统的副作用一并回滚。一个请求可能已提交数据库，随后在发送响应时失败；客户端看到超时，不能据此断定事务未发生。服务的返回状态与数据库的提交状态需要通过幂等键、查询或恢复协议重新关联。

多版本并发控制（multiversion concurrency control，MVCC）使读取能够选择符合可见性条件的历史版本，而不必始终阻塞所有写者。MySQL 8.4 InnoDB 的普通一致性读在可重复读隔离级别下通常复用本事务首次此类读取建立的快照；在读已提交下，每次一致性读使用新的快照。同一事务自己先前的修改另有可见性处理，不能把快照简化为“数据库在某一时刻的完整只读副本”。[30]

一致性读、加锁读和更新语句也不是同一种访问。普通快照读取看到的历史版本，不表示稍后的更新仅作用于同一份历史集合。若业务先读取余额再无条件写回计算结果，两个请求可能互相覆盖；可以把必要条件放进同一个受数据库约束的状态转换，或按适当锁协议保护相关记录。事务存在并不能替代对隔离级别、锁范围和失败重试的分析。[30]

持久性则连接内存更新与崩溃恢复。重做日志记录恢复所需的修改信息，使尚未写入数据页的更新可以在相应恢复流程中重放；撤销信息承担回滚与历史版本等不同职责。日志已进入进程缓冲、写入操作系统缓存、达到要求的持久存储边界，以及脏数据页已落盘，是不同事件。具体提交保证还取决于产品配置和底层存储，不能把一次内存修改或普通文件写入等同于耐久提交。[31, 41, 45]

索引选择同时改变并发行为。一个更新可能需要访问并锁定比最终修改行更多的记录或区间；两个事务以不同顺序取得资源，可能形成等待环。死锁重试需要重新执行一个满足业务幂等与输入条件的操作，而不是盲目重发任意产生副作用的函数。缩短事务持有时间和固定访问顺序，可以减少某些冲突，却不能保证所有负载中都不存在死锁。[32]

跨服务状态还需要扩展提交模型。事务型发件箱将业务变更与待发送事件写入同一个本地事务，之后由中继发布事件，缩小“数据库成功而消息没有记录”的窗口。中继在发布后、确认前失败可能再次发布，消费者仍需处理重复；该模式提供的是带前提的可靠推进路径，不是即时跨服务原子提交或恰好一次业务效果。[265]

由此，事务设计要回答的不是单独一项“支持 ACID”，而是哪些状态共同提交、读取选择哪个版本、失败后哪些动作可以重试，以及恢复进程如何判定先前结果。网络超时、任务取消和数据库回滚分别控制不同边界，需要明确衔接，不能互相冒充。

缓存、过期与一致性窗口

缓存把一部分读取从事实来源移到更近或成本更低的存储，但同时引入第二份可能失效的数据。旁路缓存的基本路径是先查缓存，未命中时读数据库并回填；写路径先修改事实来源，再安排相应缓存更新或失效。这减少某些重复读取，却不使数据库和缓存自动具有同一事务边界。[264]

一个反例可以说明删除缓存仍然存在窗口：请求甲未命中缓存，读到数据库旧值后暂未回填；请求乙更新数据库并删除缓存；甲随后把旧值写回缓存。最终缓存又含旧值。这个时序是机制分析，不是某个部署的故障记录。缩短有效期可以限制部分旧值保留时间，却不能在所有并发和故障情形下证明读到最新值；版本标识、串行化、可靠失效或选择不缓存，需要结合要求确定。

过期与淘汰处理的是不同约束。过期表达数据的有效期，淘汰是在内存压力下按策略选择删除候选。数据可能因为容量压力早于有效期消失，也可能在某些物理清理路径中暂时留有已过期记录而不再作为有效值返回。设置过期时间不等于给缓存总内存建立上限；内存限制、策略适用范围和额外缓冲还需要单独分析。[33, 43]

热点未命中又可能把大量请求同时推向数据库。按键合并回源、限制回源并发和适当的过期分散，可以改变这部分瞬时负载；负缓存可以暂存不存在的结果，却增加新数据短暂不可见的可能。使用布隆过滤器提前排除明显不存在的键，还要维持过滤器与实际数据的更新关系，不能把概率数据结构当作事实来源。控制回源量与维持业务新鲜度之间存在取舍，而不只是提高命中率。

Redis 的持久化也不等于缓存与数据库一致。状态快照与追加写文件分别保存不同形式的恢复依据，追加写文件的刷盘策略还区分每次追加批次、周期刷盘和交由系统等配置。命令已执行、响应已返回、日志已同步到要求的存储层，是需要按配置核对的边界；不能把某个常用周期下的风险描述当成所有故障中严格不超过该周期的数据损失上界。[34]

缓存内的原子操作同样具有范围。单实例上的一次条件更新可以避免该实例内部的某种交错，却不自动把数据库更新、外部调用和多个分片合成一个原子事务。[36] 基于租约的锁在持有者暂停、租约到期后也可能出现旧持有者继续访问资源；受保护资源若需要拒绝旧动作，还须具有自己的版本或防护协议，不能只验证持锁者曾经取得一个键。[35]

缓存故障时的服务策略必须与存储容量协调。所有请求同时绕过缓存，可能使原本被缓存保护的数据库过载；一律拒绝请求又可能违反可用性要求。受限回源、返回明确允许的旧值、按业务降级或拒绝新增工作，分别改变容量、时效与可用性。选择应落实到具体数据类别及请求预算，而不是假定“缓存只是加速层，坏了不影响正确性”。

存储层最终向服务提供的不是一个孤立组件，而是一组可见性、耐久性、容量和恢复契约。缓存命中率、数据库查询时间及复制进度只是其中不同观测；架构层需要将它们对应到同一请求生命周期，才能解释成功、超时和恢复后的状态。

第六篇 工程设计与服务架构

对象、执行器、网络和存储各自维持局部约束，服务架构负责把它们连成可解释的请求生命周期。模块接口需要同时表达所有权、完成条件、容量和错误；构建与诊断则把源码层的设计联系到实际产物与观测，避免将局部成功误当成系统保证。

请求生命周期与服务边界

一个 C++ 后端服务可以沿请求生命周期分解：连接层取得字节，协议层建立完整请求，准入层确认资源预算，业务层决定状态转换，存储层提交结果，输出层交付响应。模块划分的依据是状态与保证的边界，不只是文件夹名称。把同一个连接指针传过所有模块，虽然减少接口数量，却也会把网络生命期、线程亲和和事务细节耦合到业务逻辑。

接口边界应说明输入由谁持有、完成以什么事件表示，以及失败后哪些对象仍可访问。纯解析可以只借用当前稳定缓冲；延迟执行的业务任务则需要拥有足够长寿命的输入。计算执行器不应默认拥有数据库连接的全部生命期，连接循环也不宜在一个长事务中等待不可控的远程调用。所有权关系与容量关系相互影响：转移一个对象可能延长其占用，也可能让准入配额继续绑定正在进行的工作。

将请求状态拆开，可以得到下面的原创分析模型。它描述职责，不对应某个现成框架的内部实现：

已接收 → 已准入 → 执行中 → 已提交 → 响应已交付
   ↘ 拒绝       ↘ 提交前失败        ↘ 响应结果未知

“响应结果未知”不同于“业务未发生”。若提交之后连接断开，服务不能仅通过重试一个新增订单操作来判断先前结果。业务幂等键可以把重复请求关联到同一操作身份；关键在于去重记录与实际状态转换具有一致的提交关系。只在内存中记录“已经见过请求”，重启后或跨实例访问时就可能丢失这项判断依据。HTTP 的方法语义提供协议层约束，不替应用补齐这样的持久协议。[26]

容量也应沿同一链条闭合。每个已接收但未结束的请求可能占有输入、闭包、协程帧、连接或结果缓冲。线程池工作线程数只限制其中一部分可同时运行的工作。分层队列若各自无限增长，只是把过载从执行层转移到内存与等待时间；有界准入需要规定何时扣除、哪个终态归还，以及拒绝是否发生在业务副作用之前。

截止时间是请求可以等待的总预算，各阶段排队、连接获取、执行和返回都消耗预算。把每层超时独立设成相同值，可能使端到端等待远超调用方预期。重试还会增加实际到达工作量：在依赖系统过载时，未加限制的重试可能放大故障。指数退避、随机分散、次数上限与仅重试可安全重试的动作，改变的是请求再次到达的过程，不会使原操作自动具备幂等性。

服务拆分则把本地调用变成具有传输、部分失败和版本兼容成本的远程交互。单体结构可在同一进程中共享事务与对象，但也共享故障影响；独立服务可以分开部署和扩缩容，却需要处理跨边界身份、协议、事件及数据一致性。是否拆分应由状态所有权、演进和隔离需要支持，而不是从模块数量或框架名称直接推出。

设计模式可以帮助组织这些边界，却不是正确性的替代物。策略封装可替换的算法，工厂集中对象创建，依赖注入将具体实现的选择移出业务逻辑；只有在实际变化方向与所有权协议清晰时，这些间接层才有价值。服务结构的质量最终表现为：请求经过哪些状态、每步依赖什么保证，以及失败之后仍能说明资源和业务结果的归属。

构建、诊断与性能证据

服务行为取决于源码，也取决于编译器、标准模式、头文件、编译选项、链接依赖和生成配置。预处理、编译、汇编与链接将不同信息逐步变为可执行程序；某个翻译单元成功编译，不证明符号、对象定义和二进制接口在最终程序中都匹配。可复现的构建记录需要能把产物追溯到实际输入，而不只是记录一个分支名称。[142]

构建依赖图决定增量结果是否可信。若生成头文件、配置或工具版本没有进入依赖关系，增量构建可能继续使用旧产物；每次清空重建又会掩盖缺失依赖并增加开发成本。正确的增量接口应把真实输入、生成步骤及产物边界表达清楚，而不是用工作区修改时间替代全部依赖身份。

诊断则需要把观察与当前二进制对应。崩溃现场中的地址必须结合匹配的可执行文件、库和调试符号解释；某个调用栈展示的是观测时刻的执行路径，不自动证明最初破坏内存的位置。异步执行还会把“发起请求”和“发现错误”分到不同线程或恢复点，操作身份、阶段和错误传播记录因此比只记录线程编号更有帮助。

内存检测器提供另一类证据。例如 AddressSanitizer 通过编译插桩及运行时支持检测相应的越界、释放后使用等问题；它观察实际执行到的路径，不证明未执行路径中没有错误，也不是所有并发协议的验证器。静态源码分析、文档工程检查、带检测器运行和完整产品测试各有不同范围，不能因为阅读页成功生成就声称教学代码已通过编译或竞态检查。[147]

性能分析同样先区分问题。处理器采样回答时间主要落在哪些执行路径，队列与阶段计时回答请求主要在哪些位置等待，内存统计回答哪类对象或页面正在占用资源。把等待时间误认作计算热点，可能促使增加线程或优化局部函数，却没有改变数据库连接竞争或排队。对异步服务，线程上的活动时间也不等于某个请求的完整停留时间。

比较方案时，需要对齐负载、并发数、数据分布、错误率、硬件、构建模式和观察窗口。提高平均吞吐不保证降低尾时延，降低单个请求的复制量不保证减少总分配，增加缓存命中不保证端到端更新仍满足新鲜度。机制分析可以给出待测假设，只有条件明确的实际观察才构成相应效果证据。

前面的线程池案例展示固定版本实现如何维持执行状态，协程篇展示控制流怎样跨暂停点保存，网络和存储篇再分别定义外部完成边界。这些关系共同构成后端推理的基础：从对象和状态出发，沿真实调用与数据路径定位保证，再用与问题相符的证据判断结果，而不是把组件名称或接口外观当成完整系统的承诺。
