# 综述与源码解读方法

本文合并了原创综述的证据组织方法与源码解读规范：问题界定、断言与来源的对应、比较的对齐条件，以及以机制和执行链为主线的实现分析要求。任务准备、证据检索与验证命令的执行位置见 [pipeline.md](pipeline.md)。

本指南用于原创综述的资料整理、论证和审校，不是阅读页正文模板。它借鉴 Feynman 的文献综述、来源比较、引文核查与研究审校方法，并结合本项目的源稿、离线阅读和权利边界。不同综述保持各自的身份与论述结构；共享方法不要求合并成一个文献汇总站。原创综述写作或精修前必须完整阅读本指南与 [中文写作原则](writing.md)，涉及实现解读时另完整阅读 [源码解读规范](method.md)。机制解释的深度、数学前提与正文表达以写作规范为准，不能只完成来源清单而省去论证。

实际批量审校、有限检索和检查触发点见 [操作工作流](pipeline.md)。本指南规定证据质量，不要求每题新增来源或反复阅读同一份手册。

## 先明确问题，再组织文献

每个主题先确定需要解释的对象和问题。例如，架构主题可以问“信息如何在序列中传播”，推理主题可以问“计算和状态分别消耗什么资源”。围绕这些问题选择原始方法论文、评测、代码和综述，不按论文数量或发表声望替代相关性判断。

章节按研究对象与论证关系组织，不固定主题数量，也不默认所有任务都有同一种预训练、后训练和服务流程。语言、视觉、音频、时间序列、生物序列及多模态设置要分别辨认；自回归语言模型的 KV 缓存需求不自动成为所有模型的共同前提。

## 保存断言到证据的联系

研读记录应能说明：哪项断言由哪一个固定版本、章节、图表或代码支持，材料提供的是报告结果、推导、实现说明还是独立实验。书目身份至少核对题名、作者、稳定标识与实际版本；同题预印本和正式版分别记录，近似题名不任意替换。

有条件时以另一书目索引交叉核对身份。索引不可用、作者未能核对或 URL 失效时记录缺口，不补造字段。已有可核对的离线 PDF 不因网页不可达而失去证据资格；原始参考文献也不因工具匹配失败就被静默删除。

引文要支持所附的具体数字、条件或结论，不能只证明主题相关。尤其区分：原论文结果、综述归纳、厂商声明、代码静态观察和本项目分析。单一原始研究仍可作为其方法的来源，但重要的跨研究结论应寻找独立佐证，或保留单一来源和条件的限制。

## 比较一致、分歧与尚不明确之处

对照记录可按研究对象、方法作用点、训练与输入条件、证据类型及局限组织。表格用于帮助发现差异，不强制每篇论文填满相同栏目，也不直接代替正文中的机制解释。

看似冲突的结果先检查模型、数据、硬件、序列长度、批量和指标定义是否一致。参数少、FLOPs 少、内存少、时延低与能耗低是不同结论；跨论文数字不能无条件拼成排名。一个方法在特定任务上有效，也不能直接写成跨模态或跨设备保证。

研究综合应说明哪些结论有共同支持、哪些分歧来自设定不同、哪些缺少足够证据。不要以语气弱化代替核对，也不要为让分类整齐而把缺失证据填成肯定结论。

## 引文语境与可选服务

引文语境工具可以帮助定位支持、质疑或仅提及某研究的语句，但分类标签不是论断真伪判定，也不是独立复现。回读引用语句及必要上下文，确认它指向被引材料的哪个结论、使用什么证据、是否保留相同条件；提到论文不等于支持其全部主张。自动分类不确定或与语境不符时，保留原句和核对限制，不强行按标签归类。

区分引文语句数、引用文章数和独立证据数量：一篇文章可以多次引用同一研究，多个工具也可能返回相同记录；都不能因此算成多项独立佐证。Scite 的 Smart Citation tallies 与 `citingPublications` 采用不同计数对象，不能当作总数与子集，也不能直接替换已有书目的引用量字段。

服务仅是可选入口，不要求上传本地全文或预设已有账号／订阅。连接授权、数据范围与费用另行确认；不可用时仍可通过本地原文及现有来源完成其实际支持的核对，明确尚缺的材料，不声称已经调用服务。

## 从原文与实现相互核对

涉及代码的断言应记录固定提交和相关实现位置，分别检查默认配置、数据处理、训练目标与输出计算。静态阅读不能写成已经训练、复现或测得性能。原论文未公开必要代码时，指出核对边界，不推测实现来补齐方法。

数学解释保留假设、维度与等价／近似条件。图示和例子用于澄清机制，不能将示意数字当作实测结果；制作原创示意时明确其性质。阅读页遵循原生 MathML 和真实相对资源文件，不因外部工具建议而引入运行时数学或绘图库。

## 审校分层，而非机械套版

可以把研究、来源核查、论证审校和写作看成不同检查职责；这不要求实际启动多个代理。是否委派仍由任务授权及环境约束决定。

- **关键问题**：身份错误、数字无来源、数学不成立、遗漏关键条件或把未经验证结果写成复现。进入正文前解决，不能以引用链接存在来掩盖。
- **主要问题**：覆盖不足、比较不公平、解释与证据脱节、重要分歧缺少处理。补充来源或缩小论断范围。
- **次要问题**：术语、指代、结构、重复或排版。修订时不损伤原始公式、代码、表格与引用。

任务中的待查项和审校记录留在任务状态或研究笔记；正文围绕技术对象连贯解释，不展示工作清单、审稿对话或固定问答脚本。中文表达参照 [中文写作原则](writing.md)。

## 原创解释与保留来源分开

外部论文的完整译文可以作为本地研究来源保存，但不是原创综述的正文。专题重组需要重新组织论证和准确归属，不把译文复制成新综述，也不沿用原论文的“我们”来指代本项目。

材料公开可访问、代码开源、原文获提供、引用得到核对，都不自动授予译文或图表的公开许可。版本、权利和必要的核对限制保留在资料记录与阅读元数据中；发表审批独立于研究资格。来源的保存与迁移应保护原稿和有用资料，不能用审校名义改写原始记录。

## 来源记录与工具边界

规范源稿、书目和有用研究笔记保留在各项目 `work/` 中；一次性计划、抓取原始响应、扫描报告和试验使用系统 TEMP。来源记录可列出接受和未接受的材料及理由、固定版本、实际核对范围和未决事项，不因多个角色重复同一来源而夸大证据数量。

借鉴研究工具的方法不等于执行其安装脚本、加载其扩展或发送本地数据。需要实际工具运行时，先核查依赖、遥测、凭据、费用与数据流，并使用隔离环境；原稿和私有资料不默认上传。

本规范适用于框架、项目和库的源码分析，也适用于原创综述中的实现解读。读者应能从文档定位实现、理解职责边界，并判断一种设计成立的条件，而不必先在整个仓库中搜索。

## 分析的最小证据链

每个主要技术对象应交代两条主线，按论证需要组织段落，不机械套用问答栏目：

- **结构与执行**：入口、模块职责、关键对象、调用顺序、数据流和状态所有权。说明谁创建、更新、共享、释放资源，哪些不变量跨越模块边界。目录树不能代替执行链。
- **业务挑战与设计回应**：先说明真实工作负载中已经被官方或社区材料识别的问题，以及朴素方案或缺少某机制时为何遇到这些问题；再沿源码逐步解释现有机制如何处理它们，并交代复杂度、容量、同步或质量方面的代价。不能从代码名称反推一段未经证实的设计动机。

设计解释以官方架构／设计文档、源码注释、维护者说明、相关论文、commit、PR 和 issue 为主要依据；可靠社区讨论用于补充跨项目的共同挑战。每项关键挑战应有可定位的出处，并说明对应版本和业务条件。所谓“业界共识”不能仅凭单篇帖子成立；区分普遍约束、某版本的故障报告和某个部署的特例。

对照是基于已有证据的逐步讲解，不是要求作者在本机进行消融。例如依次说明重复预填充的计算成本、连续缓存的容量浪费、共享缓存的回收风险，再对应缓存、分页和引用保护的实现。可以用复杂度或简短状态例子帮助理解，但它们是辅助解释，不能替代问题来源，也不能把逻辑上可能出现的风险写成社区已经确认的历史故障。

案例包括业务负载、触发条件、已知问题、对应机制及适用边界。使用 commit、PR 或 issue 解释演进时，核对仓库、固定链接、修改前后代码及维护者表述；区分用户报告、维护者确认、修复方案和合并状态。没有核实的历史动机不补写。引用上游测量时保留其条件与归属，不将其写成本文复现。

这类文档研读不编译、启动或部署上游项目，不运行其测试、benchmark 或修改代码做消融；不能用本机试错代替已有工程知识的检索与整理。源码只读检查、固定提交摘录核对和文档生成属于不同操作。额外的上游执行任务必须获得单独明确授权。

## 可直接阅读的代码证据

路径索引用于定位，关键控制流仍应展示短而完整的源码片段。每段保留完整来源记录：仓库、固定提交、仓库相对路径、真实行范围、函数／类／内核名和该片段的作用。使用语言标记的围栏代码，构建时生成离线 token 着色。

可核查不等于把完整提交号和长路径全部排成代码之前的正文。默认可见说明先交代片段用途，并提供简短仓库名、文件名与真实行范围；完整来源可以放在同一片段附近的原生 `details`／`summary` 中。收起详情不能隐藏代码，展开后应能在本地、无脚本环境读取完整版本、路径、符号、来源链接及必要归属，不要求先访问外部仓库。短 hash 只能作为显示标签，不能替代完整提交与固定版本链接；同名文件也不能因路径缩写而失去区别。呈现建议及检查见 [阅读页规范](reader.md#compact-source-code-presentation)。现有普通说明仍可使用，不因本条建议而假设构建器新增了源码卡片指令。

- 原文摘录保持代码不变，解释放在相邻正文，不悄悄插入作者没有写过的注释。
- 路径、起始行和符号可写在片段附近的来源详情，或以明确标注为“编者定位注释”的注释展示。行号针对固定提交，不能只跟随不断变化的分支；显示行号和说明不混入可复制的原始代码。
- 公共缩进可以只在显示层收起，但须标明这种处理，保留完整原始文本、逐行相对缩进及原文复制／回退。不能直接重写规范摘录来节省手机宽度，也不能以显示处理掩盖删行、变量替换或控制流改写。
- 不连续摘录分别标记行范围，省略不得伪装成连续代码；精简、翻译变量、改写控制流都标为教学伪代码。
- 只展示支撑论点的最小片段，并解释状态变化和调用上下文。不要复制整仓库、整文件或用巨大代码块代替分析。
- 本地检出可能有修改；摘录前检查状态，并对照 `git show <commit>:<path>`。有差异时声明来源，不能把工作树内容冒充固定提交。
- 保留上游许可证和归属。片段及其分析不会自动获得本库 MIT 授权或公开许可。

## Markdown 组合接口

使用现有 Python 构建器，不新增在线文档服务或第二套运行时。一级章节在 `work/content/*.md`，子稿位于其下的主题／项目目录。例如：

```text
content/
  05-frameworks.md
  frameworks/
    vllm.md
    sglang.md
    flash-attention/
      algorithms.md
      gpu.md
```

父稿保留章节标题、必要的过渡和阅读顺序。下面的独立行在构建时原位展开：

```markdown
{{include:frameworks/vllm.md}}
```

路径相对于含有该指令的文件，必须指向同一 `content/` 根目录内的 `.md` 文件，统一使用 `/`。允许递归组合；拒绝绝对路径、逃逸（含符号链接）、循环、缺失文件和超出大小／深度限制的输入。围栏代码和缩进代码中的示例不展开。它不是模板语言，不执行 Python、shell 或表达式，也不从网络或源码仓库自动抓取文件。

子稿不会另成顶层章节；展开后共享目录、脚注、引用和标题锚点。资源链接仍相对于生成的阅读页，**不会**改为相对于子稿。一级文件仍按文件名排序，子目录不被自动遍历，只有父稿显式引用的子稿进入阅读页。为避免重复锚点，同一内容通常只嵌入一次，并用唯一标题或显式 ID 交叉引用。

`manifest.json` 的 `content_dependencies` 记录每章实际读取的源稿；内容哈希覆盖父稿及递归子稿。因此修改单个项目文件即可改变对应阅读页，无需维护重复正文。共享样式修改仍通过 `tools/assets.py` 更新，不能创建项目私有 CSS/JS。

## 维护与验证

按独立技术对象拆分文件，不按任意行数截断。项目特有设计属于项目子稿；共同原理属于主题子稿，项目通过过渡或锚点引用，避免复制后漂移。文件名使用稳定的技术名称，章节顺序由父稿负责；维护索引说明修改入口，但不进入读者正文。

Python 使用 `tools/dev-env.ps1` 管理的系统 TEMP 虚拟环境，依赖在 `requirements.txt` 固定。Pygments 仅在构建时运行；输出是普通 HTML 与共享 CSS，离线阅读和打印不执行着色脚本。未知语言保留原样，不猜测语言。

修改后检查递归依赖、目录与锚点、离线资源、源码行范围、MathML 和版权信息，并核对业务挑战与来源材料的对应关系。文档工具的回归测试覆盖 include 的正常／异常路径、子稿修改后的哈希变化、代码内容与 HTML 转义；这些检查只验证文档工程，不用于发现或证明上游框架的设计必要性。任务日志与文档检查报告保存在系统 TEMP。
