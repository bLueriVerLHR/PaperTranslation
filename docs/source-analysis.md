# 源码解读与模块化书稿

本规范适用于框架、项目和库的源码分析，也适用于原创综述中的实现解读。读者应能从文档定位实现、理解职责边界，并判断一种设计成立的条件，而不必先在整个仓库中搜索。

## 分析的最小证据链

每个主要技术对象应交代两条主线，按论证需要组织段落，不机械套用问答栏目：

- **结构与执行**：入口、模块职责、关键对象、调用顺序、数据流和状态所有权。说明谁创建、更新、共享、释放资源，哪些不变量跨越模块边界。目录树不能代替执行链。
- **业务挑战与设计回应**：先说明真实工作负载中已经被官方或社区材料识别的问题，以及朴素方案或缺少某机制时为何遇到这些问题；再沿源码逐步解释现有机制如何处理它们，并交代复杂度、容量、同步或质量方面的代价。不能从代码名称反推一段未经证实的设计动机。

设计解释以官方架构／设计文档、源码注释、维护者说明、相关论文、commit、PR 和 issue 为主要依据；可靠社区讨论用于补充跨项目的共同挑战。每项关键挑战应有可定位的出处，并说明对应版本和业务条件。所谓“业界共识”不能仅凭单篇帖子成立；区分普遍约束、某版本的故障报告和某个部署的特例。

对照是基于已有证据的逐步讲解，不是要求作者在本机进行消融。例如依次说明重复预填充的计算成本、连续缓存的容量浪费、共享缓存的回收风险，再对应缓存、分页和引用保护的实现。可以用复杂度或简短状态例子帮助理解，但它们是辅助解释，不能替代问题来源，也不能把逻辑上可能出现的风险写成社区已经确认的历史故障。

案例包括业务负载、触发条件、已知问题、对应机制及适用边界。使用 commit、PR 或 issue 解释演进时，核对仓库、固定链接、修改前后代码及维护者表述；区分用户报告、维护者确认、修复方案和合并状态。没有核实的历史动机不补写。引用上游测量时保留其条件与归属，不将其写成本文复现。

这类文档研读不编译、启动或部署上游项目，不运行其测试、benchmark 或修改代码做消融；不能用本机试错代替已有工程知识的检索与整理。源码只读检查、固定提交摘录核对和文档生成属于不同操作。额外的上游执行任务必须获得单独明确授权。

## 可直接阅读的代码证据

路径索引用于定位，关键控制流仍应展示短而完整的源码片段。片段前的可见说明至少包含：仓库、固定提交、仓库相对路径、真实行范围、函数／类／内核名和该片段的作用。使用语言标记的围栏代码，构建时生成离线 token 着色。

- 原文摘录保持代码不变，解释放在相邻正文，不悄悄插入作者没有写过的注释。
- 路径、起始行和符号可写在片段前，或以明确标注为“编者定位注释”的注释展示。行号针对固定提交，不能只跟随不断变化的分支。
- 不连续摘录分别标记行范围，省略不得伪装成连续代码；精简、翻译变量、改写控制流都标为教学伪代码。
- 只展示支撑论点的最小片段，并解释状态变化和调用上下文。不要复制整仓库、整文件或用巨大代码块代替分析。
- 本地检出可能有修改；摘录前检查状态，并对照 `git show <commit>:<path>`。有差异时声明来源，不能把工作树内容冒充固定提交。
- 保留上游许可证和归属。片段及其分析不会自动获得本库 MIT 授权或公开许可。

## Markdown 组合接口

使用现有 Python 构建器，不新增在线文档服务或第二套运行时。一级章节在 `work/content/*.md`，子稿位于其下的主题／项目目录。例如：

```text
content/
  05-frameworks.md
  frameworks/
    vllm.md
    sglang.md
    flash-attention/
      algorithms.md
      gpu.md
```

父稿保留章节标题、必要的过渡和阅读顺序。下面的独立行在构建时原位展开：

```markdown
{{include:frameworks/vllm.md}}
```

路径相对于含有该指令的文件，必须指向同一 `content/` 根目录内的 `.md` 文件，统一使用 `/`。允许递归组合；拒绝绝对路径、逃逸（含符号链接）、循环、缺失文件和超出大小／深度限制的输入。围栏代码和缩进代码中的示例不展开。它不是模板语言，不执行 Python、shell 或表达式，也不从网络或源码仓库自动抓取文件。

子稿不会另成顶层章节；展开后共享目录、脚注、引用和标题锚点。资源链接仍相对于生成的阅读页，**不会**改为相对于子稿。一级文件仍按文件名排序，子目录不被自动遍历，只有父稿显式引用的子稿进入阅读页。为避免重复锚点，同一内容通常只嵌入一次，并用唯一标题或显式 ID 交叉引用。

`manifest.json` 的 `content_dependencies` 记录每章实际读取的源稿；内容哈希覆盖父稿及递归子稿。因此修改单个项目文件即可改变对应阅读页，无需维护重复正文。共享样式修改仍通过 `tools/assets.py` 更新，不能创建项目私有 CSS/JS。

## 维护与验证

按独立技术对象拆分文件，不按任意行数截断。项目特有设计属于项目子稿；共同原理属于主题子稿，项目通过过渡或锚点引用，避免复制后漂移。文件名使用稳定的技术名称，章节顺序由父稿负责；维护索引说明修改入口，但不进入读者正文。

Python 使用 `tools/dev-env.ps1` 管理的系统 TEMP 虚拟环境，依赖在 `requirements.txt` 固定。Pygments 仅在构建时运行；输出是普通 HTML 与共享 CSS，离线阅读和打印不执行着色脚本。未知语言保留原样，不猜测语言。

修改后检查递归依赖、目录与锚点、离线资源、源码行范围、MathML 和版权信息，并核对业务挑战与来源材料的对应关系。文档工具的回归测试覆盖 include 的正常／异常路径、子稿修改后的哈希变化、代码内容与 HTML 转义；这些检查只验证文档工程，不用于发现或证明上游框架的设计必要性。任务日志与文档检查报告保存在系统 TEMP。
